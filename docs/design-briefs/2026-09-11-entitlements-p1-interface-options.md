# P1: варианты интерфейса прав

Статус: анализ вариантов; комбинация B/A принята в согласованном проекте P1A. База исследования — `39d36fd88107313aadd99f29092b5a24bf8f0626`,
включая Commercial P0 из PR #503. Три варианта подготовлены независимыми агентами по
`design-an-interface`; ниже — их сопоставление и предлагаемая комбинация.

Задача интерфейса: дать всем клиентам, API и фоновым задачам один расчёт коммерческих прав,
сохранив авторизацию, атомарные квоты и восстановление ранее разрешённой работы.
Сигнатуры ниже описывают проект, а не существующие экспорты.

## A. Снимок действующих прав

```ts
interface Rights {
  resolveSnapshot(authorizedRead, { asOf, usage }): Promise<RightsSnapshot>;
  evaluate(authorizedOperation, operation): Promise<CommercialDecision>;
  withQuotaChange(tx, authorizedOperation, operation, change): Promise<Result>;
}
```

Кабинет получает один согласованный ответ: тариф, период, модули, квоты, использование,
источники и ближайшее изменение. Проверка операции заново читает факты по серверному времени;
она не принимает ранее полученный снимок как разрешение.

Пример: экран подписки вызывает `resolveSnapshot` и показывает, что три места дала базовая
подписка, ещё два — дополнение. Создание устройства использует `withQuotaChange` с той же
транзакцией, в которой сохраняется устройство.

Интерфейс скрывает выбор активного периода, сложение дополнений, пересечения сроков,
источники и согласованное чтение. Он удобен для объяснения прав и административного просмотра.
Однако большой снимок легко ошибочно закешировать и использовать при последующей записи.
Даже три метода не гарантируют, что проверка расположена прямо перед внешним запросом.

Исторический просмотр имеет отдельное ограничение: текущие таблицы не позволяют восстановить
все прежние количества устройств и отменённые назначения. `asOf` не превращает сегодняшние
данные в исторический факт. Нужны сохранённый снимок или явный ответ о недоступности истории.

## B. Допуск конкретной операции

```ts
interface OperationAdmission {
  withAdmission(tx, { actor, operation, input }, commit): Promise<Result>;
  atExternalEffect({ persistedWork, step, lease }, send): Promise<Result>;
  retainEvidence(tx, authenticatedRecovery, retain): Promise<EvidenceReceipt>;
}
```

Вызывающий код называет действие: создать предложение импорта, применить его, отправить
новую заявку ЧЗ или получить результат уже отправленной заявки. Закрытый реестр определяет
нужные модули, версию доступной операции, проверку квоты и характер восстановления.

Пример: `catalog.import.apply@1` заново проверяет `chzIntegration` даже для старого предложения.
Повтор уже выполненной команды возвращает прежний результат. Перед новым внешним запросом
worker выполняет `atExternalEffect`; наличие старого задания в очереди не заменяет эту проверку.

Интерфейс скрывает связь действия с правами, выбор общей квоты, безопасную причину отказа
и требования к происхождению разрешения. Существующие бизнес-сервисы продолжают владеть
транзакциями, состояниями задач, идемпотентностью и хранением результатов.

Этот вариант лучше защищает от обхода через GET, worker или клиентский флаг `recovery`.
Цена — явный реестр и адаптеры для семейств операций. Не следует превращать их в универсальный
движок бизнес-процессов или держать транзакцию БД открытой во время HTTP-запроса к провайдеру.

## C. Разрешение, сохранённое вместе с работой

```ts
interface WorkAuthority {
  issue(tx, verifiedCaller, subjectAndIntent): Promise<Admission | Denial>;
  present(tx, verifiedCaller, admissionAndCommand): Promise<Permit | Denial>;
  retain(tx, verifiedRecoveryCaller, evidence): Promise<EvidenceReceipt>;
}
```

Основной объект — разрешение на конкретную задачу, её снимок и устройство. Оно сопровождает
работу при переподключении и перезапуске. Повторное скачивание задачи возвращает прежние
границы; оно не продлевает старую смену.

Пример: вход в инвентаризацию связывает разрешение с её immutable snapshot, режимом,
устройством и поколением учётных данных. При загрузке событий сервер отделяет разрешённое
продолжение от новых действий и сохраняет неподтверждённые данные для разбора.

Интерфейс скрывает проверку исходного допуска, области задачи и границ завершения.
Он хорошо подходит устройствам и восстановлению, но требует собственного жизненного цикла
разрешений, долговременного хранения и совместимости протоколов. Обычному экрану кабинета
такая модель сложнее необходимого.

Существующий kiosk admission — непрозрачное подтверждение, проверяемое сервером по БД.
Оно не является подписанным разрешением, которое станция или ТСД может проверить офлайн.
Подпись, ключи, часы после перезапуска и сроки действия требуют отдельного проекта P1C.

## Рекомендация

Взять **B для допуска действий**, **A для отображения и объяснения прав** и использовать
подход **C в последующем этапе офлайн-разрешений**. Общий расчёт остаётся в существующем
`EntitlementsService`; фасад операций не загружает и не пересчитывает тарифы самостоятельно.

Так форма интерфейса соответствует задаче вызывающего кода. Экран получает согласованные
данные, сервис выполняет проверенную операцию, а устройство позже получает узкое разрешение
с понятными сроками. Цена этой комбинации — три явные границы вместо одного универсального
метода, зато снимок, допуск действия и подтверждение сохранения данных не подменяют друг друга.

Первый этап и его критерии приведены в
[проекте P1A](../superpowers/specs/2026-09-11-entitlements-p1-foundation-design.md).

## Опора на текущий код

- `apps/api/src/subscriptions/entitlements.service.ts`: существующий resolver, источники
  plan/addon, текущие usage и транзакционные блокировки квот.
- `apps/api/src/authorization/authorization.service.ts`: авторизация и текущий read model;
  уже зависит от resolver, поэтому обратная зависимость создала бы цикл.
- `apps/api/src/modules/national-catalog/national-catalog-import-apply.service.ts`:
  tenant timeline lock, повтор сохранённой операции и повторная проверка worker.
- `apps/api/src/modules/pickup-orders/kiosk-admission-proof.ts` и
  `pickup-orders.service.ts`: существующее подтверждение точного заказа и серверное время.
- `apps/api/src/modules/station-scans/station-scans.service.ts`: восстановление смены,
  открытой до окончания подписки; полноценного срока завершения P1 здесь пока нет.
- `apps/saas-admin/src/pages/tenants/SubscriptionPanel.tsx`: локальный пересчёт прав,
  который предлагается заменить серверной проекцией.

в [плане](../superpowers/plans/2026-09-11-entitlements-p1a.md).
