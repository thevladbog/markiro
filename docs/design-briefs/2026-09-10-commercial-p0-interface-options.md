# Коммерческая подсистема: выбор интерфейсов P0

Дата: 2026-09-10. Статус: вариант C с внутренними расчётами B и правила сроков согласованы пользователем 2026-09-10. История сравнения сохранена.

Основа: [ФТ MKR-FR-COMMERCIAL-002 v1.1](../superpowers/specs/2026-09-10-catalog-entitlements-functional-requirements.md). Проверенный исходный код: `9cdd7f634949fde28528f4ca172ac8ed9769796a`. Три альтернативы независимо подготовлены по подходу Design It Twice и сопоставлены с существующими сервисами.

## Уже принятые решения

- Честный ЗНАК и Национальный каталог — один коммерческий модуль `chzIntegration`. Отдельного продаваемого `nationalCatalogImport` нет.
- В примере Start модуль приобретается дополнением; Workshop и Production включают его. Это не публикация производственных тарифов.
- Операционные возможности, внешние полномочия, готовность релиза и общее подключение с Signer остаются отдельными проверками.
- Текущие документы и клиентские условия не пересчитываются при миграции.

## Порядок проектирования

Первый самостоятельный проект — P0: корректность условий каталога и их прохождения через предложение, счёт, оплату и активацию. P1 разделяется на серверные права/миграцию и офлайн-разрешения/восстановление; P2 — регулярные услуги. Каждый последующий проект получает собственный согласованный дизайн и проверки.

P0 не означает включение новых ограничений P1. Публикация предложений, обещающих ещё не готовые модули или требующих несогласованных правил эксплуатации, остаётся закрыта соответствующими проверками. Исправленный редактор сам по себе не разрешает такие продажи.

## Задача и вызывающие стороны

Пользователь SaaS admin должен создать или изменить черновик, проверить условия, опубликовать версию, подготовить предложение/счёт и применить подтверждённую оплату. Все пути должны одинаково понимать цену, период, налог, количество ресурсов и наименование в документе.

Вызывающие стороны: редакторы каталога, `PlatformCatalogService`, `PlatformOffersService`, `BillingService`, `BillingApplicationService`, `SubscriptionLifecycleService` и их тесты. Контроллеры сохраняют существующие границы платформенной авторизации. `EntitlementsService` остаётся источником эффективных коммерческих прав.

Внешний интерфейс сообщает намерение, идентификаторы и ожидаемые ревизии. Внутри должны оставаться денежная и календарная арифметика, загрузка продавца, сборка снимка, блокировки, повторная валидация и защита от повторного исполнения.

## Что подтверждено в коде

1. `packages/platform-contracts/src/catalog.ts:7` использует одну положительную схему для квот и пробного срока. `packages/db/src/schema/saas.ts:189` повторяет запрет нулевых квот.
2. `CatalogCreatePanel.tsx:40` задаёт НДС 22%, а на строке 111 отправляет месячный период. `CatalogVersionPanel.tsx:212` не передаёт период в изменение. Клонирование в `catalog/api.ts:23` уже сохраняет период.
3. `PlatformCatalogService.publish` проверяет наличие эффектов, но не полный набор требований P0 к публикации.
4. `billing-application.service.ts:343` передаёт план в lifecycle без окончания срока; `subscription-lifecycle.service.ts:310` сохраняет отсутствующий конец как `null`.
5. `platform-offers.service.ts:525` имеет отдельный путь исполнения оплаты, который также создаёт подписку и дополнения с `endsAt: null`. Исправить только счёт недостаточно.
6. Снимки документов, ревизия продавца, блокировки и журнал применения оплаты уже существуют. Нужны расширения этих механизмов, а не второй биллинг.
7. Старые строгие парсеры не принимают новые поля; квоту `0` они также отвергают. Удалить дополнительные поля из ответа недостаточно. Подменять ноль безлимитом нельзя.

Номера строк относятся к указанному исходному коммиту. Это чтение исходников и тестов, а не результат запуска сценариев или проверки production.

## A. Небольшой общий фасад

Три операции скрывают большинство деталей. Типы ниже — эскизы внутренних интерфейсов; существующие HTTP-маршруты сохраняются. `Actor`, `Transaction`, идентификаторы и остальные именованные типы обозначают существующие либо будущие строго валидируемые доменные значения.

```ts
interface CommercialTerms {
  preview(actor: Actor, candidate: CommercialCandidate): Promise<Review>;
  seal(tx: Transaction, actor: Actor, target: ReviewedTarget): Promise<Snapshot>;
  fulfilPaid(tx: Transaction, actor: Actor, source: PaidSource): Promise<Fulfilment>;
}

type ReviewedTarget =
  | { kind: "catalog"; id: string; expectedRevision: string }
  | { kind: "offer"; id: string; expectedRevision: string }
  | { kind: "invoice"; id: string; expectedRevision: string };
```

Пример вызова внутри существующего сервиса выставления счёта:

```ts
return db.transaction(async (tx) => {
  return terms.seal(tx, actor, {
    kind: "invoice",
    id: invoiceId,
    expectedRevision: review.revision,
  });
});
```

Фасад сам перечитывает данные, проверяет текущие условия и сохраняет снимок в переданной транзакции. Предпросмотр не служит разрешением на последующую запись.

Он скрывает налоги, расчёты, снимки, порядок применения плана и дополнений. Число методов мало, но за `seal` стоят существенно разные действия: публикация каталога, предложения и выдача счёта. Вызывающий код прост; ответственность фасада широка. Для корректного использования нужно закрыть обходные способы выпуска и исполнения. Возможность загружать данные один раз в транзакции сохраняется, однако большой union запросов делает зависимости отдельных сценариев менее очевидными.

## B. Типизированные этапы расчёта

Существующие сервисы управляют транзакциями; общие правила оформляются как фиксированные преобразования данных. Универсального движка политик нет.

```ts
interface CommercialCalculations {
  validatePublication(draft: CatalogDraft, context: PublicationContext): Result<PublishableTerms>;
  resolveSale(source: PublishedTerms | FrozenOfferLine, purchase: Purchase): Result<ResolvedSale>;
  prepareIssuance(draft: DocumentDraft, context: IssuanceContext): Result<IssuableDocument>;
  resolveActivation(line: IssuedLicenseLine, context: ActivationContext): Result<Activation>;
}
```

Пример вызова:

```ts
return db.transaction(async (tx) => {
  const draft = await loadLockedDraft(tx, invoiceId);
  const context = await loadCurrentIssuanceContext(tx, draft);
  const result = calculations.prepareIssuance(draft, context);
  if (!result.ok) throw commercialError(result.errors);
  return persistInvoiceAndAudit(tx, actor, result.value);
});
```

Расчёты скрывают денежную арифметику, календарь, правила налогов и создание документарных строк. Отдельные типы не позволяют передать необработанный черновик туда, где требуется выпущенная строка. Runtime-проверки всё равно обязательны.

Это самый гибкий интерфейс: одна и та же арифметика применима в редакторе, предложении, счёте и активации. Данные можно загрузить один раз, расчёты остаются детерминированными. Но вызывающая сторона должна правильно собрать контекст, выбрать порядок этапов и удержать блокировки. Риск пропуска этапа выше, а набор типов может распространиться далеко за пределы подсистемы. Интерфейс оправдан только если скрывает существенные правила, а не просто перекладывает поля.

## C. Явные сценарии в существующих сервисах

Рекомендуемый внешний интерфейс. Методы соответствуют действиям пользователя; общие расчёты из варианта B остаются внутренними. Это форма границ ответственности, а не требование создать два новых класса поверх всех существующих сервисов.

```ts
interface CatalogWorkflows {
  createDraft(actor: Actor, input: CreateDraft): Promise<DraftVersion>;
  saveDraft(actor: Actor, input: SaveDraftWithRevision): Promise<DraftVersion>;
  cloneVersion(actor: Actor, input: CloneVersion): Promise<DraftVersion>;
  reviewPublication(actor: Actor, versionId: string): Promise<PublicationReview>;
  publishVersion(actor: Actor, input: PublishReviewedVersion): Promise<PublishedVersion>;
}

interface SalesWorkflows {
  reviewInvoice(actor: Actor, invoiceId: string): Promise<InvoiceReview>;
  issueInvoice(actor: Actor, input: IssueReviewedInvoice): Promise<IssuedInvoice>;
  applyPaidInvoice(actor: Actor, input: ApplyPaidInvoice): Promise<ApplicationResult>;
}
```

Пример вызова:

```ts
const review = await sales.reviewInvoice(actor, invoiceId);
// Интерфейс показывает сумму, налог, строку документа и правило начала срока.
await sales.issueInvoice(actor, {
  invoiceId,
  expectedReview: review.fingerprint,
  idempotencyKey: issueCommandId,
});
```

При выпуске сервис повторно проверяет данные под блокировками. Изменившийся продавец, черновик или исходное предложение дают структурированную ошибку устаревшего предпросмотра. Интерфейс сохраняет введённые значения и предлагает обновить проверку. Обновление одного fingerprint не должно молча менять согласованную цену или налог.

Сценарии скрывают сбор контекста и транзакционные требования. Методов больше, чем у фасада, зато сохранить черновик и выдать документ невозможно спутать. Новый сценарий добавляется явно. Общие вычисления и чтения можно переиспользовать без повторных запросов. По глубине это узкие бизнес-операции, скрывающие несколько существенных правил; по безопасности использования они лучше общего набора этапов.

## Синтез для P0

Выбрать C для вызывающего кода и ограниченный набор чистых расчётов B внутри. Не вводить общий command bus, произвольные правила или параллельную модель документов.

1. Общие контракты различают ресурсную квоту `0 | положительное число | null`, положительное приращение дополнения и `положительные дни | null` для trial. Годовая цена означает стоимость одного года; количество плана равно одному, количество дополнения означает число ресурсов.
2. Создание, изменение и клонирование используют одну модель условий и явный период. Предпросмотр и выпуск используют одинаковые расчёты, сервер проверяет их независимо от клиента. Названия для документов версионируются отдельно от отображаемых названий. Налоговые значения берутся из явной ревизии политики продавца; режим не выводится из названия или организационной формы.
3. Оба существующих пути оплаты вызывают один внутренний механизм применения лицензионной строки, расширяющий текущий lifecycle. Сохраняются источник оплаты, журнал применения, блокировки, аудит и повторяемость результата. Взаимодействие предложения и созданного из него счёта проверяется отдельно: разные ключи offer-line и invoice-line не доказывают защиту от двойного исполнения одной продажи.
4. Календарные границы вычисляются сервером от исходного якоря, а не от последнего укороченного месяца. Для согласования предлагаются `Europe/Moscow`, сохранение исходного дня и времени, последний день месяца при отсутствии нужного дня; 29 февраля ежегодно переходит на 28 февраля в невисокосном году и возвращается к 29 февраля в високосном. Часовой пояс и правило сохраняются с условиями; это не пересчёт старых подписок.
5. Снимки выданных документов не изменяются. Неполные старые записи остаются явно legacy и попадают в отчёт проверки; новые поля не дорисовывают исторические факты из текущего каталога.
6. Новые представления контракта вводятся совместимо. До публикации нулевых квот обновляются все потребители, которые обязаны читать эти значения. Непредставимые в старом формате записи нельзя выдавать с ложными квотами; безопасные исторические чтения и восстановление остаются доступны по матрице клиентов.

## Решение о датах, требующее согласования

FR-PER-03 требует одинаковые точные даты в документах и подписке. FR-PER-04 допускает начало после оплаты или текущего срока. Если оплата ещё не произошла, будущая дата активации не известна; подставить её в уже выданный счёт позднее нельзя.

Предлагается различать два случая:

- Когда начало заранее согласовано, документ фиксирует конкретный интервал.
- Когда начало зависит от применения оплаты, документ фиксирует длительность и правило активации. Фактические даты вычисляются один раз при применении подтверждённой оплаты либо от конца текущего срока и сохраняются в отдельной неизменяемой записи активации со ссылкой на исходную строку. Повторное применение возвращает те же даты. Выданный документ остаётся прежним.

Вариант с началом от применения оплаты, а не от банковского времени платежа, предлагается для согласования: задержка ручного применения не должна незаметно сокращать купленный срок. Правило и календарная политика согласованы пользователем; они включены в ФТ v1.2 и окончательный дизайн P0.

## Проверки будущей реализации

- Контракты и БД: ноль, конечное число и безлимит; отрицательные, дробные и переполненные значения; отдельные trial и increments; старые и новые строгие ответы.
- Редакторы: создание/изменение/клонирование, месяц/год, годовая цена, единица измерения, НДС, документарное имя, сохранение ввода при ошибке.
- Выпуск: отсутствующее имя, недопустимый налог, смена продавца после предпросмотра, конкурентная правка, точное содержимое аудита, отказ другого тенанта/неподходящей роли.
- Календарь: 31 января → февраль → 31 марта, 29 февраля, смена часового пояса браузера, точная граница `[start, end)`, независимый период дополнения в пределах базового доступа.
- Оплата: оба текущих пути, повтор и конкурентный повтор, отказ посреди транзакции, предложение и созданный из него счёт, сохранение одной записи активации и неизменных дат.
- Документы: переименование каталога/смена продавца не изменяют перепечатку, предложение не перечитывает текущую цену при переносе согласованных условий в счёт.
- Итоговые проверки затронутых пакетов, миграции в тестовой БД, браузерные сценарии SaaS admin и отдельная проверка документов. Production-данные и внешние системы проверяются отдельными согласованными действиями.

Для текущей записки тесты приложения не запускались: код не менялся. Проверки текста ФТ и форматирования выполняются отдельно. После выбора направления следующий результат — согласованный дизайн P0, затем план реализации и разработка с тестом на каждое изменяемое правило.
