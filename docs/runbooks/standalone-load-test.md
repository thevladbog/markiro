# Нагрузочный и длительный тест хоста «Автоном»: инструкция владельцу

Тест отвечает на один вопрос приёмки вехи «несколько станций в одной смене на одной линии» (спека
`docs/superpowers/specs/2026-10-20-standalone-multi-station-shift-design.md`, §8): остаётся ли хост на SQLite ровным и
точным, когда 4 станции и 2 ТСД одновременно сканируют в одну смену. Он запускает настоящий `markiro-host` на одноразовой
папке данных, создаёт шесть устройств, гоняет сканы (обрывы связи, дубликаты между устройствами, гонки, повторные отправки,
блоки SSCC по правилу половины), меряет и в конце сверяет итоги хоста с тем, что хост подтвердил. Он ничего не пишет в
продуктовые данные и не нужен на заводском ПК.

**Что доказано на сегодня.** Только то, что наблюдали на одной отладочной сборке на macOS с хостом внутри процесса
(`--host in-process`) и короткими прогонами `tiny` и `smoke` (п. 8). Длинный прогон (`soak`), Windows, Linux, режим
`attach` и workflow в GitHub Actions ни разу не запускались. Зелёный отчёт не означает «выдержит завод»: он означает
«в этом сценарии, на этой машине, числа сошлись».

## 1. Когда запускать

- перед выпуском хоста, который меняет `host/src/db.rs`, `facts/`, `routes/device_shifts.rs`, `sscc_blocks.rs`, `backup/`,
  `restore.rs` или миграции;
- перед пилотом на новой площадке и раз в квартал;
- после любого изменения порогов (см. п. 10).

## 2. Что нужно

Компьютер, не продуктовый ПК площадки. Rust (stable). Для длинного прогона: до 3 ГБ свободного места и отключённый сон.
Данные прогона удаляются при успехе; при провале (или с `--keep-data`) остаются `data/`, `restored/` и журнал хоста.

Три режима хоста (`--host`):

| Режим                  | Что делает                                                                                             | Что не судит                                                                                     |
| ---------------------- | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------ |
| `in-process`           | хост внутри процесса теста, слушает только `127.0.0.1`; ничего собирать отдельно не нужно              | память и дескрипторы хоста, строки ERROR и «база занята» в его журнале (в отчёте предупреждения) |
| `spawn` (по умолчанию) | отдельный процесс `markiro-host` рядом с тестом (или `--host-bin`); судит память, дескрипторы и журнал | —                                                                                                |
| `attach`               | уже запущенный одноразовый хост (п. 11)                                                                | зависит от `--data-dir` и `--pid`                                                                |

**Сеть.** У `markiro-host run` нет параметра адреса: порождённый хост слушает `0.0.0.0`, то есть все интерфейсы, пока
идёт прогон. Пароль администратора и ключи устройств одноразовые, но порт достижим из сети. Поэтому `spawn` без флага
`--accept-network-exposure` отказывается стартовать (код выхода 2). Давайте флаг только на доверенной или изолированной
сети (домашний ПК за маршрутизатором, не общедоступный Wi-Fi и не раннер с открытым адресом). Если сомневаетесь, берите
`--host in-process`: он безопасен, но не судит память и дескрипторы.

## 3. Сборка

Для `spawn`:

```
cargo build --release -p markiro-host -p markiro-loadtest --manifest-path apps/standalone/Cargo.toml
```

Оба файла лежат в `apps/standalone/target/release/`; тест берёт `markiro-host` рядом с собой.

Для `in-process` достаточно собрать только тест:

```
cargo build --release -p markiro-loadtest --manifest-path apps/standalone/Cargo.toml
```

## 4. Проверка самого теста (tiny, 20 секунд)

```
apps/standalone/target/release/markiro-loadtest run --profile tiny --host in-process --out ~/markiro-load
```

2 станции и 1 ТСД, 20 секунд. Это самопроверка инструмента, а не нагрузка: пороги задержек у неё в четыре раза мягче.
Наблюдалось (отладочная сборка, macOS): `PASS`, 78 из 78 проверок, код выхода 0. Предупреждения «журнал хоста недоступен» и
«число дескрипторов недоступно» ожидаемы для `in-process`.

## 5. Быстрый прогон (smoke, около 5 минут)

С отдельным процессом хоста (сеть доверенная, см. п. 2):

```
apps/standalone/target/release/markiro-loadtest run --profile smoke --accept-network-exposure
```

Без раскрытия порта в сеть:

```
apps/standalone/target/release/markiro-loadtest run --profile smoke --host in-process
```

4 станции и 2 ТСД по 5 сканов/с, 3 минуты, затем закрытия, шесть сценариев (п. 6), последняя копия и восстановление. Код
выхода: 0 — успех, 1 — не прошёл порог или сверка, 2 — прогон не удалось выполнить (плохая строка команды, нет
`markiro-host`, отказ без `--accept-network-exposure`, папка отчётов в git-репозитории). Отчёты:
`~/markiro-load/smoke-<дата>-<время>/` (`report.json`, `report.md`, у `spawn` ещё `host-stdout.log`). Другая папка: `--out`
или `MARKIRO_LOAD_OUT`. Папка внутри git-репозитория отвергается, поэтому в клонах репозитория отчёты не появятся.

Отчёты очищаются от секретов (ключи, сессии, коды сопряжения, пароли) перед записью, но это внутренние результаты:
не публикуйте их вместе с данными площадки.

Без своего ПК: workflow «Standalone load test» (Actions, «Run workflow», профиль `smoke`). Он запускается только вручную
(`workflow_dispatch`), не входит в обязательные проверки, всегда использует `--host in-process` на `ubuntu-latest` и ни
разу не запускался в GitHub. Отчёт приходит артефактом `standalone-load-<профиль>-…` и в сводке запуска.

## 6. Шесть сценариев (drills)

В конце каждого прогона идут шесть проверок завершения общей смены: закрытие частей в трёх порядках (станции первыми, ТСД
первыми, вперемешку), принудительное закрытие из офиса, закрытие без причины и устаревший `leave` (выход с прежним
`joinedRev` не должен отменять повторный вход). Это **способы закончить общую смену**, а не внесение сбоев: процессы не
убиваются, сеть и диск не ломаются.

## 7. Длинный прогон (soak, 4 часа)

Память и дескрипторы судит только `spawn` (или `attach` с `--pid`), поэтому soak имеет смысл запускать так, на
доверенной или изолированной сети. macOS:

```
caffeinate -i apps/standalone/target/release/markiro-loadtest run --profile soak --accept-network-exposure --out ~/markiro-load
```

Linux (сон отключите сами, например `systemd-inhibit`):

```
apps/standalone/target/release/markiro-loadtest run --profile soak --accept-network-exposure --out ~/markiro-load
```

Windows (PowerShell, сон отключён в параметрах питания):

```
apps\standalone\target\release\markiro-loadtest.exe run --profile soak --accept-network-exposure --out D:\markiro-load
```

То же, что smoke, но по 10 сканов/с, четыре часа, три копии под нагрузкой (на 25, 50 и 75 %). Каждые 30 секунд прогон пишет
строку хода в stderr. Параметры меняются без пересборки: `--set scanRate=7 --set durationS=600` (поля профиля: `stations`,
`handhelds`, `scanRate`, `durationS`, `boxCapacity`, `palletBoxes`, `boxBlockSize`, `palletBlockSize`, `flushMs`, `batchMax`,
`meanOnlineS`, `meanOfflineS`, `lateDupRate`, `checkedDupRate`, `raceRate`, `resendRate`, `totalsPollS`, `backupAt`,
`sampleS`, `seed`, `closeOrder`).

Как читать итог: в конце печатается `# Load run soak: PASS` или `FAIL`, ниже предупреждения, задержки по маршрутам,
сверка, строка «Host» (память, дескрипторы, WAL), копии и сценарии; код выхода 0 при PASS. Откройте `report.md` и
прочитайте раздел «Warnings» до вердикта: непросуженная проверка там помечена предупреждением и вердикт не ломает.
Четырёхчасовой soak ещё не запускался ни разу, поэтому пороги для него (п. 9) не калибровались.

## 8. Что наблюдали (одна отладочная сборка, macOS, хост внутри процесса)

Это единственные измеренные числа. Это не доказательство производительности на Windows, на дисках завода и при 4 часах
нагрузки.

| Прогон                                 | Наблюдалось                                                                                                                               |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| tiny, `in-process` (при написании)     | 300 сканов, факты p99 23–32 мс, 78 из 78 проверок, очередь WAL до 986 кадров                                                              |
| tiny, `spawn` (при написании)          | 297 сканов, факты p99 32 мс, память хоста 35 → 42 МиБ, дескрипторы до 37, 986 кадров WAL                                                  |
| smoke, 180 с, `in-process` (Задача 13) | 5403 скана (4 станции и 2 ТСД), факты p99 ≈ 34 мс, блок SSCC p99 112 мс, очередь WAL около 997 кадров, 168 из 168 проверок, сверка точная |

**Очередь WAL: измерение (Задача 12 плана 2026-10-22).** Хост пишет в журнал WAL; SQLite сама переносит его в основной
файл (автоматическая контрольная точка) после коммита, оставившего в журнале 1000 кадров или больше, и затем начинает
журнал сначала. Наблюдатель `walWatch` читает заголовок `host.db-wal` (счётчик перезапусков журнала) и `host.db-shm`
каждые 100 мс, ничего не записывая (файлы только на чтение; чтение-только соединение контрольную точку выполнить не
может: тест `a_read_only_observer_cannot_checkpoint_the_log`). Измерено: macOS (Darwin 25.6.0), отладочная сборка,
по одному прогону smoke, 180 с, `--set scenarios=none`, на каждый режим.

| Режим хоста  | журнал начинался заново     | самый длинный промежуток без перезапуска | очередь p50 / p99 / максимум | замеров выше 1000 кадров | наибольший кадр | файл журнала не больше        | замеров с недоконченной контрольной точкой |
| ------------ | --------------------------- | ---------------------------------------- | ---------------------------- | ------------------------ | --------------- | ----------------------------- | ------------------------------------------ |
| `in-process` | 269 раз (около 89 в минуту) | 7,8 с                                    | 504 / 993 / 1046             | 0,17 %                   | 1539            | 2128 кадров (8 767 392 байта) | 4 из 1789                                  |
| `spawn`      | 121 раз (около 40 в минуту) | 10,2 с                                   | 491 / 992 / 1040             | 0,22 %                   | 1361            | 2060 кадров (8 487 232 байта) | 4 из 1790                                  |

Пятисекундный сэмплер в тех же прогонах показал максимум 981 и 987 кадров (он не видит верхушек пилы). Вывод: пик очереди
около 1000 кадров — верх «пилы» автоматической контрольной точки: она срабатывает и журнал начинается сначала в среднем
каждые 1–2 секунды, самое долгое наблюдавшееся без перезапуска — 10 с; очередь выше 1000 кадров бывает редко (0,2 % замеров)
и ненамного (до 1046: один пакет сверх порога). Явная контрольная точка при такой нагрузке по этим измерениям не нужна.
Оговорки, которые измерение не закрывает: файл журнала вырастает до 2060–2128 кадров, вдвое выше порога (контрольная точка
иногда не дописывает до конца, пока читатель держит снимок, и журнал дописывается дальше; SQLite не уменьшает файл
без `journal_size_limit`, а хост его не задаёт), то есть 8–9 МиБ на диске постоянно после первого такого пика; один
прогон на одной машине в отладочной сборке; Windows и долгий прогон (soak) не измерялись. Изменение хоста (явная
контрольная точка, `wal_autocheckpoint`, `journal_size_limit`) в этой работе не делается и по этим числам не требуется.
Порог 8000 кадров остаётся сторожем на случай, если контрольные точки перестанут успевать (долгое чтение, копия).
Следите за `walWatch` в отчёте: `restarts` = 0 за 60 с и более даёт предупреждение (не отказ).

## 9. Что считается успехом

Все проверки отчёта выполнены и ни один порог не превышен (`verdict.pass`). Пороги (smoke; soak: p95 150, p99 400, p99 под
копией 800 мс; tiny: латентности в четыре раза мягче):

| Что                                                                   | Порог                                                                                                                         |
| --------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| маршрут фактов                                                        | p95 ≤ 100 мс, p99 ≤ 250 мс, максимум ≤ 2000 мс (таймаут занятости базы 5 с)                                                   |
| факты во время копии                                                  | p99 ≤ 500 мс                                                                                                                  |
| проверка кода (станция ждёт 300 мс)                                   | p99 ≤ 150 мс, дольше 300 мс — не более 0,1 %                                                                                  |
| прочие маршруты (список смен, блоки, вход)                            | p99 ≤ 500 мс                                                                                                                  |
| ответы 5xx и строки ERROR журнала хоста                               | 0                                                                                                                             |
| строки журнала про занятую базу (`database is locked`, `SQLITE_BUSY`) | 0                                                                                                                             |
| запросы без ответа; запросы, отвергнутые хостом (4xx)                 | 0                                                                                                                             |
| очередь журнала WAL (кадры, которые не перенесла контрольная точка)   | ≤ 8000; файл WAL ≤ 256 МиБ                                                                                                    |
| память хоста (прогон от 30 минут, только `spawn`/`attach` с `--pid`)  | рост ≤ 20 МиБ/ч                                                                                                               |
| дескрипторы хоста (то же)                                             | ≤ 64 + 4 на устройство; к концу не более чем на 8 больше, чем после разогрева                                                 |
| сделано сканов                                                        | не менее 90 % идеала (иначе отстаёт сам тест; у tiny 60 %)                                                                    |
| сверка                                                                | точная: сканы, квитанции, короба, паллеты, владельцы кодов, конфликты `late` и `displaced`, живые позиции                     |
| SSCC                                                                  | ни один номер не встречается дважды; блоки устройств не пересекаются                                                          |
| копия под нагрузкой                                                   | открывается, проходит `integrity_check`; сканов в ней не меньше подтверждённых до просьбы и не больше отправленных к её концу |
| восстановление                                                        | в девяти таблицах фактов ровно столько же строк, сколько в живой базе; хост на восстановленной папке отвечает итогом смены    |
| выключение                                                            | хост завершается по Ctrl+C (SIGINT) сам (кроме Windows)                                                                       |

**Недоступные пробы дают предупреждение, а не провал.** Если память, дескрипторы, размер WAL или журнал хоста прочитать
нельзя (всегда у `in-process`; на Windows возможно и у `spawn`), отчёт пишет предупреждение, а проверка не судится, и
вердикт может быть PASS. Вопрос, делать ли такую недоступность провалом для `spawn`-хоста, не решён и ждёт вашего решения.
Пустой список проверок (сверка не выполнена) — всегда провал.

## 10. Если прогон не прошёл

| Сообщение отчёта                                                      | Что это значит и куда смотреть                                                                                                                                                          |
| --------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `facts p99` / `p95` / `max`                                           | хост медленный: смотрите очередь WAL, диск (fsync), `facts_during_backup` (копия мешает записи), загрузку процессора; маршрут `device_shifts` — запросы итогов                          |
| `busy database`                                                       | запись держит блокировку дольше 5 секунд: настоящий дефект пути записи. Запустите `cargo test -p markiro-loadtest --test write_review`, найдите транзакцию по строкам `host-stdout.log` |
| `server errors`                                                       | первые строки ERROR в `log.firstErrors` отчёта и в `host-stdout.log`                                                                                                                    |
| `check db_*`, `totals_*`, `by_device_*`, `office_*`                   | итоги хоста расходятся с подтверждёнными: факт потерян или посчитан дважды. Сравните `expected` отчёта с базой; серьёзно                                                                |
| `sscc_unique`, `sscc_blocks_disjoint`, `sscc_serials_from_own_blocks` | два короба или паллеты с одним SSCC: серьёзно, выпуск блокируется                                                                                                                       |
| `conflicts_injected_vs_observed`                                      | внесённые дубликаты и гонки не стали конфликтами: тест не внёс их (смотрите `lateDups`, `racesTaken` устройств) либо реестр кодов пропустил конфликт                                    |
| `backup … between`                                                    | копия под нагрузкой потеряла подтверждённое или содержит неотправленное: копия не была снимком                                                                                          |
| `restore_rows_*`                                                      | восстановление потеряло строки                                                                                                                                                          |
| сценарии `close-*`, `force-close`, `missing-reason`, `stale-leave`    | логика закрытия смены на хосте (план 2b)                                                                                                                                                |
| `WAL backlog`                                                         | контрольные точки не успевают (долгие читающие транзакции): смотрите ряд `series` и копии                                                                                               |
| `host memory growth` / `descriptors`                                  | утечка: ряд `series` покажет ступеньку или наклон                                                                                                                                       |
| `the devices made … % of the ideal scans`                             | тест на слабом ПК или сканер ждал серию SSCC (`stalls`)                                                                                                                                 |
| `device N stopped`                                                    | хост отверг пакет (4xx): версии теста и хоста не совпадают по протоколу                                                                                                                 |
| `the host did not stop on request`                                    | зависание остановки хоста                                                                                                                                                               |

## 11. Прогон на уже запущенном хосте (attach)

Только на одноразовом хосте: тест создаёт устройства, товар и смены. Ключ офисной станции и данные администратора — из
окружения, не из командной строки. Режим ни разу не запускался:

```
export MARKIRO_LOAD_OFFICE_DEVICE_KEY=… MARKIRO_LOAD_ADMIN_LOGIN=… MARKIRO_LOAD_ADMIN_PASSWORD=…
markiro-loadtest run --profile smoke --host attach --attach-url https://10.0.0.5:45710 --fingerprint <64 hex> [--data-dir <папка данных>] [--pid <pid хоста>]
```

Без `--data-dir` нет сверки по базе, копий и восстановления (остаётся сверка через API); без `--pid` нет памяти и
дескрипторов; журнала хоста в этом режиме нет (занятая база видна только по ответам 5xx).

## 12. Сравнение с прошлым прогоном

Первый успешный отчёт профиля сохраните как базовую линию (вне репозитория):

```
mkdir -p ~/markiro-load/baseline && cp ~/markiro-load/smoke-<дата>-<время>/report.json ~/markiro-load/baseline/smoke.json
```

Следующий прогон сравнивается командой (код выхода 1 при регрессии, 0 и «no regression» без неё):

```
markiro-loadtest compare ~/markiro-load/baseline/smoke.json ~/markiro-load/smoke-<новая дата>/report.json
```

Регрессия: другой профиль; вердикт стал хуже; p95 или p99 маршрута фактов выросли больше, чем в 1,5 раза плюс 20 мс (проверка
кода и список смен: плюс 10 и 20 мс); сканов в секунду меньше 90 % прежнего; максимум памяти хоста вырос больше, чем в 1,25
раза плюс 16 МиБ; очередь WAL — больше, чем в 1,5 раза плюс 1000 кадров; появился класс ошибки, которого не было.
`markiro-loadtest summary <report.json>` печатает краткий отчёт ещё раз. Базовую линию обновляйте только после осознанного
изменения хоста, с записью причины. Сравнивайте отчёты одного режима хоста и одной машины.

## 13. Пороги и их изменение

Пороги — код (`apps/standalone/loadtest/src/profile.rs`, `Thresholds::for_profile`). В спеке §8 числовых порогов нет:
это стартовые числа, калибровка — первые три прогона smoke на раннере CI и на вашем ПК. Порог можно ужесточать свободно;
ослаблять — только с тремя отчётами в описании изменения и вашим «да». Пересмотр самой СУБД (спека §8) — не тут: больше
~20 одновременных устройств на хост (профиль принимает не больше 16 станций), больше ~50 млн строк в `scans` или нужда в
тёплом резерве.

## 14. Чего тест не доказывает

**Не моделируется вообще:** настоящие принтеры и сканеры, Wi-Fi и сеть завода, Windows-службу как службу, диски завода,
1С, проверки этикеток (`box_label`, `pallet_label`), исключения коробов, режим проверки, расформирование, складские
паллеты и склад ТСД.

**Не упражнено нагрузкой (этих путей в прогоне нет, даже если у части есть модульные тесты):**

- отказ `shift_line_full` (в смене больше участников, чем `maxStations`);
- устройство без `multi-station-v1`: ответ `protocol_unsupported`;
- выход (`leave`) и повторный вход под нагрузкой (проверен только отдельным сценарием `stale-leave` без потока сканов);
- закрытая часть, которая принимает живые факты, и «последний закрывающий» при конкурентных закрытиях;
- несколько одновременных закрытий; несколько линий и несколько смен сразу (в тесте одна линия и одна смена);
- копия и восстановление посреди закрытия смены;
- сбои на уровне процесса: убийство и перезапуск хоста посреди записи, восстановление WAL после аварии, повторы с
  отступлением после ответов 5xx.

**Только Windows, не проверялось:** чтение `host.db-shm` для очереди WAL; повтор при `os error 32` в восстановлении
(копия ещё занята процессом); сбор памяти и дескрипторов через PowerShell; на Windows хост завершается принудительно
(там нет SIGINT); перезапуск хоста на том же порту (сценарии `kill-restart` и `outage` на Windows не судятся: результат «не судилось» с пояснением).

**Не запускалось ни разу:** `soak`, `spawn` на `smoke`, `attach`, Linux (чтение `/proc`), workflow `standalone-load.yml` в
GitHub.
