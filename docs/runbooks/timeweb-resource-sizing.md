# Ресурсы Timeweb: только Маркиро

Обновлено 18 октября 2026. Текущий согласованный контур — Markiro platform-only
на **2 vCPU / 4 GiB RAM / 50 GiB диска** с локальным PostgreSQL. CRM, Twenty,
Chatwoot и n8n исключены из этого расчёта. Серверы, DNS и production не изменены.
Цены здесь не пересчитываются.

Компактный профиль сохраняет платформенную авторизацию, выпуск автономных
лицензий, диагностику и долговечную очередь отчётов. Лендинг и SaaS-интерфейс
раздаёт Caddy. Сборки выполняются вне production VM. Базовый вариант с внешним
PostgreSQL остаётся доступен; compact применяется отдельным overlay.

## Память и CPU

| Компонент                                      |     Лимит RAM |    Лимит CPU |
| ---------------------------------------------- | ------------: | -----------: |
| API, HTTP/auth pool 6, очередь pool 4 + LISTEN |     1,536 MiB |         1.25 |
| PostgreSQL 17                                  |     1,024 MiB |         0.50 |
| Caddy, статические приложения                  |       192 MiB |         0.25 |
| **Сумма работающих сервисов**                  | **2,752 MiB** |     **2.00** |
| ОС, Docker, мониторинг и резерв на VM 4 GiB    | **1,344 MiB** | общий CPU VM |

Node heap API ограничен 1,024 MiB; это не полный RSS. PostgreSQL имеет
max_connections=32, shared_buffers=256 MB, work_mem=4 MB, maintenance_work_mem=64 MB
и autovacuum_work_mem=32 MB. fsync, full_page_writes и synchronous_commit включены.
Обычно приложение может занять до 11 соединений; мониторинг, CLI и резервное
копирование требуют отдельного запаса. Один процесс генерации отчётов работает
за раз; другие очереди могут работать одновременно.

Миграции выполняются при остановленных API и edge: PostgreSQL 0.5 CPU / 1 GiB
плюс migration 1.5 CPU / 512 MiB, Node heap 384 MiB. Обычный `compose up` на
работающем контуре не заменяет этот порядок.

## Что подтверждает локальная проверка

Методика, точные ограничения и воспроизводимые команды находятся в
[runbook нагрузочного теста](timeweb-compact-load.md); числовой протокол — в
[results.json](../evidence/timeweb-compact/2026-10-18/results.json).

Проверка использует реальные PostgreSQL/TLS, API, edge, платформенные HTTP-входы
с TOTP, подписи лицензий, зашифрованную диагностику и pg-boss/S3-отчёты с
проверкой содержимого. Данные полностью синтетические: 100 организаций,
3,000 коммерческих фактов, 10 площадок и 10 учётных записей. Полный цикл —
60 секунд прогрева, 180 стабильной нагрузки с пятью пользователями, 60 всплеска
с десятью и 60 восстановления с пятью.

Сумма cgroup-квот сервисов равна 2 CPU; локальная VM физически имеет 6 CPU и
около 3.53 GiB RAM. ОС, внешние синтетические SMTP/S3 и драйвер нагрузки не входят
в эти квоты. Локальные runtime-образы собраны с host-built dist; точная сборка
релизных образов ранее упиралась в память локальной VM. Поэтому положительный
локальный результат поддерживает компактный стартовый бюджет для заявленного
малого сценария, но не доказывает ёмкость или задержки конкретной VM Timeweb.
Он не заменяет проверку восстановленных исторических данных и реальной нагрузки.

Фактический полный прогон завершён успешно: 21,143 проверенных ответа без
ошибок; стабильная фаза 49.36 запросов/с при p95 27.43 мс, всплеск
102.89 запросов/с при p95 25.61 мс. Все 25 отчётов содержали по 300 строк
и завершились максимум за 21.681 секунды; очередь восстановилась до нуля.
930 лицензий и 930 диагностик совпали с долговечными записями в БД.

Одновременный наблюдаемый пик памяти сервисов — 655.90 MiB, сумма отдельных
наблюдаемых kernel peaks — 723.95 MiB; максимум среднего CPU за интервал
измерения — 0.641 ядра. Эти интервальные значения не исключают коротких CPU
пиков: cgroup зарегистрировал ограничение CPU, но без нарушения задержек.
Максимум соединений БД — 11. OOM, перезапусков и незавершённых отчётов не было.
Полные ограничения измерения и таблицы — в
[читаемом протоколе](../evidence/timeweb-compact/2026-10-18/README.md).

## Диск 50 GiB и восстановление

50 GiB допустимы только после измерения восстановленной БД с индексами, WAL,
временными файлами, образом ОС, несколькими релизными образами и ротируемыми
логами. Размер сжатого дампа не доказывает размещение. `max_wal_size` — мягкий
ориентир, не жёсткий предел потребления диска. Для полного восстановления и
временных выгрузок нужно отдельное свободное место; задайте уведомления о
свободном диске до переключения.

Релизы и частные вложения хранятся в S3 с разделёнными правами. Резервные копии
БД, ролей, объектов, конфигурации и криптографических ключей должны быть вне VM,
с независимой восстановительной копией вне основного аккаунта провайдера.
Живой PGDATA не копируется как backup. Нужен проверенный изолированный restore;
существование архива само по себе недостаточно.

Перед переездом остаются обязательными точные релизные образы/CI,
производительность целевой VM и диска, права файлов TLS и app-роли PostgreSQL,
SMTP/S3, backup/restore, мониторинг и согласованное окно одного писателя.
Смотрите [основной runbook](timeweb-platform-preparation.md).

## Уточнение после проверки валидаторов

В полном прогоне проверялись число строк, контрольная сумма CSV, значения
agreements_signed, наличие запрошенных организаций и отсутствие одной контрольной
организации. Эти проверки не доказывали точный набор пар «организация/день».
Исходные ZIP удалены вместе с тестовым S3; повторная проверка их содержимого
невозможна. Полные измерения и их хеши сохранены без изменений.

Исправленный валидатор требует точного набора всех запрошенных пар без чужих,
повторных и пропущенных строк; отдельный
[короткий прогон](../evidence/timeweb-compact/2026-10-18-validator-smoke/README.md)
проверяет новые реальные ZIP. Это дополнительная проверка содержимого, а не
повторное измерение ёмкости. Проверка OOM теперь учитывает `oom`, `oom_kill` и
`oom_group_kill`; сохранённые нулевые счётчики полного прогона проходят её.
