# Дубликат Data Matrix: приёмка и включение

Дата программной проверки: 2026-09-08. Ветка: `codex/validation-dm-duplicate`.
Объём: одна единица продукции внутри упаковки — тот же полный Data Matrix снаружи.
Новая функция прошла программную и браузерную приёмку. Дополнительный общий тест
выявил существующую ошибку инвентаризации, описанную ниже. Аппаратная приёмка
существующего парка оборудования имеет статус `not_run`. Режим на линии не включён.
Задачи 1–15 зафиксированы в `5f65bf89f4d029f344d7521525a1b62c016946c0`;
заключительные проверки и исправления находятся в том же коммите, что этот отчёт.

## Зафиксированное поведение

Администратор в кабинете и оператор на станции задают печать и обязательность
проверки до открытия смены. Без печати сохраняется прежний сценарий. Параметры
открытой смены, шаблон и данные этикетки фиксируются; последующие изменения
библиотеки шаблонов не меняют уже подготовленные этикетки.

При обязательной проверке следующая единица недоступна, пока полное содержимое
кода новой этикетки не совпадёт с исходным и подтверждение не сохранится локально.
Пауза сохраняет задание. Без обязательной проверки можно продолжать после
сохранения результата отправки, но интерфейс не называет этикетку проверенной.

Неизвестный результат отправки после сбоя/перезапуска не вызывает автоматическую
печать. Оператор сканирует вышедшую этикетку либо явно повторяет печать с причиной
«не напечатана», «повреждена» или «потеряна». Повтор использует сохранённые байты,
включая первоначальную дату, и не увеличивает количество принятой продукции.

В кабинете отдельно видны отправки, проверки, незавершённые задания и повторные
попытки. Полный Data Matrix не показывается в истории; используются безопасный
суффикс и идентичность станции/задания. Серверные конфликты сохраняются в журнале.

## Программные доказательства

- Domain: разбор полного GS1-кода (AI93 и AI91+92), сохранение разделителя GS,
  порядка AI, регистра и криптохвоста, сравнение полного содержимого, неизменность
  повторной печати, GS1-растр и обе команды ZPL/TSPL при 203/300 dpi.
- SQLite: запись приёмки и зависимых фактов одним statement, конкуренция двух
  соединений, потеря ответа после commit, восстановление, заморозка snapshot,
  запрет закрытия при незавершённой этикетке, смена credential generation,
  очистка только после всех ACK. Это не физическое отключение питания.
- API/Postgres: миграции на отдельной временной локальной БД, изоляция tenant/device,
  старые станции, frozen policy, выключенный gate, точные receipts, повторная
  доставка, quarantine, история и пагинация одинаковых jobId разных станций.
- Station sync: сервер без явного receipt не удаляет ни scan, ни label events;
  закреплённый полный batch повторяется неизменно; позднее verified остаётся для
  следующей доставки. Смена организации не переносит локальные задания другой.
- Browser: реальные кабинетные маршруты и `NewShift`/`WorkScreen`; API и принтер
  **mock**, журнал — отдельная настоящая SQLite с двумя чередующимися соединениями.
  Перезагрузка страницы сохраняет журнал. Scanner fixture входит через штатный
  `createHardwareScanSource`, без физического HID/COM устройства.
- Геометрия: кабинет 1920×1080, станция 1280×800; русский/английский, светлая/тёмная
  темы. Проверены обязательное окно, отсутствие пропуска, фокус, действия 64 px,
  отсутствие внешней прокрутки на станции. Галерея дополнительных состояний
  использует production-компоненты с синтетическими состояниями, не исполняет печать.

Проверка обнаружила ограничение окна проверки шириной небольшого уведомления.
Диалоги новой операции вынесены из контейнера уведомлений. Регрессионная проверка
теперь требует фактическую ширину 1280 px; существующие уведомления не изменены.

Дополнительно проверены настройки принтера на 1024×768: разрешение и язык печати
должны читаться полностью, checkbox и основные действия остаются в видимой области.
Карточка дубликата использует отступы и типографику существующих приборов Station.
Подсказка до первого скана берёт обязательность проверки из сохранённой политики
смены, даже когда первого задания ещё нет. Эти дефекты подтверждены падающими
проверками до исправления.

### Существующий сбой инвентаризации

`apps/api/test/station-inventory-sync.e2e.test.ts`, сценарий
`owns repack boxes and membership on the server across real competing devices`,
нестабилен: если более поздний скан станции B уже размещён в коробе с датой
2026-08-22, а затем приходит более ранний победивший скан A с датой 2026-08-20,
обновление `inventory_code_results.observed_production_date` опережает удаление
прежнего членства. Postgres отклоняет его с `23503` по
`inventory_repack_items_tenant_result_active_date_fk`.

Происхождение проверено на исходном commit
`c2e0ef01871e89f6ca8a1d519df0b4893d0526a3`: обычный тест может пройти; временный
probe меняет только порядок доставки с `Promise.all` на B → A и воспроизводит
тот же FK-сбой в исходной версии. Временный probe удалён, исходный checkout
сохранён. Inventory service, исходный тест и его миграции эта ветка не меняет.
Исправление относится к отдельной задаче переупаковки; весь расширенный API gate
не объявляется зелёным. Это не аппаратное подтверждение новой печати и не
разрешение выпуска.

## Повтор программной приёмки

Использовать Node 24+, зависимости из lockfile и отдельную тестовую БД.
Сначала собрать domain и db, затем выполнить serial lint/typecheck/test/build
всех workspace-пакетов с переменными тестовой инфраструктуры по AGENTS.md.
После этого:

```sh
pnpm --dir tools/production-browser run test:product-labels
pnpm test:production-bundle:contract
pnpm format:check
git diff --check
```

Браузерный сценарий запускает отдельные локальные серверы на 43181/43182,
`strictPort`, `reuseExistingServer:false`, один worker, без retries. Middleware
SQLite подключён только тестовой конфигурацией Vite, ограничен loopback origin
и временными файлами; в production entrypoint его нет. Каждый сценарий получает
свою БД, соединения закрываются и временные файлы удаляются при остановке сервера.

В текущем worktree pnpm запуск блокируется существующей записью packageManager
в lockfile. Проверки запускаются непосредственно установленными Vitest, tsc,
ESLint, Vite/Nest/Astro и Playwright тех же версий. Lockfile, ограничения возраста
релизов и конфигурация production-окружения для обхода не менялись.

## Аппаратная матрица

Используется существующий разнородный парк, отдельный новый перечень моделей
не утверждён. Заполнять по каждой реально испытанной комбинации. Допустимы только
`passed`, `failed`, `not_run`; отсутствие оборудования не означает совместимость.

| Существующий принтер ZPL, 203 dpi, USB/очередь Windows       | not_run   | Записать модель, firmware, драйвер, носитель 58×40 и ID теста                        |

| Существующий принтер TSPL, 203 dpi, USB/сеть/serial          | not_run   | Записать конкретную комбинацию модели и подключения                                  |

Протокол для каждой комбинации:

1. Зафиксировать commit, станцию, оператора, Windows/Tauri, принтер/firmware,
   сканер, подключение, язык, DPI, носитель и synthetic test ID.
2. Подать синтетические полные коды отдельно с AI93 и AI91+92. Включить GS,
   кавычки, скобки, `^`, смешанный регистр; поля этикетки — с кириллицей.
3. Напечатать, отсканировать этикетку штатным сканером и проверить
   `compareDuplicateKm(original, scanned) === "match"`. Сравнивать полное
   содержимое, а не только GTIN/серийный номер.
4. Повторить после смены календарной даты: байты и дата исходной этикетки
   сохраняются. Количество продукции не растёт; номер попытки растёт.
5. Испытать обрыв до send, во время send и после send до сохранения результата;
   также завершить процесс/отключить питание в соответствующих точках.
   После восстановления возможна проверка/явный повтор, автоматического повтора нет.
6. Пройти required/none, паузу, смену оператора, закрытие, offline/reconnect,
   повторную доставку batch и восстановление уже закрытой удалённо смены.
7. В журнале приёмки указать результат каждого теста. Реальные товарные коды,
   credentials и ключи не добавлять в Git/скриншоты.

## Порядок выпуска и откат

1. Применить совместимые добавочные миграции Postgres и API. Оставить
   `VALIDATION_DM_DUPLICATE_ENABLED=false` (значение по умолчанию).
2. Поставить совместимую Station с протоколом `validation-dm-duplicate-v1` и
   добавочными SQLite migrations. Проверить восстановление старых очередей.
3. Пройти аппаратную матрицу на конкретных линиях, затем отдельно разрешить
   включение флага. Кабинет/станция рекламируют создание режима только при
   включённом флаге; обычные смены продолжают работать при выключенном.
4. При проблеме выключить gate: новые duplicate-смены не создаются, но bundle,
   recovery и sync уже существующих заданий продолжают работать. Это не команда
   удаления очередей, отмены обязательной проверки или повторной печати.
5. Не понижать Station до версии, не понимающей новый журнал: старый бинарник не
   имеет механизма защиты от такого downgrade. Восстановление — совместимым
   исправлением. Не удалять SQLite/очереди и не откатывать применённую миграцию.

Публикация ветки, PR, установка на линиях и включение флага требуют отдельного
поручения. В рамках этой разработки они не выполнялись.
