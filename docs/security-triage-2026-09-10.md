## CodeQL #1: random input IDs

[CodeQL #1](https://github.com/thevladbog/markiro/security/code-scanning/1) points
to the design handoff's `Input.jsx`. This is a DOM label/input identifier, not
an authentication token or production credential. `React.useId()` replaces
`Math.random()` and preserves caller-supplied IDs.

A rendering regression test forces identical random values and checks that two
inputs still have distinct matching label targets. It failed on the old code and
passes on the new code. A second test preserves an explicit ID.

## Remaining findings

### Dependabot #11: glib / GTK3

[Dependabot #11](https://github.com/thevladbog/markiro/security/dependabot/11)
reports `glib` 0.18.5 in `apps/signer/Cargo.lock`.
[RUSTSEC-2024-0429](https://rustsec.org/advisories/RUSTSEC-2024-0429.html) fixes
`VariantStrIter` unsoundness in **glib >=0.20.0**.

Tauri 2.11.5 declares GTK `0.18` for Linux/BSD; GTK 0.18.2 requires glib `0.18`.
A lockfile bump to glib 0.20 cannot satisfy those constraints or preserve the
GTK type boundary. Signer is Windows-only, and that GTK dependency is outside
the supported Windows target. `cargo tree --locked --offline --target
x86_64-pc-windows-msvc --invert glib` confirmed no dependency path for Signer on
Windows. No direct glib/VariantStrIter use was found in Signer source. Station's
lockfile also contains the same glib line.

No Cargo files were changed. An upstream GTK/Tauri migration or a maintained
backport would be separate work requiring platform validation. Do not add an
unused glib 0.20 dependency or rewrite the lockfile to hide the old copy.

### CodeQL #5: upload body length

[CodeQL #5](https://github.com/thevladbog/markiro/security/code-scanning/5)
reports `body.length` in `ExchangeController.post()`, not the current line 406
at the same path. Its recorded source commit is
`8d00334995016eb8c5ad8ba5a5f42d834f0253c3`.

Both that source and current source reject a body unless
`isRequestBuffer(body)` succeeds; that local predicate calls `Buffer.isBuffer`.
Only then is the body appended and its byte length journaled. Query values also
pass through `singleQueryValue`, which rejects non-string/non-undefined values.
Existing protocol e2e tests cover repeated query parameters and bracket syntax.
Source review therefore indicates a likely false positive at this sink; the
controller's runtime behavior was not weakened or rewritten for the scanner.

The latest GitHub CodeQL analysis is **2026-08-24 03:57:36 UTC**. Default setup
reports `not-configured`; the old workflow was deliberately removed in
`b0e4e56bf` with the commit message `ci: remove unsupported CodeQL workflow`.
The two CodeQL findings are historical results. A supported fresh scan and,
if still reported, an evidence-backed false-positive disposition are needed.
This work does not enable a paid repository feature or dismiss the finding.

### Additional finding: existing inventory repack race

`station-inventory-sync.e2e.test.ts`, test
`owns repack boxes and membership on the server across real competing devices`,
can fail with PostgreSQL `23503` on
`inventory_repack_items_tenant_result_active_date_fk`.

When the later scan arrives first, it creates a repack membership with production
date `2026-08-22`. The earlier scan then wins according to the existing timestamp
policy. `StationInventorySyncService` updates the result's date to `2026-08-20`
at line 633 while the old repack item still references the old composite key.
PostgreSQL rejects the update before the membership can be reconciled.

The original test uses `Promise.all`, so a normal baseline run and eight targeted
baseline repetitions passed when the earlier scan was processed first. A
temporary copy of the test changed only the arrival order to:

```ts
await service.ingest(
  tenantId,
  deviceBId,
  repackInventoryId,
  repackBatch("repack-race-b", [loser], 1),
);
await service.ingest(
  tenantId,
  deviceAId,
  repackInventoryId,
  repackBatch("repack-race-a", [winner], 1),
);
```

That reproduced the **same foreign-key failure against the unchanged original
checkout and its old dependencies**. The relevant service, test, and schema
sources match the worktree base. This is an existing ordering defect, not a
reason to weaken the foreign key or roll back the security updates. No inventory
implementation or migration was changed; it needs a separate focused fix.
