# US-06 — Readiness Server Design

**Date:** 2026-09-28
**Status:** Written design approved by the owner on 2026-09-28; no implementation is claimed.
**Scope:** Isolated U.S. P0 instance, read-only readiness assessment. This refines the Readiness section of the [approved US-06 design](2026-09-27-us-06-current-trace-search-readiness-design.md); it does not change the current trace or search contracts.

## Outcome and boundaries

The QA / Traceability Manager can select a clearly displayed scope and see whether the **recorded data** in the current chain has concrete gaps. Every finding identifies its rule, severity and exact lot, event revision and line where available. The result is diagnostic: it is neither a legal determination nor a percentage score. It cannot turn an incomplete trace into an export-ready request package. The U.S. instance, capability boundary and no-release constraint remain unchanged.

P0 covers the server assessment and contract. The office Readiness view follows in the separate US-06 presentation phase. Partner-specific expectation profiles, classification review-due workflow, percentage score, request-package preparation, Station, scanner and printing are outside this phase. The `US_GENERIC_LOT_TRACEABILITY` profile is not evaluated for FTR applicability; FTL-specific rules run only for `US_FSMA204_PROCESSOR`.

## Selected approach

Use a **single scoped, repeatable-read assessment** over current finalized event snapshots and relevant lot identities. A pure rules layer receives normalized frozen evidence and returns deterministic findings. The read layer selects records, verifies their current-root and tenant relationships, and resolves referenced origins. The HTTP layer validates filters and authorizes the current U.S. principal. This follows the current trace/search architecture without persisting a second readiness state.

Two alternatives were considered and rejected for P0: persisting a materialized readiness score would require invalidation on every amendment, void and source correction; rerunning draft finalization validators directly on finalized records would consult mutable master data and could retroactively change historical evidence. Existing Receiving, Transformation and Shipping rules may be reused only where their inputs can be supplied from frozen snapshots. Draft preparation remains a separate view of the existing per-event validators.

## Scope and record selection

`GET /api/us/traceability/readiness` accepts optional `eventDateFrom`, `eventDateTo` (civil `YYYY-MM-DD`, inclusive), `productId` and `lotId`. Dates are not inferred from `created_at` or converted from a UTC event timestamp. With no date parameters, the window is the **24 calendar months ending on the tenant's current civil day**: from the first day of the month 23 months before the current month through today. Supplying one date requires the other. A valid window is ordered and may span at most 24 distinct calendar months; the response echoes its exact bounds and whether it was defaulted. Product and lot identifiers are tenant-scoped; a missing or foreign explicit identifier has the same 404. Date bounds and UUID syntax are strict 400s.

The primary event set contains each current finalized Receiving, Transformation or Shipping root once when its `event_date` is inside the window. The current predicate is the root's `current_event_id` pointing to a tenant-matching event with `status='finalized'` and no successor. Product or lot filters **select whole events** that directly mention the matching lot/product on any frozen line; they do not cut other lines out of a multi-line CTE. Every included event is checked as a whole, and any finding on a different line is labelled with that line's product/lot. Voided, superseded, amended and draft revisions are never counted as current events.

The lot set is the unique lots directly referenced by selected events, plus lot identities with **any** recorded origin event date in the selected window (including a now-void origin) that match any product/lot filter. This lets a retained output lot with no current origin appear even when no current event still references it; the void event itself is not counted. A lot with no recorded origin event can be included by an explicit `lotId` filter; it is labelled as having no CTE date and does not acquire a date from `created_at`. Lot status does not erase an origin gap. A lot's ID, TLC, source, status and case links are never mutated by this read.

For a selected Shipping or Transformation input, the evaluator also checks its referenced **current** Receiving/Transformation origin even when that origin's `event_date` precedes the window or does not match the product/lot filter. Such an origin is a dependency, not an in-scope checked event or lot. A missing or contradictory dependency produces an in-scope finding anchored to the consuming event/line, with the dependency reference attached. It does not increase `recordsChecked` or create a second out-of-scope finding. When an origin is independently in scope, its own findings are assessed once under its own provenance. This distinction applies to the default window and every custom filter.

The response reports exact `recordsChecked.events` (current root count) and `recordsChecked.lots` (unique selected lot count), plus `dependenciesChecked` separately. An empty set is an **empty scope**, not a clean/readiness result. A nonempty set with zero findings says only “No findings in the displayed scope.” The response must never imply whole-tenant completeness from a filtered result.

## Rules, severity and provenance

Rules consume immutable current event snapshots, current lot identity/source fields and verified current-root/line relationships. They cover required frozen CTE date, source/recipient location and reference pieces, product, TLC/source identity, required documents/references, line quantity and UOM, current origin and event-to-lot association. Quantities remain decimal strings in their recorded UOM; no inferred conversion or 2→2 allocation is allowed. A later master rename, archive or coverage edit does not retroactively create a missing-snapshot finding. Rule versions are explicit so a later rule change can be distinguished from changed evidence.

`origin_gap` is an **error**, including a retained output lot after its Transformation is voided. It blocks export-ready preparation under the [MVP contract](../../us/mvp-contract.md). Existing active SSCC links remain visible with “no current origin”; the assessment does not unlink them. A current TLC/source mismatch is an error even when the event revision is greater than one. An amendment reason can explain a resolved historical discrepancy, but cannot downgrade an unresolved current one. Required frozen KDE, invalid/absent quantity or UOM, unresolved source and broken event–lot relation are errors. Warnings are reserved for nonblocking data-quality concerns, and infos for explanatory context; no P0 rule may demote a blocking contract error to a warning. Unknown FTL coverage and exemption review pending follow the blocking policy in the MVP contract for the processor profile. The generic profile shows “General lot traceability only; FTR applicability is not assessed in this profile.”

Each finding has a stable code, `error|warning|info`, CTE kind where applicable, field path, concise EN/ES-ready message parameters and source references. Event-wide gaps carry the actual event ID, number and revision with an event link, but no lot or line. A Transformation non-FTL input gap likewise has no lot; it carries event provenance plus `lineSide='inputs'` and a one-based `lineNo`. Lot-only gaps carry the tenant-derived lot ID and lot link without inventing an event or line. A finding may carry both lot and event provenance when the saved event line names a lot. `lotId` and `links.lotHref` are present together or null together, and at least one of lot or event must be present. Public line provenance is the actual event plus `lineSide` (`items|inputs|outputs`) and `lineNo`, never a fabricated persisted line UUID; the pure evaluator keeps its internal line ID combined with event ID for deduplication and dependency matching. Links open the owning current record or exact historical revision; a void-origin gap links both the retained lot and the void revision. A stable key formed from rule code and source identity deduplicates the same issue within one assessment. Group totals by CTE, product and severity derive from the same finding set, not a second query. FTL-profile coverage is visibly separated from general traceability checks.

Malformed saved JSON, a root pointing to the wrong tenant/revision/status, an impossible missing child row, or contradictory tenant keys are **storage inconsistencies**, not “missing KDE” findings. They return a sanitized, retryable 503 for the whole request. A structurally valid frozen event with a genuinely absent business field or a business-level lot association mismatch yields a finding. This distinction prevents corrupt storage from being represented as a complete assessment.

## Response and draft work

The successful response includes `scope` (effective dates, filters, tenant profile, defaulted flag), `assessedAt`, `recordsChecked`, `dependenciesChecked`, severity counts, grouped counts, ordered findings and `draftWork`. Findings sort by severity, CTE date, event/root ID, line position and rule code for stable rendering. There is no percentage, pass/fail badge, legal conclusion or inferred partner requirement. The API returns one complete assessment; it never sends a successful truncated finding list. For P0 the server enforces a bounded synchronous workload of at most 10,000 selected event roots, 10,000 selected lots and 10,000 findings. A larger scope returns a specific retryable “narrow the scope” error, never zero findings. These bounds are workload safety limits, not product completeness claims, and timed seed evidence is required before changing them.

`draftWork` is a separate summary/list of draft event references in the same displayed date/product/lot scope, with each draft's existing per-event readiness state or a link to calculate it. It is explicitly labelled “Incomplete preparation” and excluded from finalized `recordsChecked`, finding totals and export-ready evidence. Undated drafts appear only on explicit lot/product selection and are labelled undated. Draft details are bounded separately; if they cannot be returned completely, `draftWork` reports its exact count and a continuation link to the existing Events list, not a silently shortened list.

The read authorizes the verified U.S. session and current `traceability.read` capability inside a repeatable-read transaction. Tenant ID and profile are server-derived. No business row or audit row is written. `401/403` mean missing session/capability, `404` hides a missing or foreign explicit lot/product, `400` means invalid filters, and `503` covers unavailable/inconsistent storage, timeout or a scope exceeding the synchronous safety limits. No 200 partial success is allowed. Raw TLCs, document contents and sensitive snapshot text are not logged in error paths.

## Verification and acceptance

- Pure rule tests: all three CTEs, exact field/line provenance, 2→2 Transformation without invented allocation, unresolved versus historically resolved TLC/source mismatch, `origin_gap` error, profile-specific FTL rules and generic-profile non-applicability text.
- Disposable-Postgres tests: current-root selection, amendment/void and retained output lot, older out-of-period origin checked only as dependency, product/lot whole-event filtering, draft exclusion, counts/groups from one finding set, cross-tenant 404 and capability denial, consistent read under concurrent finalization, and no read-side writes.
- HTTP/contract tests: strict date/ID bounds, empty versus zero-findings state, exact response shape, sanitized 503 for corruption/timeout/oversized scope, and U.S.-only proxy/mount checks.
- A timed controlled seed reports selected roots/lots, assessment duration and bounds without claiming production throughput. The separate office phase verifies EN/ES, 1024 px, keyboard access, source links and the metric/grouping states in the [design brief](../../design-briefs/us/04-trace-and-readiness.md). Automated checks do not prove live hosting or regulatory acceptance.

## Owner decisions carried into this design

- Current chain and excluded history stay separate; Transformation is an event node with frozen line quantities.
- An out-of-period origin is verified as a dependency of an in-scope consumer, but is not counted as an in-period record or finding.
- A retained lot without current provenance remains visible and unchanged; its `origin_gap` is a blocking readiness error, not a warning or automatic archive.
- The U.S. work remains isolated, without release or deployment while development continues.
