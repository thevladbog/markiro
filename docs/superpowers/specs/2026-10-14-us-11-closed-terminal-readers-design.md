# US-11 closed terminal readers design

2026-10-14. Selected architecture after independent review; implementation and performance acceptance remain pending. This is the next prerequisite slice of `2026-10-13-us-11-unit-trace-composition-design.md`, not acceptance of the 260+2 dataset, Shipping timings, API aggregate or CI. Standing user authorization preserves delegated implementation and independent review, unchanged assertions and budgets, US isolation and no releases. The implementation plan must be independently reviewed before code changes.

## Decision and bounded change

Use type-only internal read dependencies and lexical implementations owned by the Shipping terminal verifier. Existing verifiers already accept store dependencies; those internal signatures may be narrowed. The accepted public boundary forbids callers supplying proof/read contexts to the unit owner, not internal dependency injection between known implementation functions.

Selected raw slots: tenant authorization-profile fields, reference parties, native lots, explicitly locked reference documents, and explicitly locked Receiving/Transformation/replayed-Shipping roots and event headers. No collections, DTOs, receipts, stage/header observations, authorization decisions or absence results are retained. Location/catalog/product-profile methods participate in the closed authorization routing but retain their business SELECTs in this slice: the inspected terminal graph does not establish a useful later duplicate for those business rows.

Two rejected alternatives remain: whole-chain topological/bulk-snapshot proof changes freshness/error order; ordinary member+profile transport fusion crosses the intervening JS role/any-of gate and is not a semantics-free SQL consolidation. The selected slice removes only proved stable point observations; no count or time saving is promised. The earlier 324 profile calls are across the whole first owner invocation, not a claim about coverage here.

## 1. Public boundary and lifetime

All public signatures stay unchanged, including `UsDatasetUnitCompositionStore.initialize/verify(context, unit)` and Shipping terminal projection methods `(context, index)`. Every public native `Store.*InTransaction` remains fresh, without an optional context/token/proof argument. Standalone, corrected and orphan paths retain ordinary dependencies.

The regular Shipping owner's existing journal `verify` callback calls a runtime-private method:

```ts
#verifyTerminalProjection(
  tx: UsDemoTransaction,
  checked: UsDatasetContext,
  intent: UsDatasetIntent,
  receipt: UsDatasetReceipt,
  mode: "fresh" | "replay",
): Promise<UsDatasetShippingProjection>
```

This method creates lexical typed raw slots, lock-eligibility sets, `active = true`, and the internal reader implementations. It binds **the exact transaction object**, tenant and actor; context-taking dependencies also bind the expected database name/user. Every reader/lock method checks active state and argument identity before touching raw input or a slot; mismatched use is an internal invariant failure, never a fallback to another transaction. Known internal calls use those same bound arguments, so no ordinary domain error is reordered by these checks.

Activation occurs only on entering final verification, after `work.apply` and receipt parsing have returned (`us-dataset-journal.ts:600-602`), or directly in replay verification (`:596-598`). No facts from application preparation or a previous stage are imported. `finally` clears all slots/eligibility sets and marks inactive before return/rejection, hence before receipt persistence and COMMIT. The returned projection contains owned domain values only. COMMIT failure cannot release it.

No exported runtime scope factory, accepts-callback wrapper, token constructor, branded capability, transaction property, WeakMap or query proxy. Cross-module type-only interfaces are allowed. A malicious caller can structurally implement a TypeScript interface, but cannot inject it into the public owner or obtain the owner's implementations. The implementations have no mutator accessors and must not be returned, installed globally, captured by asynchronous work, or passed to caller-selected code. Calls are awaited sequentially; no concurrent transaction work. Pure mapper exports establish neither authority nor proof.

## 3. How eligibility is established without caller assertions

Existing lock operations must be routed through closed implementations that **execute** the lock SQL, not receive a boolean proving it happened. Keep `lockUsDatasetShipping` and `lockUsDatasetTransformation` as shared native operations; terminal wrappers invoke them at the same existing callsite, await success, then record only the exact normalized keys whose cardinality/type/identity their SQL checked. Their internal dependency signatures are `typeof lockUsDatasetShipping` and `typeof lockUsDatasetTransformation`; ordinary dependencies are the original functions. They accept no caller “locked rows”.

For inline reference/document locking blocks, extract only the existing SQL block into a shared internal operation, preserving all order and checks. The closed implementation invokes it, retains the actual successful locked key identities, and returns the same data to the caller. Specifically preserve `shipping-prepare.ts:148-184,203-222`, `reference-verify.ts:67-81`, `receiving-verify.ts:174-188` and `transformation-verify-content.ts:132-146`. Do not move the document-absence comparison currently after Cases verification earlier merely because its SELECT has returned.

Expose these finite lock-operation dependencies alongside the read dependencies in an internal `UsDatasetTerminalDependencies` type, not through a public factory. The operation wrappers never expose or accept the eligibility sets. A failed/missing/cardinality-mismatched lock query cannot qualify a row. Identity from a receipt alone never qualifies it. ID-only locks qualify the **key**, not the full value; a later original full SELECT is still required.

The first full profile read itself obtains the required shares. Receiving verifier's full root `FOR UPDATE` and full revision-range `FOR UPDATE` likewise establish their own row eligibility; keep those statements and comparisons. **Explicit choice for I2:** an always-fresh range may populate individual full raw-row slots after the existing range/identity checks, but only for exact unique keys with a protecting row lock already held (or obtained by that same range). The range and every cardinality/absence check run on every invocation; neither its array nor its membership becomes a slot. In this slice this rule is used only for the Receiving and Transformation event rows listed below. No additional or earlier SELECT, no added locks, and no lock-strength/order change are permitted. This explicit routing is necessary; inferring eligibility merely from a getter's name is not sufficient.

## 5. Shared parsing, native errors and untouched freshness

Reuse the existing `partyResponse`/`locationResponse` (`master-data-support.ts`), `lotResponse` (`lots/us-lot-support.ts:18`), `referenceDocumentResponse` (`documents/us-reference-document-support.ts:5`), `productResponse`, product-profile mappers and native receiving/transformation/shipping validators. Where a mapper is currently embedded in a SQL reader, extract the same logic into a pure helper used by **both** ordinary and terminal cores. No copied alternate lifecycle rules; no cached canonical digest replaces a current comparison.

At each getter boundary preserve its original parse/authorize order. Most getters authorize before UUID parsing; product-profile getters parse IDs before authorization. Every logical member/capability/profile gate remains in place, including the preparation-specific WRITE capabilities. Only the profile raw SQL can be omitted after stable raw profile observation. Required arrays, comma-role parsing/trim/unknown roles, forbidden-before-profile, schema/baseline errors and all existing translations remain exact. Do not batch member and profile into one SQL snapshot.

Always execute fresh: owner provenance/cardinality; membership LIMIT 1 selection; journal/header/stage/receipt/digest observations; reference natural-key or absence checks; every revision/child/genealogy/support/link/basis range; operations/audits; current origin/balance/consumers/status effects; private-xmin tests. The intentional joined current-root/revision linearization in `shipping-origin-status.ts:465` remains untouched—it is not replaced by independently retained root/event rows. Those roots may not be held on every path.

No routine in the closed interval may perform business DML, invoke mutating SQL functions, trigger caller code/getters, or hand out tx/readers. Prior application triggers have completed before entry; deferred trigger/COMMIT behavior remains outside and unchanged. Exact key share/update locks block external changes to eligible rows, but do not block new collection members. A second matching membership is possible because tenant+user is not unique; every member and owner observation stays fresh. READ COMMITTED is not changed to a common snapshot.

## 6. Required implementation review and first falsification tests

First review the actual dependency closure and each matrix row, before claiming implementation-ready. The plan must enumerate changes to the demo verifier types/routing, native pure/core reader factoring, and finite lock-operation wrappers above. Ordinary wrappers must still issue original SQL; a source-level injected-store ownership contract should reject public scope factories, optional proof args, returned readers, arbitrary tx-keyed maps and mutators in terminal dependencies.

First native falsifications, in this order:

1. **Confinement and own writes:** mutate profile/time-zone, lot, document and root/event in application before verification and prove new values are observed/rejected. Same-tx public getters still reload after caller writes. Closed readers reject wrong tx/tenant/actor and post-finally reuse; no output exposes them. Verify exception/COMMIT paths clear state and preserve original error identity.
2. **Profile short circuit / phantom membership:** denied or empty-any-of membership must not acquire later profile/org locks. Real concurrent membership insert between two guard boundaries must reach fresh member selection and later owner cardinality as in reference. Profile UPDATE held before entry must block then be observed; UPDATE after retained share must wait. Run exact combined-role/Unicode-trim policy tests without moving policy into SQL.
3. **Per-row eligibility:** for each enabled slot, demonstrate an existing full SELECT after lock, a later matching point request, same schema result/error, and unchanged earlier failure. Missing/unlocked/partial rows and incomplete finite sets must still run the original query; fresh Shipping roots must not enter replay slots. Test mutable raw-value ownership so returned DTO mutation cannot alter later validation.
4. **Fresh relations and first error:** insert an extra child/revision/audit/operation/support row or absent relation between earlier and later reads; preserve current cardinality/absence checks and error ordering. Basis integrity/count/page, Shipping joined status linearization and history chain validation must execute, not just return matching DTOs. Real writer/lock-order barriers and READ COMMITTED/RR reference comparisons, including malformed profile and earlier ancestor drift before later failure.

Then run the already required native differential cases (fresh/pending/replay/verify, regular 0/1/181/259, correction/orphan regressions, exact receipts/audits/digests/no-write snapshots), followed by one reviewed unchanged-budget performance comparison. No default new profiler/probe cycle. All original 5000/900000/60000 budgets, whole original files and full acceptance gates remain. A smaller dispatch count is not a latency proof or sufficient full-run forecast.

## Review handoff

This design resolves the unnecessary same-module/no-internal-interface restriction: concrete fresh/terminal implementations may share narrow type contracts and pure native logic across modules. Only slot state/construction/lifetime remain private to the owner. The unresolved work is implementation and native falsification of this exact row matrix—not finding a new performance hypothesis. If review identifies a call capable of same-transaction mutation or an unproved lock for a row, that row stays fresh; do not broaden locks, weaken a check or add invalidation heuristics.
