# US-05 — Shipping on the shared event shell

**Status:** Owner approved the architectural direction and both design sections on 2026-09-27. This written specification awaits separate owner review. It does not claim implementation, deployment, or regulatory acceptance.

**Scope:** SHP-001..010 under the [U.S. MVP contract](../../us/mvp-contract.md), [requirements](../../us/requirements.md), and [Shipping KDE mapping](../../us/data-dictionary.md#75-shipping-kde-mapping). This document supersedes the 2026-09-03 US-05 draft where they differ. It follows the actual US-03 Receiving and US-04 Transformation implementation, not their early proposed paths or tables.

## Outcome and boundaries

The U.S. office can draft, finalize, amend, and void a Shipping CTE for existing tenant lots. A current finalized record says which TLC/product/source, exact quantity and unit, ship-from location, date, immediate subsequent recipient, and reference document type/number were recorded. Shipping never creates or changes a TLC or lot identity. One event may ship several lots, and one lot may be shipped in several events. Current and historical revisions are separately readable; finalized KDE snapshots do not change when master data changes.

P0 is lot-and-quantity based. The event quantity `100 case` in the synthetic demonstration is distinct from the 100 server-side SSCC links to the output lot. Neither the API nor UI claims that particular case IDs were selected or physically shipped. Case selection, scans, Station, printing, shipment import/ASN adapter, unusual-flow classification, hosted rollout, and RU changes are outside this slice. English and U.S. Spanish are the only new office copy.

This is an operational traceability balance derived from recorded events, not warehouse inventory, proof of physical movement, or a legal verdict. An unknown balance is never displayed as zero or available stock.

## Architecture decision

Extend `traceability_events` with the `shipping` type, preserving its `event_date`, IANA timezone, root/revision pointers, lifecycle states, draft version, immutable finalization snapshot, and event-document links. Add a typed `shipping_event_roots` pointer row, Shipping detail and item tables, strict contracts, U.S.-only controller/service modules, and a third branch in the unified Events registry/UI. Do not introduce a parallel all-purpose shipment header or rewrite Receiving/Transformation roots.

This is preferred to a standalone shipment lifecycle, which would duplicate concurrency, history and search behavior, and to a temporary shipment record without amendments/void, which would not meet SHP-001. The common shell is extended with explicit per-type constraints and regressions; simply adding an enum value is insufficient.

## Storage and migration

1. Create an additive migration after the current US-04 migrations. Add a type-conditional Shipping root key and tenant-composite FK on the common shell, a `shipping` branch to the existing lifecycle/number checks, and `SHP-YY-NNNN` event-number allocation. Preserve the existing Receiving/Transformation checks, IDs, stored dates, revisions, and snapshot bytes. Upgrade tests include both types with draft, finalized and historical rows. New typed child rows must reject cross-tenant and wrong-type references at the database boundary.
2. `shipping_event_roots` owns permanent event identity, number, lifecycle version, next revision, current finalized pointer, and pending draft pointer. Its FK and one-current/one-pending rules mirror the existing typed roots. A finalized predecessor remains current while its amendment draft is open.
3. Shipping detail stores `recipient_location_id` and its frozen Location Description snapshot. The common event's `location_id` and `location_snapshot` are ship-from; `event_date` is date shipped. Finalization requires a current tenant-owned, description-ready `ship_from` location and a distinct, description-ready `recipient` location; neither may be a carrier in place of the immediate subsequent recipient. An optional carrier/transport reference is operational metadata only.
4. `shipping_event_items` stores `(tenant_id, event_id, line_no)`, existing `lot_id`, exact positive decimal-string `quantity`, explicit `unit_of_measure`, and frozen TLC, source and Product Description snapshots at finalization. Tenant-composite FKs and indexes cover the event and lot. P0 has at most one line for a given lot in an event, avoiding ambiguous repeated-unit entries. There is no writeable TLC, product, source, or `createLot` field on a Shipping line; strict request validation rejects those keys.
5. Reuse the existing tenant-scoped reference-document association and snapshot conventions. Finalization requires at least one usable document type and number; the demonstration includes BOL and invoice. No case/SSCC-to-shipment table is added in P0, and the shared `boxes` schema is unchanged.
6. Immutable child/snapshot guards cover finalized and superseded revisions. A void or amendment changes lifecycle metadata and current pointers, never historical KDE bytes. Recovery uses a verified backup/restore path; already-applied migrations are not rewritten or rolled back destructively.
7. Record Shipping-owned automatic lot-status transitions in a tenant-scoped effect table with lot ID, causing event revision, prior/new status, and compensation state. At most one uncompensated Shipping status effect may own a lot's current status. A later manual status change invalidates that ownership under the same lot lock. Audit history remains separate; the current status text alone is not proof that Shipping owns it.

## Current-origin and balance rules

For each lot, the service reads _all_ current finalized Receiving lines that reference that exact lot UUID and the current finalized Transformation output lines for that UUID. Multiple current Receiving lines contribute their respective quantities; a single old creation receipt is not privileged. These are recorded supply contributions, not the Receiving basis count alone. Current finalized Transformation input use and Shipping lines are recorded deductions. A revision whose root no longer points to it, or a void event, contributes no current quantity; pinned history retains it. Before an amendment successor is evaluated, the predecessor's active effects are excluded, then replaced atomically on finalization.

All arithmetic uses exact decimal strings at the repository's supported three-decimal precision; no floating-point sums or implicit UOM conversions. A lot has a comparable balance only when it has a current valid origin/contribution and every relevant quantity has the same UOM. If an existing current record has missing, corrupt, mixed-unit or otherwise ambiguous quantity evidence, the result is `unknown` with a reason, not a partial sum. The separate Transformation genealogy event-delta projection is not a lot-availability ledger and must not be reused as one.

P0 finalization requires the shipment line UOM to match the origin/contribution UOM, a known comparable remaining quantity, and `quantity <= remaining` after accounting for all other current finalized consumers. Over-shipment is a blocking readiness error, not the warning suggested by the old draft. Mixed UOM is likewise a blocking finalization error in P0; historical mixed-unit data remains readable as `unknown`. A manually entered lot with no current finalized Receiving or Transformation output origin cannot be shipped merely because its operational status is `active`. Drafts may save incomplete lines so the operator can see these blockers.

Only currently usable lots may be finalized. Quarantined, recalled, consumed or archived status cannot be bypassed by a positive arithmetic balance. A partially shipped `active` lot stays `active`; when a Shipping deduction makes a previously positive comparable balance exactly zero, the service performs a system-only, audited `active -> shipped` transition and records its ownership effect. A zero or negative balance before the candidate shipment blocks finalization. On void/amend, `shipped -> active` is permitted only through Shipping recalculation with the event/revision reason and a matching, still-owned status effect, never through the manual lot-status endpoint. If a manual status change intervened, Shipping preserves it and reports the balance/status divergence rather than clearing a control. If existing non-Shipping consumption exhausts a lot, its `consumed` status remains governed by that workflow; Shipping must not relabel it `shipped`.

All commands that can change a lot's current quantity contribution or deduction use the common per-lot serialization protocol. Finalization locks the event root, then affected lots in stable UUID order, re-reads current origins, balances, coverage, locations and documents in the same transaction, and commits effects and exact audit atomically. Two concurrent shipments cannot both pass against the same pre-shipment balance. Receipt/Transformation corrections and Shipping void/amend cannot race past one another; pre-existing downstream-dependency guards remain in force.

## Commands, errors and snapshots

`/traceability/shipments` is U.S.-edition only. Endpoints are create, get revision, replace draft, saved-version readiness, finalize, open amendment, void, and bounded revision list, following the current Transformation controller's versioned/operation-key contract. The unified `/traceability/events` list includes Shipping type, status, current/history and search filters. Read access uses `traceability.read`; Shipping draft writes use `traceability.shipping.write`; finalization, amendment and void require the applicable QA capability in addition to current U.S. membership/profile checks. The precise role/capability mapping is tested against the current guard rather than inferred from UI visibility.

Create/save requests are strict and tenant-neutral: event date, timezone, ship-from ID, recipient ID, lot IDs, quantities/UOM, document IDs and notes. The server owns tenant, actor, number, lifecycle and snapshots. Save compares `expectedDraftVersion`; readiness addresses the saved version; finalize compares draft version and input digest; lifecycle commands compare `expectedLifecycleVersion`. Stable operation keys replay identical requests and conflict on changed payloads. Wrong-tenant IDs are indistinguishable from absent IDs. Draft references are validated as tenant-owned even if the draft is incomplete.

Readiness/finalization distinguish missing date, ship-from, immediate recipient, invalid/equal locations, missing document type/number, missing/blocked lot, unresolved TLC source, incomplete product/coverage description under the processor profile, missing current origin, unknown/mismatched balance and over-shipment. The processor profile cannot treat unknown coverage or pending exemption review as complete. Generic lot traceability gets no FDA-labelled interpretation, but P0 still requires the core event data and a usable reference document. Every error has a stable code and a field/line path. Acknowledgement cannot turn a blocking issue into success; transport and storage failures propagate as retryable failures rather than fake completeness errors.

Finalization freezes ship-from and recipient Location Descriptions, event timezone/date, each line's exact TLC, source kind/value/resolved description, Product Description and quantity/UOM, plus document type/number and issuer context. It writes the current revision, balance/status effects and an audit row with exact actor, tenant, action, target, result, relevant lot IDs and status changes in one transaction. Historical reads use the saved snapshot, not live master data.

An amendment draft leaves the predecessor current until the successor finalizes. Finalization atomically supersedes it and recalculates affected lots against the replacement quantity. A reason is required. Void of a current finalized revision removes only its current balance contribution, preserves historical snapshots and audit, and reopens `shipped` only by the restricted system rule. Void of an amendment draft leaves its predecessor current. If a future finalized downstream event pins the Shipping revision, a material correction/void is blocked with bounded tenant-safe blockers and correction order; no consumer is silently rebound. Shipping itself creates no new lot identity or genealogy edge.

## U.S. office workflow

The approved 2026-09-27 balance addendum exposes `GET /traceability/lots/:id/shipping-balance`
only through the isolated U.S. read boundary. The uncontextualized result reflects current
finalized events. An optional pending Shipping draft ID and expected version make a replacement
preview that excludes its verified current predecessor. The editor labels the exact projected
remaining quantity as a preview and offers refresh; unknown balance, zero, mismatched unit and
over-shipment have explicit guidance. A finalized or historical detail separately labels the
uncontextualized **current recorded lot balance** beside its frozen recorded quantity; it never
infers a historical before/after value from today's ledger.

Add Shipping to the existing unified Events list/filter and keep Receiving and Transformation editors intact. The Shipping draft offers existing-lot selection, quantity/UOM in the lot's origin unit, ship-from and immediate-recipient selection, date, document references, saved readiness, and explicit blockers. It has no new-TLC action. The finalized card shows frozen KDEs, event/revision state, balance effect, audit-relevant history, and a clear distinction between recorded shipment quantity and any independent case-link count. Amend/void dialogs require reasons and surface downstream blockers.

Reuse `@markiro/ui`, established U.S. client/session/error patterns and exact EN/ES keys. Keep identifiers and user-entered values untranslated; preserve keyboard/focus/labels/non-color-only states. The interface never implies that 100 case links are selected shipment cases, that a synthetic case was scanned, or that a Shipping record proves physical dispatch. A safe direct-URL unavailable state remains for an edition/profile without this feature.
