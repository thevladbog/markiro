# Обмен с 1С (CommerceML) — дизайн-спека

> Статус: утверждён к планированию (2026-07-29).
> Первый канал секции «Интеграции», анатомия которой описана в
> `docs/design-briefs/08-integrations.md` — этот документ её не пересказывает,
> а наполняет.
> Закрывает отложенное в `docs/superpowers/specs/2026-07-23-pickup-kiosk-design.md`
> §14 «CommerceML-готовность (только хуки)»: хуки (`products.external_ref`,
> цена на товаре и позиции заявки, устойчивая структура заявки) уже в `main`,
> здесь появляется сам обмен.
> Подключается как адаптер формата по `docs/architecture.md` §5.

## 1. Что решаем

Сегодня цены в каталог заводятся руками, а заявку «Для себя» администратор
перебивает в учётную систему тоже руками. Обмен снимает и то и другое: цены
приезжают из 1С, заявки уезжают в 1С, а чек или списание рождается там, где для
этого есть учётный контур.

**Вне среза:** несколько подключений к 1С у одного тенанта, обмен по
контрагентам, выгрузка отгрузок (ждёт агрегацию из плана 06), zip-транспорт,
интеграция с ККТ.

## 2. Решения, принятые на брейншторме

| Вопрос                 | Решение                                      | Почему                                                                                |
| ---------------------- | -------------------------------------------- | ------------------------------------------------------------------------------------- |
| Кто инициирует         | 1С приходит к нам на `/1c_exchange`          | Типовая 1С умеет это из коробки; дорабатывать конфигурацию клиента не нужно           |
| Сколько подключений    | Одно на организацию                          | Множественность потом добавить можно, убрать — нет                                    |
| Хозяин каталога        | Markiro                                      | Обмен не может сломать GTIN, этикетки и перечни киосков                               |
| Новая номенклатура     | Кандидат в очереди, карточку создаёт человек | Каталог остаётся нашим, но обмен не молчит про незнакомое                             |
| Когда выгружаем заявку | Сразу при создании                           | Ждать смены статуса — значит зависеть от того, вспомнит ли администратор её перевести |
| Тип документа          | Один, «Заказ товара», причина в комментарии  | Словарь документов в конфигурациях разный; разделение — настройка, а не допущение     |
| Статусы                | Двусторонние, по таблице сопоставления       | `type=sale&mode=file` документирован как «из 1С на сайт»                              |

## 3. Транспорт

Постоянный адрес `/1c_exchange`. Диалог по протоколу «Обмен с сайтом»:
`checkauth → init → file → import` для каталога и
`checkauth → init → query → success` для заявок, плюс обратное направление
`type=sale`, `mode=file` + `mode=import`.

**Тенант определяется учётными данными, а не адресом.** Организация в пути
потребовала бы всё равно проверять, что путь и учётка согласны, — то есть ту же
проверку по учётке плюс лишний режим отказа, когда одно верно, а другое нет.

**Учётные данные обмена — отдельные машинные.** Логин и пароль, сгенерированный
и показанный один раз, в базе только хэш — та же дисциплина, что у токена
киоска и кода привязки. HTTP Basic по проводу делает TLS обязательным; для
on-prem это уже зафиксировано в брифе 07.

**Сеанс.** `checkauth` отдаёт cookie, которую 1С возвращает дальше. Нужен стор
«cookie → организация, подключение, срок» и промежуточная площадка под куски
файла: файл приезжает частями, дописываясь в одно имя. Срок жизни сеанса
ограничен и переживает один обмен, а не сутки — предлагаю час, чего хватает на
загрузку большого каталога партиями; недогруженные куски по истечении сеанса
удаляются, иначе брошенный на середине обмен оставит мусор навсегда.

**Куски складываем в Postgres.** Объектное хранилище есть в архитектуре, но
появляется в плане 09, и завязывать на него обмен рано. Размер куска назначаем
мы сами в `init`, поэтому в Postgres он помещается спокойно. Когда хранилище
появится, сменится место складирования, а не протокол.

**`zip=no` в v1.** Архивы — новая зависимость и поверхность для zip-бомбы ради
экономии трафика на файле в единицы мегабайт.

**Перебор пароля.** Эндпоинт открыт до `checkauth`. Берём тот же счётчик в базе,
что защищает привязку киоска, — без новых зависимостей.

## 4. Входящий поток: цены и кандидаты

Сопоставление по `products.external_ref` — это `<Ид>` из CommerceML.

**Совпало** — применяем цену и только цену. Имя, GTIN, ЕГАИС, шаблон этикетки,
перечень киоска обмен не трогает никогда. Это жёсткое правило в коде, а не
договорённость.

**Не совпало** — позиция становится кандидатом: сохраняем присланное
(наименование, артикул, единица, цена, GUID) и показываем в очереди.

**Пропало из выгрузки** — не делаем ничего. Обмен бывает частичным, и
отсутствие товара в одном файле не означает, что его больше нет.

### 4.1 Первый обмен

При первом обмене несопоставленным окажется **весь каталог**: у существующих
товаров нет GUID из 1С. Поэтому кандидат обязан предлагать три действия —
привязать к существующему товару, создать новый, скрыть — и подсказывать
вероятное совпадение по наименованию и артикулу, с групповым подтверждением
подсказок. Очередь, умеющая только «создать», заставит администратора
продублировать каталог целиком.

### 4.2 Разрыв связи

Связь разрывается из карточки товара (там она видна) и из очереди. После
разрыва цена остаётся прежней, позиция 1С при следующем обмене возвращается
кандидатом — это и есть путь к правильной привязке. Разрыв пишется в журнал:
«почему товар перестал получать цены» — типовой вопрос поддержки.

«Скрыть» — не то же самое, что разорвать: скрытое не всплывает каждый обмен, но
остаётся под фильтром и восстанавливается.

### 4.3 Цены

Тип цены, который ложится в `products.unit_price`, — настройка подключения.
Если она не задана и тип цены в файле **один**, берём его. Если типов
несколько, а настройка не задана — **не применяем ничего** и пишем в журнал,
какие типы пришли: угадывать, какая из трёх цен розничная, значит однажды
проставить киоску закупочную. Валюта не рубль — позиция не применяется и
попадает в журнал. Цены нет для сопоставленного товара — прежняя остаётся, не
обнуляется.

**Историю цен по товарам не ведём.** `pickup_order_items.unit_price` уже хранит
цену на момент заявки, поэтому переоценка не переписывает прошлое. В журнал
идёт сводка за сеанс: обновлено, без изменений, ушло в кандидаты.

### 4.4 Повтор и объём

Применение цены идемпотентно по природе; кандидаты ключуются парой
«подключение + GUID», поэтому переигранный `import` не размножает очередь.

Большой каталог не грузим одной транзакцией: у протокола для этого есть свой
механизм — `import` отвечает `progress`, и 1С приходит снова. Обрабатываем
партиями, прогресс держим в сеансе.

## 5. Исходящий поток: заявки

**Выгружаем сразу при создании**, в статусе `pending`. Чек или списание
рождается во внешней системе; ждать перевода статуса значит зависеть от того,
вспомнит ли администратор его перевести.

«При создании» означает **при появлении заявки на сервере**, а не в момент
скана: киоск офлайн-первый, и заявка, оформленная без связи, доезжает позже.
Документ при этом несёт `createdAt` — время отбора, — потому что для учёта
важен момент, когда работник забрал продукцию, а не когда об этом узнал сервер.

Документ несёт **причину, выбранную работником на киоске** (`buy` / `writeoff`)
— она известна в момент создания. По умолчанию один тип документа, «Заказ
товара», причина уходит в комментарий и дублируется отдельным реквизитом,
который конфигурация 1С может замапить. Настройка подключения разделяет
списание в свой тип, если конкретная 1С его принимает.

**Подтверждение до пометки.** 1С забирает пачку в `mode=query`, подтверждает в
`mode=success`; помечаем выгруженным только на `success`. До него документ
предлагается снова. Падение между двумя шагами должно приводить к повтору, а не
к потере — та же дисциплина, что в очереди киоска. Повтор безопасен: у
документа стабильный GUID (идентификатор заявки), и 1С узнаёт его как тот же.

**Товар без связи придерживает заявку.** В строке документа номенклатура
опознаётся GUID-ом; выразить строку нечем. Отдать документ с пустой
номенклатурой хуже, чем не отдать, поэтому такие заявки не уходят и показывают
причину со ссылкой в очередь кандидатов.

**Отмена после выгрузки возможна** — это цена выгрузки при создании. Базово
отменяется руками в двух местах, но карточка заявки обязана показывать
«выгружена в 1С», иначе указание отменить и там невидимо ровно тогда, когда оно
нужно.

## 6. Сопоставление статусов

Двустороннее, с честным разделением надёжности.

**Из 1С к нам — основной путь.** 1С присылает изменённые заказы через
`type=sale&mode=file` + `mode=import`; узнаём документ по GUID и двигаем статус.

**От нас в 1С — best-effort.** Свой статус мы можем только заново предложить в
`mode=query`; применит ли его конфигурация — не наша гарантия. В интерфейсе не
обещаем больше, чем есть.

**Сопоставление — данные, а не код**: таблица «внешний статус → наш» на
подключение. Названия реквизита и словарь значений в УТ, Рознице и самописных
конфигурациях разные; стандарта нет, и захардкоженный словарь гарантированно не
подойдёт второму клиенту.

**По умолчанию слой выключен.** Неизвестный внешний статус не двигает заявку
молча: он попадает в журнал как «статус не сопоставлен», что и подсказывает
администратору, чего не хватает в таблице.

**Инварианты жизненного цикла сильнее внешнего статуса.** Сопоставленный статус
не может протащить переход, запрещённый нашей моделью: отмена уже пробитой
заявки не применяется, а показывается как расхождение. Внешняя система
управляет статусом, но не ломает наши правила.

## 7. Ошибки и наблюдаемость

Событие журнала: время, канал, сеанс, направление, исход, короткая строка для
человека, детали. **Ни одна ветка не завершается молча.**

Именованные случаи: неверные учётные данные и счётчик попыток; неразобранный
XML с позицией ошибки; позиция в чужой валюте (пропущена); заявка, придержанная
из-за несвязанного товара; несопоставленный внешний статус; разрыв связи.

**Молчание — состояние, а не отсутствие состояния.** Если 1С перестала
приходить, ошибки не будет, потому что нет запроса. У канала есть «нет обмена N
дней», порог — настройка подключения со значением по умолчанию **48 часов**: у
одного клиента обмен раз в час, у другого раз в сутки, и общая константа
соврёт обоим, а отсутствие значения по умолчанию оставит состояние выключенным
у всех, кто до настройки не дошёл.

**Текст ошибки адресован специалисту по 1С со стороны клиента**, а не нашему
администратору: последний неуспешный сеанс показывается целиком, включая то,
что мы ответили в протокол.

**Ретенция по зерну.** Сеансы — 90 дней. Построчная детализация внутри сеанса
растёт быстрее и ограничивается отдельно: сводка остаётся, разбор по позициям
нет.

## 8. Тестирование

**Закрываем тестами:** протокол — записанными диалогами
(`checkauth → init → file → import`), прогнанными через API как существующие
e2e; разбор CommerceML — на фикстурах XML; сопоставление статусов — чистой
функцией над данными; кандидаты, придержанные заявки, идемпотентность повтора —
обычными тестами за границей адаптера.

**Проверяется только на живой 1С** и потому идёт в приёмочный чек-лист по
образцу `docs/hardware-acceptance-checklist.md`: выгружает ли конфигурация
клиента изменённые заказы обратно; принимает ли отдельный тип документа для
списания; как называется реквизит статуса и каков словарь его значений.

**Нужно от заказчика:** реальные `import.xml` и `offers.xml` из рабочей 1С —
станут фикстурами и снимут часть догадок. Не блокирует: начинаем на
синтетических.

## 9. Разбивка на планы

**И-1 «Каркас интеграций и приём цен».** Секция и анатомия канала, общий
журнал, транспорт `/1c_exchange`, входящий поток, кандидаты со связыванием и
разрывом, ключи публичного API. Результат: цены из 1С едут, каталог связан.

**И-2 «Выгрузка заявок и статусы».** Исходящий поток, придержанные заявки,
сопоставление статусов. Результат: администратор перестаёт перебивать заявки
руками.
