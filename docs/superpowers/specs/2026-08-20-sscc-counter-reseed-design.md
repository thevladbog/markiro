# Перевыдача счётчика SSCC: настройка, которая реально применяется

Дата: 2026-08-20

## Проблема

Админ задаёт в настройках «Начальный серийный номер» — на этикетках номера
продолжают идти с прежнего места (в наблюдавшемся случае: в настройках 2000,
на этикетке 11).

Причина — цепочка из трёх звеньев:

1. Настройка пишет только `sscc_counters.next_serial`
   (`OrgProfileService.putSscc` → `atomicSeedSscc`).
2. Счётчик читается ровно в одном месте — при нарезке **нового** блока
   (`SsccService.allocate`).
3. Станция получает серийники только через bundle смены, а
   `SsccService.allocateForBundle` намеренно возвращает уже выданный
   устройству блок, пока тот не исчерпан целиком (размер блока
   `BOX_BLOCK_SIZE = 2000`). Локально станция жжёт номера из `sscc_pool`
   через `burnSerial`, который берёт `ORDER BY from_serial LIMIT 1` — всегда
   самый младший диапазон.

Итог: устройству когда-то выдали блок `1..2000`, курсор дошёл до 11, и новое
значение счётчика подействует только после исчерпания этих 2000 номеров.
Механизма отзыва выданного блока в коде нет.

Дополнительно: `seedFloor` не даёт задать значение ниже
`MAX(sscc_blocks.to_serial) + 1`, то есть при живом блоке `1..2000` минимум
равен 2001 — сохранение значения 2000 обязано было упасть с 400.

## Решение

Сохранение счётчика отзывает выданные блоки, чтобы следующий bundle нарезал
свежий блок с заданного номера. Нижняя граница опускается до фактически
напечатанного, а безопасность обеспечивается запретом правки при активных
сменах.

### 1. Модель данных и семантика счётчика

Новая колонка `sscc_blocks.revoked_at timestamptz NULL`.

Отозванный блок:

- невидим для `allocateForBundle` — она нарежет свежий блок из счётчика;
- по-прежнему видим для `recordConsumedSerial` — поздно доехавшие закрытия
  коробов должны записывать потребление, иначе теряется факт печати;
- виден для аудита — объясняет разрыв в нумерации.

`seedFloor` меняет определение с «выше всего выданного» на «выше всего
фактически напечатанного»:

```
floor = MAX(consumed_through_serial) + 1   -- по ВСЕМ блокам, включая отозванные
floor = max(floor, 1) для extension digit 0, max(floor, 0) для остальных
```

То же выражение синхронно меняется в `setWhere` внутри `atomicSeedSscc`:
гарантия обязана оставаться в одном стейтменте с записью, иначе возвращается
гонка между чтением границы и записью, ради которой её туда и складывали.

После этой правки значение в настройках впервые означает ровно то, что
написано на лейбле: серийник, с которого пойдёт следующая этикетка.

### 2. Гуард и отзыв: общий сервис

`putSscc` продублирован байт-в-байт в `org-profile.service.ts` и
`counterparties.service.ts`. Логика становится тяжелее (гуард + отзыв +
транзакция), поэтому она выносится в `SsccService.seedCounter(tenantId,
issuerPrefix, dto)`; оба вызывающих модуля резолвят свой префикс и зовут её.

Внутри, одной транзакцией:

1. Проверка активных смен: `SELECT ... FROM shifts WHERE tenant_id = ? AND
   status = 'active' LIMIT 1`. Если есть — **409** с id и номером смены в
   теле, чтобы UI показал «закройте смену №N».
2. Проверка нижней границы (`consumed + 1`) — **400** с числом-минимумом.
3. `atomicSeedSscc` — **409** при сдвиге границы, как сейчас.
4. Если новое значение **отличается** от текущего счётчика:
   `UPDATE sscc_blocks SET revoked_at = now()` по (tenant, prefix, ext) для
   неотозванных. При совпадении значений отзыв не выполняется: иначе каждое
   повторное «Сохранить» сжигало бы блок и рвало нумерацию на 2000 номеров.

**Мягкий барьер против офлайн-станции.** Остаточный риск: станция офлайн,
держит незасинканные закрытые короба, смену закрыл админ через
`POST /shifts/:id/close`. Их SSCC попадут в отозванный диапазон и при
ingest'е упрутся в `boxes_tenant_sscc_uq` (23505), что валит всю
батч-транзакцию — станция встаёт на синхронизации. Полностью закрыть это
нельзя: сервер не знает про локальные короба. Поэтому `seedCounter`
дополнительно возвращает 409, если у устройства с живым (неотозванным)
блоком под этим префиксом `station_devices.last_seen_at` равен NULL или
меньше `MAX(shifts.closed_at)` по тенанту — то есть устройство не выходило на
связь после закрытия последней смены и могло не отдать свои короба. В теле —
имя устройства. Обходится только исправлением ситуации, флага-обхода нет.

### 3. Доставка отзыва на станцию

Сервер не может рассчитывать, что станция сама догадается выкинуть старый
диапазон: `burnSerial` берёт самый младший `from_serial`, и новый блок просто
ляжет второй строкой ниже по приоритету.

`ShiftBundleDto` получает поле рядом с `sscc`:

```
ssccRevokedFrom: number[]   // from_serial отозванных блоков этого устройства
                            // для (issuerPrefix, extensionDigit)
```

Явный список, а не «удали всё, что не названо в bundle»: последнее сломается
в тот день, когда у устройства легитимно окажется два живых блока — код
применения top-up'а в `sync.ts` уже написан, сервер его пока просто не шлёт.

Станция:

- новая `dropRanges(exec, issuerPrefix, extensionDigit, fromSerials)` в
  `sscc-pool.ts` — `DELETE` по первичному ключу
  `(issuer_prefix, extension_digit, from_serial)`;
- вызывается в `shift-bundle.ts` **до** `addRange`, внутри уже обоснованного
  там порядка «сначала пул, потом `upsertBundle`»;
- пустой массив и `sscc: null` — no-op: деградированный bundle не удаляет
  ничего.

### 4. Админка

Обе формы — настройки организации (`OrgProfilePage.tsx`) и карточка
контрагента (`CounterpartyForm.tsx`):

- `GET .../sscc` дополнительно отдаёт `minSerial` (текущая граница) и
  `blockedBy` (активная смена / несинхронизированное устройство, либо `null`);
- при `blockedBy` поле и кнопка заблокированы с внятным текстом, а не
  молчаливым 400 после нажатия;
- ошибки 400/409 локализованы в ru/en — сейчас в тост падает голая
  английская строка с сервера;
- под полем подсказка: «следующая этикетка получит номер N», где N — текущее
  значение счётчика.

## Тесты

- e2e (`apps/api/test/sscc-settings.e2e.test.ts`): блокировка активной сменой;
  граница `consumed + 1`; блокировка несинхронизированным устройством; после
  сохранения bundle отдаёт новый блок с заданного номера и `ssccRevokedFrom`
  со старым `from_serial`; повторное сохранение того же значения блок не
  отзывает.
- юнит станции: `dropRanges` удаляет строку пула; `burnSerial` после удаления
  выдаёт номер из нового диапазона.
- админка: заблокированное состояние формы при `blockedBy`.

## Что осознанно не делается

- Не трогается поведение `allocateForBundle` для неотозванных блоков — оно
  защищает от выдачи двум устройствам пересекающихся диапазонов.
- Не смягчается `boxes_tenant_sscc_uq` и обработка 23505 при ingest'е: два
  физических короба с одним SSCC — это реальная проблема данных, её нельзя
  проглатывать.
- Не реализуется серверная отправка `ssccBlock` в ответах ingest'а (top-up):
  код на станции есть, но это отдельная задача.
