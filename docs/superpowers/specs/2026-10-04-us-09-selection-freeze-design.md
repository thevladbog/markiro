# US-09 — Selection, Validation and Freeze Design

**Status:** Owner-approved written design, 2026-10-04. No push, release or deployment is authorized by this document.

**Scope:** Stage 2 of the [owner-approved US-09 design](2026-10-04-us-09-trace-request-current-design.md): complete scope selection, consistent validation and immutable preparation. Foundation and stage-2 internal implementation have completed independent local review; see the [implementation checkpoint](../plans/2026-10-04-us-09-selection-validation-freeze.md#local-implementation-checkpoint--2026-10-04) for executed gates and limits. Current source and tests remain the implementation authority. HTTP, worker, artifact publication, UI, hosted infrastructure and release are outside this stage.

## Decisions and approach

Use a dedicated US-only selector and a transaction-aware form of the existing US-07 source reader. The US-06 search/trace projections are for bounded presentation; their page and graph limits cannot prove a complete response. A persistent materialized genealogy index is unnecessary for this P0 bound and would introduce another synchronization authority. The selector reads the authoritative tenant-scoped events, revisions, lots and relation rows within the same transaction as validation or freeze.

This document refines, rather than replaces, the parent design. It records these confirmed choices:

- Different supplied filters combine with **AND**. Multiple values within TLC and location lists combine with **OR**. A date, location and document predicate must match the **same event**; the selector cannot satisfy each predicate using a different event in a lot's history.
- A lot/TLC selection includes its complete connected chain of provenance and subsequent events, not just the initial match or the first graph page. Dependencies outside the input date range remain in the response and are identified as dependencies.
- The selected closure is bounded at **500 event revisions**, including dependency and included historical revisions. A result above the bound fails explicitly; it is never silently truncated or called complete. The frozen serialized snapshot is bounded at **16 MiB**. A timeout or corrupt source is a technical failure, not a successful Incomplete result.
- `Validate` and `Prepare` use the same mode-neutral scoped-content digest. `Prepare` reselects within its own repeatable-read transaction and rejects drift. A run stores immutable source content and exact identities, not a pointer to today's graph.
- The stage is not accepted on tests that skip PostgreSQL: transactional/concurrency checks must execute against an owned disposable US database, never a shared or production database.

## Scope resolution and complete closure

First normalize and validate the server-side scope under the strict US contract; client-provided tenant, actor, arbitrary event pins and lifecycle labels do not confer authority. Resolve product ID or description, TLC single/list/range, lot, source reference, event date range, locations and document number against tenant-scoped records. Distinct predicates narrow the initial match by AND; each list predicate is OR within that field. Event-level predicates are evaluated on one event revision. The accepted normalized scope, exact seed matches and why each matched are retained in the validation envelope.

Identity selectors resolve persisted tenant lots. Proposed product/TLC values in a create-on-finalize draft with no persisted lot do not constitute an identity match; saved event date/location/document selectors may match that draft, and linked drafts enter closure. Receiving and Shipping source values come from the exact saved revision being matched. Missing draft values do not inherit values from a finalized revision.

An event seed brings its referenced lot rows into the traversal. A lot seed starts from the matching lot. Traverse Transformation input/output relations in both directions, with visited event/root/lot sets: upstream to its Receiving or earlier Transformation origin and downstream through subsequent Transformation and Shipping. Include the event nodes and their exact input/output/shipping lines; do not infer a 2→2 quantity allocation from a direct lot-to-lot edge. Receiving and Shipping are terminal event types for this P0 graph. Include a dependency even when its date, document or location lies outside the initial filter, and record that it was dependency-included rather than a direct match. This distinction prevents a broad response from being presented as if all records met the input predicates.

The canonical selection envelope contains all current connected records plus linked noncurrent/draft/void revisions and relevant root/lot lifecycle facts needed to determine both modes. The mode does not change the selected universe or its digest. For `export_ready`, derive only the current finalized chain and reject any required missing, noncurrent or otherwise blocking dependency. For `available_records_incomplete`, retain available excluded revisions with explicit lifecycle/finding labels, separate from current records. Never replace a missing pinned row, inconsistent root, broken relation, invalid source snapshot or cross-tenant relation with an empty result or a fabricated finding. Such corruption is a technical failure.

Execute the traversal to exhaustion within the supported bound. Count distinct event **revisions** after closure, not merely roots or paged results. Each bounded database read obtains at least one sentinel beyond the remaining allowance, so 501 is detected rather than dropped. An empty valid scope is an exact zero-match validation, eligible only for an explicit Incomplete preparation with no workbook input. Exceeding 500, 16 MiB or the finite query deadline prevents preparation; none is an invitation to choose an arbitrary subset. Tenant ID is applied to every relation read and join, and mixed-tenant links fail closed.

## One consistent validation view

`Validate` reloads current membership/capability and the request revision inside a repeatable-read transaction. It selects the whole envelope, evaluates source-linked findings, resolves the effective US-08 Plan by exact ID and verified PDF hash when present, and freezes registry, baseline and required build-identity stamps. An absent effective Plan is an explicit readiness finding; corrupt or mismatched Plan evidence is a technical failure. The stage receives immutable build identity as an injected dependency; runtime Git or mutable package metadata is not a fallback. This internal seam does not make a production build provider or publication ready.

Compute the scoped-content digest from a canonical, lossless envelope: request revision, requester reference, name, organization, contact and deadline facts, normalized scope, matched values/reasons, current and excluded source identity/content/lifecycle, lot/product/source/coverage and genealogy facts, findings, effective Plan identity/hash or explicit absence, and registry/baseline/build stamps. Sort unordered sets and object keys deterministically. Exclude actor, chosen mode, idempotency key, run ID, run revision, warning-acknowledgement metadata and generated-at instant. The exact bytes used for digest calculation must be retained or reproducible in tests; a content edit that changes readiness cannot leave the digest unchanged.

Persist the validation summary, digest and time only if the request revision is still the one read. Request edits and closure use expected revision and invalidate validation. A warning acknowledgement binds its reason to the exact digest but does not itself change the request's semantic revision or digest; new source or request content invalidates that acknowledgement. Validation can report business findings, including no matches or missing Plan, but transaction errors, timeouts and corrupt data must propagate as technical failures without replacing a prior successful validation with a false new one.

Partial request edits retain deadline policy when the due instant is omitted: correcting receipt time recalculates a default elapsed 24-hour deadline; an alternative due instant/reason is retained and revalidated. A semantic no-op retains revision and validation. Every changed digest-bearing request field invalidates validation and acknowledgement.

## Atomic Prepare and replay

`Prepare` opens one repeatable-read transaction and reloads current authorization. It locks the tenant/request row and checks `(tenant, actor, idempotency key)` before checking current request state or live source drift. An existing key with the same request ID and mode returns its **original** run, even after request closure or source changes; a different request/mode is a conflict. Only a new key requires the request to be open and validated. Command identity does not incorporate mutable source content, validation time or the request's later revision, because a retry of an accepted command must remain a retry. The DB uniqueness constraint is the final race arbiter.

For a new key, reselect the full scope and read exact source revisions, lot facts, findings, effective Plan/hash, registry, baseline and build identity in that **same transaction**. Refactor the current public `readUsExportSources` into a private transaction-aware core while preserving its public authorization, tenant isolation and 500-pin behavior. Do not call the public reader from inside Prepare: it opens an independent snapshot. Compare the recomputed scoped-content digest to the stored validation digest. A mismatch returns a stale-validation conflict and creates no run; the user must Validate again. Serialization/deadlock retry restarts the whole transaction, not only the last query.

Apply mode eligibility only after the digest matches. `export_ready` requires a complete current finalized chain, no blocking findings, effective verified Plan and representable nonempty workbook input. `available_records_incomplete` is explicitly marked Incomplete, may contain excluded lifecycle records or zero matches, and never converts infrastructure/corruption errors into a successful run. Before inserting, measure the UTF-8 bytes of the canonical serialized full immutable snapshot and enforce 16 MiB; count all selected revisions against 500. Allocate the next positive request run revision under the lock; atomically persist the complete selection, source content, request facts, findings, stamps, Plan pin, generation instant and exact US-07 `ExportInputV1` when nonempty. Store its canonical `inputDigest` separately from the mode-neutral scoped-content digest. With no event, store explicit `selectionKind: empty` and a null input digest, not a fabricated event or XLSX promise.

Derive the ready path by traversing current finalized relations from the semantic scope seeds. Excluded revisions cannot bridge otherwise disconnected current branches. A lot-only query may retain an extra linked draft in its validation evidence without requiring that draft in the ready path; event-level predicates require a representable current revision of their matched root. Recompute model representability on this current input, while preserving full-history findings in the validation snapshot. A typed model failure may be retained in incomplete mode for explicit absent-workbook handling; corrupt current provenance cycles and hard selection/snapshot limits fail in both modes.

An existing run revision is never recomputed from current request/source rows. A later correction or Plan supersession requires a new validated run. The run's idempotency identity and unique `(tenant, request, revision)` remain enforced by the additive US-09 schema; concurrent Prepare calls must either return the accepted same-key run or produce distinct properly serialized revisions, without a partial record. Every accepted/rejected mutation emits exact tenant, actor, request/run, action, outcome, mode, revision/digest metadata through the existing US audit boundary; requester contact stays out of routine logs and errors.

## Verification and acceptance boundary

The implementation plan should divide this into independently reviewed steps: transaction-aware reader seam; selector and closure; validation/digest; atomic Prepare/idempotency. A focused failing test precedes each behavior change. Tests must cover AND/OR and same-event matching; seed-to-upstream/downstream closure; multiple Transformation inputs/outputs; out-of-range dependencies; current versus excluded revisions; zero results; the 500/501 and 16 MiB edges; cross-tenant denial and corrupt links; changes to each digest-bearing class; Plan absent/mismatch; concurrent amendment or Plan supersession; same-key replay after drift; different-key revision races; and transaction rollback on failure. Assert exact audit fields, not only audit-row counts.

Use the owned disposable US PostgreSQL fixture to execute transaction and migration tests, including simultaneous writers and repeatable-read behavior. A test suite that reports database skips does **not** satisfy this stage's acceptance. Run relevant domain/contracts/DB/API tests, typecheck, lint, builds, formatting and `git diff --check`; report exact unrun gates. The stage remains internal: no HTTP route, worker, object publication, browser claim, push, PR or release. A local frozen run proves neither external storage residency nor backup/restore, legal readiness or production throughput.
