> Смежный дизайн: `docs/design-briefs/07-device-commissioning.md` и
> `docs/superpowers/specs/2026-07-24-device-commissioning-design.md` (привязка

## 1. Обзор и цель

Plan B поставляет **само устройство** — сенсорный киоск самообслуживания
`apps/kiosk` у проходной цеха/склада. Сотрудник сканирует QR-бейдж, затем коды
маркировки «Честный ЗНАК» с продукции, которую забирает для себя; киоск
формирует заявку и передаёт её на сервер. Серверная часть (заявки, лимиты,
дедуп, админка) уже работает — она поставлена планом A.

Ключевое требование: киоск **работает офлайн** (цех может остаться без сети) и
**запускается на любой платформе**, включая Android-планшеты.

## 2. Зафиксированные решения (decision log)

1. **Платформа — веб-ядро (PWA), а не нативная оболочка.** `apps/kiosk` —
   React 19 + Vite 8 + TS, PWA (service worker, шрифты bundled, без CDN).
   Работает на Android/iOS-планшетах и сенсорных моноблоках Windows/Linux.
   _Обоснование:_ требование «все платформы, включая Android». Tauri (как в
   `apps/station`) дал бы OS-lockdown и serial, но не покрывает планшеты:
   serial на Android требует нативного USB-Host-плагина, на iOS практически
   нереализуем.
2. **Tauri-оболочка — отдельный поздний шаг.** Тот же фронтенд позже
   заворачивается в Tauri для десктоп-моноблоков (kiosk-lockdown, updater,
   serial через Rust) по образцу `apps/station`. Абстракция транспорта сканера
   делает это добавлением оболочки, а не переписыванием. **Вне Plan B.**
3. **Сканер — плагаемый транспорт.** `KeyboardWedgeSource` (USB-OTG/Bluetooth
   HID) — везде, включая планшеты; `WebSerialSource` — где доступен
   `navigator.serial` (десктоп-Chromium), сырые байты с разделителем GS.
   Поверх — обязательный доменный guard (§6).
4. **Хранилище — IndexedDB.** Одна реализация на все платформы (работает и
   внутри Tauri-вебвью). SQLite-зеркало станции здесь избыточно: объём данных
   мал (снимок справочников + короткая очередь заявок).
5. **`apps/kiosk` целиком принадлежит Plan B** — рабочие экраны, офлайн,
   транспорт сканера, **экран привязки** (дизайн 07, screen 3) и **экран
   настройки сканера** (дизайн 07, screen 5).
6. **Инициализация данных происходит при привязке.** Обмен pairing-кода
   возвращает и креденшел, и полный стартовый набор справочников — киоск
   сразу готов к работе (согласовано с треком 07).
7. **Серверный pairing — минимальный, по контракту 07, внутри Plan B.**
   Одноразовый числовой код с TTL и серверным lockout; обмен возвращает
   **существующий `x-kiosk-token`**. Серверная часть плана A не переделывается.
8. **Конфликты синхронизации сохраняются на заявке** и показываются админу
   (иначе отвалившиеся при синке коды исчезают бесследно — см. §7).
9. **Политика устаревшего кэша:** предупреждение через 24 ч, блокировка новых
   заявок через 7 суток; пороги настраиваемые.

## 3. Границы

**В Plan B:**

- приложение `apps/kiosk`: рабочие экраны (Ожидание / Отбор / Передано),
  экран привязки, экран настройки сканера, экран блокировки;
- офлайн: кэш справочников, очередь заявок, фоновая синхронизация;
- транспорт сканера (клавиатурный + Web Serial) и доменный guard;
- минимальный серверный pairing (выдача кода в кабинете + обмен на устройстве);
- персист конфликтов синхронизации на заявке + их отображение в админке.

**Вне Plan B:**

- кабинетный раздел «Устройства», квота подписки, печатный лист инструкции,
  привязка станции, реестр операторов — всё это план 07;
- Tauri-оболочка (десктоп-lockdown, updater, serial через Rust);
- CommerceML; прямой вывод из оборота через ГИС МТ/СУЗ.

## 5. Привязка устройства (pairing)

### 5.1 Серверная часть (минимум)

Новая таблица `kiosk_pairing_codes`: `id, tenant_id, kiosk_id, code_hash,
expires_at, used_at, attempts, created_at`; композитный FK на
`kiosks(tenant_id, id)` по общему паттерну.

- **`POST /kiosks/:id/pairing-code`** (админ-сессия, `TenantGuard`) — выдаёт
  одноразовый **8-значный числовой** код, TTL **15 минут**. Хранится только
  хэш. Повторный вызов инвалидирует предыдущий код. Ответ: `{ code, expiresAt }`
  (плейнтекст показывается один раз).
- **`POST /kiosk/pair`** (без аутентификации) `{ code, serverUrl? }` — сверяет
  код: не использован, не истёк, лимит попыток не исчерпан. Успех → помечает
  код использованным, выпускает device-токен через существующий
  `generateDeviceToken()`/`hashDeviceToken()` и возвращает **provisioning-бандл**:

```ts
{
  device: { kioskId: string; kioskName: string; place: string | null },
  token: string,                 // существующий x-kiosk-token
  nextDeviceSeq: number,         // см. §7.2 — защита от коллизии после переустановки
  servicePinHash: string | null, // PHC-хэш сервисного PIN (§5.3)
  bootstrap: KioskBootstrapDto,  // тот же тип, что отдаёт GET /kiosk/bootstrap
}
```

- **Защита от перебора:** серверный lockout после **5** неверных попыток на
  код (и на IP-окно); код претендует на заранее созданную запись киоска, что
  ограничивает пространство перебора.

Вложенный `bootstrap` — **ровно тот же `KioskBootstrapDto`**, что уже отдаёт
`GET /kiosk/bootstrap`. У киоска один путь приёма данных: и при инициализации,
и при каждом обновлении. Никакого второго формата.

### 5.2 Клиентская часть (дизайн 07, screen 3)

Экран «Привязка устройства»: числовая клавиатура для ввода кода + кнопка
«Сканировать код» (использует тот же `ScanSource`) + свёрнутое поле «Адрес
сервера» (для on-prem; в SaaS-сборке origin вшит в билд). Состояния:
идёт привязка → «Загружаем настройки и справочники»; неверный/истёкший код →
«Обновите код в кабинете»; слишком много попыток → «Подождите или получите
новый код»; нет сети → «Проверьте адрес и подключение», повтор. Успех →
«Киоск привязан к точке X» → рабочий режим.

### 5.3 Настройка сканера (дизайн 07, screen 5)

- **До привязки** — доступна без логина прямо с экрана привязки (сканер часто
  нужно поднять раньше, чтобы отсканировать pairing-код).
- **После привязки** — из настроек киоска за **сервисным PIN**: его хэш
  приходит в provisioning-бандле и проверяется офлайн (PBKDF2, тот же контракт
  хэширования, что у станции: `packages/…` крипто-хелпер станции — переиспользуем
  формат PHC). _Решение по умолчанию:_ дизайн 07 говорит «за логином», но у
  киоска нет операторов; сервисный PIN не вводит новых сущностей и работает
  офлайн.

Экран: выбор режима (клавиатурный / Web Serial + выбор порта), **тестовый
скан** с показом распознанного типа (бейдж / КМ / не распознано).

## 6. Транспорт сканера и доменный guard

**`ScanSource`** — общий интерфейс: подписка на поток `onScan(raw: string)`,
`start()`/`stop()`, статус доступности.

- **`KeyboardWedgeSource`** — глобальный слушатель клавиатуры: копит символы до
  терминатора (Enter) или таймаута тишины; отсеивает «человеческий» ввод по
  скорости. Работает на всех платформах.
- **`WebSerialSource`** — `navigator.serial`, чтение сырых байтов (GS
  сохраняется), авто-reconnect при обрыве. Доступен только на десктоп-Chromium;
  при отсутствии API источник объявляет себя недоступным и UI его не предлагает.

Каждое событие проходит через доменный слой (`@markiro/domain`, готов):

- `classifyScan(raw)` — структурный детект: бейдж (не-КМ) vs КМ;
- `validatePickupKm(raw)` — group-aware guard: `not_km` / `incomplete` / `ok`.
  `incomplete` (пропал GS у клавиатурного сканера) → «Код прочитан не
  полностью, поднесите ещё раз»;
- `kmKey(km)` — канонический ключ дедупа внутри корзины.

## 7. Офлайн-модель

- **Кэш (IndexedDB):** снимок `KioskBootstrapDto` + `fetchedAt`. Пишется при
  привязке и при каждом успешном обновлении **атомарно, полной заменой** (по
  образцу `upsertBundle` станции): удалённый на сервере сотрудник исчезает и
  из кэша.
- **Обновление:** периодически при онлайне (интервал по умолчанию **5 минут**)
  и при возврате сети (событие `online`). Оно же служит **heartbeat** — любой
  device-вызов обновляет `kiosks.last_seen_at`, по которому админка показывает
  «в сети». Отдельного heartbeat-эндпоинта не нужно.
- **Валидация — всегда локальная**, одинаково онлайн и офлайн (отдельных
  онлайн-эндпоинтов резолва в плане A нет):
  - бейдж → сотрудник по `employees[].badgeCodes`; неизвестный → «Бейдж не
    распознан»;
  - КМ → guard, затем поиск `gtin14` среди `products` кэша (это уже allowlist
    киоска); не найден → **красная модалка** «Товара нет в каталоге,
    обратитесь к администратору»;
  - дедуп внутри корзины по `kmKey` → янтарный баннер «Этот код уже в списке»;
  - дневной лимит — **best-effort** по локальному журналу заявок киоска
    (сервер остаётся авторитетом).
- **Очередь:** заявка кладётся в `queue` с монотонным `deviceSeq` и `createdAt`
  (время отбора, не синка — сервер это поддерживает). Отправка строго по
  порядку `deviceSeq`, экспоненциальный backoff при ошибках. Идемпотентность
  серверная по `(tenant, kiosk, deviceSeq)` — повтор безопасен и возвращает ту
  же заявку.
- **Авторитет — сервер.** `orderNo` и `conflicts` приходят в ответе на
  `POST /kiosk/orders`. Онлайн-экран «Передано» показывает номер сразу; в
  офлайне — локальное подтверждение **без номера** («Заявка передана, номер
  появится после синхронизации»).
- **Возраст кэша:** >24 ч — ненавязчивая плашка «Данные обновлялись N назад»,
  отбор разрешён; >7 суток — экран `blocked` («Киоск не на связи, обратитесь к
  администратору»), новые заявки не принимаются, **очередь продолжает
  досылаться**. Оба порога настраиваемые.

### 7.1 Конфликты синхронизации (важно для офлайна)

Офлайн-заявка уходит на сервер спустя часы, когда сотрудник уже ушёл с
продукцией. Сервер может отклонить часть позиций (`duplicate`, `over_limit`,
`unknown_product`, `not_allowed`, `not_km`, `incomplete`) — заявка создастся
только с принятыми. Сейчас `conflicts` возвращаются в ответе и нигде не
сохраняются, поэтому админ не увидит расхождения.

Plan B добавляет:

- **сохранение конфликтов** при создании заявки (JSONB-поле на `pickup_orders`
  либо дочерняя таблица — выбирается при планировании) и их отдачу в
  `PickupOrderDetailDto`;
- **в админке** — плашка в карточке заявки: «При синхронизации отклонено 3
  кода: дубль ×2, лимит ×1» с перечнем сырых КМ, и признак в своде.

Киоск дополнительно пишет результат синка в локальный журнал (для служебного
экрана).

### 7.2 `deviceSeq` после переустановки (защита от тихой потери заявки)

Идемпотентность сервера работает по `(tenant, kiosk, deviceSeq)`: повтор с уже
виденным `deviceSeq` возвращает **существующую** заявку, не создавая новую.
Если хранилище киоска очистить (переустановка, сброс браузера), счётчик
начнётся с нуля — и первая же новая заявка будет принята за повтор старой,
то есть **молча потеряется**.

Решение: provisioning-бандл возвращает **`nextDeviceSeq`** — на единицу больше
максимального `device_seq`, уже использованного этим киоском на сервере.
Киоск инициализирует свой счётчик этим значением. При повторной привязке
после сброса нумерация продолжается, коллизий нет.

### 7.3 Пороговые значения и конфигурация

Дефолты v1 — константы сборки киоска: обновление кэша **5 мин**, предупреждение
**24 ч**, блокировка **7 суток**. Серверная настройка порогов (поля на `kiosks`)
в v1 не делается — добавляется позже без изменения клиента, когда появится
потребность.

## 8. Экраны

По прототипу `pickup-kiosk.dc.html`; две ориентации — альбом 1180×800 и
вертикаль 800×1180. Тёмная тема `@markiro/ui`, все цели касания ≥44 px
(основные 56–84 px). RU primary + EN.

1. **Ожидание** — «Возьмите продукцию для себя», зона скана QR-бейджа.
2. **Отбор** — шапка (лого, ФИО + аватар, кнопка «Не я»); зона скана КМ;
   список «Вы берёте» (фото, название, хвост кода, цена, удаление 56×56);
   счётчик и сумма; лимит N шт/день с остатком; выбор причины: **Покупка**
   (по умолчанию) / **Списание** + обязательная подпричина-чип; кнопка
   «Готово — передать администратору» (активна при ≥1 позиции и заполненной
   причине). Повторный код → янтарный баннер (~2,6 с); достигнут лимит →
   янтарная блокирующая зона вместо сканера; неизвестный товар → красная
   модалка. Цены скрыты, если `showPrices = false`.
3. **Передано** — «Заявка № N передана» (или без номера в офлайне), сводка
   (причина · штук · сумма), автосброс через 10 с.

Служебные: **Привязка** (§5.2), **Настройка сканера** (§5.3), **Blocked**
(§7, кэш старше порога).

## 9. Архитектура приложения

`apps/kiosk` — модули с одной ответственностью, тестируемые независимо:

- **`scanner/`** — `ScanSource` + две реализации (§6).
- **`domain-guard/`** — тонкий адаптер над `@markiro/domain`: различение
  бейдж/КМ, статусы `ok`/`incomplete`/`not_km`, `kmKey`.
- **`store/`** — IndexedDB: `cache` (снимок bootstrap + `fetchedAt`), `queue`
  (заявки + `deviceSeq`), `journal` (результаты синка, конфликты), `config`
  (токен, serverUrl, пороги, хэш сервисного PIN).
- **`sync/`** — фоновый воркер: обновление кэша, отправка очереди, backoff,
  строгий порядок по `deviceSeq`.
- **`session/`** — чистая стейт-машина экранов (по образцу `nextStationView`
  станции): `pairing → idle → cart → done`, плюс `scanner-setup` и `blocked`.
- **`ui/`** — экраны и floor-компоненты. Числовую клавиатуру для pairing можно
  поднять из `apps/station/src/ui/PinPad.tsx` (при необходимости — вынести в
  `packages/ui`).
- **`api/`** — клиент device-API: заголовок `x-kiosk-token`, базовый URL из
  конфига, типизированные вызовы `pair` / `bootstrap` / `orders`.

## 10. Тестирование (TDD)

- **kiosk (vitest + jsdom):** стейт-машина экранов (чистая функция); оба
  `ScanSource` (эмуляция потока keydown и serial-чанков с реальным GS 0x1D);
  интеграция guard'а (валидный КМ / пропавший GS / бейдж); IndexedDB кэш и
  очередь (`fake-indexeddb`); sync-воркер (порядок по `deviceSeq`, backoff,
  идемпотентный повтор, атомарная замена кэша); пороги возраста кэша (плашка и
  блокировка); экран привязки (успех / просрочен / lockout / нет сети);
  экраны отбора (дубль, лимит, неизвестный товар, скрытие цен).
- **api (e2e, живой Postgres):** выдача кода → обмен → бандл содержит рабочий
  токен, которым проходит `GET /kiosk/bootstrap`; повторное использование кода
  → отказ; истёкший код → отказ; lockout после N попыток; персист конфликтов
  виден в `PickupOrderDetailDto`.
- **admin:** плашка конфликтов в карточке заявки и признак в своде.

## 11. Принятые допущения (решения по умолчанию для плана)

Все пункты ниже — **решённые**; альтернативы записаны, чтобы план не
переоткрывал обсуждение.

1. **Сервисный PIN** охраняет настройку сканера после привязки (§5.3). Хэш
   приходит в provisioning-бандле, проверяется офлайн по PHC-контракту
   станции (`apps/station/src/lib/crypto.ts`); вынести ли хелпер в общий пакет
   или скопировать — решает план. Альтернатива (вход сотрудника по бейджу)
   отклонена: у сотрудников нет ролей и прав.
2. **Конфликты хранятся в JSONB-поле на `pickup_orders`** — проще, и выборки
   по ним в v1 не нужны (нужен только показ в карточке и признак в своде).
   Дочерняя таблица — если позже понадобится фильтрация по причинам.
3. **Пороги — константы сборки** (§7.3), серверная настройка позже.
4. **Фото товаров в v1 не показываем** — в `KioskBootstrapDto` их нет, а
   офлайн-кэш картинок заметно усложняет приложение. В списке «Вы берёте» —
   типовой плейсхолдер; название и хвост кода дают достаточную идентификацию.
   Добавление фото — отдельная поздняя доработка (URL в bootstrap + кэш).
5. **`deviceSeq` инициализируется из `nextDeviceSeq`** provisioning-бандла
   (§7.2) — закрывает тихую потерю первой заявки после переустановки.
