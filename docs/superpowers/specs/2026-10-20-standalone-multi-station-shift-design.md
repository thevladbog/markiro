# Автоном: несколько станций в одной смене на одной линии (веха «2b»)

Статус: проект, ждёт проверки владельцем. Дата: 2026-10-20.
Связанные документы: `docs/superpowers/specs/2026-09-26-standalone-station-design.md` §6.9,
`docs/superpowers/specs/2026-10-08-standalone-2a-shift-and-boxes-design.md`, `apps/standalone/AGENTS.md`.

## 1. Цель и границы

Сейчас смена привязана к одной станции: вторая станция (и ТСД) при входе получает `shift_busy`.
Цель: на одной линии в одной смене параллельно работают несколько станций и ТСД с одним продуктом;
итоги, план и закрытие смены считаются по смене целиком; работа остаётся offline-first.

Решения владельца (сессия 2026-10-20):

| Вопрос         | Решение                                                                                                    |
| -------------- | ---------------------------------------------------------------------------------------------------------- |
| Сценарий       | Параллельно, один продукт, у каждой станции свои коробы                                                    |
| Паллеты        | У каждой станции свои (паллета собирается только из коробов своей станции)                                 |
| Закрытие       | Каждый участник закрывает свою часть; смена закрывается, когда закрыли все; из офиса можно закрыть целиком |
| Счётчик и план | «Моя станция: N · Всего в смене: K из M»; план достигается по общему числу                                 |
| Вход           | Свободный вход, на линии лимит станций (по умолчанию 1)                                                    |
| ТСД            | Полноправный участник наравне со станцией                                                                  |
| СУБД           | Остаёмся на SQLite (см. §8)                                                                                |

Не входит в веху: общая паллета нескольких станций; режим «сборка паллеты грузчиком» (§10); разные продукты
в одной смене; смена владельца смены; второй хост и отказоустойчивость; шифрование базы.

## 2. Что есть сейчас (по коду)

- Единственная блокировка: `host/src/routes/device_shifts.rs:455-460` (`enter_shift`) возвращает `shifts::busy()`
  (`host/src/shifts.rs:483`, `shift_busy`), если `shifts.owner_device_id` другое устройство.
- Модель уже по устройствам: `shift_participants` PK (shift_id, device_id) (`host/migrations/0009_shifts_sscc_blocks.sql`),
  коробы, паллеты, сканы, исключения, блоки SSCC, чеки (`fact_receipts` PK (device_id, record_id)) несут `device_id`;
  реестр кодов общий; конфликт «код принят двумя сканами» работает (`host/src/facts/registry.rs`: выигрывает самый ранний скан).
- Закрытие: любой участник закрывает смену для всех (`facts/mod.rs` `close_shift`), факты остальных становятся «поздними».
- Станция: открытый короб и паллета локальные, по одной на (устройство, смена) (`floor_boxes_open`, `floor_pallets_open`);
  итог закрытия и «Принято N из M» считаются только по своим `floor_*` строкам.
- Лицензия: места считаются на площадку (станции и ТСД в одном пуле, `host/src/license/seats.rs`), лимита на линию нет.
- Спека 2026-09-26 §6.9 описывает «закрытие только из офиса, как только хост видит второе устройство»: не реализовано.

## 3. Рассмотренные подходы

- **А (выбран).** Смена одна; у участника своё состояние и своё закрытие; смена закрывается, когда закрыли все.
- Б. Один владелец, остальные «второстепенные», закрывает владелец или офис. Меньше изменений, но владелец не может уйти раньше, поломка требует офиса.
- В. Смена линии как родитель, у каждой станции подсмена. Чистая изоляция, но дублирует снимки и счётчики и ломает отчёты и экспорты.

## 4. Хост

### 4.1 Данные (новая миграция хоста; номер — следующий свободный на момент реализации)

- `lines.max_stations INTEGER NOT NULL DEFAULT 1 CHECK (max_stations BETWEEN 1 AND 16)`.
- `shift_participants`: добавить `state TEXT NOT NULL DEFAULT 'active' CHECK (state IN ('active','left','closed'))`,
  `joined_at`, `left_at`, `closed_at`, `closed_actual_qty INTEGER`, `closed_reason TEXT`. Существующие строки: `active`
  для участников активной смены, `closed` для закрытых смен.
- `shifts.owner_device_id` остаётся как «открыл» (первый участник) без особых прав. CHECK жизненного цикла не трогаем.
- Не добавляем столбцов-счётчиков: итоги считаются запросами по реестру, как в `office_shifts.rs:34-70`.

### 4.2 Правила

- **Вход (`enter_shift`).** Устройство, уже участвовавшее, входит всегда, если смена не закрыта (участник `left` → `active`
  при свободном месте). Новое устройство: если число участников в состоянии `active` (станции и ТСД) меньше
  `lines.max_stations`, добавляется строка; иначе `409 shift_line_full`. Участник `left` не занимает место.
  Для смены только `planned` первый вход открывает её, как сейчас (замороженный снимок).
- **Выход.** Не меняет смену: участник → `left` (освобождает место), может вернуться.
- **Закрытие своей части (`shift_closed` от устройства).** Участник → `closed` (фиксируются `closed_actual_qty`, причина).
  Если после этого нет участников в состоянии `active` или `left`, смена переходит в `closed`
  (`closed_by_kind = 'devices'`, итог — сумма по реестру). Факты закрытого участника после закрытия участия: «поздние».
- **Принудительное закрытие из офиса.** Все `active`/`left` участники → `closed` с отметкой «закрыт офисом»; причина обязательна;
  предупреждение со списком незакрывших; запись аудита. Поздние данные остаются поздними и смену не переоткрывают.
- **План и причина.** `close_reason_required` считается по общему числу смены (из реестра на хосте), а не по `actualQty`
  станции. Причину требуют у участника, закрывающего последним (или у офиса при принудительном закрытии);
  остальные закрывают часть без причины.
- **Итоги станциям.** В списке смен устройства (`/v1/device/shifts`) добавляется `totals { accepted, boxesClosed, pallets, asOf }`
  и `byDevice[]`; `asOf` нужен для пометки устаревших данных офлайн.
- **Аудит.** Новые действия: `shift.join`, `shift.leave`, `shift.part_closed`, `shift.force_closed`, `line.max_stations_changed`.
  Проверки аудита — точные (исполнитель, цель, результат, метаданные), по правилам репозитория.
- **Реестр кодов, блоки SSCC, чеки** без изменений. Лицензионные места без изменений.

### 4.3 Протокол и совместимость

Изменения добавочные (поле участников и итогов в форме смены, код `shift_line_full`, `max_stations` у линии). Нужна проверка
правил окна протокола (`tools/standalone-release/releases.json`, `MIN_PROTOCOL_VERSION`) — решение о повышении
`PROTOCOL_VERSION` принимается при реализации. Фикстуры Rust/TS и Kotlin обновляются вместе. Порядок выпуска: хост раньше
станции, офиса и ТСД. При `max_stations = 1` поведение для клиентов не меняется (вторая станция получает `shift_line_full`
вместо `shift_busy`; старые клиенты должны показывать то же «занято»: сообщение остаётся совместимым).

## 5. Станция

- **Карточка смены** (`ShiftCard.tsx`, `shift-entry.ts`): вместо «занято» кнопка «Присоединиться» при свободном месте;
  при `shift_line_full` — «Линия занята: N из N», без действия; список участников (имя устройства, вид).
- **Рабочий экран:** строка «Моя станция: N · Всего в смене: K из M». K из `totals` хоста; без связи — последнее известное
  значение с пометкой «данные от ЧЧ:ММ»; план достигнут по общему числу, уведомление при следующем обновлении.
- **Закрытие:** «Закрыть мою часть» (блокировки те же: свой открытый короб, этикетки, паллета). Причина недовыполнения —
  только у закрывающего последним; остальным «Смена закроется, когда закроют остальные».
- **Выход из смены** остаётся паузой (`left`).
- **Офлайн:** вход офлайн только в смену, которую станция уже знает; закрытие своей части ставится в очередь и подтверждается
  идемпотентно; блоки SSCC и дубликаты — как сейчас. Конфликты видны и восстановимы (`conflict-notices.ts`).
- Локальные таблицы (`floor_shifts`, `floor_boxes`, `floor_codes`) не меняются по смыслу; добавляется только кэш итогов смены.

## 6. ТСД (Kotlin)

Вход без `busy` при свободном месте, общий счётчик по `totals`, закрытие своей части, отображение `shift_line_full`.
Общие фикстуры протокола обновляются в паре с TS. Склад паллет ТСД (события `pallet-events`, без смены) не меняется.

## 7. Офис, отчёты, тексты

- **Линия:** поле «Максимум станций» (по умолчанию 1); уменьшение ниже числа активных участников отклоняется; аудит.
- **Смена:** таблица участников (устройство, вид, вошёл, состояние, принято, коробов, паллет); итог по смене и разбивка по
  устройствам; «Закрыть смену целиком» с предупреждением «Не закрыли: …» и обязательной причиной.
- **Устройства и «Обзор»:** статус участия в смене; на карточке линии «станций в смене: N из M»; пункт «Требует внимания»,
  если активный участник молчит дольше порога (10 минут).
- **Бланк смены** (`packages/domain/src/print-forms/shift-task-form.ts:204`): новая формулировка «Каждая станция закрывает
  свою часть; смена закрывается, когда закрыли все, или из офиса». Меняются эталонные фикстуры `packages/domain/test/fixtures/print-forms*`
  и хеши аттестации (`pnpm test:production-bundle:contract`).
- **Экспорты (ЧЗ, CSV/1C)** ключуются по `shift_id`; проверить формат при нескольких устройствах.

## 8. SQLite: решение остаться

- Хост — единственный писатель мастер-базы; станции и ТСД ходят по HTTP и держат локальные зеркала. Вторая станция — больше
  клиентов у одного сервиса, не вторая запись в базу.
- Нагрузка: порядка десятков сканов/с (сотни строк записи/с); SQLite в WAL выдерживает десятки тысяч вставок/с. Текущие
  настройки хоста подходят (`host/src/db.rs`: WAL, `synchronous=FULL`, `busy_timeout` 5 с, пул 4, горячие записи в `BEGIN IMMEDIATE`).
- Локальный Postgres отвергнут: служба на заводском ПК, обновления, восстановление; хост написан под SQLite (51 миграция,
  частичные индексы, замена триггеров, эпохи восстановления). Решение 2026-10-13 «Postgres не тащим» сохраняется.
- Turso/libSQL отвергнут: синхронизация базы по принципу «последняя запись выигрывает» ломает наши доменные гарантии
  (идемпотентные факты, чеки, SSCC-блоки, конфликты кодов); новый движок с MVCC — бета. Единственная интересная область —
  шифрование базы без платной лицензии: отдельная задача.
- **Приёмка вехи:** нагрузочный и длительный тест (симулятор 4 станций и 2 ТСД по 5–10 сканов/с, часы), p99 задержки маршрутов
  фактов, поведение WAL-контрольных точек, резервная копия под нагрузкой, восстановление; ревью записи (короткие транзакции,
  одно писательское соединение для горячих путей, нет долгих читающих транзакций).
- **Пересмотр при пороговых значениях:** больше ~20 одновременных устройств на хост, больше ~50 млн строк в `scans`,
  потребность в тёплом резерве (тогда сначала непрерывное копирование и резервный хост, не смена СУБД).

## 9. Порядок внедрения

1. Хост: миграция, вход по вместимости, закрытие своей части, автозакрытие, принудительное закрытие, `totals`, план по общему числу; тесты хоста и протокола, фикстуры.
2. Нагрузочный и длительный тест (§8) как критерий приёмки.
3. Станция: карточка, счётчик «моё и всего», «Закрыть мою часть», офлайн-случаи.
4. Офис: линия, участники, принудительное закрытие, «Обзор», бланк.
5. ТСД (Kotlin): вход, счётчик, закрытие своей части, общие фикстуры.
6. Сквозная проверка: две станции и ТСД в одной смене, обрыв связи у одной станции, закрытие в разном порядке, принудительное закрытие.

Каждый шаг выпускается отдельно, хост раньше клиентов.

## 10. Будущее: сборка паллеты коробами (не в этой вехе)

Режим станции «заполнение паллеты коробами»: станции выключают паллеты и физически складывают коробы на одну паллету, грузчик
сканирует эти коробы на паллете и собирает паллету (станция в роли сборщика или ТСД, как складская паллета без смены). Точка
расширения в этой вехе: паллета не привязывается жёстко к смене и станции в новых контрактах; существующие `pallet-events` ТСД
не меняются.

## 11. Риски

- Дубль скана на двух станциях при потере связи: реестр кодов решает (самый ранний скан); добавить тест с двумя станциями.
- Расхождение числа: итог считает хост по реестру, различия снимаются при синхронизации.
- Висящий участник блокирует автозакрытие: офис видит предупреждение и закрывает принудительно; таймаут простоя — открытый вопрос.
- Старые клиенты: при лимите 1 поведение прежнее; хост выпускается раньше клиентов.
- Поздние данные после принудительного закрытия: помечаются, смену не переоткрывают.

## 12. Открытые вопросы (не определены по коду)

1. Реализовано ли облачное правило «смена только офисное закрытие после второго устройства» в `apps/api`; важно для согласованности текста.
2. Допущения одного устройства в `routes/pallet_sheets.rs` (лист А4 паллеты), `routes/disaggregation.rs` и инструменте перегруппировки коробов.
3. Валидационные сканы (`0020`, `code_owners` без короба) при двух станциях.
4. Действие аудита `shift.enter` для второго устройства (в `AGENTS.md` сказано, что оно придёт с планом 2b).
5. Взаимодействие отзыва устройства-«открывшего» с активной сменой (`routes/devices.rs` смены не затрагивает).
6. Таймаут «левого» участника (`left`): считать ли его закрывшим через N часов, чтобы смена закрывалась сама.
7. Как ТСД сейчас обрабатывает `busy` в интерфейсе и считается ли ТСД устройством для правила закрытия — подтверждается при реализации.
8. Верхний предел `max_stations` (в проекте 16) и кто может его менять (роль администратора).
9. Станция офлайн не знает, закрывает ли она последней: причина недовыполнения плана запрашивается у закрывающего последним
   только по данным хоста. Предлагаемое правило: офлайн-станция закрывает часть без причины; если хост при приёме обнаружил,
   что она оказалась последней и план не выполнен, смена закрывается с пометкой «причина не указана» и видимым запросом в офисе
   (смена не блокируется, причину вносит офис).
