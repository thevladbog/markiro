# Продажа коробом на кассе: мобильный показ DataMatrix кодов

Дата: 2026-08-23. Статус: согласовано в brainstorming, ждёт implementation plan.

## Проблема

Продукция иногда продаётся на кассе целым коробом (6–20 бутылок). Сейчас продавец
вскрывает короб и сканирует каждую бутылку. Система уже хранит связь короба и кодов
внутри него (`boxes` + `box_items` + `codes.canonicalRaw`), поэтому кассир может
сканировать DataMatrix прямо с экрана телефона, не доставая бутылки.

## Решение (вариант A)

Мобильная страница внутри `apps/admin` под обычной сессией кабинета и новой
capability. Кассир — сотрудник тенанта с учёткой в кабинете.

Флоу: кассир открывает страницу на телефоне → сканирует SSCC-этикетку короба
камерой (или вводит SSCC вручную) → экран показывает по одному крупному
DataMatrix с навигацией тап/свайп → касса сканирует каждый код с экрана →
финальный экран «все коды показаны» → следующий короб.

Страница read-only: статус короба не меняется, продажа и вывод из оборота
происходят на кассе / в Честном знаке. Фиксируется только аудит-событие просмотра.

## API (`apps/api/src/modules/boxes/`)

- Один эндпоинт `GET /boxes/sell-codes?sscc=` — UI-флоу всегда начинается со
  сканирования/ввода SSCC, и строки списка коробов тоже несут SSCC, поэтому
  вариант по boxId не нужен.
- Авторизация: сессия кабинета + `CABINET_CAPABILITY.OPERATIONS_READ`
  (`@RequirePermissions`), тенант-скоуп через `RequestWithTenant`. Отдельная
  capability не вводится: capabilities выводятся только из ролей
  (`resolveCabinetAccess`), и новая была бы выдана ровно тем же ролям
  (manager+), то есть не сузила бы доступ — только добавила бы кода.
- Ответ: `boxId`, `sscc`, статус, продукт/GTIN, количество, и активные items
  (`displacedAt IS NULL AND removedAt IS NULL`) с `canonicalRaw`, `gtin14`,
  `serial`.
- `canonicalRaw` отдаётся только этим эндпоинтом. Существующий `BoxCardItemDto`
  не расширяем — сырые КМ не должны попадать в обычную карточку короба.
- Ограничения: короб закрыт (`closedAt IS NOT NULL`), не разобран
  (`disassembledAt IS NULL`) и содержит хотя бы один активный код, иначе 409 с
  машиночитаемым кодом ошибки (`box_not_closed` / `box_disassembled` /
  `box_empty`).
- Аудит: каждый успешный вызов пишет событие «просмотр кодов короба для продажи»
  (пользователь, время, boxId) в существующий аудит-механизм API.

## UI (`apps/admin`)

Роут `boxes/sell` внутри Shell под `RequireCapability`, mobile-first; ссылка из
раздела «Короба». Десктоп — та же страница центрированной колонкой.

**Экран 1 — выбор короба.** Кнопка «Сканировать этикетку» (камера:
`BarcodeDetector`, фолбэк zxing-js, всё в lazy-чанке) + ручной ввод SSCC.

**Экран 2 — показ кодов.** Один DataMatrix почти на весь экран, белый фон,
максимальная контрастность, Wake Lock API (экран не гаснет). Счётчик «3 / 12»,
прогресс-полоска, крупные зоны «Назад / Далее», свайп. Пройденные коды
помечаются. Финальный экран «Все N кодов показаны» с кнопкой «Следующий короб».

Рендер: lazy-компонент по образцу `apps/admin/src/pages/pickup/ItemCode.tsx`
(`renderDataMatrixSvg` из `@markiro/domain`, bwip-js вне основного бандла).

## Ошибки

- SSCC не найден / чужой тенант → «Короб не найден» (без различения причин).
- Короб открыт или разобран → объясняющее сообщение, кодов нет.
- Камера запрещена/недоступна → автоматический фолбэк на ручной ввод.
- Потеря сети после загрузки → коды уже в памяти, показ продолжается; ретрай
  только на этапе загрузки короба.

## Тесты

- API e2e: 403 без capability, тенант-изоляция, 409 для открытого/разобранного
  короба, наличие `canonicalRaw` в ответе, аудит-событие.
- Admin компонентные: ввод SSCC → загрузка → навигация по кодам → финальный
  экран; фолбэк без камеры; обработка 409/404.
- Визуальная проверка в реальном браузере при реализации (mobile viewport).

## Вне скоупа

- Отметка короба разобранным / изменение статусов.
- Доступ без логина (публичные ссылки, PIN точек продаж).
- Отдельное PWA.
- Оффлайн-режим.
