# Кабинет КА, печатные формы счетов и КП

**Статус:** согласовано для проектирования 2026-08-12.

## Цель

Сделать выставленные счета доступными контрагенту в его кабинете и выпускать
неизменяемые печатные формы для счетов и коммерческих предложений. Документ,
который скачивает оператор или КА, должен соответствовать данным на момент
выставления или публикации, а не текущему каталогу или реквизитам сторон.

## Границы MVP

Входит:

- операторская HTML- и PDF-форма для счета и коммерческого предложения;
- реквизиты продавца и КА, номера, даты, строки, НДС, итоги и визуальные места
  для ручной подписи и печати;
- кабинет КА со списком, карточкой и скачиванием только своих счетов;
- безопасный Markdown WYSIWYG-редактор условий КП;
- неизменяемые снимки и versioned private artifacts;
- повторный рендер при технической ошибке без изменения уже готового артефакта.

Не входит:

- КП в кабинете КА;
- ЭДО, факсимиле, квалифицированная подпись, изображения, вложения, iframe,
  raw HTML и произвольный код в условиях КП;
- редактирование опубликованного КП или выставленного счета;
- несколько юридических лиц оператора или КА.

## Жизненный цикл и снимки

### Счет

При `issue` сервер фиксирует номер, дату, seller/buyer profile snapshots,
строки, НДС и итог. Затем создаёт HTML и PDF для одной document revision.
Повторный рендер создаёт следующую revision; готовые байты и object key прежней
revision не перезаписываются.

### Коммерческое предложение

При `publish` сервер фиксирует реквизиты сторон, строки, срок действия,
итоги и условия предложения. Форма содержит маркировку «Коммерческое
предложение» и «Не является счетом на оплату». Печатные артефакты доступны
оператору; КА их не видит.

### Общие статусы

Для каждого формата и revision используются `pending`, `ready`, `failed`.
Ошибка рендера не меняет финансовый статус; оператор видит причину в безопасном
виде и может явно запустить retry. Артефакты сохраняются в private object
storage, загрузка выдаётся short-lived signed URL.

## Печатный шаблон

Один серверный renderer имеет режимы `invoice` и `offer`; PDF строится из той
же нормализованной print model, что и HTML. Общие блоки:

1. заголовок, номер, дата и статус;
2. реквизиты продавца и покупателя;
3. пронумерованная табличная часть: позиция, единица, количество, цена,
   НДС, сумма;
4. подытог, НДС и итог в RUB;
5. визуальные поля «Руководитель/уполномоченный представитель», подпись и
   печать.

У КП после табличной части выводится блок «Условия предложения», если он не
пуст. В счёте остаются issue date и due date; в КП — publish date и expires at.
Реквизиты, цены и текст берутся только из снапшота.

## Условия коммерческого предложения

Черновик КП содержит `termsMarkdown`. Редактор WYSIWYG хранит и изменяет
Markdown, предоставляя кнопки для заголовков, абзацев, жирного/курсива,
маркированных/нумерованных списков, ссылок и таблиц, а также режим
предпросмотра.

На API принимается ограниченный Markdown. Renderer преобразует его через
allowlist в безопасный HTML: без HTML-тегов источника, изображений, файлов,
iframe, inline styles, event handlers и небезопасных URL-схем. При публикации
сохраняются исходный Markdown и безопасный HTML snapshot. Пустое значение
разрешено и не отображает секцию в форме.

## Доступ

| Действие | Оператор | КА |
| --- | --- | --- |
| Просмотр/скачивание счета | Да, по billing capability | Только issued/paid/cancelled своего tenant |
| Просмотр/скачивание КП | Да, по billing capability | Нет |
| Retry рендера | Да, по billing capability | Нет |
| Банковские данные, audit, import | Да согласно capability | Нет |

Контроллеры загружают tenant из аутентифицированного customer session, а не из
клиентского параметра. Неготовый документ не скачивается; tenant из другого
tenant получает такую же non-leaking denial response, как и неизвестный ID.

## Кабинет КА

Маршруты: `/billing/invoices` и `/billing/invoices/:id` в `apps/admin`.

Список показывает номер, дату, срок оплаты, статус и итог. Карточка показывает
снимок строк и итогов, состояние генерации документа и кнопку скачивания при
`ready`. Она не показывает КП, банковские строки, платформенных акторов,
технические object keys или аудит. Есть loading, empty, failed-document и
access-denied состояния; таблица имеет доступное имя и локальный horizontal
overflow на мобильном экране.

## Изменения данных и API

Потребуются новые versioned document tables/колонки для offer snapshots и
артефактов, а также новый additive migration. Existing invoice document records
сохраняют совместимость. Нельзя переписывать применённые миграции.

Новые/расширенные границы:

- оператор: publish КП с terms, статус/повторный рендер/загрузка HTML и PDF;
- оператор: status/повторный рендер/загрузка счета;
- КА: tenant-scoped list/detail/download счетов.

Все входные DTO валидируют bounded length и строго известные поля. В журнал и
аудит не попадают raw Markdown сверх bounded metadata, signed URL и object key.

## Проверка

- unit tests print model и Markdown sanitization: escaping, unsafe URL, table,
  empty terms, стабильная разметка;
- DB/API tests: snapshot invariance после изменения профиля/каталога, offer
  publication, renderer retry/revision, status и short-lived download;
- customer API tests: tenant isolation, no offers/bank/audit fields, ready-only
  download;
- component tests: WYSIWYG toolbar/preview and admin invoice list/detail;
- package tests/typecheck/lint/build, migration test, format/diff;
- browser inspection operator forms and 390 px customer-cabinet view.

## Решения и допущения

- PDF и HTML строятся из одного server-side print model; front-end не формирует
  самостоятельную финансовую форму.
- Для MVP оператор и tenant используют по одному current billing profile;
  историческая точность обеспечивается snapshots.
- Подпись и печать — пустые визуальные поля для ручного подписания, не
  электронная подпись.
