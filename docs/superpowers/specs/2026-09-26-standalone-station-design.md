# Автономная станция Markiro без облака — дизайн

**Дата:** 2026-09-26
**Статус:** дизайн согласован владельцем по разделам 2026-09-26; ожидает
итогового просмотра перед планом первого этапа.
**Рабочее название:** «Markiro Автоном», каталог `apps/standalone`.
**Затрагивает:** новое приложение `apps/standalone`; `packages/domain` и
`packages/ui` как зависимости; генераторы печатных форм в `apps/api` (этап 0);
позже `apps/handheld` (этап 7). Текущая станция `apps/station` не меняется.

## 1. Зачем

Владелец предложил автономную десктопную станцию, которая не зависит от облака
и кабинета. Её разворачивают в локальной сети завода, несколько станций работают
с единой базой, а каталог, настройки и выгрузки живут в том же приложении.
Исходная идея — положить базу в сетевую папку.

Целевой клиент — заводы, где облако запрещено службой безопасности или нет
стабильного интернета. Продукт должен годами работать без связи с нами.
Типичная площадка — одна-две станции.

## 2. Решения владельца

| Вопрос                 | Решение                                                                                                                                     |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Главный сценарий       | Нет облака и интернета: выгрузки файлами, офлайн-лицензия, обновления вручную                                                               |
| Хост недоступен        | Линия продолжает работать: у станции своя база, данные досылаются при восстановлении связи, дубли между станциями становятся конфликтами    |
| Сценарии первой версии | Агрегация в короба, паллеты, валидация с печатью дубликата DM. Каталог, шаблоны, операторы, настройки и выгрузки входят всегда              |
| Масштаб                | 1–2 станции на площадке                                                                                                                     |
| Хост                   | Роль того же приложения: служба Windows на Rust (вариант A из трёх)                                                                         |
| ТСД                    | Механизм закладывается сразу: протокол и хост понимают устройства `handheld`. Локальный режим приложения ТСД — отдельный этап после станций |
| Лицензия               | По умолчанию бессрочная на площадку с лимитами станций и ТСД; срочную поддерживает тот же формат                                            |
| Форма                  | Новое приложение в монорепо на общем дизайне, а не урезанная текущая станция                                                                |

Отвергнутые варианты хоста: отдельная служба на Node.js (второй рантайм и
нативный модуль SQLite в установщике, больше памяти на цеховых ПК) и обмен
файлами через сетевую папку (задержка в секунды, дубли ловятся с опозданием,
сбои из-за антивирусов и кеша каталогов SMB). On-prem текущего серверного стека
в Docker не рассматривается: для 1–2 станций без ИТ-службы он требует
Linux-сервер и администрирование.

## 3. Почему не общий файл SQLite в сетевой папке

Документация SQLite прямо предупреждает против такой схемы:

- эксклюзивные блокировки на сетевых файловых системах иногда работают
  неправильно, и это приводило к порче баз; порядок записи при синхронизации
  тоже не гарантирован ([Use Over a Network](https://www.sqlite.org/useovernet.html));
- режим WAL по сети не работает: все процессы должны быть на одном компьютере,
  потому что делят общую память ([WAL](https://www.sqlite.org/wal.html));
- без WAL в каждый момент пишет только одна станция, остальные ждут;
- рекомендуемые варианты — клиент-серверная база либо база на локальном диске
  одной машины плюс посредник на ней же. Хост в этом дизайне и есть такой
  посредник.

Сетевая папка остаётся в продукте как место для резервных копий (раздел 9.3).

## 4. Почему новое приложение, а не урезанная станция

Замеры по коду на 2026-09-25:

- в станции 43,9 тыс. строк TypeScript без тестов. Около 43% (~19 тыс.) — это
  синхронизация, офлайн-гранты, сопряжение, восстановление учётных данных и
  замена устройства. Ещё около 21% — инвентаризация вокруг серверного снимка
  из ЧЗ. Переиспользуемо около 37% (~16 тыс. строк);
- из 74 таблиц SQLite вне облака нужны около 18. Остальные 56 обслуживают
  синхронизацию, гранты (24 таблицы), восстановление и замену устройства,
  инвентаризацию (19 таблиц);
- триггеры одной вставкой пишут производственный факт, исходящую очередь и
  списание гранта (`offline_grant_scan_apply`,
  `product_label_accept_command_apply`);
- около двух третей `apps/station/src/App.tsx` (2 417 строк) занято учётными
  данными, восстановлением, синхронизацией и обновлениями;
- из ~3,9 тыс. строк рабочего Rust-кода около 60% онлайновые (обновления ~2,1
  тыс., часы грантов, конфигурация учётных данных); около 40% переиспользуемы.

Вывод: новое приложение, в которое чистые модули станции переносятся
копированием. Текущая станция остаётся нетронутой.

## 5. Архитектура и роли

```
┌──────────── ПК-хост (одна из станций или офисный ПК) ────────────┐
│  Служба «Markiro Хост» (Rust, служба Windows)                    │
│    главная база SQLite (WAL) · счётчики SSCC · реестр КМ         │
│    каталог и настройки · приём данных · резервные копии          │
│         ▲ localhost                                              │
│  Приложение: режим «Станция» или «Офис», своя локальная база     │
└─────────▲────────────────────────────────────────────────────────┘
          │ локальная сеть, HTTPS, ключ устройства
┌─────────┴──────────────────┐     резервные копии →
│ Вторая станция (или ТСД)   │     сетевая папка или флешка
│ своя локальная база        │
└────────────────────────────┘
```

### 5.1. Роли

- **Хост** — фоновая служба Windows `markiro-host.exe`, включается на одном ПК.
  - Работает независимо от окна приложения: даже если окно закрыто или в
    систему никто не вошёл.
  - Хранит главную базу и делает всё, что требует единого места (раздел 6).
  - Это отдельный исполняемый файл из того же Rust-воркспейса. Для пользователя
    по-прежнему одно приложение и один установщик.
- **Станция** — цеховой режим: вход оператора по PIN или бейджу, смены,
  сканирование, агрегация, печать.
  - У станции своя локальная база.
  - Уже открытую смену станция продолжает без хоста.
- **Офис** — режим технолога или руководителя: вход по логину и паролю;
  каталог, шаблоны, настройки, смены, выгрузки, конфликты, сервис.
  - Работает только при связи с хостом: читает и пишет главную базу через
    службу хоста, без локальной копии. Прямого доступа к файлу базы у офиса
    нет.
  - Запускается на станции (руководитель входит поверх киоск-режима) или на
    офисном ПК, где приложение ставится с ролью «только офис», без оборудования.
  - Офисные экраны рассчитаны на мышь и клавиатуру. На станции они доступны,
    но под касание не оптимизируются.

### 5.2. Принципы

1. **Одна модель для одного и двух ПК.** Даже на единственном компьютере
   станция работает через свою базу и службу на localhost. Отдельной ветки
   кода для одного ПК нет.
2. **Хост хранит и арбитрирует.** Правила маркировки, выгрузки и печатные формы
   считаются в TypeScript кодом из `packages/domain` — тем же, что в облаке.
   Хост не разбирает КМ и не рендерит этикетки.
3. **Цех работает локально, офис — через хост.** Станция и ТСД пишут факты в
   свою базу и досылают их. Офис читает и пишет главную базу через службу
   хоста, без локальной копии.
4. **Окружение.** Windows 10/11 x64, как у текущей станции. Все шрифты, иконки
   и звуки в поставке, исходящих соединений в интернет нет.

## 6. Данные и синхронизация

### 6.1. Где что лежит

| Данные                                                                                                                     | Хост (главная база)                                          | Станция (своя база)                                                           |
| -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ | ----------------------------------------------------------------------------- |
| Справочники: организация, GLN и префиксы, контрагенты, товары, шаблоны, операторы, офисные пользователи, линии, устройства | источник правды                                              | копия только для чтения — то, что нужно для работы без хоста                  |
| Смены                                                                                                                      | создание, номер, снимок товара и шаблонов при открытии, итог | копия открытых смен своей линии                                               |
| SSCC                                                                                                                       | счётчики и выдача блоков                                     | свои блоки; номер списывается при закрытии короба или паллеты                 |
| Сканы, короба, паллеты, исключения, задания печати                                                                         | сводная история всех устройств                               | свои факты — до подтверждения хостом плюс N дней (по умолчанию 30, раздел 15) |
| Конфликты, журнал действий офиса, резервные копии, лицензия                                                                | хранятся                                                     | нет                                                                           |

В модели нет `tenant_id` и серверных учётных записей устройств в облачном
смысле. Идентификаторы фактов — UUID, их создаёт устройство.

### 6.2. Логическая модель

Точные DDL определяются в спецификациях этапов 1 и 2a. Логический состав:

- **хост:** профиль организации, контрагенты, товарные группы ЧЗ (справочник
  поставляется с приложением), товары, шаблоны и их умолчания, операторы,
  офисные пользователи, линии, устройства (тип, линия, хеш ключа, возможности,
  версия протокола, последняя связь, расхождение часов), счётчики и блоки SSCC,
  счётчики номеров смен, смены со снимками, участники смен, реестр КМ, сканы,
  короба и их состав, паллеты, исключения, задания печати дубликатов с
  попытками и событиями, квитанции приёма, конфликты, журнал действий,
  резервные копии, лицензия, настройки;
- **станция:** копии справочников и открытых смен, состояние синхронизации
  (последняя ревизия, идентичность хоста), свои блоки SSCC, журнал сканов,
  короба и их состав, паллеты, исключения, задания печати этикеток и
  дубликатов, записи о закрытии смен, исходящая очередь, квитанции, уведомления
  о конфликтах, принтеры и настройки рабочего места.

### 6.3. С хоста на устройство

- У каждой строки справочника есть номер ревизии хоста. Устройство держит
  открытый поток изменений (SSE) и забирает всё после последней известной ему
  ревизии. Для устройств, у которых фоновые соединения обрываются (Android),
  есть запасной вариант — периодический опрос того же источника изменений.
- Если поток оборвался, устройство переподключается и дозапрашивает
  пропущенное.
- При открытии смены замораживаются поля товара, шаблоны и политика валидации.
  Правка каталога не меняет идущую смену и её перепечатки: сохранённые
  исторические факты не пересчитываются.

### 6.4. С устройства на хост

- Факт и запись исходящей очереди сохраняются одной транзакцией.
- Пока хост на связи, очередь уходит сразу, по одной записи или пачкой при
  догоне.
- Хост принимает записи идемпотентно по паре «устройство + UUID записи» и на
  каждую отвечает квитанцией:
  - **принято;**
  - **конфликт** — с данными победившего скана;
  - **отклонено** — с точной причиной. Отклонённая запись не повторяется, а
    попадает в видимый список на устройстве и в офисе.
- Повторная отправка той же пачки даёт те же квитанции.
- Временные сбои хоста или сети отвечают ошибкой транспорта, а не
  квитанцией; устройство повторяет с нарастающей паузой.
- Правки справочников из офиса идут с проверкой ревизии, чтобы две офисные
  сессии не затирали друг друга.

### 6.5. Дубли КМ

1. Сначала устройство проверяет код по своей базе.
2. Если хост на связи, оно спрашивает, принят ли уже этот код, с таймаутом
   около 300 мс. Дубль с другой станции отсекается до того, как товар попадёт
   в короб.
3. Если ответа нет, скан принимается локально, а дубль проявится как конфликт
   при досылке.

Конфликт решается как в облаке: побеждает самый ранний скан. Проигравший скан
помечается, его короб — на исправление, руководитель видит конфликт в офисе,
линия не стоит.

Правило «самый ранний» работает, только если часы устройств сходятся. Хост
измеряет расхождение часов при каждом обмене и предупреждает на станции и в
офисе, если оно превышает порог.

### 6.6. SSCC

- Хост выдаёт каждому устройству блоки номеров для коробов и для паллет.
- Новый блок запрашивается, когда израсходована половина текущего, поэтому у
  устройства обычно запас в полтора блока.
- Размер блока настраивается. Где хост бывает выключен подолгу, блок делают
  крупнее.
- Неиспользованные номера отозванного блока — это пропуски, они допустимы.
- Если компания уже печатала SSCC другой программой, мастер первого запуска
  спрашивает стартовый номер.
- Счётчик можно сдвинуть только вперёд: хост не даёт опустить его ниже уже
  выданного максимума.
- Состав SSCC строится функцией `buildSscc` из `packages/domain`: расширение 0 —
  короб, 1 — паллета, как в облаке.

### 6.7. Смены

- Номер смены присваивает хост.
- Смену создают в офисе (планирование) или на станции, когда хост на связи.
- Открытие замораживает снимок (раздел 6.3).
- Дата производства — гражданская дата смены. Срок годности на этикетке
  считается `shelfLifeExpiryDate` из `packages/domain` по принятому правилу
  (день производства — первый день).

### 6.8. Работа без хоста

- **Можно:** войти оператором, продолжить открытую смену (сканировать,
  собирать короба и паллеты, печатать, оформлять исключения) и закрыть смену
  локально, если станция знает её как смену одного устройства (раздел 6.9).
- **Нельзя:** открыть новую смену, править каталог и настройки, делать
  выгрузки.
- Станция показывает время с последней связи, число неотправленных событий и
  остаток SSCC в блоке.

### 6.9. Закрытие смены на нескольких устройствах

Правило то же, что в облаке (решения 4–5 спецификации
`2026-08-14-station-shift-close-and-line-presence-design.md`, серверная проверка
усилена в #639):

- Станция закрывает смену сама, только если знает её как смену одного
  устройства. Закрытие записывается локально, работает без хоста и
  досылается.
- Как только хост видит на смене второе устройство, смена навсегда
  становится закрываемой только из офиса (администратор или технолог).
  Признак «только офис» не снимается, даже если устройство ушло, отключилось
  или отозвано. Станция получает его вместе со сменой и вместо закрытия
  показывает, что смена открыта на нескольких устройствах.
- Станция, которая без связи поставила закрытие в очередь до того, как узнала
  о втором устройстве, не закрывает смену. Хост превращает такое закрытие в
  конфликт, видимый в офисе: офис закрывает смену или отклоняет попытку с
  записью в журнал. Повторная доставка того же закрытия новый конфликт не
  создаёт.
- Второе устройство хост определяет не только по записи о входе в смену, но и
  по уже сохранённым фактам другого устройства на этой смене — так же, как в
  облаке после #639.
- Сканы, сделанные без связи уже после закрытия, приходят как «поздние
  данные». Руководитель их видит, они не теряются, не принимаются молча и не
  открывают смену заново.

### 6.10. Связь и подключение устройств

- Соединение идёт по HTTPS с самоподписанным сертификатом, который хост
  создаёт при первом запуске. При подключении устройство запоминает его
  отпечаток и дальше проверяет только его.
- Подключение — по одноразовому коду с коротким сроком жизни и ограничением
  попыток. Офис показывает код и его машиночитаемую версию, в которой есть
  адреса хоста, отпечаток сертификата и сам код. Станция или ТСД может
  считать её сканером или ввести вручную.
- Устройство получает свой ключ. На Windows ключ хранится под защитой DPAPI.
- Адрес хоста находится поиском в сети (mDNS). Запасные варианты —
  машиночитаемый код или ручной ввод.
- Станцию на самом ПК-хосте мастер первого запуска подключает автоматически
  тем же механизмом кода.

### 6.11. Протокол

Логический состав (точные маршруты и форматы — в спецификации этапа 1):

- **служебное:** приветствие с версией протокола, возможностями устройства и
  отметкой времени, состояние;
- **подключение:** обмен одноразового кода на ключ, отключение устройства;
- **с хоста:** изменения справочников после ревизии и их поток, снимок смены,
  выдача блоков SSCC;
- **на хост:** пачка фактов с квитанциями, проверка КМ;
- **смены:** создание, открытие, закрытие;
- **офис:** изменение справочников, данные для выгрузок и печатных форм, поиск
  кода, конфликты, резервные копии и восстановление, обновление, лицензия,
  пакет для поддержки, журнал действий.

Каждый запрос несёт версию протокола. Хост понимает текущую и предыдущую
версии.

## 7. ТСД: что закладывается сразу

- **Протокол не привязан к типу устройства.** Клиент хоста — это устройство
  типа `station` или `handheld` со списком возможностей, например
  `validation-dm-duplicate-v1`, как в облаке. В протоколе нет ничего
  специфичного для Tauri: HTTPS, JSON, поток изменений с запасным опросом.
- **Семантика подтверждений ТСД.** Этикетки ТСД печатает сам, и состояние печати
  с устройства не уходит. Поэтому хост принимает от ТСД закрытие короба без
  условий, а события печати дубликата подтверждает по одному. Квитанции на
  каждую запись покрывают оба случая.
- **Подключение сканированием кода** (раздел 6.10) — основной способ для ТСД.
  Оно работает и там, где Wi-Fi режет mDNS.
- **Лицензия** ограничивает станции и ТСД раздельно.
- **Фикстуры протокола** в `proto/fixtures` проверяются в Rust и TypeScript, а
  с этапа 7 — и в Kotlin, по схеме нынешних фикстур ТСД.
- **Хост раздаёт подписанный APK** для обновления ТСД.

В самом приложении ТСД на этапе 7 понадобятся локальный режим (новый транспорт
к хосту поверх существующих `SyncTransport` и `StationApi`), подключение
сканированием кода и отключение облачного в этом режиме: гранты, замена
устройств, инвентаризация, списание. Сканер, печать, база Room и экраны
остаются как есть.

### 8.3. Три технических решения

1. **Транзакции.** Чтение и запись локальной базы идут через команды Rust.
   Команда записи выполняет набор операторов в одной транзакции на одном
   соединении (обобщённый `grant_atomic_execute` из станции).
   `tauri-plugin-sql` не используется, поэтому логику не нужно прятать в
   триггеры, чтобы обойти пул соединений.
2. **Миграции с номером версии.** У обеих баз есть таблица версии схемы и
   нумерованные SQL-файлы. Их применяет Rust при старте, каждую миграцию в
   своей транзакции. Станция сейчас при каждой загрузке заново прогоняет
   около 320 операторов.
3. **Сеть только в Rust.** Интерфейс сам не делает HTTP-запросов, а вызывает
   команды. Rust ходит к хосту, проверяет запомненный сертификат и пересылает
   интерфейсу поток изменений событиями. Так самоподписанный сертификат не
   упирается в ограничения WebView.

### 8.4. Контракт, обновления, правила разработки

- Типы протокола описаны в `proto` на Rust и в Zod на стороне TypeScript.
  Общие JSON-фикстуры проверяются с обеих сторон.
- Из `apps/station/src-tauri/src/updater.rs` берётся только проверка подписи
  minisign — для обновления из файла.
- SQL-миграции живут рядом с Rust-кодом, который их применяет
  (`host/migrations/`, `src-tauri/migrations/`). Это, а также правила
  транзакций и протокол хоста, фиксируется в новом `apps/standalone/AGENTS.md`.
  В корневой `AGENTS.md` добавляются ссылка на него и строка в карту
  репозитория.

## 9. Эксплуатация

### 9.1. Установка и первый запуск

- Один установщик NSIS, как у станции. При установке выбирается роль: «хост и
  станция», «только станция» или «только офис».
- Для хоста установщик регистрирует службу и открывает её порт в брандмауэре
  только для частной и доменной сети. Права администратора нужны один раз, при
  установке.
- Мастер первого запуска на хосте:
  1. администратор (логин и пароль);
  2. организация: название, ИНН, GLN, префиксы GS1;
  3. стартовый номер SSCC;
  4. линии и первые операторы;
  5. файл лицензии;
  6. папки для резервных копий.

  Типовые шаблоны этикеток создаются автоматически из `packages/domain`, местная
  станция подключается автоматически.

- Вторая станция: мастер находит хост в сети, оператор вводит или сканирует
  одноразовый код из офиса и выбирает линию. Затем настраиваются принтеры и
  сканеры.

### 9.2. Памятка для ИТ

Целевые заводы часто требуют согласования служб и портов. Вместе с установщиком
поставляется памятка: имя и учётная запись службы, порт, правило брандмауэра,
каталоги с базой и копиями, рекомендации по исключениям антивируса, отсутствие
исходящих соединений в интернет.

### 9.3. Резервные копии и восстановление

- **Когда.** Хост делает копии на ходу штатным механизмом SQLite (online
  backup): каждый час во время работы, раз в сутки и обязательно перед каждым
  обновлением. Каждая копия проверяется на целостность.
- **Куда.** В локальную папку на хосте и дополнительно в сетевую папку или на
  флешку. Хранятся последние часовые, суточные и месячные копии.
- **Контроль.** Офис показывает время последней проверенной копии. Сбой
  копирования выводится заметным предупреждением, а не строкой в журнале.
- **Восстановление** — мастером в офисе, текущая база сохраняется рядом. После
  восстановления:
  - хост поднимает счётчики SSCC и номера смен с запасом выше всего, что
    устройства успели получить, иначе появятся повторные SSCC;
  - устройства заново досылают хранящиеся у них факты. Приём идемпотентный,
    дублей не будет. Для этого устройство держит подтверждённые факты ещё N
    дней (по умолчанию 30), считая от подтверждения. Если восстановить копию
    старше N дней, факты, подтверждённые между моментом копии и началом этого
    окна, на устройствах уже удалены и не вернутся. Поэтому мастер предлагает
    самую свежую проверенную копию и предупреждает, если выбранная старше N
    дней.

### 9.4. Обновления из файла

- Пакет с подписью minisign приносят на флешке и открывают в офисе на хосте.
  Шаги: проверка подписи и версии → резервная копия → остановка службы →
  установка → миграция базы → запуск.
- Станции забирают тот же пакет с хоста и ставят его сами, тоже с проверкой
  подписи.
- Хост понимает протокол текущей и предыдущей версий, поэтому станции можно
  обновлять после хоста. Станция новее хоста синхронизироваться откажется и
  попросит обновить хост.
- Отката версии нет: миграции идут только вперёд. Вернуться можно
  восстановлением копии, сделанной перед обновлением. Предыдущий пакет
  хранится для переустановки.

### 9.5. Лицензия

- Файл подписан нашим ключом. В нём: организация, ИНН, лимиты станций и ТСД,
  включённые функции, необязательный срок и привязка к установке хоста.
- Активация без интернета: офис показывает код запроса, клиент присылает его
  любым способом, мы отвечаем файлом. При замене ПК-хоста — новый код и новый
  файл.
- Хост не даёт подключить больше устройств, чем разрешено лицензией.
- Если срок задан и истёк, линия внезапно не останавливается: сначала льготный
  период, затем нельзя открывать новые смены, но можно доработать открытые и
  сделать выгрузки. Чтобы срок нельзя было обойти переводом часов назад, хост
  запоминает самое позднее время, которое видел.
- По умолчанию лицензия бессрочная.

### 9.6. Диагностика

- Кнопка «Пакет для поддержки» в офисе и на станции. В пакете журналы, версии,
  состояние очередей и блоков SSCC, расхождение часов, результат проверки
  базы. Ключей устройств, хешей PIN и паролей и других секретов там нет.
- Экран состояния в офисе: хост и последняя копия; по каждому устройству —
  когда было на связи, сколько не дослано, версия, расхождение часов; место на
  диске; лицензия.
- Журнал действий офиса фиксирует пользователя, действие, объект, результат и
  существенные детали.

## 10. Функции первой версии

### 10.1. Офис

- **Каталог.** GTIN-14 с проверкой контрольной цифры и владельца по префиксам,
  название для печати, товарная группа ЧЗ, вместимость короба и паллеты, срок
  годности, шаблоны по умолчанию, признак «Не использовать», фото. Правило
  облака сохраняется: товар активен, только когда заданы группа и обе
  вместимости.
- **Шаблоны.** Импорт ZPL/TSPL/JSON, форма размеров, предпросмотр, совпадающий
  с печатью, типовые шаблоны. Назначение (короб, паллета, дубликат), товарные
  группы, умолчания организации и категории. Шаблон по умолчанию нельзя
  удалить или выключить.
- **Организация и контрагенты.** Реквизиты, GLN, префиксы GS1, логотип для
  печатных форм. Контрагенты нужны, чтобы при контрактном производстве
  выпускать SSCC под чужим префиксом.
- **SSCC.** Счётчики (просмотр и сдвиг вперёд), размеры блоков, блоки по
  устройствам (просмотр и отзыв).
- **Люди.** Операторы с PIN и бейджами. Офисные пользователи с двумя ролями:
  администратор может всё, включая пользователей, лицензию, восстановление и
  обновление; технолог работает с каталогом, шаблонами, сменами, выгрузками и
  конфликтами.
- **Линии и устройства.** Подключение по коду, линия, время последней связи,
  версия, отключение.
- **Смены.** Планирование: товар, линия, режим (агрегация с паллетами или без,
  либо валидация с дубликатом DM или без), обязательность проверки отпечатка,
  дата производства, шаблоны. Карточка смены: прогресс по устройствам, короба,
  паллеты, исключения, конфликты, поздние данные. Закрытие из офиса — в том
  числе смен, на которых работало несколько устройств, и разбор конфликтов
  закрытия (раздел 6.9).
- **Выгрузки.** Форматы смены из `packages/domain` (TXT и CSV, по коробам и
  паллетам, XML агрегации для ГИС МТ) и паллетный XML. Выгрузка доступна
  только по закрытой смене и с теми же проверками полноты, что в облаке. Файл
  сохраняется в папку или на флешку, чтобы загрузить его в ЧЗ с другого
  компьютера.
- **Печатные формы.** «Состав короба», «Состав паллеты», «Ярлык паллеты» (A4
  или A5), «Бланк смены».
- **Поиск кода** по КМ или SSCC: в каком коробе, паллете и смене лежит код, кто
  и когда его сканировал.
- **Конфликты.** Список и карточка: какой скан победил, какой проиграл, в каких
  коробах. Отметка об исправлении.
- **Сервис.** Состояние, резервные копии, восстановление, обновление, лицензия,
  журнал действий.

### 10.2. Цех

- Вход по PIN или бейджу, блокировка при бездействии.
- Выбор запланированной смены. Создание смены на станции, когда хост на связи.
- Агрегация, всё как на текущей станции, включая экран смены для малого
  монитора:
  - короба: сканирование КМ, закрытие полного или неполного короба, этикетка,
    проверка печати, восстановление после сбоя печати, исключения;
  - паллеты: сборка и закрытие, этикетка паллеты.
- Валидация и дубликат DM: печать дубликата, затем проверка отпечатка или
  явный пропуск проверки; перепечатка с указанием причины; если неизвестно,
  дошла ли печать, — восстановление без автоматической повторной отправки.
- Закрытие смены одного устройства с причинами из `packages/domain`. Смену,
  на которой работало несколько устройств, закрывает офис.
- Строка состояния: связь с хостом, неотправленные события, остаток SSCC в
  блоке. Прогресс смены по своей станции, а при связи с хостом — по всем
  устройствам.
- Настройка рабочего места: принтеры (сеть, COM, USB) и их назначения
  (короба, паллеты, дубликаты); сканеры (несколько COM-портов и клавиатурный
  ввод); звук; тестовая печать.
- Киоск-режим; компьютер не засыпает во время смены.

### 10.3. Чего нет в первой версии

- **Облачного:** сопряжения с облаком, офлайн-грантов, замены устройств,
  мультиарендности, биллинга, онлайн-обновлений.
- **Отложено:**
  - локальный режим приложения ТСД (этап 7; механизм в хосте и протоколе
    закладывается сразу);
  - инвентаризация и расформирование;
  - Нацкаталог, CommerceML/1С, импорт каталога из файла;
  - статусы кодов из ЧЗ и подписант УКЭП;
  - повторная обработка кодов из прошлых смен;
  - аналитический дашборд, архивация по годам;
  - английский интерфейс: строки сразу идут через i18n, чтобы добавить его
    позже.
- **Отличия от облака:** КМ проверяется только по формату и на дубли. Документы
  в ЧЗ отправляются файлами вручную.

## 11. Отказы

| Ситуация                                      | Поведение                                                                                                                                                                                                                         |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Хост недоступен                               | Станция продолжает открытые смены и показывает время без связи, число неотправленных событий и остаток SSCC. После восстановления связи досылает всё сама.                                                                        |
| Блок SSCC кончается без хоста                 | Запас в полтора блока, предупреждения на порогах: «осталось N коробов без хоста». Где хост часто выключен, блок крупнее.                                                                                                          |
| Дубль КМ между станциями без связи            | Конфликт: побеждает самый ранний скан, короб проигравшего помечается. Руководитель разбирает конфликт в офисе, линия не стоит.                                                                                                    |
| Расходятся часы                               | Хост измеряет расхождение при каждом обмене и предупреждает. Даты на этикетках берутся из даты производства смены и от часов не зависят.                                                                                          |
| Сбой принтера или неизвестно, дошла ли печать | Статусы задания: «подготовлено», «отправляется», «исход неизвестен», «проверено». Повторной отправки без решения оператора нет.                                                                                                   |
| Пропало питание                               | Хост и станции работают с `synchronous=FULL`: каждая транзакция сбрасывается на диск. Прерванная отправка на печать после перезапуска получает статус «исход неизвестен».                                                         |
| Испорчена база хоста                          | Проверка при старте и после каждой копии. Если база испорчена, хост не пишет в неё и предлагает мастер восстановления; дальше как в разделе 9.3.                                                                                  |
| Умер диск станции                             | Неотправленные факты теряются вместе с диском. Поэтому при связи факт отправляется сразу, а объём неотправленного всегда виден. Короб с таким SSCC, попавший на другую станцию, обрабатывается как исключение «неизвестен хосту». |
| Сеть мигает, пачка ушла дважды                | Та же пачка получает те же квитанции; повторы — с нарастающей паузой.                                                                                                                                                             |
| Несовместимые версии                          | Проверка версии протокола при каждом обмене; хост понимает текущую и предыдущую версии.                                                                                                                                           |
| Сбой миграции при обновлении                  | Миграция идёт в транзакции, база остаётся нетронутой. Предыдущий пакет хранится для переустановки, перед обновлением всегда делается копия.                                                                                       |
| Кончается место на диске                      | Хост следит за свободным местом и предупреждает. Если копия не удалась, предупреждение заметное.                                                                                                                                  |

## 12. Тестирование и критерии готовности

### 12.1. Автоматические проверки

- **TypeScript (Vitest):** логика цеха (журнал, короба, паллеты, закрытие,
  задания печати, жизненный цикл дубликата DM), движок синхронизации против
  поддельного хоста, офисные формы.
- **Rust (cargo test), хост:** та же пачка даёт те же квитанции; правило «самый
  ранний скан» при перемешанном порядке прихода; выдача и дозаказ блоков SSCC,
  подъём счётчиков после восстановления; необратимый признак «закрывает только
  офис» при втором устройстве, конфликт устаревшего закрытия со станции и
  поздние данные; миграции с каждой предыдущей версии на реальных старых базах;
  цикл «копия → восстановление»; проверка лицензии и защиты от перевода часов;
  подключение устройства и проверка отпечатка сертификата.
- **Контракт:** фикстуры `proto/fixtures` проверяются в Rust и TypeScript, с
  этапа 7 — и в Kotlin.
- **Сквозные сценарии на одной машине:** хост и два экземпляра станции с
  имитацией сканера и принтера — обычная смена; хост выключен и включён; дубль
  при связи и без связи; смена двух станций закрывается из офиса, а устаревшее
  закрытие со станции становится конфликтом; восстановление хоста из копии;
  обновление сначала хоста, потом станций.
- **Инъекция сбоев:** убить хост посреди приёма; убить станцию во время
  отправки на печать; сетевой прокси, который теряет, дублирует и задерживает
  пакеты. Проверяется, что ничего не потеряно и не задвоено.
- **CI:** новые задания в `.github/workflows/ci.yml` и `tools/ci/affected.mjs`:
  TypeScript-гейты и `cargo test` для воркспейса, Windows-раннер для кода
  оборудования, как у станции.

### 12.2. Приёмка на Windows

Выполняется вручную, в отчётах указывается отдельно от автоматических
проверок:

- роли установщика; служба стартует без входа в систему; правило брандмауэра;
- два ПК через коммутатор и через Wi-Fi, поиск хоста в сети;
- реальные принтеры ZPL/TSPL на 203 и 300 dpi, сканеры COM и клавиатурного
  ввода;
- отключение питания на хосте и на станции посреди смены;
- копии в сетевую папку и на флешку; обновление с флешки.

### 12.3. Критерии готовности к пилоту

1. Две станции и хост: полная смена агрегации с паллетами, хост выключен не
   меньше чем на час посреди смены. После восстановления связи на хосте каждый
   факт ровно один раз: число кодов, коробов и паллет совпадает на устройствах
   и на хосте.
2. Дубль с другой станции при связи отсекается сразу; без связи становится
   конфликтом и разбирается в офисе.
3. Смена валидации с дубликатом DM проходит все статусы, включая неизвестный
   исход отправки и пропуск проверки.
4. По закрытой смене формируется XML агрегации для ГИС МТ. Его приём в личном
   кабинете ЧЗ — внешняя проверка с другого компьютера с интернетом.
5. Учебное восстановление хоста из часовой копии: устройства досылают факты,
   счётчики SSCC подняты, повторных SSCC после этого нет.
6. Обновление с флешки: сначала хост, потом станции; в переходный период
   работает предыдущая версия протокола.
7. Отключение питания на хосте и на станции посреди смены: зафиксированные
   факты не потеряны, прерванная печать получает статус «исход неизвестен».
8. Лицензия: подключение сверх лимита отклоняется; цикл «код запроса → файл»
   работает.

## 14. Риски

- **Сопровождение двух продуктов.** Всё, что не лежит в `packages/domain`,
  `packages/ui` и общем пакете печатных форм, придётся поддерживать дважды.
  Новые правила маркировки, форматы этикеток и выгрузок кладутся в общие
  пакеты с первого дня.
- **Ограничения ИТ на целевых заводах.** Службы, порты и антивирусы могут
  требовать согласования. Отсюда памятка для ИТ и проверки в установщике.
- **Часы в изолированных сетях.** Без NTP часы расходятся. Отсюда мониторинг
  расхождения; учёт смещения при арбитраже конфликтов решается на этапе 2b.
- **Рост базы за годы.** Для 1–2 линий SQLite на локальном диске справляется с
  запасом. Хост показывает размер базы и свободное место; архивация по годам
  отложена.
- **Потеря неотправленных фактов с диском станции.** Снижается немедленной
  отправкой при связи и видимым объёмом неотправленного.
- **Разнообразие оборудования.** Принтеры и сканеры принимаются по моделям,
  как у текущей станции; имитации в тестах не доказывают поддержку конкретной
  модели.
