# US-04 — Transformation revisions and genealogy views

**Status:** Approved by the owner on 2026-09-26, including stable output-line order. This is an implementation specification, not a claim that the behavior exists or is deployed.

**Parent:** [Approved US-04 design](2026-09-26-us-04-transformation-current-design.md) and [MVP contract](../../us/mvp-contract.md). This stage covers TRN-009, TRN-011 and LOT-008 after original Transformation finalization. It does not add HTTP/UI, cases/SSCC, Station, deployment, release or RU behavior.

## Decisions and invariants

1. Each Transformation revision uses the existing `traceability_events` shell, typed child tables and `transformation_event_roots`. A new additive migration follows `0131_us_transformation_original.sql`; applied migrations are not edited. Receiving's revision rules and data remain compatible.
2. Starting an amendment copies the current finalized revision into one pending draft. The predecessor stays current until the new revision finalizes. Only one pending draft is allowed per root; a stale lifecycle or draft version conflicts. A failed command changes neither the current pointer nor frozen evidence.
3. A finalized amendment retains **every** existing output lot's ID, product, TLC, processor source and assignment basis. The output line number is the stable binding for this stage: output count, order and identity cannot be changed in an amendment. The draft may change inputs, input/output quantities and UOM, event date, reason and linked documents, subject to current facts, readiness and downstream checks. An incorrect output identity requires void, then a new original event/lot if void is permitted. No amendment creates a replacement output lot.
4. Voiding a finalized Transformation without finalized downstream dependencies preserves each output lot's ID, product, TLC, source, assignment basis, operational status and permanent source lock. It removes the event from the **current-origin view**, not from history; lot reads show `currentOrigin: false` or an equivalent explicit unavailable-origin state. Do not auto-archive, quarantine, release or reopen a lot. Frozen snapshots and historical edges remain addressable.
5. Historical event snapshots, line identities and edges are immutable. Only lifecycle metadata may mark a finalized predecessor `amended` or a current finalized event `void`. The current revision predicate remains `status = 'finalized' AND superseded_by_event_id IS NULL`, corroborated by its typed root pointer. A pending draft is never current evidence.

## Lifecycle and storage

- Extend the Transformation branch of event/root constraints and guards to permit revision `n > 1`, `draft → finalized`, `finalized → amended`, and `finalized/draft → void`, without loosening the Receiving branch. The root's `current_event_id`, `pending_draft_id`, `next_revision` and `lifecycle_version` must agree with revision states at commit. Preserve tenant/type-composite FKs and one-current/one-pending uniqueness.
- Amend/void commands use current server authorization, an operation key plus payload digest, expected lifecycle version, and a reason; finalization also compares expected draft version and readiness digest. A same-key/same-body replay returns the stored receipt after authorization; a different body conflicts. The command, exact actor/tenant/action/target/result audit row and receipt commit atomically.
- An amendment draft copies typed details, inputs, outputs (including their bound lot IDs), documents and `previousRevisionId`; it does **not** copy active edges into the draft. The client never supplies an output lot ID: draft save maps each output by its existing `lineNo` and retains its server-owned lot binding. Saving it never changes the predecessor's edges or lot state. The server rejects output count/line/identity changes on save and finalization, including direct SQL attempts at a forged finalized snapshot.
- At finalization, reload authoritative facts, lock root and affected lots in a deterministic order, validate source and coverage, calculate against current effects **excluding only the predecessor revision being replaced**, and reject any cycle in the candidate current graph. Write a new immutable snapshot and revision-attributed edges. Update the predecessor lifecycle and root current pointer in the same transaction. Never delete or mutate predecessor edges. Existing quarantine/recall controls survive all derived balance/status updates.
- A finalized void changes the event status and root pointer atomically; historical output lots/edges persist but no longer supply current origin. A pending draft void removes only the pending pointer. Reject void when it would strand a finalized dependent event. The exact blocker list is returned without changing anything.
- The migration expands Transformation operation-command checks and guards. It tests both a fresh database and an upgrade containing finalized original Transformation plus Receiving amendment history. No data backfill should reinterpret frozen snapshots.

## Downstream safety and concurrency

- A **current finalized downstream consumer** is a current finalized event that uses an affected lot as an input. For this stage, query current Transformation input lines; future Shipping must join the same guard before its finalization is enabled. A historical amended/void consumer or a pending draft is not a blocker. Resolve only within the authorized tenant and return safe event IDs/types and correction order, not foreign-tenant details.
- Refuse a Transformation void if any output lot has such a consumer. Refuse material amendment changes—input topology, output quantities/UOM or other effects that alter current genealogy/balance—when an output lot has such a consumer. A purely documentary correction may proceed with downstream consumers only if input/output lineage, quantities/UOM and output identities are unchanged. Revalidate this classification at finalization, not only when the draft is saved.
- Receiving void and material Receiving amendment finalization must also check current finalized Transformation consumers of affected lots. A Receiving draft or documentary correction does not silently invalidate a finalized Transformation. This closes the current Receiving void gap; the existing Receiving public behavior otherwise remains unchanged.
- Origin/consumer checks and finalization must share a per-lot serialization rule. Both sides lock the affected lot IDs in canonical order and must detect a committed consumer or origin change even if a repeatable-read snapshot began earlier (for example, by a version write that forces retry, or an equivalent proven isolation strategy). Tests force both transaction orders and a waiting stale snapshot; a successful retry is not a substitute for proving the race is closed. Root and lot lock order must not introduce deadlocks.

## Current and pinned genealogy

- `current` traversal reads edges only from each root's **current finalized** revision. It excludes pending, amended and void revisions, and verifies that root pointers and event status agree; corruption fails closed. A lot with no current origin remains visible with an explicit origin gap, not a fabricated source.
- `pinned` traversal takes an explicit, tenant-scoped set of finalized/amended/void historical revision IDs (or an already frozen request selection) and returns their stored snapshots and edges exactly. It does not silently substitute today's current revision or rehydrate old descriptions from live master data. The result names the selected revisions and their lifecycle states.
- Both directions return lot IDs, event/revision provenance and each line's own exact quantity/UOM. A 2→2 event yields four directed FTL lot edges, without multiplying the quantity KDEs into four event totals. A zero-FTL-input→one-FTL-output event has no fabricated input lot edge; its non-FTL input survives in the pinned/current event snapshot.
- Traversal is tenant-scoped and cycle-safe with deterministic order and explicit depth/node limits. A cycle or limit produces an incomplete/diagnostic result, never export-ready completeness. Mixed units return balance `unknown` with their separate values; no implicit `lb ↔ case` conversion, false zero or partial total. Pure graph helpers do not decide current/pinned selection or regulatory readiness.

## Delivery and acceptance

1. **Lifecycle and dependency guard:** migration/schema upgrade checks, amendment/void commands, stable output identity, Receiving downstream guard, exact audit/replay, race and rollback tests. Original 2→1 and Receiving regressions stay green. No public Transformation route is enabled.
2. **Genealogy and fixture expansion:** current/pinned read service, provenance/completeness, cycle/limit and mixed-unit behavior, 2→2 and zero-FTL-input→1 finalization fixtures. No case/SSCC or office UI is implied by a green internal API test.

Each increment starts with focused failing tests and ends with affected package test/typecheck/lint/build, migration inspection, isolation checks, `git diff --check`, independent review and an explicit account of skipped infrastructure or browser gates. Commit, push, PR, merge and deployment are separate authorizations.
