# Диагностика автонома по тенанту в SaaS-админке — дизайн

Статус: черновик на утверждение владельцем, 2026-10-15. Только документ: кода, миграций и ключей нет.
Требование: `docs/standalone/ROADMAP.md`, раздел 5. Формат токена: `docs/superpowers/specs/2026-10-13-standalone-license-and-updates-design.md`
(раздел 5, ключи), `apps/standalone/src/office/info/support-crypto.ts`, `tools/standalone-support/decrypt.mjs`. Публичный
формат статистики: `apps/standalone/src/host/usage-stats.ts` и `apps/standalone/proto/fixtures/usage-stats.json`.

## 1. Что строим и чего нет

Клиент автонома нажимает «Сведения для поддержки» (страница «О программе») и присылает текст. В нём открытая часть (версии,
роль ПК, связь, копии) и блок «Данные для анализа» с токеном `MKS1.<kid>.<тело>`. Сегодня токен открывает владелец
вручную (`decrypt.mjs --key …`). Нужно, чтобы оператор вставил весь текст в карточку тенанта в `apps/saas-admin`, API расшифровал
токен закрытым ключом поддержки, сохранил **историю** диагностик и **статистику по месяцам**, а карточка показала текущую версию
и использование лицензии.

Не входит: автоматическая отправка с клиента (клиент остаётся «копирует и присылает сам»); сохранение открытой части текста
(она не защищена и произвольна — парсить её нельзя, источником служит только расшифрованная нагрузка); алерты и уведомления;
сравнение версии с последним выпуском (вопрос В5); любые данные о кодах, SSCC, именах, ПИН, бейджах.

## 2. Что уже есть (проверено по коду на ветке `claude/integration`)

- Токен: ECDH P-256 (эфемерный ключ) + HKDF-SHA256 (соль пустая, `info` = `MKS1.<kid>` ‖ epk) + AES-256-GCM, AAD =
  `MKS1.<kid>` ‖ флаг; флаг 1 — открытый текст сжат raw-deflate. Раскладка тела: `флаг(1) ‖ epk(65) ‖ iv(12) ‖ шифртекст ‖ тег(16)`.
  Расшифровка в `decrypt.mjs` (`findBlob`, `parseBlob`, `decryptBlob`) использует только `node:crypto` и `node:zlib`.
- Нагрузка v1 (`support-usage.ts`, `usagePayload`): `v`, `generatedAt`, `appVersion`, `hostVersion`, `months[]` (до 12, по
  календарным месяцам, текущий последний: смены по режимам, сканы, короба, паллеты, исключения, конфликты, перепечатки,
  расформирование, отказы синхронизации), `devices {station, office, handheld}`.
- Чего **нет** в нагрузке: роли ПК (она только в открытой части текста), идентификатора хоста, лицензии. Это ровно «расхождение
  для проверки» из ROADMAP, разд. 5.
- Лицензия на стороне хоста читается страницей «О программе» из `GET /v1/office/license` (`officeLicenseSchema`, фикстура
  `office-license.json`): состояние, срок, квоты `{limit, used, over}` по `lines`, `stations`, `kiosks`, `cabinetUsers`,
  возможности, привязка (`hostId`, `innMatches`). Для статистики поддержки доступны те же права администратора, что и для
  `usage-stats`.
- Облако: `standalone_sites` (площадка = `hostId`, UNIQUE; `host_history` — все прежние `hostId`), `standalone_license_issuances`
  (миграция 0192). Платформенные маршруты автонома: `PlatformStandaloneLicensesController`, `platform/tenants/:tenantId/standalone-sites`,
  политика `["tenants.read", "standaloneLicenses.manage"]`, перезагрузка актора с 2FA и `FOR SHARE`
  (`requireStandaloneLicenseActor`). Миграции в облаке: последняя 0193 (`custom_logo_entitlement`).
- Открытый ключ поддержки уже в сборке: `proto/fixtures/support-keys.json` (kid `sup-d11c3182`). Закрытого ключа в репозитории нет и не будет.

## 3. Решения

### 3.1. Нагрузка v2 (шифрованная часть; правки в `apps/standalone`)

Все новые поля идут **внутрь токена**, а не в открытый текст: открытый текст клиент может править, а лицензия и идентификаторы не
должны читаться посторонним, кому текст перешлют. Версия `v: 2`; v1 принимается API без новых полей (клиенты беты 3).
Копирование идёт поле за полем по белому списку (как `pickMonth`), неизвестные поля хоста не попадают.

| Поле                        | Тип                                                               | Источник                                                 |
| --------------------------- | ----------------------------------------------------------------- | -------------------------------------------------------- |
| `v`                         | `2`                                                               |                                                          |
| `generatedAt`               | ISO-инстант                                                       | как в v1                                                 |
| `appVersion`, `hostVersion` | строка или `null`                                                 | как в v1                                                 |
| `hostId`                    | UUID или `null`                                                   | `facts.hostId` целиком (в открытом тексте идут 8 знаков) |
| `role`                      | `"host" \| "station" \| "office" \| null` (разработческая сборка) | `facts.role`                                             |
| `months`, `devices`         | как в v1                                                          | `GET /v1/office/usage-stats`                             |
| `license`                   | объект или `null`                                                 | `GET /v1/office/license`, см. ниже                       |

`license` (копируется по белому списку, строго): `state`, `plan`, `licenseId`, `sequence`, `kid`, `validFrom`, `validUntil`,
`graceDays`, `daysLeft`, `quotas {lines, stations, kiosks, cabinetUsers: {limit, used, over}}`, `features` (булевы, ключи
`STANDALONE_FEATURE_KEYS`), `innMatches` (булево из `binding`). **Не** копируем: `customer.name`, `customer.inn`, `fingerprint`,
`trial.inn`, `orgInn` — организация и ИНН у облака уже есть, а лишние идентификаторы в токене незачем. `license = null`, когда
хост не ответил или пользователь не администратор (как для статистики: текст не называет причину).

Изменения клиента (задача Т1): контекст `SupportContext` получает `license?: LicenseLoad` (по образцу `UsageLoad`), загрузка
рядом с `getUsageStats`; `usagePayload` собирает v2; `decrypt.mjs` печатает версию, роль и сводку лицензии (таблица месяцев
остаётся); фикстуры и тесты `support-usage` с проверкой, что в нагрузке нет ни одного поля вне белого списка (в том числе
подсунутого в ответ хоста). Ключ шифрования и формат токена `MKS1` **не меняются** — старые тексты открываются теми же ключами.

### 3.2. Закрытый ключ поддержки: только окружение API

- Переменная `STANDALONE_SUPPORT_KEYS_JSON` — JSON-массив `[{ "kid": "sup-…", "pem": "-----BEGIN PRIVATE KEY-----\n…" }]`
  (PEM допускает `\n`-экранирование, как `STANDALONE_LICENSE_PRIVATE_KEY_PEM`). Несколько записей = ротация: новые тексты
  шифруются активным ключом сборки, старые остаются читаемыми, пока запись в массиве есть. Ключ лежит в тех же секретах, что и
  ключи лицензий (инвентарь `.env.example` — только имя и пустое значение; значения в репозиторий и в CI-логи не попадают).
- Старт API: переменная пуста → приём отключён, API поднимается, маршрут записи отвечает `503 standalone_diagnostics_not_configured`;
  непустая, но разобрать не удалось, `kid` повторяется, не P-256 или не приватный ключ → старт падает с общим сообщением без
  материала ключа (образец `configureStandaloneLicenseSigning`, `STANDALONE_LICENSE_SIGNING_ERROR`).
- Проверка соответствия открытому набору: `kid` должен совпадать с хешем публичной точки (`publicEntry` в `decrypt.mjs`) — иначе
  предупреждение при старте (не отказ: владелец может задать `--kid`).
- Закрытый ключ не логируется, не попадает в аудит, ответы, ошибки, дампы (включая `sanitizeAuditMetadata`).
- Ключ поддержки — **отдельный** от ключей лицензий и грантов (принцип разд. 5.1 спеки лицензий): компрометация одного не
  открывает другое.

### 3.3. Модуль API и разбор токена

`apps/api/src/modules/standalone-diagnostics/`: `support-blob.ts` (чистая функция `openSupportBlob(text, keys)`),
`standalone-support-keys.ts` (конфигурация и загрузка ключей), `standalone-diagnostics.service.ts`,
`platform-standalone-diagnostics.controller.ts`, `standalone-diagnostics-views.ts`.

`openSupportBlob`:

1. Ищет **первый** токен регулярным выражением `decrypt.mjs` (`MKS1.<kid 1–32>.<base64url>`); токена нет → `no_token`.
2. Длина токена ≤ 16 КиБ; тело — канонический base64url (повторное кодирование должно дать ту же строку, иначе подмена
   «мусорным» хвостом проходила бы с другим хешем); раскладка ≥ 1+65+12+16 байт; флаг 0/1; epk — несжатая точка P-256 на кривой
   (проверяется `createPublicKey`, не произвольные байты).
3. `kid` ищется в загруженных ключах → иначе `unknown_key`.
4. ECDH → HKDF → AES-GCM с AAD; любая ошибка проверки → `undecryptable` (для чужого ключа, подмены `kid`/флага/epk/шифртекста
   одна и та же причина, чтобы ответ не служил оракулом).
5. Распаковка: **только** `inflateRawSync(…, { maxOutputLength: 256 КиБ })` — иначе токен-бомба (сжатие 1000:1 в 16 КиБ) раздувается
   в гигабайты; превышение → `payload_too_large`. Результат UTF-8 строго, затем `JSON.parse`; нагрузка >64 КиБ после
   распаковки — `payload_too_large`.
6. Валидация Zod `.strict()` v1/v2 (новая схема `standaloneSupportPayloadSchema` в `packages/platform-contracts`, а не в API,
   чтобы клиент и сервер читали одно): месяцы — регулярное выражение `YYYY-MM`, строго возрастающие, ≤ 12, все счётчики
   целые ≥ 0 и ≤ 2^53−1; версии — ≤ 64 знаков без управляющих; `generatedAt` — валидный инстант и не позднее `now + 1 сутки`
   (`generated_in_future`; клиентские часы — единственный источник времени, поэтому будущее режем; прошлое принимаем).

Реализация расшифровки на сервере повторяет `decrypt.mjs`; чтобы они не разошлись, тест чётности (разд. 6) открывает **один и
тот же** токен-фикстуру обеими реализациями, а фикстуру создаёт настоящий `support-crypto.ts` (WebCrypto) с тестовым ключом.
`decrypt.mjs` остаётся автономным инструментом владельца; расширяем его только выводом v2.

### 3.4. Таблицы Postgres (миграция 0194)

**Номер.** Следующий свободный после 0193 на этой ветке — **`0194_standalone_support_diagnostics.sql`**. Как 0192 и 0193, она
помечена **«перенумеровать перед любым PR в main»** (ROADMAP, разд. 6): в PR к `main` номер, запись в `meta/_journal.json`
и снимок берутся заново от тогдашнего `origin/main`, а тесты порядка миграций перепрогоняются. Это пункт чек-листа задачи Д1 и
строка в разделе 6 ROADMAP (`Облако (Drizzle): 0192, 0193, 0194 — перенумеровать`).

`standalone_support_diagnostics` — история, по строке на принятый токен:

| Колонка                                                 | Тип и ограничения                                                                                                                                              |
| ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                                                    | `uuid` PK                                                                                                                                                      |
| `tenant_id`                                             | `text` NOT NULL → `organization.id`                                                                                                                            |
| `site_id`                                               | `uuid` NULL; составной FK `(tenant_id, site_id)` → `standalone_sites(tenant_id, id)` (чужая площадка невозможна)                                               |
| `host_key`                                              | `text` NOT NULL: `hostId` из нагрузки или `unknown` (v1); `CHECK` UUID-формат либо `unknown`                                                                   |
| `blob_sha256`                                           | `text` NOT NULL, `CHECK ~ '^[0-9a-f]{64}$'`: SHA-256 канонической строки токена (после извлечения из текста)                                                   |
| `kid`                                                   | `text` NOT NULL, 1–32 знака                                                                                                                                    |
| `payload_version`                                       | `smallint` NOT NULL, `IN (1, 2)`                                                                                                                               |
| `generated_at`                                          | `timestamptz` NOT NULL (из нагрузки)                                                                                                                           |
| `received_at`                                           | `timestamptz` NOT NULL DEFAULT now() (по часам БД)                                                                                                             |
| `received_by_platform_user_id`                          | `text` NOT NULL → `platform_users.id`                                                                                                                          |
| `app_version`, `host_version`                           | `text` NULL, `CHECK length ≤ 64`                                                                                                                               |
| `pc_role`                                               | `text` NULL, `IN ('host','station','office')`; `NULL` для v1 и разработческих сборок                                                                           |
| `devices_station`, `devices_office`, `devices_handheld` | `integer` NOT NULL ≥ 0                                                                                                                                         |
| `license`                                               | `jsonb` NULL (сводка v2, строго по схеме; `octet_length ≤ 8192`)                                                                                               |
| `payload`                                               | `jsonb` NOT NULL (проверенная нагрузка целиком; `jsonb_typeof = 'object'`, `octet_length ≤ 65536`) — для перерасчёта агрегатов и разбора, без исходного токена |

Ограничения: `UNIQUE (blob_sha256)` — **идемпотентность по хешу токена, глобально** (один и тот же токен не может лечь в два
тенанта); `UNIQUE (tenant_id, host_key, generated_at)` — вторая линия: повторно сформированный тот же отпечаток другим токеном
(эфемерный ключ делает токены разными) считается повтором; `UNIQUE (tenant_id, id)`; индекс `(tenant_id, generated_at DESC)` и
`(tenant_id, host_key, generated_at DESC)` для карточки. Сам токен и исходный текст **не хранятся**: хранить нечего, что не
восстановимо из `payload`, а открытая часть текста ненадёжна и может содержать произвольное.

`standalone_support_usage_months` — агрегаты, по строке на (тенант, хост, месяц):

| Колонка                 | Тип                                                                                                |
| ----------------------- | -------------------------------------------------------------------------------------------------- |
| `tenant_id`, `host_key` | как выше; PK `(tenant_id, host_key, month)`                                                        |
| `month`                 | `text`, `CHECK ~ '^[0-9]{4}-(0[1-9]                                                                | 1[0-2])$'` |
| `stats`                 | `jsonb` NOT NULL: один месяц из нагрузки без изменений (`usageMonthSchema`), `octet_length ≤ 4096` |
| `source_diagnostic_id`  | `uuid` NOT NULL; составной FK `(tenant_id, source_diagnostic_id)` → диагностика                    |
| `source_generated_at`   | `timestamptz` NOT NULL                                                                             |

Правило записи (в одной транзакции с историей): для каждого месяца нагрузки
`INSERT … ON CONFLICT (tenant_id, host_key, month) DO UPDATE … WHERE excluded.source_generated_at > existing.source_generated_at`.
Месяц в диагностике — накопительный счётчик на момент её формирования: побеждает **самая поздняя по `generated_at`**, а не по
порядку вставки, поэтому присланная позже, но старая диагностика (клиент прислал два текста в обратном порядке) не затирает
свежую. Счётчики хоста за прошлые месяцы не меняются, а текущий растёт, так что последняя побеждает по смыслу. Сколько месяцев
применено и сколько пропущено как устаревшие — в ответе и в аудите.

Чтение «статистики по месяцам» для тенанта: сумма `stats` по `host_key` в месяце (по всем хостам) либо по выбранному хосту;
сумма считается в сервисе по ≤ 12×(число хостов) строкам, не SQL-JSON-арифметикой, чтобы схема счётчиков не размазывалась по SQL.
Отсутствующий месяц — **пропуск, а не ноль** (правило метрик API: отсутствующий факт — `null`).

Изоляция: каждый запрос с `tenant_id` в условии; составные внешние ключи не дают привязать диагностику к площадке или источнику
другого тенанта; тесты на чужого тенанта обязательны (разд. 6). Данные тенанта не удаляются автоматически; срок хранения и
удаление — вопрос В6.

### 3.5. Маршруты API

Контроллер `PlatformStandaloneDiagnosticsController`, префикс `platform/tenants/:tenantId/standalone-diagnostics`,
`@ApiTags("platform-standalone-diagnostics")`, параметр `tenantId` — `standaloneOpaqueIdSchema` как у соседей. Новой
возможности платформы **не вводим** (её добавление ломает фикстуры принципалов, см. корневой `AGENTS.md`): переиспользуем
существующие.

| Метод и путь          | Политика                                              | Назначение                                                               |
| --------------------- | ----------------------------------------------------- | ------------------------------------------------------------------------ |
| `POST` `` (ingest)    | `["tenants.read", "standaloneLicenses.manage"]` + 2FA | Вставить текст, расшифровать, сохранить. `200`, идемпотентно.            |
| `GET` ``              | `["tenants.read"]`                                    | История (курсор по `generated_at DESC, id`, ≤ 50 за страницу).           |
| `GET` `overview`      | `["tenants.read"]`                                    | Текущая версия, использование лицензии, последняя диагностика по хостам. |
| `GET` `statistics`    | `["tenants.read"]`                                    | Месяцы: `?hostKey=` (необязателен), `?from=YYYY-MM&to=YYYY-MM`.          |
| `GET` `:diagnosticId` | `["tenants.read"]`                                    | Одна запись истории: сводка лицензии, версии, устройства, месяцы.        |

«Просматривать открыто» — это `tenants.read` (любой оператор платформы, видящий карточку тенанта), без финансовой возможности;
записывает только тот, кто выпускает лицензии (вопрос В2 о более широкой записи). Данные счётчиков — эксплуатационные, не
финансовые и не персональные.

`POST` — тело `{ "text": string, "acknowledgeUnboundHost"?: boolean }`, `text` 1–32 768 знаков (в настоящем тексте поддержки
≈ 2–4 КиБ: открытая часть + токен ≈ 3 КиБ). Лимит проверяется в схеме Zod **до** разбора и поверх лимита `express.json()`
(100 КиБ по умолчанию; маршрут не расширяет его). Больший текст → `413 standalone_diagnostics_text_too_large` (платформенная
форма ошибки, `PlatformExceptionFilter`), а не ошибка парсера.

Порядок обработки (после общей загрузки актора по `requireStandaloneLicenseActor`: 2FA, роль и тенант перезагружаются; для
записи — `FOR SHARE`, как у выпуска; тенант не найден → `404` до любой работы с токеном):

1. `ключи не настроены` → `503`.
2. `openSupportBlob` → отказы по разд. 3.3 (`400`/`422`/`413`), с аудитом отказа (разд. 3.6).
3. Привязка к тенанту (защита от вставки не в ту карточку): `hostKey` ≠ `unknown` → ищем площадку `standalone_sites` по
   `host_id`/`host_history`.
   - площадка того же тенанта → `site_id` заполняется;
   - площадка **другого** тенанта → `409 standalone_diagnostics_host_other_tenant` (без указания, какого; запись не создаётся);
   - площадки нет (пробный период, установка не из лицензии) → `409 standalone_diagnostics_host_unbound`, **если** не передан
     `acknowledgeUnboundHost: true`; с подтверждением запись создаётся с `site_id = NULL` и пометкой в аудите.
   - v1 (`unknown`): всегда требует `acknowledgeUnboundHost`, привязку оператор делает на глаз.
4. Идемпотентность: `blob_sha256` уже есть в этом тенанте → `200` с `duplicate: true` и ссылкой на существующую запись (без
   новой записи, без пересчёта агрегатов; аудит `duplicate`); в чужом тенанте → `409 standalone_diagnostics_token_conflict` (без
   указания тенанта). Пара `(tenant, host_key, generated_at)` совпала — тоже `duplicate`.
5. Транзакция: вставка истории + `upsert` месяцев + аудит; успех → `200` со сводкой записи, `duplicate: false`,
   `monthsApplied`, `monthsSkipped`.

Параллельная вставка одного токена двумя операторами решается `UNIQUE` и `ON CONFLICT`: проигравший получает ответ-повтор, а не
`500`. Ошибка БД — `5xx` без записи частичного состояния (история и агрегаты в одной транзакции).

Ответы строятся схемами из `packages/platform-contracts` (новый `standalone-diagnostics.ts`), добавляются в OpenAPI и инвентарь
маршрутов: `test/platform-route-contracts.ts`, `test/platform-contract-openapi.test.ts`, платформенный список в `cors`/маршрутных
тестах (проверить, нужны ли правки по образцу `platform-standalone-licenses.routes.test.ts`).

### 3.6. Аудит (точные поля)

Через `PlatformAuditService.record` внутри той же транзакции (успех) и отдельной транзакцией (отказ — иначе откат стёр бы след):

| Поле                               | Значение                                                                                                                                                                         |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `action`                           | `standalone.diagnostics.ingest`                                                                                                                                                  |
| `outcome`                          | `success` \| `duplicate` \| `rejected`                                                                                                                                           |
| `actorPlatformUserId`, `actorRole` | принципал платформы                                                                                                                                                              |
| `tenantId`                         | из пути (и для отказа, если тенант существует)                                                                                                                                   |
| `targetType`                       | `standalone_support_diagnostic`                                                                                                                                                  |
| `targetId`                         | `id` записи; для `rejected` и `duplicate` — `null` / `id` существующей записи                                                                                                    |
| `reason`                           | для `rejected` — код отказа (`unknown_key`, `undecryptable`, `host_other_tenant`, …); иначе `null`                                                                               |
| `before`                           | `null`                                                                                                                                                                           |
| `after`                            | `{ blobSha256, kid, payloadVersion, hostKey, siteId, generatedAt, appVersion, hostVersion, pcRole, licenseState, monthsApplied, monthsSkipped, unboundAcknowledged, textBytes }` |

Ловушка: `sanitizeAuditMetadata` скрывает ключи, подходящие под `/token|secret|…/i` и под финансовый список — поэтому поле
называется `blobSha256`, а не `tokenSha256`; тест проверяет, что значение не превратилось в маску. В аудит **не** попадают
текст, токен целиком, расшифрованная нагрузка, счётчики, ключи. Для `rejected` без распознанных полей `after` содержит только
`{ textBytes, kid? }` (`kid` — только если он прошёл формат). Тесты проверяют точные поля, а не рост числа строк
(корневой `AGENTS.md`, «Audit assertions»).

Чтение (`GET`) аудитом не пишется: оно соответствует чтению карточки; запись аудита на чтение — вопрос В7.

### 3.7. Страница в `apps/saas-admin`

Новая вкладка «Диагностика» в `TenantPage` (`DataTabs`, id `diagnostics`, `?tab=diagnostics`, видима при `tenants.read`,
нумерация следующая за `legal`), компонент `pages/tenants/TenantDiagnosticsPanel.tsx` + модули `diagnostics-api.ts` (react-query,
как `standalone-api.ts`) и `diagnostics-format.ts`. RU/EN в `i18n/ru.json` и `en.json` (оба обязательны).

Блоки сверху вниз:

1. **Сводка** (`GET overview`): по каждому хосту — роль ПК, версия приложения и хоста **по последней диагностике**, «получено
   N дней назад» (бейдж с текстом и иконкой, не только цветом, при давности > 45 дней), лицензия: состояние, план, срок
   (`validUntil`, `daysLeft`), квоты «занято из доступного» по `lines`/`stations`/`kiosks`/`cabinetUsers` (`∞` при `null`;
   превышение — предупреждающий бейдж с текстом), устройства по видам (станции/офисы/ТСД), возможности (включено/выключено).
   Если диагностик нет — пустое состояние с подсказкой «Вставьте текст «Сведения для поддержки»».
   Сравнение с лицензией в облаке (последний выпуск `standalone_license_issuances`): «в файле на ПК — №3; в облаке выпущен №4»;
   расхождение показывается нейтрально («файл на площадке устарел»), без вывода о нарушении.
2. **Вставка** (только при `standaloneLicenses.manage`; иначе блока нет): `textarea` (моноширинная, с подписью и счётчиком
   знаков), «Разобрать и сохранить». Ошибки — по `standaloneDiagnosticsErrorKey(code)` на человеческом языке в духе
   `standalone-format.ts`; на `host_unbound` показывается подтверждение «Площадка не найдена среди площадок клиента. Сохранить
   без привязки?» (кнопка повторяет запрос с `acknowledgeUnboundHost`). Успех — зелёное сообщение «Сохранено: <хост>, <версия>,
   месяцев обновлено N» (или «Уже загружено»); `textarea` очищается, токен из состояния формы убирается.
3. **Статистика по месяцам** (`GET statistics`): переключатель хоста («Все хосты» + список), таблица месяцев (как в
   `decrypt.mjs`: смены по режимам, принято/дублей/отклонено, короба, коды/короб, паллеты, исключения, конфликты, перепечатки,
   расформирование, отказы синхронизации), под ней — 2–3 диаграммы (смены по режимам, принято vs отклонено, ошибки), на
   компонентах `@markiro/ui`; **если подходящего компонента диаграмм в `@markiro/ui` нет** (на момент спеки не найден), строим
   SVG-полосы на токенах, без внешних библиотек. Пропущенный месяц — «нет данных», не 0. Все данные также доступны таблицей
   (доступность: диаграмма не единственное представление).
4. **История** (`GET`): таблица «Получено / Сформировано / Хост / Роль / Версия приложения / Версия хоста / Состояние
   лицензии», выбор строки открывает деталь (`GET :diagnosticId`); пагинация «Показать ещё».

Операторский 2FA-сеанс, подтверждение выхода при несохранённом вводе — по существующему `useUnsavedChanges`. Тексты ошибок не
содержат введённого токена.

## 4. Обратная совместимость и порядок выпуска

1. Облако (Д1–Д6) выпускается первым и принимает v1 и v2; без ключа в окружении вкладка работает на чтение, запись говорит
   «приём не настроен».
2. Клиент v2 (Т1) выходит в следующей бете автонома. Тексты беты 3 (v1) принимаются с ручным подтверждением привязки, без
   лицензии и роли на карточке (в сводке «нет данных»; роль в v1 есть только в открытой части — оператор её не вводит).
3. Ротация ключа: новая запись в `STANDALONE_SUPPORT_KEYS_JSON` и `support-keys.json` (сначала в API, потом в сборку, как у
   лицензий); `retiredKids` в сборке — только после того, как клиенты обновились; ключ в API удаляется последним.

## 5. Безопасность и данные

- Закрытый ключ: только окружение API (разд. 3.2); не в репозитории, не в тестах (тесты генерируют одноразовую пару), не в логах.
- Токен — недоверенный ввод оператора: размеры, формат, ограничение распаковки и строгая схема до записи; ничего, кроме
  проверенной нагрузки, в БД не пишется.
- Статистика без персональных и товарных данных (набор полей — белый список клиента **и** строгая схема сервера: лишнее поле
  v2 → `payload_invalid`).
- Подлинность: GCM доказывает, что токен собран тем, кто знает **открытый** ключ, то есть любой желающий может создать
  валидный токен (открытый ключ в каждой сборке). Это не криптографическая гарантия происхождения: оператор видит, что хост
  принадлежит площадке тенанта (`hostId`), и доверяет им как данным клиента, не как подписанным фактам. Для лицензионных
  решений диагностика **не используется** (лицензия проверяется хостом по подписи облака). Подписанный отчёт — вопрос В3.
- Нагрузка на БД: одна транзакция, ≤ 12 upsert; ограничение частоты — общий платформенный ограничитель, если он есть для
  `POST` платформы (проверить при реализации; иначе вопрос В8).

## 6. Тесты (минимум; тест-первый)

Чистые (без БД) — `apps/api/test/standalone-support-blob.test.ts`, `standalone-support-keys.test.ts`:

- **Чётность**: токен, созданный настоящим `support-crypto.ts` с тестовой парой, открывается `openSupportBlob` и `decrypt.mjs` с
  одинаковым JSON (оба флага 0 и 1).
- **Подмена**: изменённый байт в каждой зоне (флаг, epk, iv, шифртекст, тег), подменённый `kid` в префиксе и в AAD, обрезанный
  и удлинённый токен, не-канонический base64url, epk не на кривой — каждый → `undecryptable`/`malformed`, без исключения наружу.
- **Чужой ключ / `kid`**: токен под другим ключом при совпавшем `kid` → `undecryptable`; неизвестный `kid` → `unknown_key`;
  ротация: токен под вторым ключом массива открывается.
- **Токен-бомба**: сжатие ≫ 256 КиБ → `payload_too_large`, память не растёт; нагрузка > 64 КиБ без сжатия — то же.
- **Нагрузка**: v1 и v2 приняты; лишнее поле, месяц не по порядку, > 12 месяцев, отрицательный/дробный/огромный счётчик,
  `generatedAt` в будущем (`+1 сутки`), версия с управляющими знаками → `payload_invalid`.
- **Ключи из окружения**: пусто — отключено; частично/битый PEM/повтор `kid`/не P-256 — старт падает, сообщение без материала.

Интеграционные (БД; явный skip без `DATABASE_URL`) — `standalone-diagnostics.e2e.test.ts`:

- Успех: запись истории, агрегаты, аудит с **точными** полями (актор, роль, тенант, действие, цель, исход, `after` целиком;
  значение `blobSha256` не замаскировано).
- **Повтор**: тот же токен → `duplicate: true`, строк не прибавилось, агрегаты не пересчитаны, аудит `duplicate`; повтор того же
  отпечатка другим токеном (`(tenant, host_key, generated_at)`) — то же; гонка двух одновременных вставок — один победитель,
  второй не `500`.
- **Порядок**: диагностика с более ранним `generated_at`, присланная позже, не затирает месяцы свежей (`monthsSkipped`), а
  недостающие месяцы добавляет.
- **Чужой тенант**: токен хоста тенанта B в карточке A → `409 host_other_tenant`, нет записи, аудит `rejected`; тот же токен,
  уже принятый в тенанте B, пастится в A → `409 token_conflict`; чтение истории/статистики/детали тенанта B по пути A —
  пусто или `404` (деталь по `diagnosticId` чужого тенанта — `404`, не `403`); составной FK не даёт вставить чужие `site_id` и
  `source_diagnostic_id` (проверка на уровне БД).
- **Привязка**: хост без площадки → `409 host_unbound`, с `acknowledgeUnboundHost` — запись с `site_id = NULL` и пометкой в
  аудите; v1 без подтверждения → тот же `409`; площадка находится и по `host_history` (перепривязка).
- **Размеры**: `text` > 32 768 → `413`, токен > 16 КиБ → `400/413` по правилам, тело > лимита `express.json()` — штатная
  платформенная ошибка; нет записи и нет аудита успеха.
- **Доступ**: без сеанса, без 2FA, роль без `standaloneLicenses.manage` (запись → `403`; чтение — разрешено при `tenants.read`),
  сессия кабинета и ключ устройства не получают доступ; политика на всех методах — тест метаданных
  `PLATFORM_ACCESS_POLICY` по образцу `platform-standalone-licenses.routes.test.ts`; приостановленный/удалённый оператор между
  запросами теряет доступ (перезагрузка актора).
- **Ключ не настроен**: `503`, записи нет.
- **Утечки**: ни токен, ни нагрузка, ни PEM не встречаются в ответах ошибок, логах (перехват) и `platform_audit_events`.
- Контракты: OpenAPI и инвентарь маршрутов; миграция — схема, ограничения (`CHECK`, `UNIQUE`, FK), прохождение на пустой БД и
  обновление с 0193.

saas-admin (Vitest, DOM): сводка с квотами и `∞`/превышением; пустое состояние; блок вставки скрыт без `standaloneLicenses.manage`;
ошибки — человеческие тексты по каждому коду; подтверждение `host_unbound` повторяет запрос с флагом; токен не остаётся в
состоянии/URL после отправки; «нет данных» вместо нуля; RU/EN-ключи. Автотесты DOM — не визуальная проверка в браузере (отдельный
обход вручную).

Клиент автонома (Т1): белый список v2 (в том числе подсунутые в ответ хоста `customer.name`, `fingerprint` не попадают);
`license = null` при отказе/неадминистраторе; тот же токен открывается `decrypt.mjs`.

Что не проверяется автотестами: реальный ключ поддержки в окружении, реальный пользовательский текст с Windows, рендер в
браузере.

## 9. Открытые вопросы владельцу

- **В1. Привязка при пустой площадке.** Принимать диагностику без `standalone_sites` с подтверждением оператора (предложено) или
  требовать сначала зарегистрировать площадку? Для пробных установок площадки пока нет.
- **В2. Кто пишет.** Запись — `tenants.read` + `standaloneLicenses.manage` (те же, кто выпускает лицензии); чтение — любой
  оператор с `tenants.read`. Нужна ли запись шире (поддержка без права выпуска)? Для этого потребуется новая возможность
  платформы и правка всех фикстур принципалов.
- **В3. Подлинность.** Достаточно «данные от клиента без подписи» (предложено), или подписывать нагрузку ключом хоста/лицензией, чтобы
  отчёт нельзя было подделать? Цена: сложность хоста и менее открытый формат.
- **В4. Нужна ли `hostId` целиком в токене**, а не только в открытой части (предложено: да, внутрь) и нужны ли `os`/`arch`/
  версия WebView2 в статистике (сейчас в открытой части текста, в нагрузку не входят).
- **В5. «Текущая версия».** Только версия по последней диагностике (предложено) или ещё сравнение с последней опубликованной сборкой
  автонома и пометка «устарела»? Второе требует источника правды о выпусках в облаке.
- **В6. Срок хранения.** Хранить историю бессрочно (предложено; ≈ 3–5 КиБ на запись) или удалять через N месяцев? Удаление
  тенанта и право на удаление данных клиента.
- **В7. Аудит чтения** диагностики и статистики — нужен ли.
- **В8. Ограничение частоты** на запись, если у платформенных маршрутов такого нет.
- **В9. Окно «повтор»** — пара `(tenant, host_key, generated_at)` считается повтором точно; допустимо ли считать повтором и
  близкое время (например, в пределах минуты)? Предложено: нет, только точное совпадение.
- **В10. Один тенант — несколько хостов** (хост на каждую площадку/перепривязку): по умолчанию статистика суммируется по всем хостам
  тенанта и есть выбор хоста. Устраивает ли суммирование при перепривязке (старый и новый `hostId` одной площадки считаются разными
  хостами и в сумме месяца дублируются, если оба прислали один и тот же месяц)?

- В5: «текущая версия» берётся из последней диагностики и сравнивается с последней опубликованной сборкой («устарела»), если её можно получить из каталога релизов — да.
- Миграции облака перенумерованы на 0192–0194 (в `origin/main` занято до 0191).

Остальные вопросы (2026-10-15, владелец принял рекомендации): В2 — запись только у выпускающих лицензии (любой с доступом в админку, имеющий это право); В4 — `hostId` целиком + ОС, архитектура, версия WebView2 в зашифрованной части; В6 — хранить 24 месяца, каскадное удаление с тенантом; В7 — чтения не аудируются; В8 — без лимита частоты; В9 — повтор только по точному `generated_at`; В10 — суммировать по хостам, в интерфейсе пометка «несколько хостов».
Хранение секрета: Yandex Lockbox (не GitHub Environments); имя записи `STANDALONE_SUPPORT_KEYS_JSON` добавляется в список `deploy/yandex/runtime-env.mjs` как необязательная запись (задача К1).

## Отклонения при исполнении (ревью Codex)

- **Привязка к хосту.** Хост, который сейчас (`standalone_sites.host_id`) числится за другим тенантом, всегда отказ `host_other_tenant`; история `host_history` своего тенанта помогает только для хоста, который ничей или сейчас свой. Подтверждение «хост не привязан» к чужому текущему хосту не применяется.
- **Хеш повторно сформированного токена.** Токен, перешифрованный для того же `(tenant, host, generatedAt)`, остаётся `duplicate`, но его SHA-256 теперь закрепляется за тенантом отчёта в новой таблице `standalone_support_token_aliases` (PK — хеш, каскад с отчётом и тенантом). Тот же токен в другом тенанте — `token_conflict`, повтор в своём — `duplicate`. После удаления отчёта (срок хранения) хеш освобождается, как и хеш первого токена. Миграция 0194 правлена на месте (не выкатывалась): таблица добавлена в неё, снимок пересоздан `drizzle-kit`.
- **Границы нагрузки.** Счётчик месяца ≤ 1 000 000 000, число устройств ≤ 1 000 000 (это же в границах `integer`), месяц отчёта — в окне `[generatedAt − 36 мес., generatedAt + 1 мес.]`; иное — `payload_invalid` с записью в аудите. Сумма по хостам в статистике насыщается на 2^53 − 1 и проверяется отдельной схемой (`standaloneUsageTotalsSchema`), а не схемой одного хоста.
