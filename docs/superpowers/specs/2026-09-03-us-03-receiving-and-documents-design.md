## Problem

Receiving is the first critical tracking event of the P0 chain and the first slice that needs an event record with a regulated lifecycle: draft, finalized, amended, void. Transformation (US-04) and Shipping (US-05) need the same lifecycle, revision chain, snapshot discipline, actor and audit semantics, and the same "reference document" concept. If each slice invented its own, trace (US-06), export (US-07) and trace requests (US-09) would have to handle three shapes. This spec therefore owns three things: the common event shell `traceability_events`, the reference document tables, and the Receiving CTE itself, including the CSV import contract (interface in P0, implementation in P1).

## Key facts of the codebase

- Tenant conventions: every tenant table has `tenant_id text NOT NULL REFERENCES organization(id)` via a local `tenantId()` helper and a `unique(tenant_id, id)` so other tables can target it with a composite FK (`packages/db/src/schema/disaggregation.ts`, `product-regulatory.ts`, `platform.ts` `counterparties`).
- Draft/apply lifecycle precedent: `disaggregation_documents` (`packages/db/src/schema/disaggregation.ts`) uses `pgEnum("disaggregation_document_status", ["draft","applied","cancelled"])`, a `CHECK ((status = 'applied') = (applied_at IS NOT NULL))`, `applied_at/applied_by_user_id`, a per-tenant counter table `disaggregation_doc_counters` for `DSG-YY-NNNN` numbers, and `disaggregation.service.ts` guards mutations with `SELECT ... FOR UPDATE` plus `assertDraft()` throwing `ConflictException({ code: "not_draft" })`.
- Preview-then-apply precedent: `product_regulatory_proposals` (`product-regulatory.ts`) persists a preview with `status preview|applied|rejected|stale`, `expires_at`, `terminal_reason`, `created_by/applied_by/rejected_by`; `product-regulatory.controller.ts` exposes `POST .../category-change-previews`. `inventories.controller.ts` exposes `GET :id/close-preview` as a blocker dry-run.
- DB-level immutability precedent: migration `packages/db/migrations/0030_saas_catalog_subscriptions.sql` installs `BEFORE UPDATE OR DELETE` triggers (`catalog_item_versions_immutable_published`, `commercial_offers_immutable_published`) that `RAISE EXCEPTION` for published rows.
- Idempotency precedents: `shift_exports` stores `idempotency_key uuid` with `unique(tenant_id, created_by_user_id, idempotency_key)` and `shift-exports.service.ts` maps `23505` on that constraint to "return existing or 409"; `apps/api/src/modules/platform-billing-idempotency.ts` stores operation + payload SHA-256 and rejects reuse with `ConflictException({ code: "idempotency_key_reused" })`; kiosk sync uses `(tenant_id, kiosk_id, device_seq)` (`pickup.ts` `kiosk_order_admissions_tenant_sequence_uq`).
- Audit: the persistent tenant log is `tenant_audit_events` (`packages/db/src/schema/team.ts`: `organization_id, actor_user_id, action, outcome, target_type, target_id, before, after, request_id`); services insert rows inside the mutation transaction (`disaggregation.service.ts`: `action: "disaggregation.document.applied"`, `after: { boxIds }`). `SecurityAuditService` (`apps/api/src/authorization/security-audit.service.ts`) is a structured logger for denials, not a table.
- Attachments: `media_assets` and `organization_logo_assets` (`packages/db/src/schema/media.ts`) keep `object_key, content_type, byte_size, checksum, status staging|active|deleting`; `shift_export_artifacts` keeps `sha256 CHECK ~ '^[0-9a-f]{64}$'` and `object_key`. Uploads go through `ObjectStorageService` (`apps/api/src/modules/storage/object-storage.service.ts`) and `FileInterceptor` + `memoryStorage()` (`products.controller.ts`, `disaggregation.controller.ts`).
- Per-row import reporting: `disaggregation_document_lines` stores `sscc_input`, normalized `sscc`, and a per-line `status` enum (`ok, not_found, not_closed, ...`), computed by `line-validation.ts`; unparseable rows stay visible as their own rows. The CommerceML journal (`integration_events` in `integrations.ts`, `journal.service.ts`) records `grain`, `outcome`, `message`, `details` per row for later reading.
- OpenAPI/DTO: controllers use `ZodValidationPipe` (`apps/api/src/zod.pipe.ts`) and the helpers in `apps/api/src/lib/openapi.ts` (`ApiZodBody`, `ApiZodQuery`, `ApiZodResponse`, `ApiHttpErrors`, `ApiZodValidationError`, `ApiCabinetAuth`). Shared Zod contracts live in `packages/platform-contracts/src/*.ts` and are re-exported from `index.ts`.
- Authorization: `RequirePermissions(...)` + `AuthorizationGuard`, `TenantGuard` (`req.tenantId`), `SubscriptionAccessGuard` with `RequireSubscriptionWrite` (`products.controller.ts`). Capabilities are the `CABINET_CAPABILITY` constant in `packages/domain/src/access/cabinet.ts`; the admin gates navigation and routes with `useCan`/`RequireCapability` (`apps/admin/src/access/context.tsx`, `layout/AppShell.tsx`).
- Admin conventions: pages under `apps/admin/src/pages/<area>/` with `api.ts` (TanStack Query over `apiFetch`, `apps/admin/src/api/client.ts`), `@markiro/ui` components (`PageHeader, Table, StatusChip, Alert, EmptyState, Combobox, DatePicker`), i18n in `apps/admin/src/i18n/{en,ru}.json`; a missing key throws in tests (`i18n/index.ts`).
- Decimal precedent: `numeric(precision, scale)` is used for money (`billing.ts`, `products.unit_price`); no decimal quantity column exists yet.
- Tests: API e2e in `apps/api/test/*.e2e.test.ts` (`describe.skipIf(!ready)`, `signUpAndActivate` from `test/support/auth`); migration runtime tests in `packages/db/test/*-migration.test.ts` use `copyMigrationsThroughIndex` to prove the upgrade path; domain unit tests in `packages/domain/test/*.test.ts`.
- Latest migration is `0111_label_template_scope_and_defaults.sql`; the traceability schema file `packages/db/src/schema/traceability.ts` does not exist yet (US-00 creates it).
- Sibling specs already drafted: US-00 defines the capabilities `traceability.read`, `traceability.receiving.write`, `traceability.shipping.write`, `traceability.qa.manage` (finalize/amend/void) and the `RequireTraceabilityProfile(...)` decorator + `TraceabilityProfileGuard` answering 403 `traceability_profile_required`; US-02 defines `traceability_lots.origin_event_id` as a reserved column whose composite FK to `traceability_events` is added by this slice's migration, `buildProductSnapshot(product, profile)`, `normalizeTlc`, `assertLotTransition` and the closed UOM vocabulary `UOM_CODES_V1`; US-06 expects the shell to carry `event_date` and an `amendment_reason` on amended revisions.

## Design

### Data model

All tables go into `packages/db/src/schema/traceability.ts`, one additive migration `0115_us_03_receiving_events_and_documents.sql` (after US-00 `0112`, US-01 `0113`, US-02 `0114`; renumber at implementation time to the next free number). Names follow data-dictionary §9. Every table has `tenant_id`, `unique(tenant_id, id)`, `created_at/updated_at timestamptz`.

Enums:

- `traceability_event_type`: `receiving`, `transformation`, `shipping`.
- `traceability_event_status`: `draft`, `finalized`, `amended`, `void`.
- `traceability_event_source`: `cabinet`, `csv_import`, `api`, `station` (reserved, REC-008).
- `reference_document_type`: `bol`, `po`, `asn`, `work_order`, `invoice`, `database_record`, `batch_log`, `production_log`, `other`.
- `reference_document_confidentiality` (P1): `public_demo`, `internal`, `confidential`.
- `traceability_lot_link_mode`: `create_on_finalize`, `link_existing`.
- `traceability_import_run_status` (P1): `preview`, `applied`, `rejected`, `expired`.

`traceability_events` (common shell; owned here, reused by US-04/US-05):

On `23505` of the unique above the service reloads by `(tenant_id, created_by_user_id, idempotency_key)` and returns the existing event (200) only when the stored hash equals the hash of the retried body; otherwise 409 `idempotency_key_reused` |

| created_by_user_id, created_at, updated_at  | as elsewhere                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |

Indexes: `(tenant_id, type, status, created_at desc)`, `(tenant_id, type, event_date)`, `(tenant_id, root_event_id, revision)` unique, `(tenant_id, event_number, revision)` unique.

The same migration adds `traceability_lots_origin_event_fk` on `traceability_lots(tenant_id, origin_event_id)` → `traceability_events(tenant_id, id)`, closing the reservation made by US-02.

Immutability guard: trigger `traceability_events_immutable_finalized` (`BEFORE UPDATE OR DELETE`) modeled on `catalog_item_versions_immutable_published`. Once `finalized_at IS NOT NULL` the only permitted updates are `status finalized → amended` together with `superseded_by_event_id`, `status → void` together with the three void columns, and `updated_at`. `DELETE` is always rejected. Subtype and item tables get the same trigger keyed on the parent's `finalized_at` (helper function `traceability_event_is_finalized(tenant_id, event_id)`).

### Domain rules

New module `packages/domain/src/traceability/` (pure, no DB):

- `events/lifecycle.ts`: `TRACEABILITY_EVENT_STATUSES`, `canTransition(from, to, ctx)` with the table draft→finalized, draft→void, finalized→void, finalized→amended (only by finalizing a successor revision), amended and void terminal. `nextRevision(previous)` returns the header copy rules (same `root_event_id`, `event_number`, `revision + 1`, `amendment_reason` required).
- `documents/types.ts`: `REFERENCE_DOCUMENT_TYPES` and `isReferenceDocumentTypeAllowedFor(eventType)`: receiving accepts any type but the P0 export registry expects `asn`, `bol`, `po`, `invoice`, `other`.
- `quantity.ts`: `parseQuantity(string)` → decimal string with at most 3 fraction digits, > 0, no exponent; `isUomCode(value)` delegates to US-02 `UOM_CODES_V1` (OQ-US03-6).
- `receiving/completeness.ts`: `validateReceivingCompleteness(input): CompletenessIssue[]` where `input` is a plain object (header, items, resolved locations, product profiles, linked documents, profile code). Issues carry `{ path, code, severity: "error" | "warning", requirementId }`. Errors: `event_date` (date received) missing; `location` (receive-at) missing or its description invalid per US-01 validator (`business_name, phone, street_or_coordinates, city, state, zip, country`); `previous_source_location` missing or invalid; no items; per item: product missing, product description incomplete per US-02 rules, `tlc` blank, neither `tlc_source_location_id` nor `tlc_source_reference`, exempt without reason, exempt with a TLC source other than the receiving site, quantity/UOM invalid, link mode `link_existing` with a lot whose product or TLC differs; no reference document when profile is `US_FSMA204_PROCESSOR` (REC-006; warning only under `US_GENERIC_LOT_TRACEABILITY`). Warnings: same TLC on two lines with the same source, previous source equals receive-at.
- `receiving/snapshot.ts`: `buildReceivingFinalizationPlan(input)` returns the exact writes (lot creates, snapshots, document snapshots) so the service is a thin transaction and tests compare plans deterministically.
- `imports/receiving-csv.ts` (P1 implementation, contract now): `RECEIVING_CSV_COLUMNS` (`tlc, product, quantity, unit_of_measure, tlc_source, tlc_source_reference, exempt_supplier, exempt_reason, supplier_lot_reference, notes`), `parseReceivingCsv(text, mapping?)` → rows with per-row issues; `product` resolves by GTIN-14, then `products.external_ref`, then exact name; `tlc_source` resolves by the US-01 location code or GLN. Column keys are the receiving keys of the US-07 field registry; until US-07 exists they are declared here and US-07 must adopt them (OQ-US03-9).

### Contracts and API

DTO types are inferred from the schemas and reused by the admin (`apps/admin/src/pages/traceability/receiving/api.ts`).

Finalization transaction (`receiving.service.ts`):

1. `SELECT ... FOR UPDATE` on `traceability_events`; assert `draft`.
2. Load header, items, documents, locations (US-01 repository), product traceability profiles and linked lots (US-02 repository).
3. Run `validateReceivingCompleteness`; any `error` → 409 `event_incomplete`.
4. `buildReceivingFinalizationPlan` → location snapshots (US-01 `buildLocationDescriptionSnapshot`), product snapshots (US-02 `buildProductSnapshot`), lot creates for `create_on_finalize` items via the US-02 lot service in the same transaction (basis `imported` or `exempt_supplier_receipt`, status `active`, `origin_event_id` = this event), document snapshots.
5. Write items (`lot_id`, `product_snapshot`), subtype snapshot, shell (`status`, `finalized_at/by`, `location_snapshot`).
6. If `revision > 1`: previous revision `finalized → amended`, `superseded_by_event_id`, `superseded_at`. Lots linked by the previous revision stay linked; the new revision may change quantities, dates, locations and documents; changing `tlc`/source of a line that already created a lot is rejected in P0 (`409 lot_identity_locked`, OQ-US03-4).
7. Insert `tenant_audit_events`: `actor_user_id = req.userId`, `action = "traceability.receiving.finalized"`, `outcome = "success"`, `target_type = "traceability_event"`, `target_id = event id`, `after = { type: "receiving", eventNumber, revision, previousRevisionId, lotIds, documentIds }`.

Other audit actions with the same target: `traceability.receiving.created`, `.updated`, `.item_added|item_updated|item_removed` (`after.lineNo`), `.documents_replaced`, `.amendment_created` (`after.reason`, `after.previousRevisionId`), `.voided` (`after.reason`, `after.wasFinalized`), `traceability.reference_document.created|updated|archived|attachment_uploaded|attachment_removed`, `traceability.import_run.previewed|applied|rejected` (`after: { fileSha256, rowCount, acceptedCount, rejectedCount }`). Failed finalization writes `outcome = "rejected"` with `after.issueCodes`.

Voiding a finalized receiving does not change lot status automatically; the lot card (US-06) shows "created by a void event" and the readiness dashboard lists it (OQ-US03-5).

### Profile gating and RU_CHZ safety

- Every route under `/traceability/**` is behind the US-00 profile gate; an `RU_CHZ` tenant gets 403 `traceability_profile_required` and no navigation entry (US-00 feature flag `traceability`). Existing routes, tables, enums and migrations are untouched; the migration only creates new objects.
- No U.S. type imports from `chz`, `integrations`/CommerceML or `product-regulatory` modules (INT-004); the receiving product reference is `products.id` plus the US-02 profile, never `chz_product_group_code`.
- Proof: the RU e2e suite runs unchanged; a new test asserts that an `RU_CHZ` tenant cannot list or create receivings and that `/access/me` does not expose the traceability navigation flag.
