# US-04 — Transformation HTTP and unified Events workspace

**Status:** Written specification approved by the owner in conversation on 2026-09-27. The implementation plans are for separate owner review; code, browser behavior and deployment are not yet verified or approved by this status.

**Scope:** The next U.S.-only increment after the internal [Transformation/revision design](2026-09-26-us-04-transformation-current-design.md), [genealogy design](2026-09-26-us-04-revisions-genealogy-design.md), and [server case bridge](2026-09-26-us-04-server-case-bridge-design.md). The [MVP contract](../../us/mvp-contract.md) prevails over historical briefs. The outcome is a usable office workflow for Receiving and Transformation in one Events section, while keeping the existing Receiving editor and HTTP behavior. Shipping, Station, synthetic seed, public deployment, merge, and release are separate work.

## Intended use and success

A U.S. production operator can create and save a Transformation draft from tenant references, see server readiness, and hand it to QA. QA can finalize, amend and void under the existing downstream rules, and can void an incomplete original draft with a reason. A reader can inspect current and historical revisions, output-lot genealogy and the separate case/SSCC links. Receiving and Transformation appear in one correctly paginated Events list with a type filter; the existing Receiving flow remains available from that list and from lot cross-links. English and Spanish users see the same capabilities, values, dates and error recovery.

Success does not imply a live U.S. deployment, physical cases, print/scan verification, regulatory acceptance, or a completed Shipping workflow. The U.S. API remains an explicit allowlist and must not mount RU modules or alter RU release paths.

## Chosen architecture and alternatives

Add one server-owned, read-only Events registry over the shared `traceability_events` shell, while keeping type-specific detail and mutation routes. The browser opens each row through its typed endpoint. This preserves the existing Receiving contract and yields global filtering, ordering and pagination in one consistent database snapshot.

Client-side merging of Receiving and Transformation pages was rejected: a page from each source cannot establish a correct global page, and failure/staleness can silently hide one type. Replacing Receiving with a new generic command API was rejected because it would rewrite a working versioned editor and historical receipts. The common registry is a read model, not a generic CTE command abstraction.

## Server contracts and authorization

- Register `UsTransformationStore` in `UsRuntime` and an explicitly allowlisted `UsTransformationController` in `UsDevelopmentModule`. The controller uses the existing US session guard, Host/Origin/no-store middleware, strict shared Zod request/response contracts, and the runtime's safe database-error boundary. Do not register any RU controller or generic box route.
- `POST /traceability/transformation` creates a draft; `GET /traceability/transformation/:id` reads any tenant-visible revision; `PUT /traceability/transformation/:id` replaces a saved draft. `GET /traceability/transformation/:id/readiness?expectedDraftVersion=N` is a non-mutating current-reference check. `POST /traceability/transformation/:id/finalize`, `/amend` and `/void` expose the internal commands. `GET /traceability/transformation/:id/revisions?limit=N&offset=N` returns a bounded chain with root identity and lifecycle version. `POST /traceability/transformation/genealogy/query` accepts the existing bounded current/pinned request schema and returns the existing bounded result; it is a read despite its structured POST transport. Register this route before any parameterized `:id` route.
- Original draft creation/save require `traceability.transformation.write`. Saving an amendment draft requires both `traceability.transformation.write` and `traceability.qa.manage`, enforced by the internal store for the target revision **before either a new write or an operation-key replay**; a production role cannot edit or replay a QA-started amendment by calling the API directly. Finalize, amend and void require `traceability.qa.manage`; detail, readiness, revisions and genealogy require `traceability.read`. The internal command reloads membership/profile/capability in its transaction before parsing or replaying input. The HTTP layer never accepts tenant, actor, role, output lot ID, case provenance or current-origin claims from the body.
- Reuse the existing strict draft, readiness, record, lifecycle, genealogy and operation-key schemas. Add only HTTP/list/revision contracts missing from the internal boundary. Draft create and replacement may use the same bounded 256 KiB JSON envelope as Receiving; other commands stay at the 16 KiB US default. A newly created route must be included in US OpenAPI and the isolation allowlist/CI ownership tests.
- Command responses remain historical, idempotent receipts. An exact authorized retry with the same operation key and payload returns the stored result; a changed payload conflicts. The UI performs a fresh `GET` after success or an uncertain retry instead of treating the old receipt as current lifecycle state. Stale draft/lifecycle versions, changed readiness digest, incomplete data, locked output identity and downstream blockers preserve their existing distinct error codes and do not partially write.

### Original-draft void

Extend the internal Transformation lifecycle so QA may void a revision-1 draft only when it is the root's pending draft and no current revision exists. The command requires a reason, operation key, current `expectedLifecycleVersion` and exact `expectedDraftVersion`; stale or already-transitioned records conflict. In the same transaction, mark the draft void, record actor/time/reason and exact audit evidence, clear the pending pointer, increment the lifecycle version and persist the idempotent receipt. The event number, draft content and root remain readable as history. No output lots, lot status/source locks, genealogy edges, case links or frozen finalization snapshot are created or changed. A replay rechecks current QA authority and returns the historical receipt; a changed key payload conflicts. A void original draft cannot be reopened or amended. This extends only the existing `transformation.void` command, not a delete or discard operation.

## Unified Events registry

`GET /traceability/events` requires `traceability.read`. Its strict query has `type=all|receiving|transformation` (default `all`), optional lifecycle `status`, `history=current|all` (default `current`), event-number search up to 200 characters, `limit` from 1 to 100 and `offset` from 0 to 100000, matching the Receiving list bounds. No Shipping choice or row is exposed before US-05. The response is a discriminated summary list: shared event ID/root ID, type, number, revision, status, civil `eventDate`, saved event timezone, location identity/display, line/document counts and update time; type-specific summaries distinguish Receiving source from Transformation input/output counts. Current display values may resolve current tenant references for drafts, but finalized labels and identity summaries come from frozen evidence, never silently from a changed master card.

The server filters by tenant and type before paging and orders globally by `(created_at DESC, id DESC)` to match the existing Receiving registry's order. `history=current` includes the current finalized revision and any pending draft; when a root has neither, it includes the last void revision as the explicit ended state. `history=all` includes amended and void history. Status only filters the selected history; it must not make a superseded row appear current. The query runs in one repeatable-read snapshot, excludes full frozen JSON payloads, returns a bounded page without a speculative total, and fails closed on inconsistent matching root/revision evidence. Cross-tenant and wrong-type detail IDs remain undiscoverable.

The existing `GET /traceability/receiving` list, Receiving detail and command routes remain compatible. Lot-to-Receiving links still open the typed Receiving detail; the new list does not replace that record or its CSV import/export routes.

## Office workspace and record flow

The US sidebar replaces its standalone Receiving entry with **Events**; `Lots`, `Products`, `Parties` and `Locations` remain. Events starts with the mixed current list, supports type/status/history/search filters and bounded paging, and provides `New Receiving` and `New Transformation` according to current capabilities. No disabled Shipping placeholder appears. Each row shows type in text and icon, number/revision, status in text, civil date with event timezone, location and bounded line/document summary. Loading, empty, filtered-empty, denied, retry, stale data and uncertain mutation states are explicit.

Opening a Receiving row uses the existing Receiving editor/detail/amendment components and preserves its unsaved-change, access-recovery, CSV, lot cross-link and version-conflict behavior. The Events shell composes the existing Receiving record components without rewriting their record logic. Opening a Transformation row loads the typed current/historical record. Its draft editor uses `@markiro/ui` and existing US tokens: event date/timezone, processor location, reason, FTL lot and documented non-FTL input rows, output product/TLC/quantity/UOM rows, reference documents, and a server-derived readiness panel. Product coverage determines input classification; a UI toggle cannot override it. The processor location is visibly the TLC source of every output. No shift selector, scanner, print affordance or client-created output lot ID appears.

The editor saves full replacements with the captured draft version. Readiness is checked only against a saved version; any local edit invalidates the displayed digest. The confirmation restates input/output quantities by unit, document count and lot consequences, but never promises case links or physical production. Only QA can finalize, amend or void. The original-draft void dialog requires a reason and states that no lot has been created; it does not say “delete” or imply case effects. Amendment opens a new revision with a visible predecessor and immutable output lot ID/product/TLC/processor source; changed inputs and quantities are reviewed against downstream blockers. Historical detail reads frozen values, shows revision/audit/void context and distinguishes current from superseded evidence. An unknown or changed response does not replace a displayed record. Keyboard focus, confirmation focus return and non-color status labels follow the Receiving pattern.

Finalized Transformation detail and its output-lot entry show Cases through the existing bridge: active count, SSCC rows, synthetic-demo versus existing-record provenance, and audited history. Authorized production/QA users may manually link eligible existing or synthetic cases and unlink an exact active link with a reason; readers/auditors have no mutation controls. A current-origin gap after void is explicit, existing links remain visible, new links are unavailable, and unlink remains possible. Event quantity `100 case` and active link count `100` are never inferred from one another. The genealogy view uses the current/pinned server result, retains incomplete/cycle/origin-gap diagnostics, and offers a textual equivalent to the visual preview.

All user-visible copy is complete in `en-US` and `es-US`; identifiers, decimal quantities, UOMs, TLCs and stored civil dates do not change on locale switch. At 1024 px, line tables and amendment comparison remain usable without truncating identifiers beyond recognition. Fluent review of Spanish safety/regulatory wording and real browser accessibility remain separate acceptance checks.

## Error and recovery contract

Input shape/oversize is rejected before the command; missing or foreign records are not found without tenant disclosure; authorization changes fail closed. A 409 carries a stable safe code and, when applicable, typed readiness issues or bounded downstream blockers. The UI renders these in the affected group and requires a fresh record/readiness check before another finalize. It does not retry a changed command under an old operation key. Infrastructure failure is unavailable, not an empty Events page or partial success.

The browser retains the exact operation key and canonical payload while a mutation is uncertain and offers a same-intent retry/reload path; it does not claim unsaved edits survived a tab close or reauthentication. Navigation away from a dirty editor prompts before discarding local changes. No UI action silently creates synthetic boxes, links cases on finalization, clears lot holds, or rewrites a historical snapshot.
