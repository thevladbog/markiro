## Problem

After US-03…US-05 the tenant holds lots, three kinds of finalized events and directed genealogy edges, but no way to answer the questions a recall or a mock trace request asks: "where did this output lot come from", "where did this input lot go", "which lot carries TLC X / reference BOL-0916-H / SSCC …", and "what is still missing before we can respond". The tabletop findings in `docs/us/regulatory-basis.md` say TLC/TLC-source linkage across CTEs is the weakest KDE in practice, so the slice must also surface cross-event inconsistencies, not only per-form validation. Everything here is read-only over data owned by earlier slices; the value is one query service whose result feeds the graph, the table, the lot card panels, the readiness dashboard, the US-07 validation tab and the US-09 dry-run.

## Design

### Data model

US-06 introduces no core entity. It reads `traceability_lots`, `lot_genealogy_edges`, `traceability_events`, `receiving_events(+items)`, `transformation_events(+input/output lots)`, `shipping_events(+items)`, `reference_documents`, `traceability_event_documents`, `trace_lot_boxes`, `traceability_locations`, `traceability_parties` and `product_traceability_profiles` by their `docs/us/data-dictionary.md` names. Assumptions beyond what US-02/US-03 already fix: every receiving/shipping item and every transformation input/output row references `lot_id` (REG-006) and stores product and location snapshots; "current revision" of an event = the row in a `root_event_id` chain whose status is `finalized` or `amended` and whose `superseded_by_event_id` is null (data-dictionary §6); `trace_lot_boxes(tenant_id, lot_id, box_id, unlinked_at, link_source)` with a partial unique `(tenant_id, box_id) WHERE unlinked_at IS NULL` (US-04); edges of superseded transformation revisions are kept and the trace filters them by the event's status (US-04 OQ-US04-7); `date_shipped` is the shell's `event_date` (US-05), which this spec assumes for all three CTEs.

Additive migration owned by US-06 (indexes only, `packages/db/migrations/NNNN_traceability_search_indexes.sql`, numbered at implementation time), created only for indexes the owning slices did not already ship:

| Index                                                                | Purpose                                                  |
| -------------------------------------------------------------------- | -------------------------------------------------------- |
| `reference_documents (tenant_id, number)`                            | reference-number search (unless US-03 OQ-US03-8 adds it) |
| `traceability_event_documents (tenant_id, document_number_snapshot)` | search by the number as it stood at finalization         |
| `traceability_events (tenant_id, type, event_date)`                  | date range + CTE filter; column placement per OQ-US06-12 |

P1 (TRC-007) table `traceability_partner_expectations` — one row per party: `id uuid pk`, `tenant_id`, `party_id` (composite FK `(tenant_id, party_id) → traceability_parties`), `direction pgEnum inbound|outbound`, `data_channel pgEnum manual|csv|edi|api_other`, `requires_case_scan boolean not null default false`, `extra_fields jsonb` (buyer-specific extras as a list of `{ key, label, required }`), `notes text`, `created_at/updated_at`. It never adds to the FTR minimum set: the readiness sweep reports its extras under a separate `partner` severity group. Deferred if the schedule compresses (OQ-US06-8).

### Domain rules

All in `packages/domain/src/traceability/`, pure and framework-free:

- `trace/graph.ts` — `traverseGenealogy(edges, rootLotId, direction, { maxDepth })` builds on US-02's `ancestorsOf`/`descendantsOf` and adds per-node depth, a depth bound (default 16, hard cap 64) and a `truncated` flag; a visited set makes cycles harmless even if a bad edge slipped past US-02's service check. Both directions share the code by swapping `from/to`. Diamonds (one input reaching the same output through two transformations) yield one node and two edges.
- `trace/result.ts` — the single result shape used by graph, table, lot card, US-07 and US-09:

```ts
interface TraceResult {
  root: { lotId: string };
  direction: "backward" | "forward" | "both";
  nodes: TraceNode[]; // kind: "lot" | "location"; lots carry TLC, source, status, product snapshot
  edges: TraceEdge[]; // kind: "received_from" | "genealogy" | "shipped_to"; quantity + UOM
  events: TraceEventRef[]; // id, eventNumber, type, status, revision, eventDate, locationId
  excluded: { eventId: string; revision: number; reason: "void" | "draft" | "superseded" }[];
  provenance: { generatedAt: string; depthReached: number; truncated: boolean };
}
```

Every edge and every node carries `provenance: { eventId, eventRevision, sourceTable, sourceRowId }` (TRC-009). The table view is exactly `edges` (one row per edge); the graph view is `nodes` + `edges`; counts therefore match by construction (TRC-004).

- `completeness/rules.ts` — `runReadinessSweep(input): CompletenessFinding[]` composes the per-CTE KDE validators owned by US-03…US-05 (imported by name from `packages/domain/src/traceability/receiving|transformation|shipping`) and US-02's `assertLotFinalizable`/`validateCoverageReview`, and adds cross-record rules owned here: `LOT_NO_EVENTS`, `OUTPUT_LOT_NO_GENEALOGY`, `EVENT_LOT_LINK_BROKEN` (REG-006), `LOCATION_SNAPSHOT_INCOMPLETE`, `QUANTITY_MISSING_OR_ZERO` (NFR-009), `REFERENCE_DOCUMENT_MISSING`, `TLC_SOURCE_MISMATCH` (TRC-006) and, for P1, `PARTNER_EXTRA_MISSING`. A finding is `{ code, severity: "error" | "warning" | "info", cte: "receiving" | "transformation" | "shipping" | "lot" | "product" | "partner", field, message, provenance, lotId?, productId?, partyId?, eventId?, eventRevision? }`.
- `completeness/tlc-source-consistency.ts` (TRC-006) — for each lot collect the `(source_location_id | source_reference)` pair from the lot row and from every current-revision event row that references it; more than one distinct pair is an `error` unless the later value comes from a revision > 1 (US-03 guarantees `amendment_reason` is set), in which case it degrades to `info` with the amendment cited. A `void` revision never contributes.
- `completeness/score.ts` — `readinessScore(findings, checksRun)` returns `{ checksRun, errors, warnings, infos, ratio, state }` where `ratio = 1 - errors / checksRun` and `state = "scored"`; when `checksRun = 0` (empty tenant, or a `from/to`/`productId`/`lotId` scope with no records) it returns the stable `{ checksRun: 0, errors: 0, warnings: 0, infos: 0, ratio: null, state: "no_data" }` instead of a `NaN` ratio, and the UI shows the empty state rather than a percentage. The UI shows it as "Data readiness" and lists the missing fields (TRC-010); the word "compliance" never appears in the label or the i18n key.
- `search/normalize.ts` — keeps TLC opaque (LOT-002, reuses US-02 `normalizeTlc`), strips the GS1 `(00)` prefix from SSCC via `parseScannedSscc` (`packages/domain/src/gs1/sscc.ts`), classifies a free-text `q` as `lot_uuid | sscc | tlc | reference | text` (mirrors `input-classifier.ts`).

Behavior:

- `TraceQueryService.trace(tenantId, lotId, opts)` runs one recursive CTE per direction (raw `sql` in Drizzle, `WITH RECURSIVE walk(lot_id, depth, path) … WHERE tenant_id = $1 AND depth < $maxDepth AND NOT (next_lot_id = ANY(path))`), then batch-loads lots, edges, current-revision event rows, locations and snapshots for the collected ids in ≤ 6 queries, and assembles the `TraceResult` through the domain builder. Void events go to `excluded` with reason `void`, superseded revisions with reason `superseded`; drafts go to `excluded` with reason `draft` unless `includeDrafts=true` (UI default off; export-ready views never include them). Unknown or cross-tenant `lotId` → 404, the same way `getBoxCard` does.
- `LotSearchHit` = `{ lot: LotSummary, product: ProductSnapshotSummary, matchedBy: ("tlc" | "reference" | "sscc" | "product" | "location" | "date" | "lot_id")[], chain: { receiving: number; transformation: number; shipping: number; firstEventDate; lastEventDate }, ssccLinks?: { boxId, sscc, linkActive: boolean, linkedAt, unlinkedAt: string | null }[], provenance }`. `ssccLinks` is present only on hits with `matchedBy` containing `sscc` and lists every `trace_lot_boxes` row between the matched box and this lot, current and historical (`linkActive = unlinked_at IS NULL`), per OQ-US06-11 (b). `q` is classified server-side; an exact TLC/reference/SSCC hit is answered from an index-backed equality query (<1 s target). `tlcFrom/tlcTo` is a lexicographic (`COLLATE "C"`) range on the opaque TLC string; the UI labels it "TLC range (text order)" (OQ-US06-3). US-02's `GET /traceability/lots` stays the plain lots list; `/traceability/search` is the cross-entity query.
- `appliedFilters` echoes the normalized filters so US-09 can prefill a trace request scope from a search (TRC-008 acceptance); the "Create trace request" button (capability `traceability.qa.manage`) navigates to the US-09 wizard with the scope in router state, no new endpoint.
- Lot card read model (`GET /traceability/lots/:id/card`): `{ timeline: CteTimelineEntry[], documents: ReferenceDocumentRef[], boxes: { boxId, sscc }[], findings: CompletenessFinding[], genealogy: { inputs, outputs } }`. Timeline entries are ordered by `eventDate, eventType, eventNumber`, each with status, revision and provenance; amended chains show superseded revisions collapsed under the current one. Product snapshot, TLC/source and status stay in US-02's `GET /traceability/lots/:id` (OQ-US06-7).
- Readiness sweep loads the tenant's lots and current-revision events (bounded by the optional date window; default last 24 months, matching REG-009's floor) and runs `runReadinessSweep`. No persistence; US-09 stores its own dry-run snapshot when it freezes a request.
- Errors: domain codes surface as `BadRequestException({ code })` for malformed filters, `NotFoundException` for unknown ids; the recursive CTE has a statement timeout of 5 s and returns `truncated: true` plus HTTP 200 when the depth cap is hit, never a partial 500.
- Audit: reads write no `tenant_audit_events` rows (consistent with code-search and dashboard). Only the P1 PUT writes audit.
- NFR-015: search responses never include full document attachments; logs record filter names and counts, not TLC lists.

### Admin UI

Pages under `apps/admin/src/pages/traceability/` with hooks in `api.ts` (`TRACEABILITY_QUERY_KEY = ["traceability"]`), routes in `apps/admin/src/app.tsx` wrapped in `RequireCapability` + `ProfileOnly`, nav items under `shell.sections.traceability`:

- `/traceability/search` — `TraceSearchPage`: exact lookup box on top (TLC / reference / SSCC / lot id, `mono`), filter row (`Combobox` product, `DatePicker` from/to, `Select` CTE, `Combobox` location, `Input` reference number, `Input` TLC list), results `Table` with columns TLC, product, source, status (`StatusChip` with text label), receiving/transformation/shipping counts, last event; row click opens the lot card; an SSCC hit adds a text label per link — "Current link" or "Previous link, unlinked <date>" (`pages.traceability.search.ssccLink.{active,inactive}`), never color alone — so a lot the box was moved away from is visibly historical; "Create trace request from results" button (visible with `traceability.qa.manage`). Empty state `pages.traceability.search.empty`; 404 codes map to `pages.traceability.search.errors.{unrecognized,notFound}`.
- Lot card `/traceability/lots/:lotId` (page owned by US-02): US-06 adds three panels fed by `useLotCard(lotId)` — CTE timeline reusing the `CodeCard.tsx` left-border list pattern with links to the US-03…US-05 event pages, reference documents (type, number snapshot, link), linked boxes, and a findings list with field names — plus "Trace backward" / "Trace forward" buttons.
- `/traceability/lots/:lotId/trace` — `TraceGraphPage`: `DataTabs` "Graph | Table" over one `useTraceGraph(lotId, direction, depth)` query. Graph = deterministic layered SVG (`TraceGraphSvg.tsx`): layers by BFS depth from the root, nodes ordered by TLC within a layer, straight edges with quantity labels, node shapes distinguished by outline and an icon glyph, never by color alone; `role="img"` with an `aria-label` summarizing node/edge counts and a visually hidden `<ul>` of nodes for screen readers; the Table tab is the accessible full representation. Both tabs show the same counts in a `MetricStrip` (`nodes`, `edges`, `excluded`). No new dependency (OQ-US06-1).
- `/traceability/readiness` — `ReadinessPage`: `MetricStrip` with the score labeled `pages.traceability.readiness.scoreLabel` = "Data readiness" and a hint "Explanatory only, not a compliance score" (TRC-010), `Select` group-by, grouped `Table` (severity chip with text, CTE, product, partner, field, message, link to record). Empty state when there are no lots ("Nothing to check yet"); an `Alert tone="info"` explains that coverage status remains a manual review (REG-011).
- i18n keys under `pages.traceability.{search,trace,readiness,lotCard}.*` and `nav.traceabilitySearch|traceabilityReadiness` in both `en.json` and `ru.json`; U.S. profile UI runs in English, RU strings exist only to satisfy the missing-key test.
- Accessibility (NFR-012): all filters are labeled controls, the graph is keyboard-reachable through the node list, focus styles come from `@markiro/ui`, statuses always pair a chip with text.

### Profile gating and RU_CHZ safety

- Server: every controller in `apps/api/src/modules/traceability/trace/` carries `RequireTraceabilityProfile("US_FSMA204_PROCESSOR", "US_GENERIC_LOT_TRACEABILITY")`; an `RU_CHZ` tenant gets 403 `traceability_profile_required` (US-00), and the module is registered only inside `TraceabilityModule`.
- Admin: routes and nav items render only when `/access/me.traceabilityProfile.features.traceability` is set and the user has `traceability.read`; `RU_CHZ` tenants see no change in `NAV_ITEMS`, `/codes` or the dashboard. Nothing in `apps/admin/src/pages/code-search/` or `apps/api/src/modules/code-search/` is modified.
- `US_GENERIC_LOT_TRACEABILITY`: the same pages run, but the readiness page and lot card panels show the Scenario B banner ("not classified as FTR-covered; general lot traceability") and the findings use generic labels ("lot source" instead of "TLC source"); FTL-specific rules (US-02 `validateCoverageReview`) are skipped, as US-02 already does for that profile (OQ-US06-6).
- Proof: the existing `apps/api/test/code-search.e2e.test.ts`, `apps/admin/test/code-search.test.tsx` and the full RU suite stay untouched and green; a new test asserts that an `RU_CHZ` tenant receives 403 on every US-06 route and that `authorization-metadata.test.ts` sees the new controller.

## Testing

- Domain (`packages/domain/test/traceability-trace.test.ts`, `…-completeness.test.ts`): traversal on chain, diamond, cycle (A→B→A injected in memory), depth cap and truncation flag, direction symmetry; readiness sweep on the seed shape (2 inputs → 1 output → 1 shipment) returns zero errors; each rule has a positive and a negative case; TLC-source mismatch with and without an amendment; score arithmetic including `checksRun = 0` → `ratio: null`, `state: "no_data"` (empty tenant and a filtered scope with no records); input classifier for TLC/reference/SSCC (`(00)` prefix and 18/20-digit forms).
