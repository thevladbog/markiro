# Product Images End-to-End Design

**Date:** 2026-08-13

**Status:** Approved in chat for specification

**Scope:** One primary product image from the tenant admin catalog through the API and private
object storage to persistent offline display in the station and kiosk applications.

## 1. Goal

An administrator can add, replace, and remove one primary photograph for a product. The admin,
station, and kiosk show that photograph when available. A station or kiosk that has downloaded an
image keeps showing it across restart and network loss.

Images are optional presentation data. Upload, object-storage, download, decode, cache, or cleanup
failures must not block product creation, catalog refresh, station work, scans, shift recovery,
kiosk pairing, or pickup orders.

The existing design brief already requires a photo on the product card. Earlier profile and kiosk
designs deliberately deferred product-image schema, API, device caching, and display. This design
closes that deferred end-to-end slice rather than adding an admin-only URL that devices cannot use
offline.

## 2. Product decisions

- A product has zero or one active image. There is no gallery, ordering, or primary-image picker.
- The image is tenant-owned and product-scoped, not owned by the user who uploaded it.
- Source JPEG, PNG, and WebP files are accepted up to 5 MiB.
- The server normalizes every accepted source into a single non-animated WebP while preserving its
  aspect ratio. It auto-orients, strips metadata, never upscales, and caps the longest edge at 1200
  pixels.
- The image is private. The system never stores a permanent public URL in PostgreSQL, SQLite, or
  IndexedDB.
- Product DTOs carry a small immutable image descriptor, not image bytes or a signed URL.
- Devices download a normalized image only when its checksum changes and persist the bytes locally.
- A new image becomes visible on a device only after its bytes are durable locally. An interrupted
  replacement therefore leaves the previous cached image visible.
- An explicit server-side deletion publishes `image: null`; devices then remove the local pointer
  and best-effort-delete unreferenced bytes.
- Missing images use the current text/monogram layout. There is no blocking error state.

## 3. Out of scope

- Multiple product images, custom ordering, captions, and custom alt text.
- Images inside printed label templates or server-side print generation.
- CommerceML image import or export.
- Public CDN delivery or anonymous object access.
- Station or kiosk editing and upload.
- Image-based product recognition.

The accessible alternative text is the current product name, so a separate mutable alt-text field
is unnecessary for this single operational product photograph.

## 4. Data model and ownership

### 4.1 Generalized media ownership

`media_assets` currently requires `owner_user_id`, which is correct for a global profile avatar but
wrong for a tenant product: deleting the uploader must not delete the organization's product
image. A migration will:

1. add nullable `owner_tenant_id`, referencing the tenant table with cascade-on-tenant-delete;
2. make `owner_user_id` nullable;
3. add a check requiring exactly one of `owner_user_id` and `owner_tenant_id`;
4. retain the existing user-owner uniqueness needed by `user_profiles`;
5. add uniqueness on `(owner_tenant_id, id)` for tenant-owned aggregate references.

Existing avatar rows remain user-owned without data rewriting. The migration must review and test
the existing avatar composite foreign key before changing nullability.

### 4.2 Product image aggregate

A new `product_images` table contains:

- `tenant_id`;
- `product_id`;
- `asset_id`;
- `created_at` and `updated_at`.

`(tenant_id, product_id)` is the primary key, enforcing zero or one current image per product. A
composite foreign key to `products(tenant_id, id)` enforces same-tenant product ownership and
cascades on product deletion. A composite foreign key from `(tenant_id, asset_id)` to
`media_assets(owner_tenant_id, id)` prevents a foreign tenant's asset from being attached. An asset
can be referenced by at most one product image.

The normalized object key is generated by the server:

```text
tenants/{tenantId}/products/{productId}/{assetId}.webp
```

Client filenames never enter keys or persisted metadata.

### 4.3 Descriptor contract

The shared structural contract is:

```ts
interface ProductImageDescriptor {
  checksum: string; // SHA-256 lowercase hex of normalized WebP bytes
  contentType: "image/webp";
  byteSize: number;
  width: number;
  height: number;
}
```

Product responses use `image?: ProductImageDescriptor | null`. The field is optional for old
persisted device payloads and rolling deployments; current servers always emit the field. Clients
treat an absent field as unknown legacy state: they retain any published local pointer and schedule
no image deletion or replacement. Explicit `null` is the only no-server-image tombstone and clears
the local pointer. This distinction prevents a temporary rollback to an old server from deleting a
new client's usable offline image.

The checksum is the immutable content version and local cache key. Asset IDs and storage keys are
never exposed to cabinet or device clients.

## 5. Image validation and normalization

The implementation extracts a reusable bounded image-processing boundary from the established
avatar path without changing avatar output semantics. Product processing applies these rules:

- accept at most 5 MiB of source bytes before decode;
- inspect actual decoder metadata rather than trusting filename or request MIME;
- accept JPEG, PNG, and WebP only;
- reject animation or multiple pages;
- reject either source dimension above 8192 pixels or more than 25 million source pixels;
- apply EXIF orientation and remove all source metadata;
- resize to fit within 1200 by 1200 pixels without cropping or upscaling;
- encode deterministic WebP with the repository-selected fixed quality;
- compute SHA-256, output byte size, width, and height from the normalized result;
- retain the existing bounded worker, memory budget, timeout, and process-wide concurrency
  protections used by avatar decoding.

A malformed or resource-exhausting image produces a precise 400 response. Decoder timeout or
worker/infrastructure failure produces a retryable service failure and does not alter the current
image.

## 6. Server lifecycle and recovery

### 6.1 Upload or replacement

For `POST /products/:id/image` the server:

1. authorizes tenant membership, subscription write access, and operations-write capability;
2. resolves the product by `(tenantId, productId)` before processing or storage;
3. normalizes the source outside a database transaction;
4. inserts a tenant-owned `media_assets` row in `staging` state and commits it;
5. uploads the normalized object;
6. in one transaction, locks/re-reads the product image, marks the new asset `active`, points
   `product_images` to it, and marks the previous asset `deleting`;
7. emits an exact `product.image.uploaded` or `product.image.replaced` audit record;
8. attempts old-object deletion after the committed switch.

If steps 3 through 5 fail, the current product image is unchanged and the durable staging row is
available to the reconciler. If the switch transaction fails, the old image remains current. If
the process dies after the switch, the new image is already authoritative and the old deleting
asset is retryable.

Concurrent uploads serialize at the product-image switch. The later committed switch wins; every
losing or replaced object is left in a recoverable deleting state, never as an untracked orphan.

### 6.2 Delete

`DELETE /products/:id/image` clears the aggregate reference and marks the current asset `deleting`
in one transaction, records `product.image.deleted`, returns 204, and performs best-effort object
cleanup afterwards. Deleting a product follows the same recoverable media cleanup path rather than
depending only on a cascading metadata delete that could orphan object bytes.

Deleting a product with no image is idempotent and returns 204. Product deletion explicitly marks
the referenced asset `deleting` in the same transaction before the aggregate row cascades away, so
the object cannot be orphaned by a metadata-only cascade. Uploading to an unknown or foreign-tenant
product returns 404 without revealing which case applied.

### 6.3 Reconciliation

The profile-only asset reconciler becomes an aggregate-aware media reconciler. It handles stale
`staging` and `deleting` rows for both avatars and product images, checks references in
`user_profiles` and `product_images`, claims work conditionally, deletes object bytes idempotently,
and then deletes metadata only when the asset is not referenced.

An active referenced asset is never removed. Reconciliation is bounded per pass and safe with
multiple API/job instances.

## 7. HTTP contracts and authorization

### 7.1 Cabinet routes

- `POST /products/:id/image` — multipart field `image`; returns the updated product DTO.
- `DELETE /products/:id/image` — idempotent 204.
- `GET /products/:id/image/:checksum` — authorized immutable WebP read for the current checksum.

Cabinet reads require operations-read. Mutations require operations-write and subscription write
access. The current product list and detail DTOs include the descriptor.

### 7.2 Kiosk route

- `GET /kiosk/products/:id/image/:checksum`

The paired kiosk guard supplies tenant and kiosk identity. The server verifies that the kiosk is
active, the product belongs to the same tenant, the product is in that kiosk's current allowlist,
and the checksum is current. A removed allowlist entry or stale checksum is denied without object
metadata disclosure.

`KioskBootstrapDto.products[]` gains the optional nullable image descriptor. The bootstrap remains
JSON-only; it does not contain image bytes or signed URLs.

### 7.3 Station route

- `GET /station/products/:id/image/:checksum`

The station device guard supplies tenant and device identity. The server verifies an active paired
station and same-tenant product. The shift list exposes product image metadata for its rows, and
the existing shift bundle's `product` DTO carries the same descriptor.

### 7.4 Binary response behavior

The API may stream the object or redirect to a short-lived private object-store read after all
authorization checks. Clients follow the response and persist the received bytes; they never
persist the temporary URL. Responses set the WebP content type, checksum ETag, bounded content
length, and private cache policy. A stale checksum returns 404 across all three trust domains so it
does not disclose whether another version exists.

Device media downloads use a separate raw-byte client path with the same bounded network deadline
and abort behavior as other device reads. JSON helpers are not cast over binary responses.

## 8. Admin catalog experience

The basic section of `ProductForm` gains a photograph control with a fixed preview area:

- empty state with accepted formats and 5 MiB limit;
- file picker labelled for keyboard and assistive technology;
- local preview before submit;
- replace and remove actions in edit mode;
- pending state that prevents duplicate image mutation but does not discard text fields;
- a specific error that states the current server image was preserved.

For an existing product, upload and delete are explicit image mutations. For a new product, the
selected file is staged only in component memory. Submit creates the product first and then uploads
the file. If image upload fails, the product remains created, the panel switches to edit mode, the
file selection and other values remain visible, and the user can retry without creating a duplicate
product. The catalog query is refreshed after each committed product or image change.

The catalog list shows a small thumbnail where the layout permits. The editor always shows the
larger preview. Image fetch failure uses the empty placeholder and does not turn the entire product
query into an error.

## 9. Kiosk offline image cache and display

The bootstrap snapshot continues to be replaced atomically for operational data. Image bytes are
stored separately in IndexedDB so one unavailable object cannot prevent a fresh roster, limit,
reason list, subscription snapshot, or product allowlist from publishing.

The kiosk adds two stores:

- immutable WebP blobs keyed by checksum;
- published product pointers keyed by product ID and containing checksum.

After a successful bootstrap publish, a bounded-concurrency media sync:

1. compares each allowed product descriptor with its published local pointer;
2. downloads only missing checksums;
3. validates response content type, byte length, and SHA-256 before accepting bytes;
4. stores the blob first and publishes the product pointer second;
5. keeps the previous pointer if download, validation, or IndexedDB write fails;
6. clears the pointer immediately for `image: null` and best-effort-removes unreferenced blobs;
7. removes pointers for products no longer in the kiosk allowlist.

The cart row replaces the current letter monogram with a 56-pixel product image when the published
blob is available. It uses `object-fit: cover`, the product name as alt text, and revokes generated
object URLs on replacement/unmount. The existing monogram remains the fallback.

Pairing redemption triggers the same background media sync after the operational snapshot is
durable. Startup renders cached images before network refresh. An image sync failure is logged and
may expose a non-blocking diagnostic in setup, but never changes kiosk reachability or order flow.

Unpairing, revoked-device recovery, and tenant identity replacement clear image pointers and blobs
together with other device-private cached data so images cannot cross pairing boundaries.

## 10. Station offline image cache and display

The station stores descriptor columns alongside its product/shift mirror records and stores WebP
blobs separately in a persistent browser Cache Storage namespace. Cache keys contain the product ID
and checksum; server URLs and credentials are not persisted.

Both shift-list refresh and shift-bundle download schedule bounded media downloads. Operational
shift and bundle mirroring remains independent and completes even if the image fails. For each
image update the station writes and verifies the WebP response first, then publishes the new local
pointer in SQLite. A failed replacement leaves the previous pointer and bytes usable.

The shift selection card shows a product thumbnail when locally available. The active work screen
shows a larger product image next to the product identity in the primary scan-result instrument.
Both retain their current text-only layout when the image is absent or cannot be decoded. Image
layout must preserve the fixed viewport and large floor controls at 1280 by 800 without introducing
scrolling.

Credential sealing, station revocation, recovery pairing, or tenant identity replacement clears
SQLite image pointers and the Cache Storage namespace after waiting for in-flight bundle/media
writes. It does not touch the operational journal unless the existing recovery contract already
requires that action.

The browser implementation remains testable outside Tauri. No CDN, native filesystem path, or
runtime network dependency is added to offline rendering.

## 11. Failure semantics

| Failure                               | Required behavior                                                         |
| ------------------------------------- | ------------------------------------------------------------------------- |
| Invalid or oversized source           | 400; current image and form values remain intact                          |
| Decoder timeout/resource limit        | Retryable error; current image remains active                             |
| Object upload unavailable             | Staging intent remains; current image remains active                      |
| Database switch fails                 | Uploaded staging object is reconciled later; current image remains active |
| Old-object deletion fails             | New image remains active; deleting asset is retried                       |
| Device image endpoint unavailable     | Operational sync succeeds; old image or fallback remains                  |
| Download checksum mismatch            | Reject bytes, retain old pointer, record bounded diagnostic               |
| IndexedDB/Cache Storage quota failure | Retain usable old pointer where possible; never block operation           |
| Corrupt local blob on startup         | Drop that pointer/blob and render fallback; retry when online             |
| Image deleted on server               | Clear device pointer; continue without image                              |
| Product removed from kiosk allowlist  | Remove its pointer and deny future kiosk downloads                        |
| Device re-paired to another tenant    | Scrub all prior image cache before showing the new tenant                 |

## 12. Compatibility and rollout

The database migration deploys before routes emit descriptors. New DTO fields are additive and
optional to readers. Old station and kiosk builds ignore them and continue operating. New builds
accept old API payloads and old IndexedDB/SQLite records without image fields.

Rollout order is:

1. database migration and generalized media reconciliation;
2. API upload/read/delete routes and additive descriptors;
3. admin upload UI;
4. kiosk cache and display;
5. station cache and display.

The single implementation branch may deliver all stages together, but each stage must remain safe
during rolling deployment. Production object storage stays private throughout.

## 13. Test strategy

### Database and API

- migration and schema tests for exactly-one owner and composite tenant foreign keys;
- existing avatar tests proving no regression after ownership generalization;
- processor tests for formats, orientation, dimensions, animation, corrupt bytes, and resource
  bounds;
- upload, replace, idempotent delete, concurrent replace, and product-delete lifecycle tests;
- storage failure and transaction failure tests proving the previous image remains active;
- reconciler tests for stale staging/deleting assets and referenced active assets;
- exact cross-tenant denial for cabinet, station, and kiosk;
- kiosk allowlist denial and stale-checksum denial;
- exact audit actor, tenant, action, product target, result, and image metadata assertions;
- OpenAPI and protected-route inventory updates.

### Admin

- create with staged image;
- product-created/image-failed recovery without duplicate creation;
- edit preview, replace, and delete;
- invalid file and storage error preserve form and current preview;
- keyboard labels, focus, and error association;
- list/detail thumbnail fallback.

### Kiosk

- bootstrap compatibility with absent, null, and populated descriptor;
- download only on checksum change;
- blob-before-pointer publication and old-pointer retention on every failure boundary;
- restart and offline rendering from IndexedDB;
- deletion and allowlist cleanup;
- unpair/re-pair cache scrubbing;
- cart image and monogram fallback without changing scan/order behavior.

### Station

- SQLite migration and old-row compatibility;
- shift-list and bundle metadata mirroring;
- bytes-before-pointer publication and old-pointer retention on failure;
- restart and offline rendering from Cache Storage;
- credential recovery cache scrubbing with in-flight write coordination;
- shift card and 1280 by 800 work-screen image/fallback behavior;
- existing journal, scan, box, print, and recovery tests remain green.

### External acceptance

Automated checks do not establish Windows WebView persistence, storage quota behavior on the target
tablet, or physical-device layout. Final acceptance separately verifies:

- real MinIO/S3 upload and private read behavior;
- kiosk tablet restart followed by offline cart rendering;
- Windows Tauri station restart followed by offline shift/work-screen rendering;
- 1280 by 800 station viewport without scrolling;
- cache scrub after actual device re-pairing.

## 14. Acceptance criteria

1. An authorized administrator can create a product with one photo, replace it, and remove it.
2. A failed replacement never removes the currently active server or device image.
3. Another tenant cannot discover or access the image through any cabinet or device route.
4. A paired kiosk can show allowed product photos after restart with no network and falls back to
   the existing monogram when bytes are unavailable.
5. A paired station can show product photos in shift selection and active work after restart with no
   network and retains the fixed-viewport floor workflow.
6. Image failures never block product catalog data, pairing, shift recovery, scanning, printing,
   pickup limits, or order queueing.
7. Device revocation or re-pairing prevents prior-tenant images from remaining visible.
8. Existing deployed clients and cached payloads without image metadata continue to work.
9. Automated results and real kiosk/Windows acceptance are reported as separate gates.
