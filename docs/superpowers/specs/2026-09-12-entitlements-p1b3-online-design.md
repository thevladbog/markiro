## Результат и границы

Следующая поставка подключает единый расчёт P1 к четырём существующим семействам:
инвентаризация, CommerceML, редактирование шаблонов этикеток, паллетные операции.
Для выполненных онлайн-действий появляется проверяемое shadow-наблюдение:
какие условия P1 разрешили бы или запретили действие и на основании каких фактов.
Сохраняются текущие фактические проверки безопасности, подписки, квот и release/config.
Ошибка наблюдения имеет результат unknown, а не allow, и не отравляет бизнес-транзакцию.

Это часть P1B.3. Полное завершение P1B.3 требует также отдельного пути публичного API.
Старт работы ТСД остаётся P1C по текущему registry, вместе с ограниченными офлайн-допусками.
Включение новых ограничений для клиентов остаётся P1D; периодические услуги — P2.

## Что установлено в текущем коде

- Фасад `EntitlementAdmissionService` уже предоставляет capture/observe/withAdmission,
  повторно проверяет proof и время, сохраняет наблюдение через savepoint. ЧЗ/НК
  используют его в реальных владельцах, остальные семейства отмечены deferred.
- Инвентаризация имеет отдельные создание, импорт доказательств и ready→running.
  Повтор start для running возвращает сохранённый manifest; он не является новым запуском.
- CommerceML использует собственные машинные credentials и exchange session.
  GET выполняет также import/query/success; HTTP-метод не определяет класс действия.
- Паллетные feature-проверки встречаются в create/update/open/enter смены;
  одна проверка на создании не покрывает остальные входы.
- Публичные ключи имеют configId=public и отдельные операции выдачи/отзыва.
  Текущий TenantGuard принимает кабинетную сессию или configId=station.
  Поиск исполняющих публичный ключ путей не выявил отдельного public principal/scope
  guard. Расширение доступа кабинета по наличию x-api-key недопустимо.

## Подключение

Выбран для согласования вариант A: прямое использование существующего фасада.
Общая система hooks или второй resolver не вводятся. Подготовка facts выполняется
непосредственно перед транзакцией; наблюдение — после действующих проверок и
определения реального действия, до соответствующей записи/нового внешнего эффекта.
Существующие порядок блокировок, isolation, leases, курсоры и идемпотентность сохраняются.
В открытой транзакции не захватывается второе подключение к пулу.

Actor определяется только проверенной серверной границей. Cabinet сохраняет user ID.
Для CommerceML внутренний actor получает отдельный domain `exchange_session` и ID
подтверждённой сессии. Это не api_key и не системный пользователь; автоматически
добавлять publicApi к CommerceML нельзя. Необходимые типы и проверки persistence
обновляются вместе, без записи credentials в observation.

Область наблюдения содержит digest серверных идентификаторов и канонической команды,
а не сырой файл, штрихкоды, credentials или произвольный клиентский scope.
Runtime берётся из действующих проверенных условий конкретного владельца.
Устаревшие facts и неизвестная готовность остаются явно unknown.

## Классификация четырёх семейств

### Инвентаризация

Подключить создание задачи и фактический первый старт отдельно; определить создание
новой версии входных данных после существующих проверок idempotent replay/fence.
Файл клиента требует inventory; новая заявка выгрузки ЧЗ требует inventory+chzIntegration
и использует уже существующего владельца экспорта. Сохранённый результат повторной
команды, ранее авторизованные события и чтение manifest не превращаются в new_work.

Существующий ID `inventory.file.create.v1` не переименовывается и не переиспользуется
для произвольного запуска. Для отличающихся действий вводятся явные версии операций
`inventory.task.create.v1` и `inventory.task.start.v1` с inventory и прежней cabinet
capability. Источники с ограниченным списком операций не получают новые ID автоматически.
Добавление ID означает только классификацию shadow, а не новое право реальному клиенту.

### CommerceML

Разделить новый import/apply, формирование новой экспортной партии и продолжение
известного обмена/подтверждение ранее предложенной партии. Проверки размещаются по
существующим границам cursor/fingerprint/batch, а не вокруг каждого GET или каждой
части файла. Вход без проверенной сессии не создаёт tenant-наблюдение.
`commerceMl.exchange.v1` используется только для новой работы; продолжение и чтение
явно описываются в inventory отдельно. Поддерживаемый коннектор не требует publicApi.

### Шаблоны этикеток

Наблюдать создание, редактирование и иные действующие операции изменения шаблона
через labelEditor.template.write.v1 у владельца записи. Печать/получение сохранённого
шаблона, регенерация из исторического снимка и производственные байты не становятся
редактированием. Учесть merged #548: выбор tenant default — отдельное действие;
его классификация определяется текущими policy и фактическим эффектом, а не названием поля.

### Паллетные операции

Покрыть все существующие входы, требующие pallets, по фактическому переходу состояния.
Сохранить различие конфигурации, начала работы и продолжения текущей смены; обычная
коробочная агрегация не получает зависимость от pallets. Исторические факты и
сохранённые шаблоны не пересчитываются. ID конфигурации не используется для приёма событий.

## Доказательство покрытия

Перед изменением владельцев составить исчерпывающий inventory маршрутов, сервисных
и фоновых входов четырёх семейств, с точкой эффекта, trust domain, действующей policy,
классом операции и регрессионным тестом. Для изменившегося смысла используется новый
versioned ID, а не молчаливое расширение старого. Registry coverage повышается только
после реального подключения всех заявленных входов; classified/deferred остаются явными.

AST inventory дополняется исполняемыми тестами DI и наблюдения настоящей операции.
Проверить: чужой tenant и credential; прежний отказ security/subscription/quota;
точные actor/operation/tenant/scope/revision; shadow deny и unknown при сохранённом
действующем допуске; ошибка записи через savepoint; stale facts после ожидания;
повтор/неоднозначный ответ; неизменность cursor, fence, manifest и исторических байтов.

Минимальные gates: contracts/DB при их изменении, focused и полный API, typecheck,
lint, build, format и diff; соответствующие клиентские/нативные проверки при реальном
изменении их контрактов. Живые 1C/ЧЗ и аппаратные проверки сообщаются отдельно.

## Публичный API и последующие этапы

Выдача ключей не доказывает готовность исполнения запросов. Следующий P1B.3b должен
явно определить публичные маршруты/scopes, проверку отзыва/срока ключа и tenant,
сочетание publicApi с модулем операции и независимость Station/Signer/CommerceML.
Настоящий исполняющий public principal нельзя заменить cabinet session или station key.
Этот проект не открывает новые публичные маршруты и не объявляет этот пробел закрытым.

Публикация тарифов, дополнений, услуг, КП и счетов сохраняет согласованное правило:
отсутствие дополнительной lifecycle policy не блокирует текущие продажи. Этот этап
не публикует производственные тарифы и не меняет условия действующих клиентов.

## Решение для согласования

Начать P1B.3a в описанном объёме четырёх существующих семейств и варианте A.
Публичный API оформить следующим отдельным этапом; ТСД/offline — P1C.
После подтверждения составить подробный план реализации и приступить к коду.
