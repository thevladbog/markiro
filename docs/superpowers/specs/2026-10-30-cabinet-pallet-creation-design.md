# Создание палета в офисе Маркиро Автоном

Дата: 2026-10-30. Статус: реализовано локально в `codex/office-pallet-creation`.
Пользователь согласовал сценарий 2026-10-30; техническая привязка уточнена
по актуальному main для Автонома. После проверки интерфейса пользователь
авторизовал создание PR. Развёртывание не входит в текущую задачу.

Офисный пользователь формирует складской палет из кодов уже закрытых
коробов. Готовый палет появляется в общем реестре и использует существующие
карточку, ярлык, состав, выгрузку агрегации и расформирование.

## Согласованные требования

- Точка входа: «Поиск кодов → Палеты», кнопка «+ Новый палет».
- Создание открывается в принятой боковой шторе `EntityDrawer`: содержимое
  прокручивается, кнопки закреплены, несохранённый ввод защищён при закрытии.
  Загрузка — общий `FileDropZone`; состав, ярлык и XML открываются в `SidePanel`.
- Коды коробов можно вводить вручную либо загружать из TXT/CSV, содержащего
  только коды коробов.
- Ошибки нужно исправить до создания. Пользователь явно выбрал этот вариант:
  частичного создания с пропуском проблемных коробов нет.
- В русских текстах офиса используется «палет» с одной «л».

## Предлагаемый сценарий

1. Кнопка открывает форму «Новый палет» на существующих компонентах
   `@markiro/ui`. Поле для списка кодов и загрузка файла работают с одним
   редактируемым списком. Открытие файла заменяет список только после
   успешного чтения и проверки формата; об этом сказано возле загрузки.
2. Подсказка: «Один код короба на строку. TXT или CSV без заголовка».
   Сохраняются ведущие нули; коды всегда строки.
3. «Проверить короба» показывает товар, число коробов и единиц, а также
   строки с ошибками. Товар определяется по первому существующему пригодному
   коробу. Смена, устройство и даты производства могут различаться.
4. «Создать палет» доступно для непустого полностью проверенного списка без
   ошибок. Изменение списка сбрасывает результаты проверки. Пока запрос
   выполняется, повторное нажатие заблокировано.
5. Сервер повторно проверяет весь список и одной транзакцией создаёт закрытый
   складской палет, выдаёт SSCC и связывает короба. При конфликте изменения
   откатываются, форма остаётся открытой с актуальными ошибками.
6. После успеха открывается существующая карточка палета. Доступны ярлык,
   состав и существующая выгрузка XML агрегации ГИС МТ для отдельного палета.
   TXT/CSV в этом сценарии используются для ввода коробов; добавление новых
   форматов экспорта отдельного палета не требуется. Реестр обновляется;
   фильтры сохраняются, даже если новый палет под них не попадает.

Это сразу завершённый палет. Постоянного офисного черновика и отдельного шага
закрытия в этом сценарии нет. Ошибка сети сохраняет введённый список
и позволяет повторить то же создание без второго палета.

## Формат ввода и ошибки

Ограничения: файл до 1 МиБ, до 1000 кодов на палет. TXT и CSV —
UTF-8, допускаются BOM и переводы строк Windows. CSV содержит одну колонку,
без заголовка; допустимы кавычки CSV. Пустые строки игнорируются, лишние
колонки и повреждённые кавычки дают ошибку формата. XLSX и архивы не принимаются.
Неверный файл не стирает текущий список. Ручной список также содержит один
код на строку; вокруг значения можно оставить пробелы.

Принимаются существующие представления SSCC: 18 цифр, 20 цифр с AI `00`,
человекочитаемый префикс `(00)`. Нормализация использует правила доменного
пакета, включая контрольную цифру. Формат не исправляется догадками.

Повтор одного SSCC, в том числе в разных представлениях, является ошибкой
с указанием обеих строк. Остальные ошибки: неверный SSCC, код единицы или
палета вместо короба, неизвестный короб, незакрытый или разобранный короб,
другой товар, короб на действующем палете. Для последнего доступна ссылка
на существующий палет площадки. Код отсутствующего короба получает ошибку
«короб не найден».

Сохраняется действующее правило складской сборки: один товар на палет;
короб с разобранного палета можно использовать повторно. Настройка вместимости
товара не блокирует офисный список: пользователь сам задаёт готовый состав,
а технический предел 1000 защищает запрос.

## Модель и серверные гарантии

Реализация принадлежит `apps/standalone`, офису Автонома. Облачные `apps/admin`,
`apps/api` и Postgres не изменяются. В актуальном main складские палеты хранятся
в SQLite хоста отдельно от производственных, в `warehouse_pallets` и
`warehouse_pallet_boxes`. Офис расширяет эту модель, добавляя источник
`device`/`cabinet`, автора и отпечаток запроса. `device_id` у офисной записи —
настоящий компьютер текущей офисной сессии; источник в интерфейсе — «Офис».
Фиктивных устройств и смен нет. Старая модель ТСД сохраняется.

`POST /v1/office/warehouse-pallets/validate` принимает `{ codes: string[] }`.
`POST /v1/office/warehouse-pallets` принимает также UUID `requestId`.
Оба маршрута используют офисную авторизацию; администратор и технолог могут
формировать палеты. Право и действительность сессии повторно проверяются в
транзакции. Ключ устройства сам по себе доступа не даёт. Создание проверяет
состояние лицензии и функцию `pallets`; чтение и выгрузки доступны для восстановления.

Весь состав повторно проверяется в `BEGIN IMMEDIATE`. Палет, связи коробов,
SSCC, номер ревизии и аудит фиксируются одной транзакцией. Ошибка любого
короба откатывает всё. Изменённые короба получают `registry_touch` для ТСД,
а фиксация через `commit_with_revision` будит подписчиков только после COMMIT.
Гонка с другим офисом, ТСД или расформированием даёт одного победителя.

UUID намерения обозначает канонический набор коробов. Повтор возвращает тот
же палет до проверки занятости коробов; тот же UUID с другим набором даёт
конфликт. Отпечаток и ID не истекают. После изменения состава клиент выпускает
новый UUID. Повтор проверяет актуальные права.

SSCC берётся с расширением 1 из существующего общего счётчика организации.
Хост резервирует диапазон из одного номера за настоящим компьютером офиса,
сохраняет его использование и двигает счётчик в той же транзакции. Счётчики
Автонома разрешено двигать только вперёд, что исключает повторную выдачу.
Отсутствие GLN и исчерпание диапазона дают понятную ошибку без частичной записи.
Номера не пересекаются с ранее выданными диапазонами ТСД и станций.

У складских палетов текущего Автонома пока нет карточки и документов.
Функция добавляет карточку этого вида палета с участниками и источниками
коробов, состав, ярлык A4/A5, XML агрегации и подключение к расформированию.
Рендеринг остаётся в `@markiro/domain` на клиенте; исторические байты не
пересчитываются. Миграции SQLite только добавляются; при перестроении таблицы
сохраняются rowid, внешние ключи и индексы.

Аудит создания использует `audit::actions` и точные офисного автора,
действие, ID палета, результат, SSCC и число коробов. Факт создания не
утверждает успешную печать.

## Написание и область изменений

Исправляются русские тексты офиса, выдаваемые им составы и ярлыки, названия
форматов в общих доменных источниках. Склонение приводится к мужскому роду:
«Новый палет», «палет создан», «состав палета», «на палете», «палеты».
Ключи API, имена таблиц и файлов `pallet` не переименовываются. Применённые
миграции, сохранённые шаблоны и контролируемые юридические артефакты не
перегенерируются ради орфографии. Остальные продуктовые поверхности
проверяются поиском; отдельное изменение Station/Android/лендинга выходит
за функциональную часть офисного сценария.

Основа реализации: офис, host, proto и IPC-клиент в `apps/standalone`,
общие печатные формы в `packages/domain`, соответствующие тесты. Существующие незавершённые изменения истории этикеток,
локализаций и дизайнов сохраняются. Коммит, push, PR и развёртывание в эту
задачу автоматически не входят.

## Приёмка

Автотесты покрывают нормализацию и CSV, ведущие нули, лимиты и дубли,
ручной ввод и файл, исправление ошибок, сброс проверки при редактировании,
сохранение списка при сбое, переход в карточку и доступ по роли.

Тесты БД/API проверяют откат всего списка, идемпотентный повтор после
неизвестного результата, параллельную сборку, принадлежность арендатора,
отказ ключу устройства, тариф, GLN, исчерпание SSCC, запрет повторной выдачи
при перенастройке счётчика, миграцию старых строк, точный аудит и публикацию
изменений в реестр коробов. Проверяется существующая карточка, ярлык,
состав, выгрузка агрегации и расформирование для офисного палета.

Проверки Автонома: test, typecheck, lint, build; cargo tests хоста и proto.
Миграции проверяются на изолированной SQLite, зависимости пересобираются.
В конце выполняются `git diff --check`, соответствующая проверка формата
и `graphify update .`. Браузерный сценарий проверяется локально отдельно
от DOM-тестов. Производство, реальная печать и аппаратные тесты не являются
результатом локальных автотестов.

## Результаты проверки реализации

- Автоном: 8701 тест пройден, 3 штатных пропуска; typecheck, lint и build успешны.
- Общий пакет domain: 1508 тестов; typecheck, lint и build успешны.
- Rust workspace: 2775 тестов пройдено, 12 штатных пропусков. Дополнительный
  итоговый целевой прогон из 47 тестов проверил последние изменения, включая
  игнорирование 15000 пустых строк при одном действительном коде короба.
- Контракты сборки Автонома: 104 проверки пройдены.
- Форматирование всех изменённых файлов, Rust format и `git diff --check` успешны.
  Полная проверка Prettier выявила только два новых JSON-примера; они исправлены
  и повторно проверены вместе со всем изменённым набором.
- Независимое ревью: существенных незакрытых замечаний нет. Исправления восстановления
  результата после потери ответа и изоляции демо-данных покрыты регрессиями.
- Локальный Chromium: реальные компоненты со специально заданными тестовыми
  ответами API; ошибка блокирует создание, CSV с BOM загружается, создание
  открывает карточку, HTML состава передаётся в тестовую функцию печати.

Пропуски требуют отдельного PostgreSQL-окружения, настройки browser-fit, живого OAuth Яндекс Диска либо
ручного запуска длительных/сетевых нагрузочных сценариев. Windows, реальные
принтеры, сканеры, приёмка XML в ГИС МТ и производство не проверялись.
