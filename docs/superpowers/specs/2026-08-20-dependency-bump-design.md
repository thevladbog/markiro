# Monorepo dependency bump — Design Spec

**Date:** 2026-08-20

**Status:** Implemented — full gate green; two major upgrades deferred by
scope, four more deferred by pre-existing blockers.

**Scope:** Bring the outdated JavaScript dependencies up to date within their
current majors, and raise pnpm from 11.10.0 to 11.22.0. Of the 47 packages
originally identified, 41 moved; the other 6 did not (see the Decision record
and "Failure handling" below for why).

**Related:**

- `AGENTS.md` (code conventions, strict TypeScript)
- `.github/workflows/ci.yml` (the `verify` gate)

## Decision record

1. **Within-major only, enforced rather than assumed.** The original premise
   here — that all outdated packages were minor or patch upgrades, with no
   major-version migration hiding in the set — was read off a ten-line sample
   and was wrong. `typescript` (6.0.3, with 7.0.2 available) and `jsdom`
   (29.1.1, with 30.0.1 available) both have a major release sitting on the
   registry; both are deliberately held back at their current major rather
   than merged. Almost every manifest pins an exact version, so `pnpm update
-r` alone is a no-op; the two exceptions are `reflect-metadata` (`^0.2.2`)
   and `rxjs`'s caret range, both in `apps/api/package.json`. Moving anything
   at scale requires `pnpm update -r --latest`, which crosses majors
   indiscriminately, so `tools/check-no-major-bumps.mjs` guards it: it fails
   the sweep if any manifest's _breaking_ version has moved relative to
   `tools/dependency-baseline.json`, a snapshot of 86 packages written by
   `tools/generate-dependency-baseline.mjs`. "Breaking" is the major at `1.0.0`
   and above and the **minor** below it, because `0.45 → 0.46` is a breaking
   change by the convention `drizzle-orm`, `drizzle-kit`, `sharp`, `fflate` and
   `@astrojs/check` all follow. The baseline is an anchor, not history: it is
   re-anchored at the post-sweep state as its own commit, so its diff is the
   reviewable record of exactly what moved. Run it with `pnpm check:deps`; it is
   covered by `pnpm test:dependency-guard`. That guard — not the incorrect
   belief that no major upgrade existed — is what makes a single sweep
   reasonable rather than reckless.
2. **Rust/Tauri is out of scope.** The station's crates build only on a
   Windows runner, cannot be validated locally, and a regression there surfaces
   on a printer or scanner rather than in a test. Bumping them belongs with a
   physical acceptance run.
3. **Node stays at `>=24`.** Not part of this change.
4. **The release-age quarantine stays inert.** `minimumReleaseAge` currently
   resolves to `undefined`, and `saveExact`/`engineStrict` are likewise absent
   from `pnpm-workspace.yaml`. Activating them is overdue but deliberately NOT
   done here: the quarantine changes what a range resolves to, so folding it in
   would leave two candidate causes for any breakage. Separate branch.
5. **One pull request.** With the guard holding every major in place and a full
   CI gate behind it, bisecting the lockfile on failure is cheaper than
   carrying several branches.

## What changes

- Dependency ranges across the 12 manifests (root, 6 apps, 5 packages).
- `pnpm-lock.yaml`, regenerated by the new pnpm.
- `packageManager` in the root `package.json`: `pnpm@11.10.0` → `pnpm@11.22.0`.
- New tooling to make `--latest` safe: `tools/check-no-major-bumps.mjs` (the
  guard, wired up as `pnpm check:deps`), `tools/dependency-manifests.mjs` (the
  discovery and comparison logic both scripts share),
  `tools/generate-dependency-baseline.mjs` (writes the baseline the guard checks
  against), `tools/dependency-baseline.json` (the baseline itself, 86 packages),
  and `tools/test/check-no-major-bumps.test.mjs` (`pnpm test:dependency-guard`).
- `packageManager` in `tools/production-browser/package.json`: `pnpm@11.10.0` →
  `pnpm@11.22.0`. This is a thirteenth tracked manifest, installed by CI with
  `--ignore-workspace` and carrying its own `pnpm-lock.yaml`, so a
  workspace-wide `pnpm update -r --latest` does not reach it and the guard —
  which scans the root plus `apps/*` and `packages/*` — does not cover it. Its
  `packageManager` is bumped by hand to keep the two pnpm pins from drifting;
  its dependencies are deliberately left where they are, and moving them is a
  separate change with its own `--ignore-workspace` install.

**No workflow edits are needed.** Every `pnpm/action-setup@v4` step in
`.github/workflows/` omits an explicit `version:`, so the action reads
`packageManager` from `package.json`. For the workspace that field is the
single source of truth for the local shell (via corepack) and for CI alike;
changing it moves both. The one exception is
`tools/production-browser/package.json` above, which declares its own — hence
the hand edit.

## The lockfile `packageManager` entry

pnpm 11.18 and newer expect the lockfile to record the `packageManager`
dependency with a registry package path and an integrity-only resolution. The
current lockfile has no such entry, which is why a globally installed pnpm
11.18+ refuses to run in this repository with
`INVALID_PACKAGE_MANAGER_LOCKFILE`.

This does NOT affect anyone whose `pnpm` is the corepack shim — corepack honours
the pinned 11.10.0 and works. The failure is confined to environments where a
global pnpm shadows corepack.

Regenerating the lockfile under 11.22.0 was expected to add the entry and
close the gap. **It did not.** The regenerated `pnpm-lock.yaml` has no
`packageManager` entry — confirmed by grepping the finished lockfile — so
`INVALID_PACKAGE_MANAGER_LOCKFILE` still reproduces for anyone whose `pnpm` is
a global install rather than corepack's shim. This is the spec's most
consequential wrong prediction: the assumption that a clean resolve under
11.22.0 would write the entry does not hold, and the underlying problem is
unresolved. It needs its own investigation — this branch does not attempt one
— rather than being folded into a routine dependency sweep.

## Verification

The full gate, matching CI: `turbo lint typecheck test build`, plus
`pnpm format:check`, which CI runs as its own step and turbo does not cover.

Database-backed suites run against a throwaway database, never the shared
`markiro` or `markiro_e2e` — both carry other branches' migrations.

**Skipped counts are part of the result.** A green gate can be empty: the API
end-to-end suites are wrapped in `describe.skipIf` on `DATABASE_URL` and the
auth secrets, so a run without the full environment passes while silently
skipping ~25 files. The report must state skipped counts, not just exit codes.

### Station gets an extra pass

The station suite is timing-sensitive — `work-screen.test.tsx` has already
flaked twice in CI on React passive-effect versus timer ordering. Because this
sweep moves `@testing-library/*`, the station suite runs additionally under
load and in a second timezone, so a scheduling regression cannot hide behind a
quiet single run.

## Risk register

Named in advance so a failure is recognised rather than rediscovered:

- **`@testing-library/user-event` 14.5.2 → 14.6.5.** Eight patches in the
  library whose event timing the already-flaky station tests depend on.
- **`@smithy/node-http-handler` 4.9.13 → 4.11.2.** S3 transport. Fails quietly
  and shows up on file upload rather than in a unit test.

`astro` was flagged here at design time as a risk for its 7.1.6 → 7.2.4 move.
It never shipped: see "Failure handling" below — 7.2.4 turned out to
invalidate `pnpm-workspace.yaml`'s `patchedDependencies`, so astro stays at
7.1.6.

## Failure handling

On a red gate, find the culprit by bisecting the lockfile — do not revert the
sweep wholesale. Any package that cannot be upgraded safely is pinned back to
its current version and **named explicitly in the pull request description**;
silently leaving it behind is not acceptable.

That happened to **four** of the 47 candidate packages, each blocked by
something outside this branch's allowed file set:

- **`better-auth` and `@better-auth/api-key`** (2 packages) stay at `1.6.23` —
  `1.7` expects an `issuer` column on the `account` table, which is declared in
  `packages/db/src/schema/auth.ts` and does not have one. Needs a schema
  change plus a migration.
- **`bwip-js`** (1) stays at `4.11.2` — `4.11.4` drops `fill="#000000"` from its
  generated SVG path, which the Data Matrix regex in
  `packages/legal-documents/src/artifacts/brand.ts` depends on.
- **`astro`** (1) stays at `7.1.6` — `7.2.4` would invalidate the exact-version
  keys in `pnpm-workspace.yaml`'s `patchedDependencies`, which is keyed on the
  literal string `astro@7.1.6`.

Those 4, plus **`typescript`** and **`jsdom`** held back by the Decision record
above, are the full set of **6** candidates that did not move. The other **41**
moved. 4 + 2 = 6; 6 + 41 = 47.

`js-yaml` is deliberately **not** in that count. It stays at `5.2.2`, but it was
never a sweep candidate in the first place: the security `override` in
`pnpm-workspace.yaml` holds it there independently of this branch, so there was
nothing for the sweep to hold back.

## Out of scope

- Rust/Tauri crates in `apps/station/src-tauri`.
- The Node engine floor.
- Activating `minimumReleaseAge` and migrating `saveExact`/`engineStrict` into
  `pnpm-workspace.yaml`.
- Major-version migrations. Two were available and deliberately held back:
  `typescript` (6.0.3 → 7.0.2) and `jsdom` (29.1.1 → 30.0.1). See the Decision
  record.
