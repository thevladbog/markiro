# MKR-INS-06 «Инвентаризация: подготовка и запуск» — дизайн

Дата: 2026-08-30
Статус: утверждён (brainstorming)
Предшественники: MKR-INS-01…04 (станция, оператор и наладчик) и MKR-INS-05
«Инвентаризация на терминале» (PR #354, merge `fc1bd7f1c`) — в main.

## Цель

Шестая печатная инструкция и второй документ подсерии «инвентаризация»:
подготовка задания инвентаризации в кабинете и его запуск. Аудитория —
менеджер или кладовщик, работающий в кабинете администратора; операторская
часть описана в MKR-INS-05.

## Ключевое отличие от предыдущих документов

Все пять предыдущих инструкций снимались из dev-галереи станции. У кабинета
галереи нет, НО есть готовый браузерный харнесс-прецедент:
`apps/admin/test/browser/tenant-billing-harness.tsx` + `tenant-billing.html`
монтируют реальные страницы админки (`appRoutes`) с синтетической сессией, а
`tools/production-browser/tenant-billing.playwright.config.ts` поднимает vite
(`apps/admin/test/browser/vite.config.ts`) и перехватывает `/api/` через
`page.route`, отдавая синтетический JSON. Скриншоты MKR-INS-06 снимаются тем
же способом — БЕЗ Postgres, API и демо-стенда.

Решение (принято в brainstorming): создать постоянный
`apps/admin/test/browser/inventory-harness.tsx` (+ html + playwright-конфиг)
по образцу биллингового. Он остаётся в репозитории как механизм для
MKR-INS-07 и любых будущих кабинетских инструкций.

## Решения (принятые в brainstorming)

- Скриншоты — через новый харнесс инвентаризации с моками API, не с живого
  стенда с БД.
- Выписки ЧЗ описываем ОБА пути: заказ из Честного Знака по True API (с
  блокерами) как основной и ручную загрузку файлов как запасной.
- Ход инвентаризации, исправления, закрытие и итоговые документы — НЕ здесь,
  это MKR-INS-07.

## 1. Документ

- Код `MKR-INS-06`, kind `instruction`, ревизия `2026.08/01`, effectiveDate
  `2026-08-30`, статус `active`, RU-only, маршрут
  `/instruktsii/inventarizatsiya-podgotovka/`.
- Контент — `packages/legal-documents/src/documents/cabinet-inventory-prep.ts`.
  Цитаты интерфейса — строго из `apps/admin/src/i18n/ru.json`, ветка
  `pages.inventory` (и `nav`/`shell` для навигации). Структура секций:
  1. Назначение: кто готовит инвентаризацию и что получают операторы
     (печатная форма-задание, см. MKR-INS-05); пять этапов подготовки:
     «Параметры» → «Выписки ЧЗ» → «Проверка снимка» → «Терминалы» → «Запуск».
  2. Создание задания: «Создать инвентаризацию»; продукт (ровно один),
     «Способ инвентаризации» («Без переупаковки» / «С переупаковкой»), линия,
     «Шаблон этикетки короба», «Дата производства с» / «по» («Период
     применяется включительно»); архивные продукты помечены «не используется».
  3. Выписки ЧЗ: шесть статусов кодов («Эмитирован», «В обороте», «Нанесён»,
     «Выбыл», «Списан», «Расформирован»), по одному результату на статус;
     «Заказать из Честного Знака» и блокеры заказа (ИНН организации, группа
     продукции ЧЗ в карточке товара, агент КЭП, токен True API) с указанием,
     где чинить; ручная загрузка файлов как запасной путь (ограничение
     размера, «Файл не прошёл проверку», счётчики ошибок и дублей); правило
     «Пустая выгрузка с нулём строк считается успешной».
  4. Проверка снимка: сверить ровно шесть выбранных загрузок и нажать
     «Зафиксировать снимок»; итоговые количества считает сервер; после
     фиксации состав снимка неизменяем.
  5. Терминалы и форма-задание: «Назначено терминалов», «N из M терминалов в
     сети»; «Открыть форму-задание» — печатная A4-форма со штрихкодом;
     распечатать и передать операторам (по ней открывается задание на
     терминале).
  6. Запуск: подтвердить остановку складских движений, «Запустить
     инвентаризацию»; задание появляется на терминалах назначенной линии;
     дальнейший контроль — MKR-INS-07.
  7. Частые вопросы (definition-list) + контакты.

## 4. Тестирование

Существующие механизмы плюс новый харнесс. Харнесс должен быть покрыт так же,
как биллинговый: playwright-конфиг запускается отдельным скриптом
(`tools/production-browser/package.json`), а сам харнесс — обычный TS,
проходящий typecheck/lint админки. Финальному whole-branch ревью задаётся
линза «текст ↔ скриншоты ↔ i18n»: в MKR-INS-03/04/05 она поймала по одному
Critical, невидимому задачным гейтам. Отдельный риск кабинета: строки в
`pages.inventory` могут быть мёртвыми так же, как на станции (найдено пять
мёртвых ключей) — цитировать только то, что видно на снятом кадре.
