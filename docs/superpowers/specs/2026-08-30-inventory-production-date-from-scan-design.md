# Дата производства из сканируемого кода в инвентаризации

Дата: 2026-08-30. Статус: принято, реализуется в этой ветке.

## Задача

В операции «Инвентаризация» на десктоп-станции оператор вручную выбирает дату
розлива (производства) и затем сканирует коды. Дата штампуется на каждое
событие скана и уходит в результат как наблюдаемая. Но у загруженных в
инвентаризацию кодов дата производства **уже известна** — она приходит вместе со
снапшотом.

Нужно при сканировании кода товара или короба подтягивать дату производства из
самого кода: если дата ещё не задана — выставлять её, если задана и не совпадает
— останавливаться и предлагать оператору решить, а не штамповать заведомо чужую
дату.

Цена сегодняшнего поведения: расхождение даты — **блокер закрытия
инвентаризации**. Оператор, забывший переключить дату при переходе на другой
паллет, может настрелять сотни кодов, и каждое расхождение потом правится
вручную коррекцией `change_date` в админке.

## Ключевые факты кодовой базы

- `inventory_snapshot_codes_mirror.source_production_date`
  ([schema.ts:346](../../../packages/db/src/sqlite/schema.ts)) синхронизируется в
  зеркало станции вместе с кодами. Всё нужное есть локально, оффлайн работает.
- Check-constraint `inventory_snapshot_codes_classification_check`
  ([inventory.ts:707](../../../packages/db/src/schema/inventory.ts)) гарантирует,
  что у любого `expected`-кода `source_production_date` не NULL. Для всех кодов,
  которые вообще должны считаться, дата известна.
- Активная дата хранится per-device в `inventory_terminal_state.active_production_date`
  ([inventory-date.ts](../../../apps/station/src/lib/inventory-date.ts)) и
  штампуется на событие как `active_production_date`, а в результат — как
  `observed_production_date`.
- При входе на экран работы дата, если её ещё нет, инициализируется значением
  `productionDateFrom` — то есть **началом диапазона задания**. Это и есть
  главный источник сегодняшних ошибок: значение выглядит осмысленным, и его
  легко не заметить.
- Расхождение `source_production_date <> observed_production_date` попадает в
  блокеры закрытия
  ([inventory-close.service.ts:750](../../../apps/api/src/modules/inventories/inventory-close.service.ts))
  и в счётчик `dateMismatchCount`
  ([inventory-reconciliation.service.ts:139](../../../apps/api/src/modules/inventories/inventory-reconciliation.service.ts)).
- Журнал сканов иммутабельный и append-only: событие резервируется, получает
  вердикт и сразу попадает в `inventory_outbox`. В простой инвентаризации отката
  нет вообще; в перекладке есть `removeLastInventoryRepackItem`.
- Очередь сканов
  ([scan-queue.ts](../../../apps/station/src/lib/scan-queue.ts)) уже умеет
  придерживать поток: `shouldProcess` отсекает работу на входе в обработку, а
  `discardBufferedScans()` сбрасывает уже набуференное.
- В перекладке дата фиксируется на коробе при открытии и попадает на печатную
  этикетку. Архитектура запрещает смешивать даты в непустом коробе. Существующая
  проверка `dateMatches`
  ([inventory-repacking.ts:517](../../../apps/station/src/lib/inventory-repacking.ts))
  сравнивает дату терминала с датой короба — с датой из кода не сверяется ничего.

## Решение

Дата из кода становится ведущей, но не молчаливо: первый скан задаёт дату сам,
дальше расхождение всегда выносится оператору. Спорный скан **удерживается до
решения** и не пишется, пока оператор не ответил — это даёт эффект «отменить
последний шаг», не ломая иммутабельность журнала и контракт синхронизации.

### Где стоит проверка

Факт доезжает до классификатора двумя правками:

- `InventoryScanSnapshotRow`
  ([scan.ts:7](../../../packages/domain/src/inventory/scan.ts)) получает поле
  `sourceProductionDate: string | null`;
- `loadClassifierFacts`
  ([inventory-journal.ts:181](../../../apps/station/src/lib/inventory-journal.ts))
  добавляет колонку в оба SELECT (по `code_hash` и по `parent_sscc`).

Сама проверка встаёт в `recordInventoryScanInternal` **после первой
классификации и до `reserveEvent`**. В этой точке не записано ничего: ни
события, ни outbox, ни проекции.

### Контракт результата

`date-mismatch` **не** добавляется в `InventoryLocalVerdict`. Этот enum отражает
персистентные значения и протёк бы в `RecentInventoryOperation.verdict` и в
разбор строк журнала.

Вместо этого `recordInventoryScan` возвращает размеченное объединение:

```ts
type RecordInventoryScanOutcome =
  | ({ outcome: "recorded" } & RecordInventoryScanResult)
  | {
      outcome: "date-mismatch";
      activeDate: string;
      /** null для смешанного короба — подставлять нечего. */
      codeDate: string | null;
      mixed: boolean;
      scanKind: "item" | "known_box";
    };
```

Это заставляет компилятор пройтись по всем местам разбора результата — в
частности по цепочке `if/else` в
[InventoryScanInstrument.tsx:44](../../../apps/station/src/ui/inventory/InventoryScanInstrument.tsx),
где новый случай иначе молча упал бы в ветку «недопустимый код».

### Простая инвентаризация

**Первый скан на терминале.** Если в `inventory_scan_events_mirror` ещё нет ни
одного события для этой пары `(inventory_id, snapshot_id)` и этого `device_id`,
активная дата молча выставляется из кода. Инициализация значением
`productionDateFrom` остаётся, но становится плейсхолдером, который первый скан
перезаписывает.

**Дальше.** При расхождении скан удерживается, очередь замирает (`shouldProcess`
возвращает `false`, пока диалог открыт, плюс `discardBufferedScans()`, чтобы
очередь сканера не проскочила мимо диалога), открывается диалог:

> Код произведён **16.08.2026**, активная дата — **15.08.2026**
> `[Установить 16.08 и зачесть]` `[Пропустить код]`

- «Установить» → `setInventoryProductionDate`, затем тот же `raw` заново
  ставится в очередь с новым `eventId`; скан проходит уже с верной датой.
- «Пропустить» → не записывается ничего, бутылка откладывается физически.

### Перекладка

- **Скан старого короба** задаёт дату нового короба по содержимому старого: дети
  старого SSCC есть в снапшоте по `parent_sscc`, их `source_production_date`
  известна. Короб открывается с правильной датой, а не с плейсхолдером, который
  потом пришлось бы менять. Если у детей даты разные либо детей в снапшоте нет
  вообще (неизвестный старый короб) — короб открывается с активной датой
  терминала, дальше работает поштучная проверка. Диалог на скане старого короба
  не показывается: это выбор контекста, а не зачёт кода.
- **Скан товара, пустой короб** (`itemCount === 0`) — дата короба подтягивается
  из кода через существующий `changeOpenInventoryRepackDate`.
- **Скан товара, непустой короб** — смешивать даты нельзя, поэтому в диалоге
  только `[Пропустить код]` и `[Коррекции]` (закрыть неполный / очистить —
  существующий поток).

Так этикетка нового короба физически не может разойтись с содержимым.

Существующая проверка `dateMatches` (дата терминала против даты короба)
сохраняется без изменений — это отдельный инвариант.

## Граничные случаи

**Проверяется только классификация `expected`.**

- `duplicate` — код уже зачтён с датой победителя, диалог был бы шумом;
- `unknown` — кода нет в снапшоте, сравнивать не с чем;
- `protected` / `known-ineligible` — переключить активную дату под код, который
  всё равно нельзя зачесть, значит испортить дату всем последующим нормальным
  сканам;
- `invalid` — сравнивать не с чем.

Остаточный эффект принят осознанно: `protected`/`ineligible`, отсканированный
под чужой датой, по-прежнему даст серверный `dateMismatch`. Он и так блокер по
своей классификации, так что новой работы для админа это не добавляет.

**Короб (`known_box`).** Случай только для простой инвентаризации: в перекладке
скан короба — это выбор старого контекста, а укладываются в новый короб всегда
поштучные KM. Берётся множество различных `source_production_date` по
**expected и ещё не зачтённым** детям короба:

- одно значение, не равное активному → обычный диалог, переключить или
  пропустить;
- несколько значений → короб физически смешанный, `mixed: true`, подставлять
  нечего. Диалог: «короб содержит несколько дат розлива», кнопки
  `[Зачесть как есть]` и `[Пропустить]`. «Как есть» — ровно сегодняшнее
  поведение, и сервер честно пометит разошедшихся детей. Без этой кнопки
  смешанный короб было бы невозможно отсканировать вообще;
- ноль подходящих детей → проверки нет.

**Прочее.**

- `source_production_date` в зеркале nullable. При NULL проверка не
  запускается, поведение как сегодня. Для `expected` NULL невозможен по
  check-constraint, но защищаемся явно.
- Автоподстановка обязана попадать в `[productionDateFrom, productionDateTo]`.
  Для `expected` это выполняется по построению `classifyInventorySnapshotRow`,
  но проверяется перед записью — иначе можно записать невалидный
  `inventory_terminal_state`. Если дата вне диапазона, кнопка переключения не
  предлагается, остаётся только пропуск.
- Активная дата хранится per-device, переключение на одном терминале не трогает
  соседний.
- Всё локально, из зеркала снапшота. Новых сетевых зависимостей нет, оффлайн
  работает без изменений.
- Падение с открытым диалогом теряет только удержанный скан: в журнале и outbox
  по нему ничего нет, `reconcilePendingInventoryEvents` его не видит. Оператор
  пересканирует.

## Что не меняется

Серверный контракт синхронизации: событие по-прежнему несёт один
`activeProductionDate`, детерминированное расширение короба на сервере не
трогается. Блокер `dateMismatch` и коррекция `change_date` в админке остаются
как страховка — для смешанных коробов, чужих терминалов и уже накопленных
данных.
