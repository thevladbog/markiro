Дата: 2026-10-10. Статус: требования согласованы; обновлённый план подготовлен, реализация не начата.
Исследованное дерево: `57d589e2a1ea33156f2cb415be2d951c6edb33e9`, эквивалентное дереву merge `1329be61cd3b1c471aaafcf0d9f982c8a3e4ea8b`. Перед реализацией повторно сверить с main.

## Результат для пользователя

В существующем разделе «Шаблоны этикеток» появляются полноценные шаблоны с назначением «Палета» и форматом «Лист А4». Пользователь может создать свой, скопировать готовый, редактировать визуально, сохранить, импортировать и экспортировать JSON. Station получает выбранный шаблон с сервера и печатает его офлайн через установленный драйвер Windows. Встроенный список макетов в настройках принтера больше не является источником дизайна.

Три стартовых шаблона:

1. А4 210 × 297 мм, один SSCC внизу.
2. А4 297 × 210 мм, один горизонтальный SSCC внизу; сверху две колонки.
3. Альбомный А4 с вертикальным разрезом посередине: две одинаковые этикетки одной палеты, каждая 148,5 × 210 мм. Один лист, одно задание Windows, `dmCopies=1`.

Это обычные tenant-owned записи библиотеки, а не зашитые в Station переключатели. Их изменение доступно через редактор и JSON. Обновление приложения не перезаписывает пользовательские правки и не меняет автоматически существующий шаблон по умолчанию.

## Неизменные требования к готовым макетам

- Контрагент не выводится. Шапка: настоящее название организации и её логотип; если логотип не установлен, встроенный логотип Маркиро.
- Прямоугольные логотипы сохраняют пропорции. Ограничена максимальная высота; ширина естественная, без квадратной рамки/обрезки. При нехватке места название переходит на следующую строку; только физическая ширина листа может потребовать уменьшения высоты логотипа.
- «Палета» пишется с одной «л». Внутренние `pallet` идентификаторы не переименовываются.
- В вертикальном А4 и каждой А5 предусмотрено пять строк названия. SSCC, GTIN и ЕГАИС никогда не сокращаются. Длинный текст, который нельзя разместить, вызывает понятную ошибку до отправки вместо молчаливого обрезания.
- Нет исходной даты производства → нет подписи и даты; `closedAt` вместо неё не подставляется. Производный срок годности также отсутствует. Код ЕГАИС появляется целиком, только если он есть. Пустая строка исчезает вместе с подписью, последующие строки поднимаются.
- SSCC обычной ориентации, штрихи вертикальны относительно основания палеты; HRI под кодом. На одной этикетке ровно один AI (00). Две отдельные копии на разрезном листе допустимы как отдельные этикетки.
- Высота штрихов стартовых шаблонов 45 мм. При исходных 300 dpi: А4 — 11 точек на модуль, А5 — 9, с предусмотренным пресетом 8 для узкой печатной области. Тихие зоны минимум 10X, полная длина GS1-128 не более 165,1 мм. В текущем А4 длина со свободными зонами 163,915 мм; растягивание на всю ширину альбомного листа исключено.

## Границы версии

Входят: domain-модель V2, общий рендер, библиотека и визуальный редактор админки, JSON import/export, API и PostgreSQL, выбор для смены и defaults, совместимый bundle/SQLite, брендинг, Windows А4, журнал и повторная печать. Старые термоэтикетки V1, ZPL/TSPL и обычный Windows-вывод этикеток сохраняются.

Не входят: редактор произвольных многостраничных документов, HTML/CSS/JavaScript в JSON, разные палеты на одном листе, произвольные картинки по внешним URL, цветной печатный pipeline и печать А4 с ТСД. Проверка совместимости ТСД обязательна, но новый формат туда не отправляется и отдельный релиз ТСД не нужен при подтверждённой совместимости старого протокола.

## Подтверждённые точки текущего кода

- `LabelTemplateSpec` — без версии, с `language: zpl|tspl`; размеры уже допускают А4, но нет логотипов/условных групп. Lenient parser удаляет неизвестные поля, поэтому V2 нельзя пускать в него как обычный V1.
- Импорт `packages/domain/src/labels/json-import.ts` принимает bare spec или `{name,purpose,spec}`. Экспорт `apps/admin/src/pages/labels/editor/download.ts` уже использует эту оболочку. Расширяем существующий путь.
- `label_templates.spec` хранится в JSONB, назначение `pallet` уже существует. Формат носителя — отдельный признак, не новое назначение.
- `ShiftsService.listPalletLabelTemplates` сейчас выбирает все enabled `purpose=pallet`, затем приводит spec к V1. Нужны типизированная маршрутизация и фильтрация, включая defaults и прямой запрос ID.
- У API уже есть `x-station-capabilities`; переиспользуем этот механизм, не создаём второй протокол определения версии клиента.
- Bundle и SQLite сейчас содержат один `palletLabelTemplate` V1. Добавляем отдельный необязательный slot V2, не заменяем содержимое старого поля.
- Админский CRUD защищён cabinet permissions и `labelEditor`; Station не получает доступ к этому CRUD.
- `palletLabelFields` подставляет дату закрытия при null; новая политика дат реализуется отдельно, исторические V1 вычисления не меняются.

## Формат JSON и редактируемая модель

Ввести `StoredLabelTemplateSpec = LabelTemplateSpec | PalletSheetSpecV2`. Существующий V1 parser и его поведение остаются отдельными. Новый `parseStoredLabelTemplate` сначала проверяет discriminator и только затем вызывает нужный parser. Наличие неизвестной версии или `kind` — ошибка, а не попытка потерять поля и прочитать как V1.

Предлагаемый V2:

- `schemaVersion: 2`, `kind: "pallet_sheet"`, `dpi: 300`; поле `language` отсутствует, язык транспортного принтера не является свойством листа.
- `page`: `size: "A4"`, `orientation: "portrait"|"landscape"`, `copies: 1|2`, `cutLine: boolean`, `marginsMm: {top,right,bottom,left}`. Две копии допустимы только на альбомном листе; обе используют один content tree и один контекст палеты.
- `body: SheetNode[]`: упорядоченные редактируемые блоки. `stack` и `row` для адаптивного потока; `canvas` для свободного позиционирования вложенных элементов в миллиметрах. Пустые условные блоки исключаются до измерения. В canvas пустой элемент не перестраивает соседей — интерфейс объясняет это различие.
- Листовые узлы: `text`, `field`, `field_row`, `organization_logo`, `line`, `box`, `spacer` и группы. Текст редактируется; поля выбираются из allowlist (`organization.name`, `product.printName`, `product.gtin`, `product.egais`, `productionDate`, `expiryDate`, `boxCount`, `itemCount`, `shiftNumber`). Источник SSCC не заменяется произвольным literal.
- Общие свойства: уникальный `id`; `when?: {field, op:"present"}`; измеримые настройки шрифта/выравнивания; `maxLines`/`reservedLines` и явная политика переполнения. `field_row` содержит подпись и значение как единый скрываемый блок. Никаких исполняемых выражений.
- `footer`: обязательный редактируемый блок `kind:"sscc"`, `source:"sscc"`, `barHeightMm`, `moduleDots`, необязательный `fallbackModuleDots`, выравнивание по горизонтали. Footer всегда внизу; ориентация и тихие зоны защищены валидатором. Его параметры и положение внутри нижней зоны редактируются, дублирование/удаление делает draft невалидным для сохранения.
- Узел логотипа: `source:"organization"`, `fallback:"markiro"`, `maxHeightMm`; JSON переносит привязку, а не логотип/название/tenant ID конкретной компании.

Лимиты новой схемы: импорт до 256 КиБ UTF-8, до 200 узлов на content tree, вложенность до 8 уровней, только конечные числа, уникальные ID, белый фон и монохромный результат. Ошибки содержат точный путь JSON и причину. Неизвестные поля V2 запрещены; их нельзя тихо удалить, как при lenient V1. Геометрия, обязательный SSCC и допустимые размеры проверяются и в админке, и API, и перед рендером на Station.

Экспорт сохраняет оболочку `{name,purpose:"pallet",spec}` и все редактируемые свойства V2, включая условия и двухкопийную раскладку. ID записи, tenant, revision, timestamps, значения полей палеты, логотип, локальные пути и очередь Windows не экспортируются. Импорт всегда создаёт новую запись; замена открытого draft — отдельное явное действие. Несовпадение назначения V2 с `pallet` блокируется. Неизвестная версия не импортируется частично. JSON export → import → export должен сохранять семантику spec.

## Админка

Библиотека: назначение «Палета», формат «Этикетка» / «Лист А4», размеры/ориентация/«2 копии», фильтр по формату; карточка V2 не показывает фиктивный ZPL/TSPL. Доступны создание с нуля, три стартовых пресета, копирование, переименование, редактирование, включение/выключение и назначение default в пределах существующих прав.

Редактор: общий shell со старым редактором, отдельные панели V2. Пользователь добавляет/перемещает/удаляет блоки, меняет подписи, привязки, размеры, шрифты, выравнивание, поля, условия и раскладку; редактирует только одну А5-копию, вторая обновляется автоматически. Undo/redo, несохранённые изменения и защищённые поля работают одинаково для визуального редактирования и загрузки JSON. Ошибки показываются рядом с элементом и в JSON-пути; ручной импорт не обходит ограничения редактора.

Предпросмотр использует тот же domain renderer и bundled fonts, что Station. Есть сценарии «с датой/без даты», «с ЕГАИС/без», длинное название, широкий логотип и резервный Маркиро. По умолчанию показывается номинальная геометрия страницы; фактические поля конкретного Windows-принтера доступны в Station. При одинаковых данных, ресурсах и геометрии результат обоих клиентов должен совпадать. Для V2 доступны JSON и превью; кнопки выгрузки ZPL/TSPL недоступны с объяснением «Лист А4 печатается через драйвер Windows».

## Хранение, версии и defaults

`label_templates` получает `format: "label_v1"|"pallet_sheet_v2"` и `revision` (целое, начинается с 1). Старые строки мигрируются в `label_v1` без перезаписи JSON. Формат согласован с discriminator spec; менять V1↔V2 через PATCH нельзя, только создать новую запись/копию. Для V2 обновление требует `expectedRevision` и атомарного compare-and-swap; конфликт не затирает чужое редактирование. Аудит указывает actor/tenant/template/revision/result, не только updatedAt.

Стартовые три шаблона создаются идемпотентно для существующих и новых tenant с устойчивыми системными ключами. Переименованные/отредактированные пресеты не пересеваются поверх; пользовательские defaults не переключаются автоматически.

Для листа вводятся отдельный глобальный default и категорийные defaults, аналогичные существующим палетным V1. Старые `defaultPalletLabelTemplateId` и таблица `org_pallet_label_template_defaults` остаются V1-only. Новые sheet defaults ссылаются только на enabled V2 того же tenant и допустимой категории. Отключение, удаление или смена категории шаблона, который используется как default, блокируются до переназначения. Локальные printer profiles не хранят layout, templateId или template revision.

## Выбор для смены и совместимость устройств

В смене сохраняются отдельные `palletLabelTemplateId` (V1) и необязательный `palletSheetTemplateId` (V2). V2 выбирается в админке и на совместимой Station; при выборе сервер атомарно сохраняет `{id,name,revision,spec,digest}` в snapshot смены. Изменение записи шаблона после этого не меняет уже выбранную версию. Явное изменение выбора для будущих попыток допускается только по действующим правилам редактирования смены; подготовленные задания всегда сохраняют прежний snapshot.

Одна попытка печатает только один формат, выбранный для данного назначения на Station. Для режима А4 нужны V2 snapshot и профиль Windows А4; для обычной этикетки нужны V1 и совместимый прежний профиль. Наличие обоих вариантов в смене не вызывает двойную печать.

Новая capability `pallet-sheet-v2` добавляется в существующий `x-station-capabilities` только клиентами, имеющими и renderer, и нужный native Windows bridge. Сервер дополнительно проверяет device kind; handheld не получает V2 даже с подставленным заголовком. Capability служит согласованию формата, не заменяет авторизацию.

- Новый cabinet запрашивает оба формата; старый запрос библиотеки без opt-in возвращает V1. Новый Station picker запрашивает выбранный поддерживаемый формат; старый picker/default resolver получает V1 без новых полей в старой форме ответа.
- Bundle добавляет `palletSheetTemplate` и соответствующий shift reference только для совместимой Station. Прямые preview/detail/open/enter/start/recovery пути проверяются отдельно; фильтрации списка недостаточно.
- При наличии legacy fallback старые Station/ТСД работают по прежнему V1. Если смена настроена только на V2, неподдерживаемое устройство получает понятный отказ до начала производственной операции и до выделения SSCC; лист не маскируется под V1 и обязательная печать не пропускается.
- Server-first rollout сохраняет старые формы ответа для старых клиентов. Новая Station со старым API показывает листовой режим недоступным, без молчаливого fallback на встроенный макет.
- SQLite хранит отдельный sheet snapshot. Проверяются идентификатор, revision, digest, версия spec и tenant/owner; поздний bundle после закрытия/смены credentials не меняет текущий контекст.

## Брендинг и офлайн

Добавить чтение брендинга и активного логотипа через API с авторизацией станции и tenant scope. Кабинетная сессия, публичная ссылка и kiosk credentials для этого не используются. Нужен отдельный запрет handheld, если endpoint предназначен только Station: `StationOnlyGuard` сам по себе проверяет вид авторизации, а не вид устройства.

Синхронизация обновляет локальный снимок только после успешной загрузки/проверки логотипа. Снимок содержит tenant, поколение credentials, название, revision, digest, байты и размеры. Пока новый снимок не готов, остаётся последний полный офлайн-снимок этого tenant. При `logoRevision: null` выбирается встроенный Маркиро. Ошибка загрузки установленного логотипа не означает его отсутствие и не должна незаметно заменять его Маркиро. На первом подключении такого устройства А4 становится доступен после подготовки брендинга; последующие печати не требуют сети.

Название организации остаётся настоящим и при резервном логотипе. Пустое название требует настройки, а не печати «Название организации». После смены владельца поздний ответ не записывается в новый tenant. Удаление логотипа синхронизируется как явное отсутствие; ранее подготовленные задания сохраняют собственный снимок.

## Общая отрисовка и Windows

`renderPalletSheet(spec, context, geometry, rasterizeText): Promise<MonoRaster>` в domain исполняет редактируемое дерево, а не переключатель трёх hardcoded layout. Контекст содержит настоящие nullable бизнес-поля, название и подготовленный монохромный логотип. Декодирование WebP и загрузка ресурсов остаются в клиентах; API только валидирует и хранит JSON. Превью и печать используют этот renderer. Обычные text/GS1 primitives переиспользуются; второй алгоритм GS1 не создаётся.

Исходник `mono-raster-v1`, 300 dpi, ≤2 МиБ. Windows использует `DMPAPER_A4`, ориентацию из spec, 100%, simplex и одну копию. Фактическая геометрия запрашивается до рендера. По умолчанию поля А4 10 мм, расширенной А5 7 мм по бокам; физические ограничения драйвера плюс защитный зазор 0,5 мм учитываются заранее. Для А5 выбирается 9 или 8 точек/модуль, без дробного масштабирования и без обрезки тихих зон. Эффективная геометрия отображается в Station и сохраняется с попыткой.

Предлагаемый вывод — 300/600/1200 dpi с целочисленным увеличением 1/2/4 без сглаживания. Неподдержанные/неравные по осям DPI дают точную ошибку. Перед отправкой native bridge повторно проверяет реальную геометрию. Старый строгий путь термоэтикеток не меняется.

## Надёжность повторной печати

Профиль определяет Windows-очередь и бумагу; snapshot смены определяет макет. До подготовки байтов фиксируются оба. В `printer_deliveries.render_snapshot_json` сохраняется версия snapshot, полный spec/revision/digest шаблона, исходные бизнес-факты, дата/null, монохромный логотип с provenance, версия renderer и эффективная геометрия. Одновременно сохраняются байты и их digest; один prepared row нельзя собрать из разных версий.

`Sending` фиксируется до транспорта. Сбой/таймаут/рестарт после начала отправки означает возможный `delivery_unknown`, без автоповтора. Изменение шаблона, его удаление, новый логотип или новая версия приложения не меняют подготовленный лист. Явное повторение неопределённой попытки использует прежние байты. После доказанного `failed_before_send` можно создать новую попытку с другой геометрией/явно выбранным шаблоном, сохраняя факты и историю предыдущей. После очистки байтов завершённой попытки повторная генерация использует её сохранённый spec и ресурсы, а не текущий templateId lookup. Renderer version сохраняется: неподдерживаемую старую версию нельзя молча заменить новой логикой.

Новая nullable колонка не меняет чтение legacy записей. Ретеншн не удаляет snapshot/ресурсы незавершённых заданий. Миграции PostgreSQL и SQLite добавляются новыми файлами/шагами; общие базы не сбрасываются.

## Приёмка

- Domain: V1/V2 dispatch, строгий JSON, round-trip, неизвестные версии, лимиты/depth/ID, обязательный SSCC, безопасная ширина/высота/quiet zones, пять строк, nullable даты и ЕГАИС, две идентичные половины.
- API/DB: tenant isolation, permissions/subscription, optimistic revision conflict, seed идемпотентность, defaults по формату/категории, сохранённый snapshot, старые клиенты на всех путях и spoofed handheld capability.
- Админка: создать/редактировать/копировать/save/reload; JSON файл и вставка; cancel импорта; undo/redo; экспорт без tenant-данных; отсутствие фиктивного ZPL/TSPL; реальные browser/canvas/font screenshots и сравнение с Station.
- Station: выбор эффективного шаблона, старый API, старый bundle, offline restart, смена владельца, смена/удаление template и logo после подготовки, неизвестная доставка, восстановление после очистки байтов.
- Windows/оборудование: реальный лазерный и струйный принтер, размеры линейкой, все SSCC сканером, обе половины после разреза, широкие логотипы, бумага закончилась/очередь недоступна/перезапуск. PDF-принтер и host Cargo не заменяют физическую приёмку.
