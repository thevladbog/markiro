## Предлагаемая архитектура первого этапа

Сохраняем NestJS, PostgreSQL, pg-boss, Astro, React и Caddy. Выделяем
явный серверный профиль `platform-only`: платформенная авторизация, API SaaS-админки,
публичная форма лендинга и служебная диагностика. Название профиля — техническое предложение.
Профиль задаётся при запуске и не переключается HTTP-запросом или ролью пользователя.
Неизвестный профиль не должен молча включать прежний полный API.

Выбран подход с отдельным составом модулей в существующем API. Отдельный новый backend
создал бы вторую реализацию лицензий/биллинга, а отключение только на proxy оставило бы
производственные задачи активными. Старый код пока остаётся в репозитории для истории,
экспорта и восстановления; в новом production-профиле его маршруты и workers не запускаются.
Обычная серверная доставка должна явно выбирать `platform-only`; legacy-профиль не является
автоматическим запасным режимом. Desktop-релизы автонома остаются отдельным продуктовым потоком.

### Сохраняемые функции

- SaaS-вход, MFA, восстановление доступа, команда платформы, capabilities и аудит.
- Тенанты без клиентского кабинета, реквизиты, коммерческий каталог, назначения прав,
  периоды обслуживания, договоры, предложения, счета, платежи, акты и документы.
- Площадки автонома, импорт запроса лицензии, диагностика/статистика из него,
  выдача и повторное скачивание лицензии, история выпусков.
- Поддержка: выделить из SupportChatModule просмотр истории/транскриптов и их сверку
  с Chatwoot, включая повтор синхронизации. Клиентский чат кабинета выключен.
  Предложение автора после проверки: запретить создание новых предложений через
  `POST :id/proposals`, поскольку их согласование сейчас требует клиентского кабинета.
  Уже ожидающие решения предложения сохранить как исторические с пояснением о закрытом
  канале согласования; не принимать, не исполнять и не переотправлять их автоматически.
  Новый способ согласования и новый канал общения автонома этим проектом не вводятся.
  Самостоятельная работа команды в Chatwoot сохраняется как отдельный контур.
- Платформенные отчёты и экспорт коммерческих данных, доступ к сохранённым документам.
  Старые производственные показатели обозначаются как исторические. Новая статистика
  автонома имеет дату снимка и источник; отсутствие снимка не превращается в ноль.
- Лендинг, формы обращения, языковые версии, опубликованные документы и стабильные ссылки.
- PostgreSQL, приватное object storage, SMTP, аудит, допустимые фоновые задачи и healthcheck.
  База/служебный API не публикуются отдельными доступными извне портами.

### Выключаемые функции

- Клиентский кабинет, его регистрация/вход, активация владельца и приглашения.
- Облачные смены/сканирование/склад/SSCC/печать как рабочий серверный функционал.
- Pairing и синхронизация station/kiosk/handheld с облаком; signer-agent и обновление токенов ЧЗ.
- Клиентские API-ключи, public integrations API, CommerceML/1С, облачные задания ЧЗ.
- Производственные workers, их boot reconciliation и планировщики, автоматические
  запросы к Национальному каталогу от имени облачных тенантов.
- Выдача новых кабинетных доступов из SaaS-админки. Запрет проверяется API, не только UI.

Общий каталог коммерческих продуктов SaaS сохраняется. Интеграция с Национальным каталогом
для облачного производства выключается; её SaaS-страница не должна запускать импорт/refresh.
Данные не удаляются. Если выявится отдельное используемое платформой назначение этой интеграции,
его нужно явно согласовать, а не оставлять всю подсистему активной.

### HTTP и старые адреса

- SaaS-домен разрешает только платформенную авторизацию/API и собственную статику.
- Лендинг разрешает статику и существующий валидируемый endpoint формы.
- Прямой API `platform-only` не регистрирует отключённые маршруты даже при обходе Caddy.
- Предложение: прежние домены кабинета/киоска показывают короткое уведомление о переходе
  на автоном с ссылкой на основной лендинг; machine/API-запросы получают явный `410`
  с безопасным кодом ошибки, без редиректа POST, SPA fallback или ложного `200`.
  Внутри API отсутствующие маршруты дают `404`; smoke различает эти две границы.
- Точные домены/алиасы/путь уведомления фиксируются по DNS-инвентаризации до реализации edge.
  Старые endpoint-адреса не перенаправляются на чужой tenant или новую лицензию.

## Данные, ключи и старые очереди

Предложение для первого переезда: полный проверенный перенос PostgreSQL с существующей
схемой, UUID, миграционным журналом и историей, без выборочного переписывания таблиц.
Отключение онлайна не означает удаление данных. Последующее уменьшение базы — отдельная задача.
Object storage переносится по инвентарю ключей/версий и связям с документами; сохранность
истории подтверждается сравнением, не только успешным `pg_restore`.

Лицензионные `issuer`, `kid`, доверенные ключи, привязки host/site и монотонные sequence
должны сохраниться. Ключи расшифровки старой диагностики и почтовых payload также нужны
для читаемости перенесённых данных. Секреты не попадают в Git, логи и документы миграции.
Локальный ключ подписи обновлений автонома остаётся локальным; переезд сервера не основание
переносить его на VM или перевыпускать уже подписанные релизы.

Новый процесс не должен подхватывать старые cloud-задачи при старте. Перед включением workers
инвентаризировать их состояния, остановить старого исполнителя и проверить отсутствие двойного
выполнения. Старые письма активации кабинета нельзя отправлять через сохранённую общую очередь.
Нужна политика по типам почты и durable-состояниям: активные платформенные письма продолжаются,
отключённые намерения помечаются прекращёнными с причиной/аудитом, без массового удаления истории.
При восстановлении тестовой копии все внешние отправки и фоновые интеграции выключены.

После переключения допускается один активный писатель и один набор исполнителей.
Rollback после новых записей не равен переключению DNS на старую базу: нужны остановка
записей, перенос/сверка новых данных и согласованный порядок восстановления. Это часть будущего runbook.

## Поставка и секреты

Подготовить облегчённый edge и профиль API, минимальный документированный env-контракт,
проверку старта без tenant/device/CHЗ-секретов, manifest состава сервисов и smoke для двух сайтов.
Настройки CORS, cookies, TLS, CSP и доверенного proxy должны соответствовать реальным адресам;
замена S3 endpoint сама по себе не обновит сохранённые URL и CSP.

Сохранить release-images / protected deploy, точный source/tooling SHA, immutable digests,
миграции отдельным этапом, preflight, запись результата и контролируемый rollback.
Провайдер-независимое ядро deployment отделить от получения секретов и адресов Яндекса.
На этапе кода определить контракт защищённого runtime-файла/secret mounts; конкретный механизм
доставки и восстановления ключей на Timeweb выбрать с инфраструктурой. Не добавлять прямой
резервный поиск секретов в Yandex metadata при отсутствии файла.

## Приёмка подготовки кода

- Реальный bootstrap профиля и OpenAPI-инвентарь содержат только разрешённые поверхности.
  Проверить отсутствие tenant/device routes на прямом API и на каждом публичном домене.
- Кабинетная cookie и device credential не дают платформенных прав; platform capabilities,
  MFA, tenant scope и точные поля аудита проходят существующие и новые негативные тесты.
- Создание офлайн-тенанта → коммерческие права → запрос лицензии со статистикой → выдача →
  импорт в автоном работает на синтетических данных; формат и доверие существующих лицензий сохранены.
- Реестр workers/cron/boot-repair содержит только разрешённые задачи. Восстановленные старые
  производственные задания и кабинетные письма не исполняются; платформенная почта/отчёты работают.
- Readiness проверяет фактический разрешённый набор, PostgreSQL, почту и storage.
  Не уменьшать требования посредством отключения проверки неисправных зависимостей.
- Платформенные отчёты, документы, диагностика и страницы SaaS не превращают старую cloud
  статистику в текущую статистику автонома; недоступные операции не остаются активными кнопками.
- CI включает затронутые API/DB/contracts/SaaS/landing, production bundle и browser smoke.
  Обновить `tools/ci/affected.mjs` и workflow при добавлении deployment-поверхности.
- Проверить восстановление в изолированном PostgreSQL и S3-совместимом окружении без внешних
  отправок. Сверить схему/UUID/ключевые связи/счётчики/лицензионные последовательности/артефакты.
- Реальная выдача лицензии, SMTP, S3, DNS/TLS и restore на Timeweb остаются отдельными
  внешними проверками. Зелёные локальные тесты не подтверждают их выполнение.

## Граница текущей работы

Независимая проверка полноты выявила зависимость предложений поддержки от закрываемого
клиентского endpoint принятия решения. Она проверена по обоим support-chat контроллерам;
предлагаемое поведение зафиксировано выше и входит в согласование документа.

Разрешены подробный план и локальная реализация подготовки кода. DNS, инфраструктура,
продуктивные данные и подписанные релизы не изменяются. Тариф и число VM не утверждены;
инвентаризация фактических CRM-серверов ещё не выполнена. Состав решения согласован;
коммит/публикация, фактическое развёртывание и переключение серверов не входят в этот этап.
