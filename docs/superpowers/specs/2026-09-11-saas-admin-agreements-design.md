# Реестр договоров в saas-admin с генерацией печатной формы — дизайн

**Дата:** 2026-09-11
**Статус:** утверждён владельцем по чанкам 1 и 2
**Контекст:** проект стандартного договора MKR-AGR-01 уже собран
генератором `packages/legal-documents` и лежит локально
(`packages/legal-documents/.local/`, папка в `.gitignore`). Текст готов,
но заполняется руками в Word и нигде не учитывается. Договор может быть
заключён до регистрации тенанта, поэтому реестру нужно жить в
платформенной панели, а не в кабинете.

## Что делаем

Новый раздел «Договоры» в `apps/saas-admin`: реестр записей, получение
реквизитов контрагента через уже существующую интеграцию DaData, ручная
правка любого поля поверх подсказки и генерация печатной формы —
договора со всеми десятью приложениями одним DOCX.

Английский перевод договора — вторая фаза и отдельная спека. Здесь
закладывается только параметр локали в интерфейсе шаблона.

## Принятые решения

| Вопрос                          | Решение                                                                                                                     |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Объём печатной формы            | Весь пакет одним файлом: договор + 10 приложений. Формы № 5–8 и № 10 печатаются пустыми бланками — так и задумано в п. 11.4 |
| Источник заполненного документа | Шаблон становится функцией данных, рендер в DOCX через существующий `renderLegalDocxDraft`                                  |
| Жизненный цикл                  | `draft` → `in_review` → `sent` → `signed` → `terminated`                                                                    |
| Связь с тенантом                | Ручная привязка, система подсказывает кандидатов по совпадению ИНН                                                          |
| Набор типизированных полей      | Шапка и реквизиты обеих сторон; приложения № 1 и № 3 остаются плейсхолдерами                                                |
| Английский вариант              | Информационный перевод того же договора, русский текст приоритетен — как в MKR-DPA-01                                       |
| Вложения                        | Загрузка подписанного экземпляра и сопутствующих файлов в карточку                                                          |

## Именование

`packages/platform-contracts` уже означает «Zod-схемы платформы».
Назвать домен `contracts` там — значит получить
`platformContractsContracts.contracts.create`. Поэтому в коде домен
называется **agreement**: таблицы `platform_agreements` и
`platform_agreement_documents`, модуль `platform-agreements`, маршрут
API `/platform/agreements`, маршрут панели `/agreements`, возможности
`agreements.read` и `agreements.write`. В интерфейсе подпись остаётся
«Договоры» и "Agreements".

## Слой шаблона: `packages/legal-documents`

`TENANT_AGREEMENT_CONTENT` заменяется функцией:

```ts
export function buildTenantAgreement(
  fields: TenantAgreementFields,
  locale: LegalLocale,
): LegalDocumentLocaleContent;
```

Русский текст остаётся на месте; интерполяциями становятся только точки
заполнения. Незаполненное поле печатает прежний литерал в квадратных
скобках через хелпер `field(value, "[плейсхолдер]")`, поэтому частично
заполненный черновик остаётся пригодным для печати и правки в Word.

Строки таблиц собираются в TypeScript, поэтому появляется условный
вывод, недоступный простой подстановке: строка КПП печатает «не
применяется» для ИП и значение для организации вместо того, чтобы
уносить в подписываемый документ формулировку на оба случая.

`docx` переводится из `devDependencies` в `dependencies` пакета: до сих
пор рендер жил только в CLI, теперь его вызывает API в рантайме.

Параметр `locale` появляется сразу, ветка `en` бросает ошибку до второй
фазы. Ретрофит локали после того, как схемы и вызовы разойдутся по трём
пакетам, дороже, чем неиспользуемый параметр сейчас.

### Состав `TenantAgreementFields`

Шапка: номер, дата заключения (гражданская дата), город.

Стороны — по структуре реквизитов на каждую: вид лица
(`individual` / `self_employed` / `sole_proprietor` / `legal_entity`),
наименование, ИНН, КПП, ОГРН или ОГРНИП, адрес, e-mail, телефон, банк,
БИК, расчётный и корреспондентский счета, налоговый режим.

Подписант заказчика: должность, Ф. И. О., основание полномочий.

Условия: компетентный суд для п. 11.3, ставка неустойки и предел для
п. 9.5.

Приложения № 1 и № 3 не входят в набор: их значения зависят от
конкретной сделки и пересекаются с разделами «Каталог» и «Предложения»,
где эти данные уже вводятся. Вытягивание приложения № 1 из связанной
оферты — отдельное решение после первой фазы.

## Данные: `packages/db/src/schema/agreements.ts`

Новый файл по образцу `platform-reports.ts`; платформенные таблицы не
складываются в `platform.ts` — вопреки названию там лежит тенантная
производственная схема.

**`platform_agreements`**

`id uuid` первичный ключ, `number text` с ограничением уникальности,
`status platform_agreement_status`, `conclusion_date date`, `city text`,
`tenant_id text` — nullable, внешний ключ на `organization.id`,
`counterparty_inn text`, `counterparty jsonb`, `contractor jsonb`,
`terms jsonb`, `signed_at timestamptz`, `signed_snapshot jsonb`,
`terminated_at timestamptz`, `termination_reason text`,
`created_by_platform_user_id text` — внешний ключ на `platform_users.id`,
`created_at` и `updated_at`.

ИНН контрагента хранится отдельной колонкой, а не только внутри
`counterparty`: по нему идут и поиск в списке, и подбор кандидатов на
привязку тенанта, и выражающий индекс по JSONB для этого хуже обычного.
Колонка заполняется из тех же данных, что и `counterparty`, одним
сервисным методом — расхождение исключается тестом.

Ограничения: `signed` требует непустого `signed_snapshot`; `terminated`
требует `terminated_at`. Индексы по `status`, `tenant_id` и
`counterparty_inn`.

**`platform_agreement_documents`** повторяет форму
`commercial_offer_documents`: `agreement_id`, `kind`
(`generated` | `attachment`), `filename`, `media_type`, `object_key`,
`sha256`, `byte_size`, `renderer_version` (только для сгенерированных),
`uploaded_by_platform_user_id` (только для вложений), `created_at`.

### Реквизиты Исполнителя

Наша сторона не вводится руками: значения читаются из
`operatorBillingProfiles`, который уже редактируется в
`/settings/organization`. При подписании они копируются в `contractor`
снапшотом, чтобы поздняя смена банка не переписала задним числом уже
подписанный документ.

### Нумерация

Автоматически `МКР-2026-0001`, счётчик в пределах года. Номер
вычисляется в той же транзакции, что и вставка записи, как максимум
существующего порядкового номера за год плюс один; уникальность
обеспечивает ограничение БД, а не проверка в приложении, и при
конфликте вставка повторяется. До подписания номер можно заменить
вручную — тогда автоматический счётчик к этой записи не применяется, но
ограничение уникальности продолжает действовать.

### Переходы и замораживание

Между `draft`, `in_review` и `sent` переходы разрешены в обе стороны:
клиент присылает правки после отправки, и это нормальный путь, а не
исключение. Поля редактируются, пока статус не стал `signed`.

Подписание записывает неизменяемый `signed_snapshot`, рендерит
финальный DOCX и сохраняет его в объектном хранилище с sha256. Из
`signed` возможен только переход в `terminated`.

Рендер черновика пишется в один стабильный ключ
`agreements/<id>/draft.docx` и переиспользует единственную строку с
`kind = 'draft'`, перезаписывая её при каждом рендере: в бакете остаётся
не больше одного превью на договор, а скачивание идёт по общей
конвенции с presigned URL. Подписание создаёт отдельный неизменяемый
объект с `kind = 'generated'` под content-addressed ключом. Класс
документа в шапке зависит от статуса — «ПРОЕКТ ДОГОВОРА» до подписания
и «ДОГОВОР» после.

## Контракты API: `packages/platform-contracts/src/agreements.ts`

`platformAgreementContracts` по образцу вертикали `offers`:

- `list` — фильтры по статусу и признаку «без тенанта», поиск по номеру,
  ИНН и наименованию, страничная выдача;
- `detail`, `create`, `update` (только до `signed`);
- `transition` — целевой статус и `terminationReason` для прекращения;
- `linkTenant`, `unlinkTenant`, `tenantCandidates` — кандидаты по ИНН
  договора;
- `documents.list`, `documents.download`;
- `attachments.upload`, `attachments.delete`.

Скачивание файла — бинарный ответ, а не JSON-конверт. План реализации
сначала уточняет, как это уже сделано для выгрузки артефактов в
`platform-reports`, и повторяет ту же конвенцию, включая описание в
OpenAPI.

Клиент и контроллер разбирают тело одной и той же схемой, как в
`pages/offers/api.ts` и `platform-offers.controller.ts`.

## Модуль API: `apps/api/src/modules/platform-agreements/`

`platform-agreements.module.ts`, `.controller.ts`, `.service.ts`,
`agreement-document.service.ts`, `dto.ts`; регистрация в
`app.module.ts`.

`agreement-document.service.ts` собирает `TenantAgreementFields` из
записи, вызывает `buildTenantAgreement`, рендерит через
`renderLegalDocxDraft` и либо отдаёт поток, либо кладёт объект в
хранилище через `ObjectStorageService` и создаёт строку документа.

DaData не трогаем: панель ходит в существующие
`GET /platform/suggestions/{organizations,addresses,banks}`.

## Интерфейс: `apps/saas-admin/src/pages/agreements/`

В навигации `AppShell.tsx` — группа commerce, сразу после «Каталога»:
порядок договор → предложение → счёт → акт → платёж отражает реальную
последовательность. Пункты группы перенумеровываются, подписи заводятся
в `i18n/ru.json` и `i18n/en.json`.

**Список.** Номер, контрагент, ИНН, статус, дата заключения, признак
привязки к тенанту, дата подписания. Фильтры по статусу и «без
тенанта».

**Создание.** ИНН вводится через `OrganizationSuggestField`, выбор
подсказки заполняет наименование, ОГРН, КПП и адрес; банк — через
`BankSuggestField`. Дальше подписант, основание полномочий, суд и
неустойка. Любое поле правится вручную поверх подсказки, ручное
значение приоритетно.

**Карточка.** Поля переходят в режим чтения после подписания;
переключатель статуса; привязка тенанта со списком кандидатов по ИНН;
кнопка скачивания проекта; список сгенерированных документов и
вложений с загрузкой файла.

Модель реквизитов контрагента переиспользует четыре вида лица и их
валидацию ИНН, КПП и ОГРН из `pages/legal/LegalProfileForm.tsx`. Второй
реализации тех же правил не появляется.

## Доступ, аудит и данные

Добавляется пара возможностей `agreements.read` и `agreements.write` в
`packages/platform-contracts/src/platform-auth.ts`: `platform_admin` и
`accountant` получают обе, `support` — только чтение.
`platformPrincipalSchema.superRefine` требует точного совпадения списка
возможностей с ролью, поэтому ответ `/me` меняется и все фикстуры
принципала правятся тем же коммитом.

Глобальный платформенный guard уже отказывает по умолчанию и
отклоняет кабинетные сессии и учётные данные станций; каждый новый
handler объявляет политику явно, иначе guard вернёт `missing_policy`.

Аудит пишется на создание, изменение, переход статуса, привязку и
отвязку тенанта, рендер документа, загрузку и удаление вложения. Записи
содержат точного актора, идентификатор договора и переход «было →
стало»; проверки в тестах сверяют поля, а не прирост числа строк.

Вложения: allowlist `application/pdf`, `application/vnd.openxmlformats-officedocument.wordprocessingml.document`,
`image/png`, `image/jpeg`; предел размера одного файла — 20 МБ; sha256
считается на сервере по фактически принятым байтам; тип проверяется по
содержимому, а не только по заголовку и расширению; ключ объекта не
собирается из присланного имени файла; исходное имя хранится отдельным
полем и используется только при отдаче; скачивание — по
короткоживущему presigned URL.

Реквизиты контрагента — сведения о юридическом лице, но Ф. И. О.
подписанта является персональными данными. Обработка укладывается в
собственную цель заключения и исполнения договора, описанную в п. 3-В.5
самого договора; отдельное поручение на обработку для этого не
требуется.

## Проверки

`@markiro/legal-documents` — подстановка каждого поля; сохранение
плейсхолдера у незаполненного; разное поведение строки КПП для ИП и
организации; детерминизм байтов при одинаковых данных; неизменность
байтов уже опубликованных артефактов MKR-DPA-01 и MKR-BRD-01.

`@markiro/db` — тесты схемы и миграции, включая оба check-ограничения.

`apps/api` — e2e на CRUD; отказ роли `support` на запись; запрет
перехода из `signed` обратно в редактируемые статусы; неизменяемость
полей после подписания; подбор кандидатов по ИНН; наличие `sha256` и
`byte_size` в строке документа; отклонение недопустимого типа вложения;
проверки аудита с точными полями.

`apps/saas-admin` — автозаполнение из DaData; приоритет ручной правки;
валидация по виду контрагента; блокировка контролов после подписания.

`tools/ci/affected.mjs` и `.github/workflows/ci.yml` — убедиться, что
новые пути поднимают джобы api и saas-admin.

## Вне объёма

- Дополнительные соглашения и редакции подписанного договора. Изменение
  подписанного договора в первой фазе оформляется новой записью;
  автоматической связи «взамен» не будет.
- Заполнение приложения № 1 из связанной оферты.
- PDF: LibreOffice есть только в CI, в рантайме конвертера нет.
- Регистрация MKR-AGR-01 в `LEGAL_RELEASES`, маршрут на лендинге,
  страница `/d/…` и запись в аттестации. Договор остаётся приватным
  документом панели, а Data Matrix в подвале ведёт на `/legal/`.
- Английский перевод договора — вторая фаза, отдельная спека.
- Отправка договора клиенту письмом из панели.

## Известная зависимость

Блок `table` в модели `LegalBlock` пока не рендерится компонентами
лендинга `LegalDocument.astro` и `InstructionDocument.astro`. Для этой
работы это не блокер, потому что MKR-AGR-01 не публикуется, но
публикация любого документа с таблицей требует сначала закрыть тот
пробел.
