## Результат первого шага

После отказа credential Station и ТСД прекращают работу с этим ключом, сохраняют
накопленные данные и переходят к восстановлению. Авторизованное повторное
подключение той же записи устройства позволяет продолжить отправку прежних
данных без смены event ID, sequence, batch digest, снимков и сохранённых байтов.
Подключение другой организации или другого устройства не получает эту очередь.

Это необходимое основание переноса лицензии. Сервер меняет ключ того же durable
device ID без второго слота, а Station и ТСД сохраняют каналы этого владельца
после отказа ключа и открывают их только после проверенного same-device recovery.

P1B разделяется на последовательные поставки:

1. **P1B.1, этот проект:** принадлежность сохранённых данных, безопасный отказ
   credential и повторное подключение того же устройства, проверка восстановления.
2. **P1B.2:** коммерческие назначения, отмена резерва, подготовка замены и выбор
   устройств при снижении лимита, соответствующие экраны кабинета и SaaS.
3. **P1B.3:** оставшиеся онлайн-адаптеры inventory, CommerceML, labelEditor,
   pallets и инвентаризация фактических public API потребителей.

P1B.2/P1B.3 потребуют своих конкретных проектов. Подписанные офлайн-допуски и
границы завершения остаются P1C; включение новых ограничений — P1D.

## Что подтверждено реализованным кодом

- `StationPairingService` сохраняет ID, проверяет kind приложения, атомарно
  погашает код и заменяет ключ. Восстановление ранее revoked записи заново
  проверяет свободное место; активная запись второго места не занимает.
- Текущий pairing требует действующего subscription write access. Этот проект
  не обещает восстановление после истечения подписки через обход такой проверки.
- ТСД связывает retained-данные с долговечным owner и поколением credential.
  `401/STATION_CREDENTIAL_REVOKED` закрывает допуск старого поколения, удаляет
  отклонённый секрет и roster, но сохраняет operational-таблицы и точные batch,
  sequence, payload и print bytes. Поздний ответ старого поколения не может
  очистить новый ключ или подтвердить его работу.
- Provisioning ТСД сохраняет durable intent до публикации config/credential,
  проверяет нормализованный origin, tenant, device и kind, восстанавливается
  после прерывания и не присваивает неопределённую или чужую базу.
- Station хранит owner отдельно от текущего ключа и открывает прежние ownership
  hashes только после проверенного same-device recovery. Все read/pin/send/ack,
  inventory, печать, исключения, close и retention проходят эту границу.

## Правила поведения

1. Принадлежность данных определяется сохранёнными server origin, tenant ID и
   durable device ID. Линия, имя, оператор и текущий API key её не заменяют.
2. Credential generation определяет текущую техническую сессию и допуск её
   незавершённых действий. Локальная generation не доказывает коммерческое право
   в прошлом и не заменяет подписанный grant P1C.
3. Отказ ключа блокирует новую локальную работу и новые запросы этого поколения.
   Ранее выданные права на локальную запись должны завершиться либо оставить
   долговечное состояние восстановления. Навигация сама по себе их не завершает.
4. Сохранённые сканы, outbox, inventory, закрытия смен, исключения, конфликты,
   контейнеры, выданные SSCC, печатные задания и события не удаляются по причине
   отказа ключа. Сохраняются все каналы подтверждений, закреплённые batch IDs,
   sequence, task snapshots и байты печати.
5. Отозванный credential остаётся недействительным. После фиксации восстановления
   удаляется секрет ключа и доступ к воспроизводимым операторским секретам.
   Сохранённая очередь не становится доступна неавторизованному оператору.
6. Поздний отказ старого запроса не запечатывает новое поколение. Поздний успех
   не записывается в новую область владельца. Контекст запроса, его подтверждения
   и локального commit остаётся связан с исходным owner/generation.
7. Повторное подключение возможно только к прежним server/tenant/device/kind.
   При несовпадении не заменяются локальные config, roster и credential, не
   стирается evidence и не перепривязываются старые записи.
8. Новый ключ того же устройства может возобновить только явно сопоставленные
   старые очереди. Исходная принадлежность строк сохраняется; восстановления
   «всех данных на этом компьютере» без проверки владельца нет.
9. Состояние печати `sending/delivery unknown` после прерывания остаётся
   неоднозначным. Восстановление не означает автоматическую повторную печать.
10. Ошибка pairing или утрата ответа оставляет данные закрытыми и сохранёнными.
    Для повторной выдачи кода используется прежняя durable запись устройства,
    а не создание новой reservation.

## Граница серверного интерфейса

Обычный `/station/pair` и его старые DTO сохраняют совместимость.
Для восстановления реализован отдельный `POST /station/pair/recovery`:
короткий pairing-код и ожидаемые tenant/device/kind. Отдельный маршрут позволяет
старому серверу ответить 404 до ротации чужого ключа; новый клиент не откатывается
молча на обычный pairing при наличии сохранённых данных.

Ожидаемые IDs — ограничение назначения кода, не доказательство полномочий.
Авторизация по-прежнему опирается на код, выданный уполномоченным пользователем,
его tenant/device-привязку, rate limit, срок и одноразовый claim. Ошибка не
раскрывает чужое устройство. Ключ возвращается один раз, ответ `no-store`.

Сервис сравнивает ожидаемую идентичность до provisioning ключа и повторяет
проверку kind/ожидаемой записи под существующим quota/row lock перед claim.
Несовпадение не погашает код и не меняет действующий credential; созданный
кандидат при проигранной гонке удаляется существующей компенсацией.

Проверки подписки, квоты, источника запроса и security сохраняются. В частности,
восстановление revoked записи не становится бесплатным enrollment поверх лимита.
Кабинет выдаёт код прежней записи существующим авторизованным путём.
Новый endpoint не является администраторским импортом доказательств и не выдаёт
ограниченный recovery credential после expiry: это отдельная будущая граница.

API и клиенты получают согласованный strict-контракт восстановления; неизвестный
или несовместимый сервер явно оставляет клиента в сохранённом состоянии.
Поля нового ответа не дописываются безусловно в старый provisioning DTO.
Маршрут, ошибки и trust domain включаются в OpenAPI и route inventory.

## Локальная модель и восстановление

Хранилище разделяет неизменяемую принадлежность retained-данных и текущее
поколение credential. На ТСД сохраняется один владелец operational database;
этот этап не превращает её в многопользовательское или многотенантное хранилище.
Нормализованный API origin фиксируется при привязке и сравнивается при
восстановлении; изменение адреса сервера не трактуется как то же окружение автоматически.

Долговечное состояние перехода имеет стадии `active`, `sealing`, `sealed`,
`restoring`. Идемпотентное завершение незаконченной стадии выполняется до
старта фоновой синхронизации и входа оператора после перезапуска.

Последовательность отказа: закрыть допуск поколения, записать намерение sealing,
дождаться либо безопасно зафиксировать уже начатые операции, сохранить owner и
границы очередей, удалить недействительный секрет/операторский доступ, завершить
sealed. Ошибка между шагами не возвращает приложение к обычной работе.
Старое сообщение об отказе сравнивается с исходной generation, а не просто
отправляется глобальным событием без идентичности.

Последовательность восстановления: получить код прежней записи, проверить
ответ сервера и owner, подготовить новые credentials/roster, записать переход,
опубликовать новое поколение, затем разрешить восстановление старых каналов.
CredentialStore и Room/config-файл не являются общей транзакцией: используется
долговечное намерение с идемпотентным завершением, а не несколько независимых
записей с предположением об атомарности.

Для Station сохраняются существующие commit leases и pooled SQLite ограничения.
Связь старого ownership с восстановленным устройством открывает доступ к нужным
очередям, acknowledgements и восстановлению печати; новые события создаются под
новым поколением. Печатные bytes и старые payload/digest не переписываются.
Отдельно проверяются все места фильтрации ownership: sync, batch pins,
job recovery, события и retention. Поддержка одного чтения очереди недостаточна.

## Миграция сохранённых данных

Добавляются новые миграции Room и авторитетного Station SQLite; прежние миграции
не редактируются. Изменение серверной схемы требуется только при доказанной
необходимости в плане реализации; этот шаг не вводит таблицы лицензирования.

При первом старте новая версия останавливает workers до окончания миграции.
Для прежней одно-владельческой базы ТСД текущая неповреждённая config-привязка
служит источником владельца существующего набора данных. Это наблюдение при
обновлении, а не утверждение о прошлой коммерческой авторизации.

Если данные существуют без достоверной config-привязки или содержат противоречия,
они сохраняются в недоступном для обычного sync состоянии `owner_unresolved`.
Следующий pairing не присваивает их новому владельцу. UI сообщает о необходимости
разбора. Административный импорт и автоматическое восстановление неопределённой
принадлежности не входят в эту поставку.

На Station старые credential ownership сохраняются. Связь с durable owner
создаётся только из сохранённого согласованного контекста. Восстановление не
расширяет выборку на чужие или неопределённые ownership и не обнуляет счётчики.
Миграция должна возобновляться после сбоя; повторный запуск не дублирует строки.

## Экран восстановления

Station и ТСД показывают причину потери доступа и сохранённое устройство,
сводку ожидающих отправки данных по каналам и действие повторного подключения.
При отсутствии доказанных счётчиков показывается неизвестность, а не ноль.
Не показываются ключи, код pairing в журнале, денежные детали или внутренние
технические поколения. RU/EN добавляются одновременно.

После успешного подключения виден результат восстановления очередей. Отдельно
показываются ещё ожидающая загрузка, конфликт/quarantine и печать с неизвестным
результатом. Завершённое подключение не называется завершённой синхронизацией.
Другой owner, неподдерживаемый сервер и повреждённое состояние имеют точную
ошибку и сохраняют данные. Экран не предлагает удалить их для продолжения.

## Проверяемые критерии реализации

1. API: tenant/device/kind mismatch не погашает код и не отзывает чужой ключ;
   rate limit и прежняя авторизация сохранены; concurrent claim имеет одного
   победителя; компенсация кандидата проверена. Подключение той же активной
   записи сохраняет ID и число мест, revoked восстановление проверяет ёмкость.
2. ТСД: вместо теста удаления operational данных — полное сохранение pending
   scans, inventory, labels, boxes, exceptions и close с точными ID/digests.
   Недействительный ключ и доступ операторов удалены; чужой owner заблокирован.
3. Оба клиента: поздние success/401 старой generation, перезапуск на каждой
   стадии, сбой credential/config публикации и повтор вызова не теряют данные,
   не воскресают старую работу и не очищают новое подключение.
4. Миграции: прежняя база с config и pending данными; база без config;
   противоречивый owner; повтор и прерывание миграции. Прежние payload и bytes
   неизменны, неопределённые данные не отправляются следующему устройству.
5. Восстановление от начала до конца: сохранить данные под старым ключом,
   отказать ему, перезапустить клиент, переподключить тот же device, отправить
   прежний batch новым ключом и подтвердить exact server acknowledgement.
   Проверить каждый канал, включая labels и inventory; иной owner не проходит.
6. Печать: незавершённая отправка остаётся `delivery unknown`; автоматического
   повторного физического вывода нет. Явное восстановление использует сохранённые
   bytes, действующие правила причины/проверки и прежний task scope.
7. Gates затронутых API/DB/contracts/Station пакетов, consumer tests, format и
   diff check; Android отдельно `testDebugUnitTest`, `lintDebug`, `assembleDebug`.
   Реальные DB integration tests выполняются без скрытых инфраструктурных skips.
8. RU/EN, обычный/narrow Station и экран ТСД проверяются отдельно от unit tests.
   Реальные принтер, сканер, Windows/Android hardware, установка и rollout
   фиксируются только при фактической проверке.

## Что этот проект не закрывает

Перенос на другой durable device ID/другое железо, коммерческое освобождение
места, retained selection и downgrade ещё не реализованы этим шагом. Подписанные
task grants, сроки офлайн-работы, security recovery при истекшей подписке,
административный импорт неопределённых данных и включение тарификации остаются
следующими явно обозначенными частями. Данные при таких ограничениях сохраняются.

Остальные online adapters P1B остаются в реестре покрытия. Исследование выявило,
что обычный `TenantGuard` распознаёт station API keys, а public keys имеют отдельную
конфигурацию выпуска. Нельзя объявить все запросы с `x-api-key` публичным API или
включить этим шагом ранее отсутствовавший публичный API surface. CommerceML имеет
собственную session-авторизацию и отличается от `publicApi`.

Shared contracts прошли **247 тестов**. Финальный полный API-прогон прошёл
**3667 тестов**, а три локальных infrastructure cases с реальными Mailpit/MinIO
прошли отдельно; единственный live National Catalog case не запускался. Station
прошёл **1471 тест**, пакет `@markiro/db` — **440**. До интеграции с текущим main
ТСД прошёл **596 тестов в 92 файлах**, `lintDebug` и `assembleDebug`; APK этого этапа
имеет SHA-256 `acc302f8983cd06ed3d0edec1b0a4b6499b8e47caeb29835b9a26e874057ef77`.

Общий gate принятой реализации `e32005dbc` выполнил **52/52 задачи** lint, typecheck,
test и build: **9392 теста прошли, 26 пропущены**. Дополнительно **22 inventory-теста**
прошли с выделенной PostgreSQL-базой: Turbo не передал их переменную подключения.
Эта проверка и три локальных infrastructure cases выше остаются отдельными
свидетельствами; они не объявляются повторным полным прогоном после интеграции.

После интеграции `origin/main` (`fca8ba8d5`, Handheld PR #519–#521) ТСД прошёл
**614 тестов в 95 файлах** без ошибок и пропусков, `lintDebug` и `assembleDebug`.
Итоговый интегрированный APK имеет SHA-256
`02d5d9da45e448b8ca2ec8e91571859b756ee89c41c6a2aae4968886fc67e248`.

регрессионным прогоном: 23 теста, один ожидаемый отказ до исправления и ни одного
после. Production-bundle contracts объединённой конфигурации прошли **549 тестов**
без пропусков. Node/API/shared-contract runtime inputs не изменились; общий gate
