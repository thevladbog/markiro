# Markiro: приватный чат и эскалация в обращение

Дата: 2026-10-06. Статус: письменно согласована пользователем 2026-10-06; реализация не начата.

## Цель и согласованные решения

В кабинете admin.markiro.app пользователь общается с SaaS-поддержкой. Оператор отвечает в Chatwoot. Если вопрос нельзя решить в чате, оператор вручную инициирует создание обращения Markiro. Клиент подтверждает перенос переписки и её доступность owner/admin своего тенанта.

Первая версия: текст, история, периодическое обновление без WebSocket. Без файлов в чате, индикатора набора, автосоздания по таймауту и автоматического закрытия обращения. Существующие вложения обращений сохраняются без изменения.

Чаты лендингов markiro.app и будущего us.markiro.app остаются отдельными sales-каналами. Этот документ не реализует виджеты лендингов и не создаёт лиды Twenty.

## Архитектура и альтернативы

Выбранный подход: кабинет → backend Markiro → отдельный API inbox Chatwoot. Backend управляет identity, mapping и доступом; Chatwoot используется оператором как интерфейс переписки. Markiro/PostgreSQL остаётся источником истины для обращений и согласий.

Обычный website widget с HMAC не выбран: ранее на установленном Chatwoot v4.17.0-ce проверка set_user отклоняла неверный hash, но анонимная отправка сообщения всё равно проходила. HMAC не обеспечивает требуемую границу admission.

Proxy всего widget-трафика не выбран: пришлось бы контролировать widget JWT, дополнительные HTTP/WebSocket-маршруты и отзыв доступа. API inbox сам по себе также не считается защитой: публичные Client API этого inbox не должны давать обход Markiro.

Новая интеграция не использует существующий Support website inbox. Его synthetic-историю не импортировать как клиентскую. Sales inbox и их public API не блокировать глобально.

## Доступ и границы доверия

- Предлагаемая политика первого выпуска: чат доступен любому текущему участнику тенанта через кабинет, независимо от billing-права; каждый видит только свой чат в этом тенанте. Это новое правило для чата, оно не расширяет права чтения существующих обращений.
- Каждый read/send/consent проверяет действующую cabinet-session и актуальное членство. station/handheld API keys и platform-session не заменяют cabinet-session.
- Tenant и user берутся из серверного principal. Browser не выбирает Chatwoot account/inbox/contact/conversation ID. UUID другого пользователя или тенанта не должен открывать историю.
- Операторская эскалация доступна через SaaS-admin с актуальной platform-сессией и billing.write. Аккаунт агента Chatwoot сам по себе не даёт платформенных полномочий.
- В браузер не передаются Chatwoot API key, contact source ID, widget JWT, pubsub token или HMAC secret. Серверные секреты хранятся вне Git и логов.
- API inbox и private-сообщения доступны backend/operator API; прямые анонимные Client API этого inbox закрыты на внешней границе. До доказательства отсутствия обхода публикация чата запрещена.
- Logout, смена тенанта и потеря членства прекращают отправку/опрос, очищают клиентскую историю. Поздний ответ старого запроса не записывается в новый контекст. Ответы не кешируются общим HTTP-кешем; React-query keys включают tenant/user.
- Подписка read-only не должна лишать клиента возможности обратиться за помощью; для новых маршрутов явно объявляется соответствующая subscription-policy.

## Чат

Уникальная серверная связь `(tenantId, userId)` определяет собственный канал истории. Модель сохраняет отдельные эпизоды диалога: после эскалации новый независимый вопрос может начать новый эпизод, не прикрепляясь к старому обращению.

Backend создаёт контакт и conversation через серверный адаптер Chatwoot. Сообщения текстовые, максимум 2000 символов; пустой текст отклоняется. Один клиентский message UUID имеет устойчивый mapping на удалённое сообщение, чтобы потеря HTTP-ответа не приводила к слепому повторному созданию. Неоднозначный результат удалённой отправки требует reconciliation; нельзя заявлять exactly-once, полагаясь только на повтор POST.

История возвращает только подтверждённые входящие/исходящие публичные текстовые сообщения ожидаемых account/inbox/conversation. Private notes, activity-события, системные метаданные и удалённые служебные credentials клиенту не возвращаются. Ошибка разбора не превращается в разрешение доступа.

Опрос в открытом чате — раз в 5 секунд; в скрытой вкладке приостанавливается. Неуспех отображается как ошибка соединения с возможностью повторить; нет ложного сообщения об успешной отправке. Все тексты переведены RU/EN существующим механизмом i18n.

## Ручная эскалация и согласие

1. Оператор открывает диалог в разделе поддержки SaaS-admin, указывает заголовок и краткое описание проблемы и нажимает «Предложить создание обращения». В Chatwoot он продолжает вести переписку; первая версия не добавляет кастомное приложение внутрь Chatwoot.
2. Backend фиксирует pending-предложение для конкретного эпизода, оператора, user и tenant. Одновременно active-предложение одно. Создание обычной заявки на этом этапе не происходит.
3. В кабинете клиент видит summary и предупреждение: «Переписка по этому вопросу будет добавлена в обращение. Её смогут читать владелец и администраторы вашей организации, а также поддержка Markiro. Новые сообщения этого диалога тоже будут добавляться». Только явное подтверждение разрешает перенос; отказ сохраняет приватный чат.
4. Согласие привязано к версии предупреждения, эпизоду, user/tenant, proposal и summary. Изменённое предложение требует нового подтверждения. Удалённое членство или смена тенанта делают подтверждение недопустимым.
5. После согласия backend создаёт существующее обращение с новым типом support, summary в description, исходным клиентом отдельно от platform-оператора и номером BR. Создание оператором не имитирует вызов от клиента без его полномочий: новая операция имеет отдельный проверенный trust domain и аудит.
6. В транзакции сохраняются consent, обращение, связь эпизода и outbox-событие импорта. Unique-ограничение на эпизод исключает две заявки при конкурентных подтверждениях/действиях. Повтор возвращает ранее созданную заявку.
7. Клиент получает номер и статус. Owner/admin может открыть существующую detail-страницу. Manager/member видит в своём чате факт эскалации и статус именно связанного собственного обращения, но не получает billing.read и не видит остальные заявки/коммерческие события тенанта.

Согласие — продуктовая фиксация изменения видимости, не утверждение юридической достаточности согласия на обработку персональных данных. Отмена уже принятого переноса не обещает изъятие уже прочитанных данных.

## Импорт истории и продолжение

Snapshot содержит все публичные текстовые сообщения эпизода до фиксированной границы согласия: автора/сторону, дату и текст. Никакого молчаливого обрезания по 4000/2000 символов.

Transcript — отдельные связанные записи с provenance `(account, inbox, conversation, messageId)` и original timestamp. Это не tenant_reply и не platform_comment: импорт не обходит статусный запрет существующего reply и не подменяет автора. Для transcript сохраняется отдельный контракт чтения; private notes не помещаются в общую events/metadata.

Новые публичные сообщения того же эпизода дополняют transcript в любом статусе, не меняя статус обращения. Закрытие Chatwoot conversation не завершает заявку. completed/cancelled не переоткрываются автоматически; новый вопрос использует новый эпизод и отдельное согласие.

Worker выполняет reconciliation с Chatwoot по серверному mapping. Webhooks не обязательны в первой версии: durable job и периодический опрос позволяют импортировать сообщения, даже когда клиент закрыл вкладку. Постоянный cursor/checkpoint, overlap-перечитывание и unique source key исключают пропуск на границе и повторные строки. После рестарта pending/outbox работа восстанавливается. Private notes никогда не импортируются, независимо от порядка доставки.

Сбой Chatwoot оставляет обращение с видимым «История синхронизируется / ошибка синхронизации», а не с ложной отметкой полноты. Клиентские страницы и операторский интерфейс показывают отставание. Ошибки и retries ограничены и наблюдаемы, содержимое переписки не попадает в технические логи.

## Изменяемые области

- `packages/db`: новые таблицы server mapping, episodes, proposals/consent, imported messages, outbox; additive migration; support в разрешённых типах обращений. Существующие данные не переписывать.
- `packages/platform-contracts`: support enum и отдельные strict-контракты чата/эскалации/transcript; API и SaaS-admin обновляются вместе.
- `apps/api`: отдельный support-chat module, Chatwoot server adapter, access policies, escalation transaction и durable worker. Расширение detail чтением transcript без ослабления billing guards.
- `apps/admin`: приватный чат, подтверждение переноса, состояние синхронизации и transcript в заявке; изолированные tenant/user cache keys, RU/EN.
- `apps/saas-admin`: список/карточка приватных support episodes для уполномоченного оператора и предложение эскалации; existing request workspace остаётся управляющим.
- Fucina: новый API inbox, конфигурация секретов и точечное ограничение публичного доступа; изменения production выполняются отдельным согласованным этапом после локальных проверок.

## Проверки и критерии приёмки

1. Cabinet и platform auth раздельны; anonymous, device key, чужой tenant/user, удалённое членство, недостаточные platform capabilities отклоняются.
2. Same user в двух тенантах и два user одного тенанта имеют разную историю. Поздний response после переключения/выхода не рисует старые данные.
3. Клиент видит operator reply; internal note и activity не видны в чате и transcript.
4. Нет согласия/отказ/устаревшее предложение → нет заявки и нет расширения видимости. Concurrent approve/retry → одна заявка, одно согласие, один audit fact на фактическую операцию.
5. Полная длинная история переносится с датами и авторами; boundary messages, повторная доставка, out-of-order, lost response и restart не теряют/не дублируют строки.
6. Tenant reply сохраняет текущий clarification_required gate. Transcript import и завершение чата не меняют статус. Обычные billing-сценарии и вложения не регрессируют.
7. Own-chat manager/member может подтвердить перенос и видеть ограниченный status; не может открыть billing detail или заявки коллег.
8. Chatwoot недоступен → понятная ошибка/отложенная синхронизация. Private данные не уходят в логи, Git, браузерные credentials и общие кеши.
9. Реальный отрицательный probe напрямую в новый API inbox доказывает отсутствие анонимного read/send обхода. Sales продолжает работать. Без этого security gate закрыт.
10. DB tests на изолированной PostgreSQL, контракт/OpenAPI inventory tests, API/admin/saas-admin unit/integration gates и browser RU/EN. Deployment, backup/restore и юридическая оценка — отдельные доказательства, не выводятся из green unit tests.

## Порядок работ и границы готовности

После письменного согласования: подробный план с интерфейсами и тестами → изолированный checkout от согласованной базы → schema/contracts → backend identity/transport → consent/escalation/import worker → cabinet/operator UI → независимая проверка и полный набор gates → отдельное согласование deployment.

Предпочтённый ранее режим работы сохраняется: отдельный исполнитель и проверка этапов. Нет разрешения на commit, push, PR, deploy или удаление synthetic production records в рамках оформления документа.

Документ не утверждает, что интеграция уже работает. API inbox, новый код, миграции и браузерные сценарии пока не реализованы. Отдельно потребуется подтвердить актуальность deployment configuration перед live-этапом и выбрать безопасный deployment порядок для enum/strict-contract расширения.
