# CommerceML: GTIN, автосвязь и фото товара — дизайн-спека

> Статус: утверждён к планированию (2026-08-28).
> Расширение канала `commerceml` из
> `docs/superpowers/specs/2026-07-29-commerceml-design.md` — тот документ
> описывает протокол, сессии, журнал и кандидатов; этот добавляет три
> возможности поверх уже работающего импорта: штрихкод (GTIN) из файла,
> автоматическую связь по GTIN и перекачку фото товара.
> Повод: клиент на СБИС. СБИС говорит тем же протоколом «Обмен с сайтом» и
> шлёт стандартный CommerceML XML на `/1c_exchange` — отдельный канал НЕ
> заводится (рассматривался и отклонён: дублирование реестра/кредов/экрана
> без доказанной нужды). Диагностическая JSON-выгрузка СБИС — не wire-формат,
> но подтверждает, что данные там есть: штрихкод EAN-13 в «Кодах» (тип 2),
> фото ссылкой на disk.sbis.ru, цена «Базовая».

## 1. Что решаем

Сегодня импорт умеет только цену (для уже связанных карточек) и кандидатов
(для несвязанных). Связь делается руками, штрихкод из файла выбрасывается,
фото не приезжает вовсе. После этого среза:

- `<Штрихкод>` товара парсится и нормализуется в GTIN-14;
- позиция с GTIN, совпавшим с `products.gtin14` тенанта, связывается
  автоматически (`products.external_ref = <Ид>`) — и уже в этом же раунде
  получает цену и фото;
- `<Картинка>` товара приводит к перекачке фото в карточку через существующий
  media-пайплайн (staging → active, webp, лимиты);
- кандидаты запоминают GTIN — для экрана связки и для автосвязи следующим
  обменом, когда карточка появится позже файла.

**Вне среза:** автосоздание карточек из обмена (каталог по-прежнему
принципиально не создаёт товары из внешней системы); несколько фото на
карточку (применяем первую `<Картинка>`); заполнение `price`/`priceType` у
кандидатов; настройка «выключить автосвязь» (v1 — всегда включена);
галерея/порядок фото.

## 2. Принятые решения (ответы владельца)

| Вопрос | Решение |
| --- | --- |
| Отдельная интеграция «СБИС»? | Нет — тот же канал `commerceml`, СБИС просто ещё один клиент протокола. |
| Связь | Авто по GTIN; несовпавшее — в кандидаты, как сейчас. |
| Фото | Заменять всегда (СБИС/1С — источник истины), с дедупом по checksum. |
| Цена | Как сейчас: обновляется каждый обмен, тип цены — настройка канала, только RUB. |

## 3. Парсер (`apps/api/src/modules/exchange/commerceml/parse.ts`)

Чисто аддитивно, существующие поля не меняются.

- `ParsedItem.barcode: string | null` — `<Штрихкод>` товара. Если у товара
  тега нет, но он есть у `<Предложение>` того же `<Ид>` в offers-файле —
  fallback на него (решается в apply, парсер offers просто отдаёт
  `ParsedOffer.barcode: string | null`).
- `ParsedItem.images: string[]` — все `<Картинка>` товара в порядке файла
  (тег повторяющийся → в `REPEATING_TAGS`). Применяется первая; остальные
  сознательно игнорируются (вне среза).
- Значения проходят через существующий `textOf` (entity-декод) и не
  валидируются парсером: валидация GTIN — не его работа (тот же принцип, что
  с типами цен).

## 4. GTIN (`apps/api/src/modules/exchange/commerceml/gtin.ts`, новый чистый модуль)

`normalizeGtin(raw: string): string | null`:

- принимает 8 (EAN-8), 12 (UPC-A), 13 (EAN-13), 14 (GTIN-14) цифр — после
  `trim()`; всё остальное (буквы, другая длина, пусто) → `null`;
- проверяет контрольную цифру GS1 (mod-10); не сошлась → `null`;
- дополняет ведущими нулями до 14: `4680089900253` → `04680089900253` —
  форма `products.gtin14` (`char(14)`, check `^[0-9]{14}$`).

Невалидный штрихкод = «штрихкода нет»: позиция живёт дальше без GTIN, а файл
получает ОДНО журнальное событие-сводку с количеством отброшенных (не item-
событие на каждый — файл с системно кривыми штрихкодами зальёт журнал).

## 5. Автосвязь (`apply.ts` → `decideApplication`)

Новый вход: `productsByGtin: Map<string, { id: string; externalRef: string | null }>`
— карточки тенанта (каталог их и так грузит для `known`; добавляется
`gtin14` в выборку). Для позиции каталога БЕЗ известной связи, с
нормализованным GTIN:

1. **Совпал, карточка не связана** (`externalRef IS NULL`) → work item
   `link`: `products.external_ref = <Ид>`; журнал `ok`/`item` «связан
   автоматически по GTIN». Позиция НЕ становится кандидатом. Цена и фото
   этого же раунда применяются к ней (порядок work items ниже).
2. **Совпал, но карточка связана с другим `<Ид>`** → конфликт: кандидат как
   сейчас (+GTIN), журнал `warn`/`item` с обоими `<Ид>` — решает человек.
3. **Не совпал** → кандидат c GTIN (см. §7) — как сейчас, плюс поле.

Эдж-кейсы, решённые здесь же:

- Два товара файла с одним GTIN → автосвязь только если претендент один;
  иначе оба в кандидаты + `warn` (не угадываем — та же дисциплина, что с
  типами цен).
- Карточка с этим GTIN уже связана с этим же `<Ид>` → это `known`, ветка
  вообще не выполняется.
- `decideApplication` остаётся чистой функцией: все решения — из входов,
  запись — в контроллере.

## 6. Фото

Новый work item `image` — для связанных товаров (включая связанные work
item'ом `link` этого же раунда), у которых позиция каталога несёт
`images[0]`.

Получение содержимого — две формы значения `<Картинка>`:

- **Относительный путь** (`import_files/…` — стандарт «Обмена с сайтом»:
  файлы картинок приходят через `mode=file` ДО import.xml и уже сохраняются в
  `exchange_uploads`) → `ExchangeSessionService.assemble(sessionId, путь)`.
  Файла нет → `warn`/`item`, раунд идёт дальше.
- **Абсолютный URL** → скачивание: только `https://`, таймаут 10 с, лимит
  5 МБ (тот же `MAX_SOURCE_BYTES`, проверяется и по заголовку, и по факту
  чтения), максимум 3 редиректа (каждый — под теми же проверками), SSRF-щит:
  резолвим DNS и отказываем приватным/локальным/link-local адресам (значение
  из файла контролирует внешняя система на ungated-маршруте). Ошибка →
  `warn`/`item`.

Применение: дедуп по checksum — sha полученных байт совпал с
`media_assets.checksum` текущего активного фото карточки → пропуск (иначе
каждый обмен плодит новый asset при неизменной картинке). Дальше —
существующий цикл `processProductImage` → staging asset → storage.put →
активация + `product_images` upsert, вынесенный из
`ProductsService.uploadImage` в метод, принимающий машинного актора
(аудит-запись от имени канала, не пользователя). Политика — заменять всегда
(§2). Любая ошибка обработки/хранения = `warn`/`item`, не падение раунда.

## 7. Схема БД

Одна миграция: `integration_candidates.gtin text` (nullable). Пишется при
upsert кандидата (в `set` тоже — GTIN мог появиться в файле позже). Индекс не
нужен: чтение кандидатов уже фильтруется по `(tenant_id, hidden_at)`, GTIN —
поле карточки кандидата, не ключ поиска.

## 8. Контроллер (`exchange.controller.ts`, `mode=import`)

- Выборка `known` дополняется `gtin14`; из неё же строится `productsByGtin`.
- Worklist: `link` → `price` → `image` → `candidate` (связь раньше цены —
  чтобы цена раунда легла в только что связанную карточку; фото после цены —
  самый тяжёлый шаг последним). Всё в fingerprint курсора (ключи:
  `l:<productId>`, `i:<productId>`), батчи `IMPORT_BATCH_SIZE` как сейчас.
  `image`-элементы сетевые и тяжёлые — но их естественный максимум на файл
  ограничен тем же батчем; отдельный лимит не вводим (принятое ограничение,
  пересмотрим по живому обмену).
- Правило «цена трогает только `unit_price`» уточняется честно: work item
  `link` трогает `external_ref`, work item `image` — фото; имя, GTIN
  карточки, шаблон этикетки, киоск — по-прежнему никогда.

## 9. Тесты

- Юнит `gtin.test.ts`: 8/12/13/14, контрольная цифра, мусор, нормализация.
- Юнит parse: `<Штрихкод>` товара/предложения, повторяющиеся `<Картинка>`,
  отсутствие тегов.
- Юнит apply: три ветки §5, двойной GTIN в файле, конфликт связи.
- E2E import: автосвязь + цена в том же раунде; картинка из файла сеанса;
  картинка по URL (fetch замокан); дедуп по checksum; ошибка скачивания не
  валит раунд; кандидат с GTIN.

## 10. Приёмка и открытый риск

Живого XML от СБИС в репозитории нет. Предположения по стандарту CommerceML
2.05: тег `<Штрихкод>`, форма `<Картинка>` (относительный путь + файлы через
`mode=file`; URL-форма — страховка). В
`docs/1c-exchange-acceptance-checklist.md` добавляется пункт: на первом живом
обмене СБИС проверить имя тега штрихкода, форму картинки и фактический тип
цены. Дизайн терпим к отсутствию любого из полей — файл без них ведёт себя
ровно как сегодня.
