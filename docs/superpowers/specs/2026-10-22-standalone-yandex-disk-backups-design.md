# Автоном: резервные копии в Яндекс Диске и восстановление на новом ПК

Дата: 2026-10-22. Редакция 4 от 2026-10-23, после живой проверки. Приложение клиента,
ClientSecret и токены в DPAPI службы; код подключения, доставки/ротации и восстановления
реализован. Браузерный стенд и живые upload/full GET/catalog/download/restore в пустую
temp-базу прошли на macOS. Windows-приёмка и остальные provider/release gates остаются
отдельным этапом: [матрица](../../verification/standalone-yandex-disk-acceptance.md),
[живой smoke](../../verification/standalone-yandex-disk-live-2026-10-23.md).

**Основание:** пользователь выбрал автоматические копии со службы хоста и восстановление через
вход в Яндекс и выбор копии, без отдельного пароля восстановления. Ключ расшифровки хранится
в той же закрытой облачной папке. Дополнительно пользователь выбрал собственное OAuth-приложение
клиента вместо общего приложения Markiro. Эти решения согласованы; остальные технические решения
ниже предложены автором документа и должны пройти проверку по плану. После успешной живой
проверки пользователь разрешил хранение персонального ClientSecret на хосте через DPAPI.
Обязательное требование: OAuth, backup и restore не обращаются к серверам Markiro ни на одном шаге.

**База исследования:** `origin/main`, `c77195aad00e03ac619baad3cde93ec0ee9cb0be`, сверена с GitHub
2026-10-22. Код другой текущей рабочей ветки не является базой этой спецификации.

## 1. Результат для пользователя и границы

Один раз администратор клиента регистрирует своё OAuth-приложение по
[инструкции](../../runbooks/standalone-yandex-disk-registration.md). В офисе нажимает
«Подключить Яндекс Диск», указывает ClientID своего приложения, входит в системном браузере и
разрешает доступ. Для автоматических копий также указывает ClientSecret своего приложения в
нативном защищённом окне ввода; не в чате и не в настройке с открытым текстом. Офис может находиться на другом ПК. После подключения служба хоста сама делает и загружает
копии: открытое окно офиса, установленное приложение Диска и вошедший в Windows пользователь
для расписания не требуются. Интернет нужен только облачной части; производство работает офлайн.

На новом ПК при установке роли «Хост» пользователь выбирает «Восстановить из Яндекс Диска», указывает
ClientID прежнего приложения, входит в тот же аккаунт, выбирает предприятие и копию, подтверждает
восстановление. ClientID берётся из кабинета Яндекса или сохранённого файла настроек без секретов.
Одного входа в аккаунт без ClientID недостаточно: до него Автоном не знает, к какой папке приложения
запросить доступ. Это явно заменяет прежнее обещание «только вход и выбор копии». Не вводит пароль
расшифровки, не переносит файл ключа и не запускает команды вручную. UAC, разрешение Яндекса и
подтверждение выбранной копии остаются обычными шагами, а не дополнительными секретами.

После восстановления сохраняется существующая сверка станций и удержание их данных. «Данные
восстановлены» не означает «сверка закончена, производство можно продолжать». Вход в офис остаётся
под восстановленными учётными записями; пароль офиса не заменяется входом в Яндекс. Восстановление
забытого пароля офиса — существующая отдельная процедура, не новый пароль восстановления.

Включено: Windows, одна пара ClientID/аккаунт Яндекса на хост, несколько разных хостов в одном аккаунте,
папка приложения на личном Диске аккаунта (в том числе аккаунта организации при доступном API).
Общие диски Яндекс 360, произвольная папка вне папки приложения, публичные ссылки, WebDAV,
непрерывная репликация, инкрементальные копии и автоматическое переключение хостов не включены.
Локальные копии и существующая вторая папка сохраняются; облако — дополнительное назначение.
В этой работе не меняются облачный Markiro, SaaS, API платформы и правила лицензирования.

## 3. Модель доверия, ключи и OAuth

Копия содержит коммерческие данные, хеши паролей/PIN/бейджей и удостоверение хоста. Принятое
решение означает: владелец доступа к папке облачных копий способен прочитать данные и выдать себя
за хост. Шифрование с ключом рядом не защищает от захвата аккаунта, токена или изменения всех
объектов в папке. Хеши/age проверяют целостность передачи, но не доказывают независимое доверие
к владельцу данных в облаке. Обещания защиты от ransomware/удаления аккаунта не даём.

Перед первым подключением показать подтверждение: «Доступ к этому Яндекс Диску позволяет
восстановить данные предприятия и ключ хоста. Отдельного пароля восстановления нет».
Рекомендовать двухфакторную защиту аккаунта. Папку не публикуем и не создаём общих ссылок.

| Секрет                      | Хранение                                                                                    | Перенос на новый ПК                                           |
| --------------------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| Ключ шифрования одной копии | Новый age X25519 private identity на каждую копию; `recovery-key.json` рядом с ней в облаке | Скачивается после входа в Яндекс                              |
| TLS private key хоста       | В native `.identity` внутри зашифрованного облачного объекта                                | Возвращается через существующий identity plan                 |
| OAuth access/refresh        | Файл вне `host.db` под DPAPI учётной записи службы + закрытая ACL                           | Не бэкапится; новый ПК получает собственные токены через вход |
| Пароль Яндекса              | Только на странице Яндекса                                                                  | Автоном не принимает и не хранит                              |

ClientSecret приложения клиента хранится вместе с access/refresh в одном атомарно обновляемом
DPAPI-контейнере вне host.db. Шифрует/расшифровывает его сама Windows-служба под своей учётной
записью (по умолчанию LocalService), **CurrentUser**, `CRYPTPROTECT_UI_FORBIDDEN`, без
`CRYPTPROTECT_LOCAL_MACHINE`. ACL файла/каталога разрешает нужный доступ службе, SYSTEM и
администраторам, без обычных пользователей. Сначала шифрование в памяти, затем запись закрытого
временного файла с ciphertext, flush и atomic replace; plaintext-файла, в том числе `.partial`, нет.
На диск попадают clientId/accountId binding, формат и зашифрованные credentials, а не открытый секрет.

Нативный Rust-диалог принимает ClientSecret (1–512 печатных ASCII символов без пробелов, без
нормализации значения). JS получает лишь успех/отмену, не secret/token. Из удалённого офиса
секрет передаётся хосту только существующим pinned TLS admin transport, без args/env/URL/log.
Служба держит его в памяти попытки до 10 минут, затем проверяет refresh; соединение становится
connected только после успешного refresh и проверки аккаунта/папки. Cancel или неверный секрет
не заменяет прежнее рабочее назначение. На новом ПК/после смены учётной записи службы секрет
вводится заново из кабинета владельца; готовый DPAPI blob с другого ПК не переносится.

Значения ClientSecret/access/refresh не входят в БД, облачные комплекты, support bundle,
`yandex-connection.json`, audit, Debug, трассы HTTP и IPC-ответы. Endpoint чтения секрета отсутствует.
Ротация секрета выполняется администратором через повторное подключение того же ClientID с новым
секретом и проверкой refresh, затем атомарной заменой credentials. Неверные credentials дают
безопасный код `client_credentials_invalid`, потеря DPAPI — `secret_unavailable`, отсутствие
секрета при включении расписания — `client_secret_required`. Ни одна ошибка не переключает на Markiro.

DPAPI CurrentUser привязан к учётной записи службы, а не является отдельной изоляцией процессов,
работающих под той же учётной записью. ACL и защита хоста остаются обязательными.
DPAPI не защищает от администратора/процесса с достаточными правами на работающем хосте.
Это персональный секрет клиента, а не общий секрет, вшитый в установщик. Секрет клиента никогда
не пересылается в Markiro, включая телеметрию, диагностику, поддержку или лицензионную проверку.

Сетевой инвариант: отсутствие **любых** обращений OAuth/backup/restore к Markiro — не только
для полезной нагрузки, но также регистрации, выдачи токенов, проверок доступа, телеметрии и
обработки ошибок. Программный транспорт разрешает фиксированные API origins Яндекса и проверенные
подписанные transfer hosts Яндекса из задачи 0. Browser login открывает только страницы Яндекса;
инструкции поставляются локально. При недоступном Яндексе — очередь/ошибка, не наш сервер.
В тестах проверять отказ запросов к origins Markiro и неизвестным origins **до отправки**;
отдельно проверить обработку redirect/ошибок. Это инвариант интеграции; прочие сетевые функции
продукта не считаются проверенными данным OAuth probe.

Уточнение живой пробы 2026-10-23: download URL может вернуть 302 на один DNS label
под `storage.yandex.net`, что подтверждено сетевой документацией Яндекса. Разрешены максимум
три ручных перехода download GET, каждый повторно проходит HTTPS/port/userinfo/fragment,
allowlist/public-DNS и generation guard. OAuth и cookies не передаются. Для API/token endpoints
автоматические redirect по-прежнему запрещены. Callback принимает bounded opaque `cid`
как необязательную корреляцию, не заменяющую проверку state.

Не использовать machine-wide DPAPI как единственную защиту. Файл токенов создаёт и защищает сама
служба под своей учётной записью. Переход на другую учётную запись требует повторного входа;
повреждённый секрет не заменяется пустым и не печатается. На не-Windows адаптер допускается только
в тестах, без обещания промышленной защиты. Восстановленные настройки копирования по умолчанию
приостановлены до нового подтверждённого подключения, а токены из старой машины не читаются.

### OAuth без сервера Markiro

Каждый клиент создаёт и сохраняет собственное приложение в своём аккаунте Яндекса. Общего ClientID
Markiro, сервера регистрации, выдачи токенов или доступа через аккаунт разработчика Markiro нет.
Все OAuth/API-запросы идут из офиса/хоста прямо в Яндекс. Приложение и архивы остаются у клиента,
если серверы Markiro недоступны; зависимость от API, правил и аккаунта Яндекса остаётся.

**Выбранный тип — «Для авторизации пользователей», владелец — клиент.** Тип приложения у Яндекса
и его владелец — разные вещи. Этот тип выбран для собственного redirect URI и PKCE, а не для
общего входа всех клиентов. «Для доступа к API или отладки» в v1 не поддерживается: у него фиксирован
`https://oauth.yandex.ru/verification_code`, поэтому он не подходит к выбранному loopback flow.
Не обещать, что debug access_token из такого приложения можно вставить вместо полноценной пары
access/refresh и получить автоматическое обновление. Ручной импорт готового токена не входит в v1; ClientSecret клиента вводится только через
нативный диалог и сохраняется службой под DPAPI, не в публичном профиле.

Нужные поля профиля: `format:1`, `provider:yandex_disk`, `clientId`, фиксированные `redirectUri`
и `scopes` из этой спецификации. ClientID — публичный параметр, не ключ восстановления и не пароль.
Он хранится вне host.db рядом с настройками подключения; admin может экспортировать
`yandex-connection.json` без токенов/ключей/учётных данных, новый ПК — импортировать. В файле
допустимы только перечисленные поля, format 1; размер до 64 KiB. Не принимать endpoint, secret,
token или произвольные scopes/redirect. `clientId` — 1–128 ASCII символов `[A-Za-z0-9_-]`.
Яндекс проверяет существование/права приложения при реальном входе. Отсутствующий ClientID даёт
ссылку на инструкцию и кабинет Яндекса, не запускает вход с приложением Markiro по умолчанию.

Для восстановления клиент сохраняет доступ к аккаунту-владельцу приложения и к аккаунту Диска;
в инструкции предлагается один аккаунт предприятия для обеих ролей. Удаление приложения или
замена его ClientID не является ротацией токена: старая папка приложения может стать недоступной
новому приложению. Не создавать приложение заново при переустановке ПК. Старый ClientID берётся
из кабинета Яндекса даже после потери исходного ПК; копия профиля — удобство, не единственная
возможность восстановления. На тестах используется отдельное приложение клиента и синтетические данные.

Authorization Code + PKCE `S256`, системный браузер, точный зарегистрированный loopback redirect
`http://127.0.0.1:45711/oauth/yandex/callback`. Rust-оболочка слушает только loopback; занятый порт
даёт понятную ошибку, без выбора незарегистрированного порта и без публичного callback на хосте.
Срок попытки — 10 минут, случайный одноразовый `state` не менее 256 бит. Нет implicit flow,
ручного вставления токенов, embedded browser и общего встроенного `client_secret`.
Персональный ClientSecret клиента допускается только для прямого refresh к Яндексу.

При подключении удалённого офиса: native Rust принимает ClientSecret и передаёт его с ClientID
на хост в admin auth/begin; тело не более 8 KiB, авторизация до разбора секретного поля.
Хост создаёт state/verifier и
связывает попытку с этим ClientID, пользователем, устройством и действующей admin-сессией.
Оболочка принимает callback и пересылает код/state хосту
через существующий pinned TLS transport; хост проверяет всё повторно, обменивает код и сохраняет
credentials сам после успешного контрольного refresh. JS получает только попытку, публичный URL
и статусы, не код/verifier/ClientSecret/токены. На новом
ПК то же выполняет локальный recovery-процесс Rust без office-сессии, только на ПК роли Host.
После завершения/отмены listener закрывается; replay и чужая сессия отклоняются.

Права: `cloud_api:disk.app_folder` и `login:info` для стабильного идентификатора/имени аккаунта.
Не запрашивать полный read/write Диска. Доступ к файлам только под `app:/`; ник/название аккаунта
не используются как идентификатор. Приложение проверяет выданные права фактической операцией
в своей папке. Обновление токена — один запрос на соединение за раз, новая пара сохраняется
атомарно, вместе с привязкой к ClientID и аккаунту; invalid_grant/revoked переводит в
«Нужно войти снова», без бесконечных попыток. Refresh использует тот ClientID, которым получена
пара токенов, и ClientSecret именно этого приложения. Смена ClientID не отправляет старый
refresh-токен или секрет в новый контекст.
PKCE-обмен кода сохраняется без client_secret; refresh выполняет служба прямым
`POST https://oauth.yandex.ru/token` с grant_type=refresh_token, client_id, client_secret,
refresh_token в form body по HTTPS. Не добавлять секрет в GET/query и не пересылать его на
Disk API, transfer URL или login API. Редиректы token endpoint не следовать автоматически.
Неправильный/отозванный ClientSecret требует действия администратора, не бесконечных повторов.
Центрального брокера, fallback в Markiro и встроенного секрета разработчика нет. Access token при успешном refresh может остаться прежним: PASS означает
успешный refresh grant и рабочий доступ к Диску, а не обязательное изменение строки токена.

**Текущий gate:** 2026-10-22 существование тестового приложения клиента подтверждено в UI:
ClientID `dacd86d869664a09847d6a54e6f26fac`, оба scope и заданный redirect сохранены.
Живая проверка на macOS: PKCE выдача без client_secret — HTTP 200, папка приложения доступна;
refresh с полученным refresh_token и тем же ClientID без секрета — HTTP 400 `invalid_client`.
Повтор с явного разрешения пользователя: refresh с ClientSecret — HTTP 200, свежий доступ к app:/
и аккаунту — HTTP 200, аккаунт тот же. HTTP-клиент пробы обращался только к oauth.yandex.ru,
cloud-api.yandex.net и login.yandex.ru; секрет передавался только token endpoint в памяти.
OAuth-возможность новой схемы подтверждена; Windows-среды здесь нет, поэтому закрытый офис,
restart, DPAPI и LocalService остаются непроверенными. Это не приёмка интеграции бэкапов.

## 4. Формат облачного комплекта v1

Фиксированный корень `app:/backups/v1/<hostId>/<snapshotId>/`, оба id — валидированные UUID,
snapshotId создаётся до загрузки и не меняется при повторе. Пользователь не вводит сетевой путь.
Внутри только следующие файлы:

| Объект              | Содержание                                                              |
| ------------------- | ----------------------------------------------------------------------- |
| `database.age`      | Native `.db`                                                            |
| `manifest.age`      | Native `.json` формата 1                                                |
| `host-identity.age` | Native `.identity` формата 1                                            |
| `recovery-key.json` | `format:1`, hostId, snapshotId, age X25519 private identity             |
| `complete.json`     | Последний объект: описание и SHA-256/размер каждого из четырёх объектов |

Шифрование — стандарт age v1, binary streaming, один случайный X25519 recipient на комплект,
не password-based encryption и не собственная криптографическая схема. Адаптер на Rust `age`
с точной закреплённой зависимостью после проверки лицензии, MSRV и сборки Windows; изученная
документация версии 0.12.1 предупреждает о pre-1.0 статусе — принять решение о зависимости в
задаче 0, не заявлять её промышленную проверенность. Ключи не выводятся через Debug/IPC/log.

`complete.json`: format, hostId, snapshotId, createdAt UTC (native timestamp), schemaVersion,
appVersion, organizationLabel, inn, oauthClientId, tlsFingerprint, nativeDbSha256 и `objects` с четырьмя
фиксированными именами, sizeBytes и sha256. До него ни один каталог не является готовой копией.
Объект неизменяемый: повтор проверяет уже существующие байты; другой SHA на том же id — конфликт,
не overwrite. Список предприятий строится из завершённых комплектов; отдельный изменяемый
`latest.json` не является источником истины. Поддержать постраничный listing всех уровней.

`oauthClientId` совпадает с выбранным профилем; его значение в архиве служит проверкой, не способом
выбрать приложение до входа. Профиль без секретов допускается сохранить отдельно; поиск папки
приложения до указания ClientID не реализуем и не обещаем.

Внешние JSON не более 64 KiB каждый, строки отображения не более 200 Unicode-символов, hostId и
snapshotId совпадают на всех уровнях и с native файлами. Три расшифрованных имени фиксированы;
произвольные пути/URL из JSON не исполняются. Лимит базы v1 — 64 GiB, native manifest/identity —
1 MiB каждый. Превышение, неизвестный format, дубли/лишние объекты — отказ до изменения хоста.
Размеры проверяются при streaming, не только по заголовку HTTP. Оперативный буфер — 64 KiB;
никаких base64 целой базы через IPC и загрузки всей базы в память.

Текущая локальная копия может обходиться без `.identity`; облачная копия так не публикуется.
Показываем «Не сохранён ключ хоста», локальный worker продолжает работу. OAuth-файлы, ClientSecret, временные
callback state, токены, Windows DPAPI blobs и восстановительные журналы в комплект не включаются.

## 5. Автоматическая доставка, проверка и хранение

После успешной локальной копии отдельный worker получает её id. Первая связь сразу отправляет
новейшую пригодную копию; если её нет, запрашивает локальную копию штатным механизмом. «Сделать
копию сейчас» создаёт локальную копию и затем ставит её в облачную очередь. Отдельная кнопка
«Повторить загрузку» не создаёт ещё одну копию базы.

Состояние работы разделено по `(clientId, accountId, hostId)`, не только по hostId. Смена приложения
или аккаунта создаёт новое назначение: старые pending jobs/retention не переносятся. Конфигурация
нового назначения активируется только после успешного входа и подтверждения администратора;
отмена подключения оставляет прежнее рабочее назначение без изменений.

Состояние работы хранится в отдельной локальной SQLite `cloud-backup-state.db`, исключённой из
backup/restore: connectionGeneration, snapshotId, immutable source, стадия, attempts, nextRetryAt,
размеры/SHA, последняя подтверждённая копия. Это не источник бизнес-данных. На диске — один
активный staged комплект и один pending latest id; при офлайне новые ожидания заменяют pending,
а не активную работу. Пропущенные часовые точки не выдаются за загруженные. До шифрования исходная
тройка закрепляется под блокировкой локальной ротации; долгий upload использует собственный
закрытый stage и не держит блокировку локальных копий. Удаление исходника между lookup/pin
обрабатывается повторным выбором, а не чтением частичного комплекта.

Переходы: `queued → staging → uploading → verifying → publishing → confirmed`; transient error
сохраняет стадию и retry; auth error требует входа; повреждённые данные дают постоянную ошибку
конкретной копии. Сбой облака не меняет успешность локальной копии и не держит транзакцию host.db.
После рестарта job возобновляется. Не более одного upload/verify на хост. Retry: 30 s, 2 min,
10 min, далее 1 h, jitter ±20%; Retry-After имеет приоритет при 429/503. HTTP connect timeout 10 s,
idle timeout 60 s, предел отдельной передачи 6 h, отмена при shutdown/disconnect; попытка
не мешает лимитам остановки существующего локального worker. При нехватке места — ошибка,
не удаление пользовательских копий. Для stage/verification резервировать расчётный размер
недостающих файлов плюс 512 MiB; не удваивать базу в оперативной памяти.

Загрузка получает свежий upload URL через API; истёкший URL запрашивается заново. После потери
ответа проверить наличие/байты объекта. 202 означает ждать результата операции, не успех.
API OAuth-заголовок идёт только на фиксированный API origin; подписанные transfer URL не получают
его. Проверять HTTPS и разрешённые transfer hosts по результату задачи 0; редиректы на loopback,
private/link-local IP, HTTP и посторонние origins запрещены. Автоматическая отправка Authorization
при редиректе запрещена. Подписанные URL/их query не попадают в журнал.

До публикации: свежий полный GET четырёх объектов, SHA/размер, расшифровка до EOF и проверка native
manifest/identity/`verify_copy`. Только затем записать `complete.json`, перечитать его и подтвердить
job локально. После crash между commit и локальным ack повтор признаёт тот же комплект, а не
создаёт дубликат. При restore всё проверяется снова; значок прошлого успеха не заменяет проверку.

Удалённая retention — объединение последних 24 копий, последней за каждый из 14 последних дней
и 12 последних месяцев UTC в namespace этого hostId; использовать существующие правила retention,
сохранять свежую подтверждённую копию и при откате часов. Удалять только после новой подтверждённой
копии, начиная с complete marker, затем четыре объекта. Другие hostId не затрагивать. Последний
подтверждённый комплект не удалять ради quota. Частичный комплект восстанавливать/переиспользовать
при retry; автоматическую сборку неизвестных orphan-каталогов v1 не делать. При нехватке quota
показывать причину, не объявлять успех. Отключение Диска никогда не удаляет удалённые копии.

## 6. Восстановление на новом компьютере

1. В роли Host до bootstrap: «Новое предприятие» / «Восстановить из Яндекс Диска». Переход также
   доступен из экрана пустого хоста. На Station/Office local recovery недоступно.
2. Ввести прежний ClientID клиента или импортировать `yandex-connection.json`, затем войти в тот же
   аккаунт. Не создавать новое OAuth-приложение. Если ClientID утрачен, открыть кабинет Яндекса
   владельца и взять его у прежнего приложения. Выбранные ClientID/аккаунт показаны до listing. Новый компьютер
   получает новые токены. Список группируется по hostId, ИНН/названию, затем по
   времени копии; нельзя автоматически взять последнее предприятие аккаунта.
3. Показать дату копии, предприятие, версию, размер, наличие идентичности и предупреждение о
   данных после этой даты. Отсутствие сети/папки/ключа/поддерживаемой версии имеет отдельный текст.
4. Пользователь подтверждает: старый хост остановлен и не будет запущен одновременно. Автоматически
   доказать его выключение в офлайн-сети нельзя. Эта интеграция не обеспечивает fencing и HA.
5. Скачать полный комплект в закрытый recovery stage, проверить §4–5 и `verify_copy`, совместимость
   миграций/checksum, принадлежность базе и fingerprint. Несовместимую новую версию предложить
   обновить; не применять `--without-manifest`, `--keep-identity` или force-fallback.
6. Только после полной проверки локальный elevated helper останавливает службу и дожидается
   `STOPPED`; проверяет роль, фиксированную data-dir и отсутствие инициализированного предприятия
   под lock. Пустая БД, созданная установщиком, допустима. Рабочая БД — отказ с направлением к
   инженеру. Адрес/путь для helper не берётся из remote JSON/IPC.
7. Вызывает `restore_with` с `without_manifest:false`, `IdentityChoice::Auto`; сохраняет все
   существующие crash-recovery, rollback, margins, restore epoch и hold. Прежнее содержимое папки
   не удаляет. Ошибка не превращается в создание нового предприятия.
8. Запускает службу, читает hello по восстановленному fingerprint, подключает локальную оболочку
   штатным loopback pairing. Показывает отчёт и переход в офис для сверки станций. Станциям при
   смене адреса нужен поиск/указание нового адреса; сохранённый ключ не гарантирует старый IP.
9. Само скачивание/восстановление не требует ClientSecret: свежая PKCE-пара живёт в памяти
   recovery-процесса. **Текущий вариант v1:** после restore данные восстановлены, cloud
   disconnected. Администратор входит в Офис прежним паролем и отдельно подключает
   автокопирование штатным native flow, вводя ClientSecret из кабинета того же приложения.
   DPAPI credentials создаёт сама служба. Этот шаг можно отложить без отмены восстановления.
   Новый privileged credential adoption IPC отложен; recovery не передаёт секреты через
   args/env/bootstrap HTTP и не меняет права loopback pairing. Секрет и токены старого ПК
   не нужны и из копии не извлекаются. Публичный профиль не содержит ClientSecret.

Отмена/сбой скачивания до шага 6 оставляет локальный хост как был. Сбой питания внутри шага 7
обрабатывается существующим intent marker. Журнал recovery с id стадии и безопасным кодом ошибки
хранится локально; секреты/пароли в нём отсутствуют. Повторное открытие мастера предлагает
продолжение/отчёт, не второй неконтролируемый restore. До записи данных проверить свободное место
с учётом encrypted stage, decrypted тройки, новой БД и сохранения прежней папки.

## 7. Протокол, доступ и пользовательские состояния

Пути ниже реализованы отдельным модулем протокола, без изменения
native backup manifest и семантики `BackupState.second`.

| Интерфейс                       | Доступ и результат                                                                                                |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `GET /v1/office/backups/yandex` | Все office-роли: статус подключения и доставки без секретов                                                       |
| `POST …/auth/begin`             | Native admin transport: `{clientId,clientSecret,expectedGeneration}` → `{attemptId, authorizationUrl, expiresAt}` |
| `POST …/auth/complete`          | Native office transport, admin той же сессии/устройства: `{attemptId,state,code}` → статус                        |
| `DELETE …/auth/attempt/{id}`    | Admin-владелец: отмена попытки                                                                                    |
| `DELETE …/connection`           | Admin, expectedGeneration: отключить, отменить работу и удалить локальные токены                                  |
| `POST …/retry`                  | Admin: поставить повтор существующей копии, 202                                                                   |

Authorisation перепроверяется перед изменением подключения; logout/revoke блокирует complete.
Generation увеличивается на смену/отключение аккаунта или ClientID; старый worker не начинает новые запросы
публикации/удаления и не обновляет статус нового подключения. Уже отправленный запрос нельзя
гарантированно отозвать: его поздний результат относится только к прежнему аккаунту/generation,
не считается подтверждением новой связи и не запускает retention. Эта граница видна в журнале.
Неавторизованный device, operator и handheld не получают office
доступ. Новые маршруты включаются в `license/gate.rs` как `NEVER`: backup/recovery не блокируются
истёкшей лицензией. В реестр device kinds занести нужные правила, если они требуются текущим router.
Нет публичного LAN restore endpoint; local recovery — только проверенные native команды.

Статус содержит connectionGeneration, state (`disconnected`, `connecting`, `connected`,
`reauth_required`), clientId, account id/label, delivery state, pendingSince, lastAttemptAt,
lastConfirmedSnapshotId/At, lastConfirmedCopyCreatedAt, safe error code и progress bytes.
Время последней загрузки и возраст данных копии — разные поля. Ошибки: `network`, `rate_limited`,
`quota_exceeded`, `access_denied`, `reauth_required`, `identity_missing`, `integrity_failed`,
`unsupported_format`, `incompatible_version`, `local_space`, `remote_conflict`, `cancelled`,
`client_credentials_invalid`, `secret_unavailable`, `client_secret_required`.
404 копии не считать истечением авторизации; 403 квоты/прав различать по коду провайдера.

В карточке: ClientID собственного приложения и аккаунт, инструкция регистрации и экспорт профиля
без секретов, native действие «Указать/заменить ClientSecret» без возможности прочитать
сохранённое значение, последняя подтверждённая облачная копия и её дата данных, текущая стадия,
ошибка/следующая попытка. Подключённый аккаунт без подтверждённой копии не показывает «Защищено».
При отсутствии облачной копии после подключения — предупреждение; если данные последней копии
старше 26 часов — «Облачная копия устарела». В RU/EN точные тексты ошибок дают следующий шаг.
Отключение не стирает архивы и объясняет отзыв доступа в Яндексе. При смене аккаунта требуется
новое подтверждение назначения; то же при смене ClientID. Не выполнять массовую миграцию/удаление
старых архивов, не обещать доступ нового приложения к старой папке.

Аудит: `backup.yandex.connect`, `.disconnect`, `.upload`, `.purge`; targets = connection/snapshot,
actor = admin для настройки или host для фоновой работы, ClientID/поколение назначения,
result/код причины/суммарные bytes. ClientID не секрет; OAuth credentials в audit не включаются.
`host.restore` остаётся основным действием восстановления; добавить source=`yandex_disk` и
snapshotId без токенов. Безопасный local recovery журнал покрывает отказы до появления базы.
Повтор после crash не создаёт второй логический success upload; служебные attempts допустимы
в локальном delivery journal, не как новые события успешной доставки.

## 8. Приёмка и выход в релиз

| ID  | Проверяемое условие                                                                                                                                                                                 |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A1  | Офис на ПК-2 подключает аккаунт; хост на ПК-1 загружает копию после закрытия офиса и logout Windows                                                                                                 |
| A2  | Интернет выключен: производство и локальные копии продолжаются; после restart/reconnect очередь доставляет пригодную копию                                                                          |
| A3  | 401/revoked/invalid_grant требует входа; 429/5xx повторяются по правилам, quota не удаляет последнюю копию                                                                                          |
| A4  | Сбой на каждом объекте/commit/ack: частичная копия не видна, повтор не дублирует, полный GET ловит подмену байтов                                                                                   |
| A5  | После потери исходного ПК новый Windows-ПК восстанавливается с прежним ClientID клиента и входом в Яндекс; отдельного пароля и DPAPI старого ПК не нужно                                            |
| A6  | Сохраняются hostId/fingerprint, лицензия и правила SSCC; станция переподключается по новому адресу, видит epoch, возвращает блоки; hold снимает admin после сверки                                  |
| A7  | Несколько hostId/аккаунтов, неверный комплект/ключ/manifest, новая версия, рабочая целевая БД и повторный callback отклоняются до destructive swap                                                  |
| A8  | Нет ClientSecret/токенов/ключей/подписанных URL в SQL snapshot, Debug, IPC JS, audit, логах и support bundle; ACL/DPAPI проверены под реальной службой                                              |
| A9  | Смена ClientID/аккаунта и disconnect прекращают новые запросы старой работы; поздний ответ не меняет новую связь; retention не затрагивает другой хост и сохраняет последнюю копию при откате часов |
| A10 | Восстановленный старый бэкап не обходит лицензию и не снимает hold; crash swap восстанавливается штатным механизмом                                                                                 |

Release gate: автоматические Rust/TS/fixture проверки плюс отдельный Windows drill A1/A5/A6/A8
с реальным тестовым аккаунтом Яндекса и двумя ПК/VM, где исходный host недоступен. Успешный upload
не является доказательством restore; host-only Cargo не доказывает Windows ACL, UAC или OAuth.
Без доступного ClientID восстановления «только по логину» нет. Проверить импорт безопасного профиля,
получение ClientID из кабинета после потери исходной машины, отказ чужого ClientID и неизменность
старой связи после отмены нового входа. Доступность серверов Markiro на эти операции не влияет.
До этого интеграция не принята для промышленного восстановления. По разрешению владельца
зарегистрировано тестовое приложение и выполнена живая синтетическая копия, без данных
предприятия. Это не выпуск релиза и не закрытие отложенной Windows-приёмки.

  фиксирует verification_code redirect — этот путь не включён в v1.
- [Инструкция клиента](../../runbooks/standalone-yandex-disk-registration.md): что создать и
  сохранить; ClientSecret, access_token и refresh_token в чат не передаются.
- [Microsoft DPAPI](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata):
  user scope, machine scope и неинтерактивная защита; это источник для проекта хранения,
  а не доказательство уже выполненного Windows-теста.
- [age v1](https://age-encryption.org/v1) и [Rust age 0.12.1](https://docs.rs/age/0.12.1/age/):
  streaming recipient encryption; версия библиотеки и её pre-1.0 статус — предмет dependency gate.

Живыми запросами подтверждены PKCE без секрета, refresh с секретом и доступ к папке/аккаунту
после refresh. Предыдущий FAIL refresh без секрета сохранён отдельно. Дополнительный smoke
проверил PUT четырёх объектов, full fresh GET/native verifier до complete marker,
readback marker, catalog и независимое скачивание всех пяти объектов. Три native файла
совпали побайтно; синтетическая запись восстановлена штатным кодом в отдельную пустую
temp-базу. База 1 064 960 байт, комплект 1 067 748 байт; customer data не использовались.

Браузер проверил production компоненты с синтетическим Host/native adapter: admin consent,
reader, stale/quota/reauth, выбор/подтверждение, светлая/тёмная темы и 1366/1024/480 px.
Полные реквизиты выбранной копии вынесены из обрезаемого списка; даты используют русский
formatter. Это не доказательство Windows native bridge или работы UI со службой на другом ПК.

Полные доказательства и безопасный JSON — в [отчёте живой проверки](../../verification/standalone-yandex-disk-live-2026-10-23.md).
Токены/ClientSecret/ключи/подписанные URL в evidence не сохраняются. Подтверждённая
синтетическая копия оставлена в закрытой папке приложения; remote DELETE не выполнялся.

Windows installer/DPAPI/LocalService/SCM/UAC, закрытый Office/logout, чистый Windows-ПК,
power-cut, реальная станция/печать и системный outbound trace остаются OPEN отдельным этапом
по указанию пользователя. Provider quota/revoke, большие файлы/каталог и live retention DELETE
также не закрыты. Задача внешних условий частично выполнена; macOS smoke не заменяет A1–A10.

### Уточнения после review PR #786

Delivery PUT прерывается при отмене generation/shutdown даже во время streaming.
Refresh и delivery имеют отдельные wake permits. Полный код ошибки сохраняется в
журнале; постоянные credential ошибки требуют повторного подключения.

Повтор helper разрешён только для незавершённого recovery job. Завершённое задание
не запускает SCM и не меняет pairing; native UI скрывает кнопку продолжения.
Recovery preflight сохраняет outbox и disposable кеши: если есть неотправленные
записи или старые копии подключения, операция останавливается до helper/forget.
Очистка старых копий выполняется только существующим явным отключением хоста.
