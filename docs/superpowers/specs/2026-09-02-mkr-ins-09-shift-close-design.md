# MKR-INS-09 «Смена: наблюдение, закрытие и отчёты» — дизайн

Дата: 2026-09-02
Статус: утверждён (brainstorming)
Предшественники: MKR-INS-01…04 (станция), MKR-INS-05…07 (инвентаризация),
MKR-INS-08 «Смена: линия, планирование и запуск» (PR #385) — всё в main,
последний merge `5ce4974df`.

## Цель

Девятая печатная инструкция, завершающая подсерию «производственная смена»:
что менеджер кабинета делает, пока смена идёт и после её окончания, —
наблюдает за производством, при необходимости закрывает смену из кабинета,
разбирает данные, пришедшие после закрытия, формирует отчёты для ГИС МТ и
разбирает их отказы. Парная ко второй половине MKR-INS-02: там оператор
ведёт цикл и закрывает смену со станции.

## Решения (принятые в brainstorming)

- Дашборд «Производство сегодня» входит КОРОТКОЙ секцией наблюдения:
  вердикт контроля с причинами, сводные счётчики и сигнал о незавершённости
  данных активных смен. Динамика, темп на час смены и полная аналитика —
  вне рамок (кандидат в отдельный документ).
- Критические изменения активной смены НЕ повторяются — они уже описаны в
  MKR-INS-08, раздел 8; здесь только отсылка.
- Скриншоты снимаются расширением существующего производственного харнесса
  (`tools/production-browser/tests/production.visual.spec.ts`) — новая
  инфраструктура не нужна.

## 1. Документ

- Код `MKR-INS-09`, kind `instruction`, ревизия `2026.09/01`, effectiveDate —
  дата выпуска, статус `active`, RU-only, маршрут
  `/instruktsii/smena-zakrytie/`.
- Контент — `packages/legal-documents/src/documents/cabinet-shift-close.ts`.
  Цитаты интерфейса — строго из `apps/admin/src/i18n/ru.json`, ветки
  `pages.shifts` (`close`, `closeModal`, `table.lateData`, `exports`) и
  `pages.dashboard` (`verdict`, `headline`, `signals`, `summary`).
  Структура секций:
  1. Назначение: место в серии (подготовка — MKR-INS-08, открытие и рабочий
     цикл оператора — MKR-INS-01/02); статусы «Активна» → «Закрыта»; чем
     занят менеджер, пока смена идёт.
  2. Наблюдение за производством: дашборд «Производство сегодня» — вердикт
     «Контроль производства» («Производство под контролем», «Требует
     внимания», «Критическое состояние») с причинами (конфликты без
     разбора, поздние данные); сводные счётчики активных смен; сигнал
     «Активная смена: данные могут измениться» — почему цифры дня не
     окончательны; список смен и фильтры по производственному периоду.
  3. Закрытие смены: штатно смену закрывает оператор со станции (отсылка к
     MKR-INS-02); кабинетная кнопка «Закрыть смену» с обязательной
     «Причина закрытия» — для случаев, когда станция недоступна или
     оператор ушёл, не закрыв смену; причина сохраняется в смене
     (`close_reason`), закрытие доступно только у активной смены.
  4. Данные после закрытия: бейдж «Данные после закрытия» в списке смен —
     сканы, доехавшие со станции после закрытия; связь с предупреждением
     отчётов «Данные смены изменились — сформируйте новый отчет».
  5. Отчёты для ГИС МТ: «Сформировать отчет» — выбор формата из
     утверждённого серверного каталога; «Разделить отчет на части» и
     «Максимум строк в части» (от 2 до 1 000 000); «История отчетов» со
     статусами «В очереди», «Формируется», «Готов», «Ошибка»; скачивание
     по частям («Часть N») и «Скачать»; «Повторить» у неудавшегося
     формирования.
  6. Почему отчёт не формируется: definition-list по реальному каталогу
     ошибок `pages.shifts.exports.errors` — закрытость смены, полнота
     распределения кодов по коробам, ИНН организации, ограничение строк
     части, некорректный SSCC/код маркировки, инфраструктурные сбои — с
     действием менеджера для каждого случая.
  7. Частые вопросы (definition-list) + контакты.

  неучтённый эндпоинт роняет тест. Моки — по реальным контрактам
  (`apps/admin/src/pages/shifts/{api,shift-exports-api}.ts`,
  `apps/admin/src/pages/dashboard/*`); формы ответов дашборда сверить с его
  API-модулем, а не выдумывать.
- Каждый мокнутый ответ обязан быть состоянием, которое API может вернуть;
  каждый вердикт/статус на кадре — производным от данных того же кадра.
  Номера смен — в формате, который порождает код (`AUG26-…`/`SEP26-…`,

## 4. Тестирование

Существующие механизмы; новых не требуется. Финальному whole-branch ревью
задаётся линза «текст ↔ скриншоты ↔ i18n» — она поймала Critical в каждом
документе серии начиная с MKR-INS-03. Отдельные риски этого документа:

- Вердикт дашборда и его причины обязаны быть производными от мокнутых
  данных того же кадра (перекликается с уроком блокировок MKR-INS-07):
  «Требует внимания» без причины в данных — фабрикация.
- Каталог ошибок отчётов описывать по фактическому маппингу кодов на
  строки (`pages.shifts.exports.errors.*`) и по реальному условию кнопки
  «Повторить» — не обещать повтор там, где UI его не рисует (урок
  MKR-INS-07 про `RETRYABLE_ERRORS`).
- Кабинетное закрытие смены — вспомогательный путь; документ не должен
  подавать его как основной (основной — станция, MKR-INS-02).
