# Station: печать через драйвер Windows с сохранением ZPL/TSPL

Дата: 2026-10-10.
Статус: утверждено пользователем 2026-10-10; реализация не начата.

## Цель и согласованное направление

Добавить печать этикеток через установленный драйвер Windows как отдельный
вариант. Сохранить явный выбор ZPL/TSPL: для прямого подключения по IP,
последовательному порту и для отправки команд через установленную очередь
Windows. Пользователь выбирает способ печати; приложение не переключает его
автоматически после ошибки.

Новое поведение распространяется на тестовую этикетку, короба, паллеты,
инвентаризационные этикетки и товарные дубликаты Data Matrix. Существующие
профили, назначения и незавершённые задания сохраняют прежнее поведение.

## Текущая реализация

- `apps/station/src/lib/print-label.ts`: общий шаблон в миллиметрах преобразуется
  в ZPL/TSPL с учётом DPI выбранного принтера.
- `apps/station/src/lib/hardware.ts`: TCP, serial и установленная очередь
  Windows, исторически названная `usb`.
- `apps/station/src-tauri/src/printer.rs`: очередь Windows получает RAW-байты;
  это не графическая печать через драйвер.
- `apps/station/src/lib/printer-routing.ts`: профили, назначения для трёх
  назначений этикеток, сериализация отправок по адресу устройства.
- `apps/station/src/lib/product-labels/`: сохранённые байты товарного задания,
  привязанный принтер, проверка языка/DPI, журнал попыток и восстановление.
- `packages/domain/src/product-labels/contracts.ts` и `state.ts`: язык входит
  в строгий контракт события `prepared` и неизменяемую проекцию задания.

## Настройка принтера

Разделить подключение и обработку этикетки.

| Подключение     | Способ печати                      |
| --------------- | ---------------------------------- |
| Принтер Windows | Через драйвер Windows / ZPL / TSPL |
| Напрямую по IP  | ZPL / TSPL                         |
| COM-порт        | ZPL / TSPL                         |

«Принтер Windows» означает установленную очередь независимо от её физического
подключения: USB, сеть либо Bluetooth, если соответствующий драйвер её создал.
Существующий внутренний `kind: "usb"` можно сохранить для совместимости хранения;
название в UI должно описывать очередь Windows, а не ограничивать её USB.

Bluetooth через виртуальный COM использует существующий serial-путь.
Нативный Bluetooth discovery, pairing, BLE и новый Bluetooth-транспорт в эту
работу не входят. Нельзя обещать поддержку Bluetooth-устройства без доступной
очереди Windows или совместимого COM-порта.

В профиле добавить явный режим `raw | windows_driver`. Отсутствующий режим
старого профиля трактуется как `raw`. `PrinterLanguage` остаётся `zpl | tspl`;
Windows не становится языком принтера. В режиме драйвера язык не применяется.
При переключении обратно в RAW можно восстановить последний выбранный язык.
Валидатор запрещает `windows_driver` для TCP/serial и неизвестные режимы.

Новые профили тоже начинают с существующего RAW-режима: пользователь просил
добавить вариант, а не изменить исходные настройки. Выбор драйвера явный.
На не-Windows системе этот выбор недоступен с понятным объяснением.

Размер этикетки берётся из шаблона; глобальный размер в профиле не должен
переопределять разные форматы этикеток. Для первой версии поддерживаются
существующие 203 и 300 DPI. Фактическое разрешение драйвера проверяется до
отправки; расширение набора DPI — отдельная задача.

## Формирование изображения

Добавить формат артефакта `mono-raster-v1`: готовое однобитное изображение всей
этикетки, физические размеры, размеры в точках, DPI и версия формата.
Определить каноническое двоичное представление с заголовком и упакованными
строками: digest покрывает геометрию вместе с пикселями. Проверять длины,
переполнения, допустимые размеры и ограничение объёма до выделения памяти.

Общий DOM-независимый код геометрии, штрихкодов и упаковки остаётся в domain;
отрисовка текста использует локальные шрифты станции. Покрыть все элементы
текущей модели: текст, поля, штрихкоды, линии и рамки, повороты и ограничения
размеров. Неподдержанный элемент — явная ошибка до отправки, а не пропуск.

Data Matrix и линейные штрихкоды рисуются из дискретных модулей без сглаживания.
Сохраняются GS1/FNC1, разделители, полный код и криптохвост. Размер модуля —
целое число точек, защитные поля и границы проверяются до создания задания.
Не использовать JPEG, снимок DOM или растягивание готового preview.

Предпросмотр нового пути показывает тот же сохранённый растровый артефакт.
ZPL/TSPL продолжают использовать текущие генераторы; их байты не меняются ради
добавления Windows. Интернет, облачный рендер и внешние приложения не нужны.

## Отправка через Windows

В Rust добавить отдельную команду графической печати; существующий
`print_bytes` остаётся RAW-транспортом. Использовать GDI и API драйвера:
настроить документ через DEVMODE, создать printer DC, выполнить
StartDoc/StartPage, передать bitmap, завершить EndPage/EndDoc.
Все операции выполняются вне UI/async-worker-потока через `spawn_blocking`.
DC, дескрипторы и незавершённый документ освобождаются на всех путях.

Перед StartDoc проверить фактически принятые драйвером размер бумаги,
разрешение, ориентацию и печатную область. Учесть физические смещения.
Не менять глобальные настройки очереди Windows: параметры относятся к
конкретному документу. Использовать одну копию и одну страницу на этикетку.
Вендорские настройки носителя, зазора, скорости и нагрева сохраняются из
конфигурации драйвера.

Не применять fit-to-page, автоматический поворот или скрытое масштабирование.
Если драйвер не принимает размер/разрешение или обрезает содержимое, показать
ошибку настройки до печати. Нельзя незаметно отправить на принтер по умолчанию,
перейти на RAW либо показать интерактивный диалог для каждого задания.

Полученный ID задания очереди хранится как локальная диагностическая
информация вместе с именем очереди и попыткой. ID может отсутствовать при
сбое между созданием задания и сохранением результата. Отсутствие задания
в очереди и успешный EndDoc не доказывают физическую печать.

## Задания, повторы и совместимость

Перед любой отправкой сохраняется факт `sending`. Сбой/перезапуск после
начала попытки переводит её в `delivery_unknown`; автоматическая повторная
отправка запрещена. Явный повтор требует прежнего подтверждения/причины.
Задание Windows может продолжить печататься после восстановления связи;
интерфейс восстановления должен учитывать наличие задания в очереди и
предупреждать о возможности выхода оригинала перед явным повтором.

Товарное задание замораживает растровые байты, геометрию и DPI. Повтор не
пересчитывает их из текущего каталога, шаблона или даты. Замена принтера
требует того же формата, DPI и подходящей печатной области. RAW-задание нельзя
переотправить через графический драйвер; сохранённый raster нельзя отправить
как RAW. Смена настройки профиля влияет только на новые задания.

Оба режима одной очереди используют общий ключ сериализации. Известные
представления одной очереди не должны получать независимые параллельные
каналы отправки. Сопоставление прямого IP с произвольным именем Windows-очереди
автоматически не гарантируется; не выдавать это за глобальную аппаратную блокировку.

Для товарных событий добавить отдельное представление формата печати.
Старый вариант `prepared` с `language: zpl | tspl`, `dpi`, `bytesDigest`
принимается без изменения структуры и digest. Новый вариант `prepared`
содержит `printFormat: mono-raster-v1`, `dpi`, `bytesDigest` и не требует
фиктивного языка ZPL/TSPL. Валидатор допускает только эти два согласованных
варианта и отвергает смешанные поля. Внутренняя проекция нормализует их в
типизированный формат артефакта; правило повторов сравнивает этот формат.

Обновить серверную валидацию, проекции истории, потребителей кабинета и
проверить Kotlin-контракты/общие fixtures. Android продолжает создавать свои
RAW-задания; Windows-печать на Android не добавляется. Старые события,
закреплённые batch payload и их digest никогда не переписываются.
Если потребуется изменение DDL или локальной проекции, оно оформляется новой
миграцией с тестом восстановления реальных старых записей.

Совместимый API и кабинет должны быть опубликованы до Station, способной
создавать новые события. Старые Station/handheld продолжают синхронизацию.
Откат Station на сборку, не понимающую raster, нельзя считать безопасным при
наличии новых заданий: перед откатом требуется завершить/сохранить их и
проверить процедуру восстановления. Деплой и релиз не входят в разрешение
на разработку этой функции.

## Проверки и критерии готовности

1. Настройки: старые профили остаются RAW, все комбинации таблицы работают,
   невозможные комбинации отвергаются, отсутствующая очередь не заменяется
   другой, назначения короб/товар/паллета сохраняются после перезапуска.
2. Renderer: все элементы и повороты, кириллица, длинный текст, реальные GS1
   payload, точные размеры, 203/300 DPI, декодирование готовых barcode bitmap,
   ошибки границ и повреждённого артефакта. Старые ZPL/TSPL fixtures неизменны.
3. Windows adapter: проверка геометрии/полей, отказ драйвера, ошибка создания
   задания и ошибки после его создания, освобождение ресурсов. Host-тесты
   используют изолированный интерфейс Win32; отдельно требуется Windows build.
4. Recovery: двойное нажатие, перезапуск на границах сохранения/отправки,
   продолжающая работать очередь, смена профиля, повтор сохранённого raster,
   несовместимая замена, точные события проверки и отсутствие автоповторов.
5. Контракты: старые неизменённые batches принимаются, новые события проходят
   полный путь Station → API → история, межтенантный доступ запрещён,
   смешанный формат отклоняется, TypeScript/Kotlin fixtures согласованы.
6. Автоматические gates по root AGENTS.md для изменённых пакетов; сборка
   зависимостей перед consumer-тестами; Cargo и затронутые Android checks;
   format/diff checks и Graphify update после изменения кода.
7. Отдельная аппаратная приёмка Windows: минимум два разных семейства
   драйверов, 203/300 DPI, USB/сетевая очередь, проверка полного кода сканером,
   масштаб линейкой, серия этикеток и скорость, отсутствие бумаги,
   отключение принтера и перезапуск Station. Bluetooth проверяется отдельно
   только при наличии соответствующего оборудования.

Готовность кода и физическая приёмка указываются раздельно. До физической
проверки функция не считается подтверждённой для производственной линии.
