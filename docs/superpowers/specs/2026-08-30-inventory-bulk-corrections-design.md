# Массовые исправления и разбор расхождений инвентаризации

Дата: 2026-08-30. Статус: дизайн утверждён, ожидает реализации.

## Задача

Экран хода инвентаризации и текущая форма исправлений не дают оператору быстро
перейти от числа расхождений к их разбору. Каждое событие исправляется отдельно,
код показан только в читаемом HRI-представлении, а пустой блок «Короба» выглядит
так, будто отсканированные короба потерялись.

Кроме UX-проблемы подтверждена ошибка жизненного цикла: `void_scan` переводит
результат в `voided`, однако безопасное закрытие считает `voided` обязательным
неустранённым расхождением. В результате карточка «Расхождения» уже показывает
ноль, а закрытие продолжает блокироваться количеством отменённых сканов.

Нужно сделать разбор расхождений основным сценарием страницы исправлений,
поддержать атомарное массовое действие с одной причиной, сохранить покодовый
аудит и привести отображение коробов в соответствие с режимом инвентаризации.

## Подтверждённые правила

- Быстрый переход по карточке «Расхождения» открывает страницу исправлений в
  представлении расхождений.
- «Выбрать все» означает все строки текущего фильтра на всех страницах, а не
  только загруженные 50 строк.
- Пользователь может снять выбор с отдельных строк после выбора всего фильтра.
- В одной массовой операции выполняется одно действие: `void_scan` или
  `change_date`.
- Причина задаётся один раз, но неизменяемое аудиторское свидетельство
  сохраняется отдельно для каждого затронутого результата кода.
- Массовое действие атомарно: либо применяются все изменения и весь аудит,
  либо не применяется ничего.
- `resultRevision` увеличивается один раз на всю массовую операцию.
- `voided` остаётся видимым аудиторским состоянием, но больше не является
  `UNRESOLVED_DISCREPANCY` и не блокирует безопасное закрытие.
- В режиме без переупаковки новые короба не показываются. Отсканированные
  существующие короба показываются отдельно как «Проверенные короба».
- В режиме переупаковки серверные `inventory_repack_boxes` показываются под
  явным названием «Новые короба».

## Текущее поведение и корневая причина

- `InventoryLivePage` суммирует только `ineligibleCount`, `unknownCount` и
  `dateMismatchCount` в карточке «Расхождения».
- `InventoryCloseService` дополнительно формирует
  `UNRESOLVED_DISCREPANCY` для `voidedCount`.
- `InventoryCorrectionsService.correct()` принимает только одну цель и
  увеличивает ревизию после каждого запроса. Клиентский цикл по выбранным
  строкам поэтому не может быть атомарным и конфликтует с собственной
  `expectedResultRevision`.
- `progress.boxes` содержит только новые короба переупаковки. Это не список
  отсканированных существующих коробов, поэтому блок закономерно пуст в режиме
  `check`.
- Один скан известного короба может породить несколько
  `inventory_code_results` с одним `firstAcceptedEventId`. Массовое действие
  выбирает событие, но обязано аудировать и изменить каждый активный дочерний
  результат.

## Выбранный подход

Добавляется один универсальный синхронный batch-endpoint. Он принимает либо
явный набор событий, либо сохранённое описание текущего фильтра. Сервер повторно
разрешает фильтр внутри той же транзакции, в которой проверяет ревизию и
применяет изменения.

Отдельный preview-endpoint и фоновая очередь в этой версии не добавляются.
Количество выбранных строк известно из ответа списка, а окончательная проверка
пригодности выполняется атомарно при применении. Если набор успел измениться,
сервер возвращает конфликт и не сохраняет частичный результат.

## UX

### Быстрый переход

Карточка «Расхождения» становится ссылкой только для пользователя с правом
изменения и только в статусе `running`:

```text
/inventory/:inventoryId/corrections?view=discrepancies
```

Верхняя кнопка «Исправления» остаётся и открывает общее представление.

### Представления и фильтры

Страница получает переключатель:

- «Расхождения» — только активные `ineligible`, `unknown` и расхождения даты;
- «Все сканирования» — существующий журнал, включая ожидаемые и отменённые.

Сохраняются поиск, тип события и классификация. Для представления расхождений
добавляется фильтр категории. Изменение любого фильтра сбрасывает выбор всех
строк, чтобы скрытое множество не менялось без подтверждения пользователя.

### Строка события

Основная строка показывает читаемый GS1 HRI, например:

```text
(01)04680089900060 (21)A7F92
```

Под ним выводится полный `copyIdentity` моноширинным текстом и кнопка
«Скопировать»:

```text
010468008990006021A7F92
```

`copyIdentity` формирует сервер из проверенного исходного значения. Клиент не
удаляет скобки из DOM и не восстанавливает Data Matrix самостоятельно. Если
каноническое значение требует GS-разделителя, управляющий символ сохраняется в
буфере обмена, а оформительские скобки и пробелы не добавляются.

В строке также показываются понятная русская классификация, исходная и
наблюдаемая даты, терминал и время. Технические вердикты вроде `duplicate`
локализуются: «Повторный скан», «Принят», «Отклонён».

### Выбор

Чекбокс заголовка сначала выбирает видимые строки текущей страницы. После этого
появляется предложение:

> Выбрано 50 строк. Выбрать все 2 582 по текущему фильтру.

После подтверждения клиент хранит режим `all_matching`, фильтр и множество
исключённых событий. Отдельные строки можно снять с выбора. Интерфейс всегда
показывает итоговое количество, например «Выбрано 2 579 из 2 582; исключено 3».

### Массовое действие

При непустом выборе появляется закреплённая панель с доступными для всего набора
действиями. Для явного выбора клиент пересекает `actions` выбранных строк. Для
`all_matching` он использует серверное `allMatchingActions`, рассчитанное по
всему текущему фильтру, а не только по видимой странице. Недоступное хотя бы для
одной строки действие не применяется молча: оно отключено с пояснением. После
исключения несовместимых строк пользователь может сузить фильтр или перейти к
явному выбору совместимых строк; окончательную пригодность всё равно повторно
проверяет транзакция.

Подтверждение содержит:

- действие;
- количество событий и затрагиваемых кодов;
- одну обязательную причину;
- одну новую дату для `change_date`;
- предупреждение, что действие попадёт в аудит по каждому коду.

Кнопка формулируется с количеством: «Отменить 82 скана» или «Изменить дату у
82 кодов». После успеха выбор очищается, прогресс и список перечитываются.

Одиночные действия остаются доступны и используют существующий endpoint.

## API списка

`GET /inventories/:id/evidence` получает необязательные параметры:

```ts
type InventoryEvidenceScope = "all" | "discrepancies";
type InventoryDiscrepancyCategory = "ineligible" | "unknown" | "date_mismatch";
```

`scope=discrepancies` выбирает только текущие активные результаты, которые
участвуют в счётчике обязательных расхождений. `classification = voided` в этот
scope не входит.

Каждая строка ответа дополнительно содержит:

```ts
interface InventoryEvidenceEventDto {
  // существующие поля
  copyIdentity: string | null;
  discrepancyCategory: InventoryDiscrepancyCategory | null;
}
```

`displayIdentity` остаётся HRI-представлением. `copyIdentity` — каноническое
копируемое значение. Для коробов это значение без `(00)` и пробелов
оформления, но с самим AI `00`. Для исторического свидетельства без сохранённого
проверенного исходного значения `copyIdentity = null`: интерфейс оставляет HRI
или digest для аудита, но не предлагает копировать его как товарный код.

Ответ списка также содержит `allMatchingActions` — пересечение допустимых
действий по всем строкам текущего фильтра до пагинации. Это поле используется
только для управления интерфейсом; batch-service независимо повторяет проверку
в транзакции.

Подсчёт страницы и выбор строк выполняются из одного общего query-builder,
который переиспользует batch-service. Так список и применение не могут получить
разную семантику фильтра.

## Batch API

```http
POST /inventories/:id/corrections/batch
```

```ts
type InventoryCorrectionBatchSelection =
  | {
      mode: "explicit";
      eventIds: string[];
    }
  | {
      mode: "all_matching";
      filter: {
        scope: "all" | "discrepancies";
        search?: string;
        kind?: "item" | "known_box" | "old_box";
        classification?: "expected" | "protected" | "ineligible" | "unknown" | "voided";
        discrepancyCategory?: "ineligible" | "unknown" | "date_mismatch";
      };
      excludedEventIds: string[];
    };

type CreateInventoryCorrectionBatchDto =
  | {
      action: "void_scan";
      selection: InventoryCorrectionBatchSelection;
      reason: string;
      expectedResultRevision: number;
      idempotencyKey: string;
    }
  | {
      action: "change_date";
      selection: InventoryCorrectionBatchSelection;
      observedProductionDate: string;
      reason: string;
      expectedResultRevision: number;
      idempotencyKey: string;
    };
```

Все объекты strict. Явные `eventIds` уникальны. Поиск и перечисления имеют те
же ограничения, что query списка. `excludedEventIds` уникальны и допустимы
только для `all_matching`.

Успешный ответ:

```ts
interface InventoryCorrectionBatchDto {
  id: string;
  action: "void_scan" | "change_date";
  selectedEventCount: number;
  affectedCodeCount: number;
  resultRevision: number;
  createdAt: string;
}
```

## Транзакция, ревизия и идемпотентность

В одной транзакции сервер:

1. Блокирует tenant-scoped строку инвентаризации.
2. Вычисляет детерминированный batch id из tenant, inventory и
   `idempotencyKey`; точный повтор возвращает прежний ответ, другой payload с
   тем же ключом возвращает idempotency mismatch.
3. Проверяет статус `running`, активный snapshot и `expectedResultRevision`.
4. Повторно разрешает явные события или фильтр без пагинации и применяет
   `excludedEventIds`.
5. Блокирует все активные `inventory_code_results`, связанные с выбранными
   `firstAcceptedEventId`, в стабильном порядке.
6. Проверяет до первой записи, что набор непустой, все события ещё являются
   текущими победителями и каждый результат допускает выбранное действие.
7. Создаёт batch-запись и отдельную `inventory_corrections` для каждого
   затронутого результата с индивидуальными before/after digest.
8. Применяет set-based update и публикует progress change для каждого
   результата.
9. Увеличивает `resultRevision` один раз и возвращает итоговые количества.

Скан короба является одной выбранной строкой, но может дать несколько
затронутых кодов. Поэтому ответ и подтверждение различают
`selectedEventCount` и `affectedCodeCount`.

При смене ревизии, исчезновении цели или несовместимом действии транзакция
откатывается целиком. Ответ 409 содержит стабильный код ошибки и текущую
ревизию, но не раскрывает приватные коды.

## Хранение аудита

Добавляется `inventory_correction_batches`:

- tenant, inventory, deterministic id;
- action, reason и нормализованный request digest;
- actor user;
- selected event count и affected code count;
- result revision и created at.

`inventory_corrections` получает nullable tenant-scoped `batch_id`. Одиночные
исторические и новые исправления сохраняют `batch_id = null`. Дочерние correction
ID детерминируются от batch id и target result id.

Одна ревизия может содержать несколько correction-строк одного batch. Это
намеренная семантика: ревизия описывает атомарное изменение проекции, а строки
аудита — его покодовые эффекты.

## Безопасное закрытие

`InventoryCloseService` перестаёт добавлять `UNRESOLVED_DISCREPANCY` для
`classification = voided`. Счётчик `voidedCount`, история события и коррекции
сохраняются.

После отмены ожидаемого скана код снова становится «Не найдено». Как и сегодня,
отсутствующий ожидаемый код является результатом инвентаризации и кандидатом
для итоговых документов, а не техническим blocker безопасного закрытия.

Обязательными blocker остаются `unknown`, `ineligible` и `date_mismatch`.

## Короба на странице хода

В режиме `check`:

- блок новых коробов не рендерится;
- API прогресса возвращает последние уникальные применённые сканы
  `known_box` как `verifiedBoxes`, плюс `verifiedBoxTotal` и
  `verifiedBoxesTruncated`;
- интерфейс показывает «Проверенные короба»: SSCC, терминал, время и количество
  зачтённых дочерних кодов;
- повторные сканы не создают новую строку и остаются в журнале как
  «Повторный скан».

В режиме `repack`:

- текущие `progress.boxes` остаются отдельной проекцией;
- блок называется «Новые короба» и показывает SSCC, состояние, число бутылок и
  состояние печати.

## Ошибки и восстановление

- Сетевая неопределённость: клиент повторяет запрос с тем же idempotency key и
  получает тот же batch.
- `INVENTORY_CORRECTION_STALE_REVISION`: ничего не применено; UI сбрасывает
  выбор, перечитывает прогресс и просит выбрать заново.
- `INVENTORY_CORRECTION_BATCH_SELECTION_CHANGED`: часть строк исчезла или
  перестала поддерживать действие; ничего не применено.
- `INVENTORY_CORRECTION_BATCH_EMPTY`: фильтр больше не возвращает целей;
  ничего не применено.
- Ошибки БД и публикации progress change откатывают всю транзакцию.

## Совместимость и границы

- Существующий одиночный `POST /corrections` сохраняется без изменения.
- Форматы station sync и офлайн-очереди не меняются. Массовые исправления —
  только online tenant-admin операция.
- Исходные scan events не изменяются и не удаляются.
- Полные коды не попадают в логи и audit metadata; в бизнес-таблицах остаются
  только уже предусмотренные ссылки и digest.
- Фоновая обработка, отмена всего batch одним действием и новые типы массовых
  исправлений находятся вне этой версии.

## Проверка

- API corrections e2e: explicit и all-matching selection, исключения, один
  revision bump, покодовый аудит, idempotent replay, stale revision, cross-tenant
  denial, короб с несколькими дочерними кодами и полный rollback при одной
  несовместимой цели.
- API reconciliation e2e: `scope=discrepancies`, категории, `copyIdentity`,
  одинаковая выборка списка и batch resolver, уникальные проверенные короба.
- API close e2e: `voided` не блокирует safe close; `unknown`, `ineligible` и
  `date_mismatch` продолжают блокировать.
- OpenAPI: strict request/response объекты и отсутствие приватных полей.
- DB: миграция batch-таблицы, tenant foreign keys, request digest constraints,
  nullable batch relation и runtime migration coverage.
- Admin: переход по метрике, HRI и копирование полного значения, выбор страницы,
  переход к all-matching, исключения, сброс при смене фильтра, единая причина,
  mass date change, ошибки ревизии и успешное обновление.
- Admin live: «Проверенные короба» в `check`, «Новые короба» в `repack`,
  отсутствие пустого блока и локализованный `duplicate`.
- Финальные package gates для `@markiro/db`, `@markiro/api` и `@markiro/admin`,
  затем `git diff --check` и `pnpm format:check`.
