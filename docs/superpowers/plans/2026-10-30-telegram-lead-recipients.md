# Telegram: личный чат и группа

## Границы

Поддержать до двух получателей уведомлений о заявках и ежедневной сводки: существующий `LEAD_TELEGRAM_CHAT_ID` и дополнительный `LEAD_TELEGRAM_GROUP_CHAT_ID`. Один бот, прежний выключатель `LEAD_TELEGRAM_ENABLED`. Старая настройка одного чата продолжает работать; одинаковый ID не получает два сообщения. Токен остаётся только в защищённой runtime-конфигурации.

Для релиза V4 выбран только канал через существующий `LEAD_TELEGRAM_CHAT_ID`; личный чат пока не подключается, дополнительный `LEAD_TELEGRAM_GROUP_CHAT_ID` не задаётся. Поддержка второго получателя остаётся необязательной. Токен и конкретные получатели не входят в Git. ПР не включает интеграцию в production: настройки вводятся вместе с защищённым развёртыванием V4.

Это отдельная ветка от main. Инструкции, формы лендинга и приём заявок не меняются. Настройка/перезапуск production и пробное сообщение — отдельные действия после получения конкретных получателей и защищённого токена.

## Доставка

Сохранить существующую outbox-строку и блокировку `FOR UPDATE SKIP LOCKED`. Версионированный прогресс по получателям хранить в её JSON payload, без миграции и без токена/открытого chat ID. Ключ получателя — SHA256 от ID. Список фиксируется при первой попытке; успешно доставленный или окончательно отклонённый получатель не вызывается повторно при обычной ошибке другого. Удалённый из конфигурации получатель помечается skipped; добавленный получает новые уведомления, без рассылки ранее завершённых строк.

У каждого получателя отдельные попытки и машинный код ошибки; предел 8 и существующий backoff сохраняются. Родитель остаётся pending, пока есть повторяемые ошибки, затем sent/failed/skipped по результатам всех получателей. Выключенная интеграция по-прежнему пропускает очередь без последующей массовой отправки.

Гарантия остаётся at-least-once: Telegram sendMessage не даёт ключа идемпотентности. Авария между фактической отправкой и коммитом БД может дать повтор; обещать exactly-once нельзя. Обычный retry частичного сбоя и перезапуск после сохранённого результата должны пропускать уже доставленного получателя. Откат на старый worker требует сначала завершить pending multi-recipient уведомления либо принять ограничение доставки старой конфигурации.

## Выполнение и проверки

1. Добавить RED-проверки конфигурации и двух получателей: оба успешны, частичный transient + новая worker instance, постоянная ошибка, одинаковые ID, изменение получателей, выключенный режим.
2. Добавить необязательный group chat ID, согласовать env/preflight/host allowlist, построить получателей и долговечный прогресс. Без новых таблиц, подавления ошибок или изменения форм.
3. Описать параметры и границы доставки в runbook и env examples. Проверить platform env contracts и API tests с mock Telegram на отдельной БД; lint/typecheck/build.
4. Подготовить защищённый шаблон runtime-настроек. Проверять бота и права только read-only методами API; реальные сообщения и production-включение требуют конкретного адресата и разрешённого protected workflow.
