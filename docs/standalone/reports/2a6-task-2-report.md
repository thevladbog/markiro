## Self-review / concerns

- Notes, none blocking:
  1. The COM subscription is the screen's: every screen that starts the source (sign-in, shifts, the work screen) stops and re-subscribes on mount/unmount, and `HardwareApi.onScan` says a scan emitted while no listener is registered is lost. A scan arriving in the instant between two screens is lost (the same window the plan's `onScan` JSDoc names); the work screen's gate (later tasks) keeps its own source started for its life, so this only matters across screen changes.
  2. A `subscribe` that throws synchronously (not rejects) would throw out of `start`. The real `onScan` is `listenTo(...)`, an async function, so it only ever rejects; the brief's code (kept verbatim) does not add a try/catch. I did not widen the behaviour.
  3. Two workstations' behaviour with both a COM scanner and a wedge scanner reading the same physical code is not de-duplicated by the merge (not in the brief; the pipeline's duplicate check in later tasks owns it).
  4. The rules say no `cd`; at the start I ran one `cd` (the shell's cwd then stayed in the worktree). No stray `.claude/.cc-writes` appeared in the tree (`git status --short --ignored` shows only the usual ignored build dirs).
- External: nothing here exercises a real COM scanner or the Tauri event channel; jsdom tests drive `HardwareApi.onScan` with fakes.
