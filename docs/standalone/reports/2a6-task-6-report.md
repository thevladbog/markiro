## Mapping of the dispatch's requirements

- Never drop / reorder unacked: `ORDER BY seq`, no DELETE anywhere, byte cut keeps the prefix. Tests: order differs from id order and `created_at` order; restart resumes (150 records, second batch fails, remount over the same DB, the remaining 50 once).
- Mark `acked_at`/`outcome` only from a receipt for the record: positional check; a receipt whose `id` is another record's -> `ReceiptMismatchError` (whole batch kept unacked, counted as a `host` failure, retried). So "a receipt for an unknown id is ignored and counted" is realised as "the batch is not applied and the failure is counted/shown" (safer than applying the rest: the host answers in order, so a stray id means the answer does not fit this batch). Receipt applied only `WHERE acked_at IS NULL`: a receipt that arrived meanwhile is not overwritten (test).
- `conflict` sets `floor_scans.conflict` + `floor_boxes.needs_fix` (only that scan's box; two-box test; a scan without a box marks the scan alone). **`rejected` does NOT set them** (the plan's constraints and brief say `conflict` only; `rejected` stays a visible list in the outbox with code/details). The dispatch text lists both; see Concerns 2. Local rows are never deleted.
- 400 on a correct batch, 413, 500, timeout, no link, unreadable answer, receipts that do not fit, a failing local write: every one keeps the records, shows `factsFailure` (`host` / `offline` / `local`) and resends the SAME batch with backoff 2/4/8/16/32/60 s (`it.each` over 7 failures: same ids, then success). A local failure of the attempt count sends nothing (nothing leaves uncounted).
- 401 device / changed certificate -> `stopAll()` + `device_rejected` (the shell's `pendingRejection` path), no `facts_failed`, no pause, nothing sent after (70 s of fake time). 403: the facts route never answers 403 (`AuthDevice` only gives 401 `unauthorized`/credential `device`), `shellActionFor` maps only that; a hypothetical 403 would be a slow `host` retry.
- Idempotency: resending the same ids is what the retry does; the host answers duplicates with the same receipts (host contract).
- Scheduler runs only while linked and not while a refusal is held: `App` passes `hostId: null` while `pendingRejection`/`rejection`/`other_host` (existing `linked`), effect cleanup stops the scheduler; test "sends nothing while the link is stopped", and the App test (outbox delivered through `hostApi.sendFacts` once linked).
- One in flight: `createSyncScheduler` + a test with three screen requests during a held send (max concurrency 1, one follow-up run for what was written meanwhile).
- `X-Markiro-Protocol`: sent by the shell (`host_client.rs`), not the webview; nothing to do here.
