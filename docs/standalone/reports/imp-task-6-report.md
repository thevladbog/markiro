## Concerns

1. Error text: the malformed-body path (`ApiJson` -> `Json` rejection `body_text`) is pre-existing and can quote a wrongly-typed JSON value from serde (e.g. a verifier string placed in a numeric field by hand-editing the file). Task 4's tests cover field names, not values; a normal tool-made file cannot trigger it and the webview verifies the checksum. A dedicated extractor for this route that replaces the text would close it; not done (outside the brief).
2. Repeat semantics: a file re-read in the office gets a new `importId`, so re-importing the same file after a successful import answers `already_imported` (409) instead of the stored summary; only a resend of the same request (same `importId`) is idempotent. That is the brief's design.
3. A handheld device can sign in to the office like any device (existing office policy, `office_auth::login` accepts any device kind); an administrator session on a handheld could import. Devices without an office session are refused.
4. Audit pruning: the repeat/`already_imported` record is the `import.cloud` audit row; if audit rows are ever pruned the site then answers `site_not_empty` (safe direction).
5. Load flake note: none this run (T4 saw `restore.rs` once).
