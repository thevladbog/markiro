## Исправления по ревью Codex

Ветка `claude/fix-tsd-android`. Все 11 замечаний проверены по текущему коду; все подтвердились. Облачные потоки не менялись (облачные тесты зелёные).

1. Список смен брал достижимость из облачного `ReachabilityTracker`: у ТСД хоста выбор ещё не загруженной смены всегда давал «недоступно». Теперь `ShiftListViewModel` в режиме `host` берёт достижимость из `HostLinkMonitor` (последний ответ хоста).
2. Линия, назначенная после привязки, не доходила до ТСД (`/v1/device` читался только при привязке). Новое `HostReferenceSync.refreshDevice()` вызывается на каждом ударе пульса, который дошёл до хоста, и в `HostBackend.shifts()` перед чтением списка; смена линии сбрасывает имя и берёт его из ленты.
3. «Исключения» (отмена, очистка, разборка, перепечатка) в режиме хоста расходились бы с хостом. Пункт меню на экране работы теперь неактивен с пояснением «недоступны при работе с хостом» (`WorkUi.hostMode`); в облаке без изменений. До шага 1б.
4. `HostAckMapper` подтверждал членство по `(palletId, sscc)`. Теперь по `addedAt` из замороженного события (`markAcceptedAt`/`markRejectedAt`); отказ по старому добавлению не трогает заменяющую строку и не снимает её claim на короб.
5. Валидационные смены не проходили проверку возможностей. Приложение их отрабатывает (простые сканы, дубль-печать в хосте выключена), поэтому на входе в смену называется `validation-v1`; `validation-dm-duplicate-v1` не называется — смену с дублем хост по-прежнему отвергает `station_update`.
6. Смена сертификата хоста: статус `HostLinkStatus.CertificateChanged`, красная плашка на хабе с подтверждением и действием «Привязать заново» (запечатывает ключ как отказ хоста, данные и очередь остаются; обычный экран привязки с подтверждением нового отпечатка и новым кодом). Сертификат молча не принимается.
7. `HostCalls` запоминает поколение ключа в начале вызова и передаёт его в `HostRevocation.reject(generation)`, как облачный транспорт; запоздалый отказ не запечатывает новый ключ.
8. Повторная привязка через другой адрес того же хоста: `DeviceRecovery.restore` допускает смену `serverOrigin`, если совпали host id, device id и сертификат (`sameHostDevice`); `serverUrl` в конфиге переезжает вместе с владельцем. Другой хост/устройство/сертификат без `allowPinChange` по-прежнему `RecoveryMismatch`.
9. Сбой локальной публикации после claim: теперь `Failed(OTHER, canRetrySync = true)`, «повторить» публикует тот же кандидат (`paired`) и не просит новый код. Отдельный вызов `resumePublication()` не нужен: повторный `restore` в фазе `RESTORING` доводит ту же публикацию.
10. Детали ошибок читаются безопасно (`JsonObject?.text`: не строка → `null`, в `HostApi` и `HostAckMapper`); `HostSyncEngine.drainAll()` не выпускает исключений (кроме отмены).
11. Конверт, отвергнутый целиком (400/403/413/422): 3 прохода повтора, затем канал шлёт по одной записи; запись, отвергнутая и в одиночку 3 раза, уходит в карантин с причиной `refused_<статус>` (видна на экране очереди хоста, источник не подтверждается), остальные идут дальше. Счётчики в памяти (после перезапуска отсчёт заново).

Проверки: `./gradlew --offline --no-daemon testDebugUnitTest lintDebug assembleDebug` — 1404 теста, 0 падений, lint и assemble BUILD SUCCESSFUL. Первый полный прогон `testDebugUnitTest` упал с выходом 134 (аварийное завершение JVM Robolectric, SQLITE_CANTOPEN при падении воркера) — повтор зелёный, как и раньше (см. «Не сделано / открыто»).
