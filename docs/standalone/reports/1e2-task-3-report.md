### D. Survivors of the final pass: six, all equivalent

- `set-d-chz_group_code`, `set-d-purpose`: the default's key `<code>:<purpose>` (built by the host from those two fields) already fixes both columns, so a same-id update never changes them; only a host record whose id disagrees with its data could tell, and that is a host defect no copy should encode.
- `prod-gtin-d` (`/^\d{14}$/`): `\d` in a JavaScript regex without the `u`/`v` flag is ASCII-only, so the pattern is the same one.
- `sql-uniq-default-pair` (`UNIQUE (chz_group_code, purpose)` on the defaults): cannot fail while the key encodes both.
- `sql-chk-archived`, `sql-chk-status`: a CHECK on a boolean and on a two-value enum cannot fail for a record that passed its schema. «No CHECK» is therefore a design rule of the migration that no behavioural test can pin.

One more mutant, run for the test I added to pin the host's GTIN contract: `prod-gtin-checkdigit` (the feed schema also demands a GS1 check digit) is KILLED — by my test «keep a product whose GTIN has a wrong check digit…» and, as it turned out, by two plan tests too (the quarantine test and the 5000-product test, whose synthetic GTINs have wrong digits), so that test pins the rule explicitly rather than closing a gap.
