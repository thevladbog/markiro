## Concerns

1. SSCC windows are the export tool's contract; the host cannot see the cloud. `check` guarantees only that every `nextSerial` is inside the prefix's serial width and per-extension origin (1 for boxes, 0 for pallets), and that (prefix, extension) is unique. A hand-edited file with a LOWER start number passes (the brief's edge test even pins `9_999_999` and pallet `0`); the defence is the checksum the webview verifies (task 7), and `Task 6` raising counters only forward. If the owner wants the host to require `nextSerial` to be the origin or a multiple of 10 000 (the tool's `START_STEP`), that is a one-line tightening plus changed edge cases; I did not do it because it changes the brief's pinned edges.
2. The host does not require a counter for the organisation's own issuer prefix (`gln[..9]`): the tool emits counters only for prefixes the cloud used, and absence means the cloud never issued. A damaged file that drops the own-prefix counters would restart at the origin; the checksum is the guard.
3. Cross-checks that need the database stay with Task 6: GLN equals the site's, product groups exist (`group_refs`), site emptiness, repeat by `importId`.
4. `badgeSalt` absent/`null` is not an error (keep the site's salt) unless the file has badges (`payload.badgeSalt`), as the T4 report required. The host must never serialise the request to a log or the audit row (Task 6).
5. One equivalent mutant (canonical re-encode of the salt) is documented, not tested away.
