# b3-stats: статистика использования в сведениях для поддержки и дата смены

Ветка `claude/b3-stats` (worktree `/tmp/claude/wt/b3-stats`), от `claude/integration`, после слияния b3-shifts (drawer смены) в ветку влит `claude/integration`.

## Пункт 1. «Статистика для анализа использования» в сведениях для поддержки

### Что просил владелец

Добавить в блок «Сведения для поддержки» страницы «Информация» статистику по месяцам: смены по режимам, сканирования, короба, паллеты, ошибки и т. д. Решение владельца (через контроллера): статистику не показывать пользователю, а шифровать открытым ключом так, чтобы читали только мы.

### Что сделано

- **Хост**: `GET /v1/office/usage-stats` (`host/src/routes/usage_stats.rs`), только администратор, только чтение, без аудита и без ревизии; добавлен в `license/gate.rs` `NEVER`. Один ответ `UsageStats` (`proto/src/usage_stats.rs`): 12 календарных месяцев (старый первым, пустые месяцы есть) и устройства по видам. По месяцам: смены (агрегация / проверка / с печатью дубликата / из офиса / со станции / с паллетами), сканы (принято / дубли / отклонено), короба (закрыто / расформировано / кодов в них, т. е. среднее кодов на короб = codes/closed), паллеты, исключения по видам (короб: undo/clear/reprint/disassemble, паллета: reprint/disassemble), конфликты (late/displaced/reviewed), перепечатки (склад + дубликаты Data Matrix), применённые документы расформирования, отклонённые записи (ошибки синхронизации на стороне хоста). Только числа и ключ месяца; типы `deny_unknown_fields`.
- Месяц строк смены = месяц ДАТЫ СМЕНЫ (`planned_date`, пункт 2), месяц инстантов хоста (конфликты, документы, перепечатки склада) = UTC-месяц.
- Запросы — группировки, ограниченные окном и ведомые индексами (`shifts_planned_date`, затем `scans_shift`, `boxes_shift`, `pallets_shift`, `box_exceptions_shift`, `pallet_exceptions_shift`, `unit_label_events_shift`, `fact_receipts_rejected`, `code_conflicts_detected`). Тест плана (`no_query_scans_a_table_of_facts`) падает на скане любой таблицы фактов, поэтому **миграция под scans не понадобилась**. Читаются целиком только `warehouse_reprints` и `disaggregation_documents` (единицы строк).
- **Шифрование в вебвью** (`src/office/info/support-crypto.ts`, `support-usage.ts`, `support-keys.ts`): ephemeral ECDH P-256 + HKDF-SHA256 + AES-256-GCM, полезная нагрузка (JSON, собранный по белому списку полей из ответа, `usagePayload`) предварительно сжимается deflate-raw (если есть `CompressionStream`). Формат `MKS1.<kid>.<base64url(флаг ‖ epk(65) ‖ iv(12) ‖ шифртекст ‖ тег)>`. AAD = `MKS1.<kid>` + байт флага (небольшое усиление против ТЗ: флаг сжатия тоже аутентифицируется), `info` HKDF = `MKS1.<kid>` ‖ epk. Хост по-прежнему отдаёт открытый JSON, шифрует только вебвью при сборке текста.
- В тексте для поддержки: заголовок «Данные для анализа использования», строка «Статистика: зашифрована, период …» и одна строка-токен (`SupportBlock.opaque`, пропускается только если подходит под форму токена). Читаемый блок (версии, роль, состояние) без изменений. При пустом ключе — «недоступна в этой сборке» (никогда не открытый текст); для техолога/без ответа хоста — своя строка причины. Кнопка «Сформировать и скопировать» как раньше; текст в окне стал 18 строк.
- **Ключ**: `proto/fixtures/support-keys.json` (формат как у `trust-keys.json`): `{ "keys": [], "retiredKids": [] }` — продакшен-набор ПУСТ до шага владельца. Схема отвергает приватный ключ (`d`), не-P-256, лишние поля, повтор kid. Реальных/тестовых приватных ключей в репозитории нет (тестовые пары генерируются при прогоне).
- **Расшифровка**: `tools/standalone-support/decrypt.mjs` (Node): `--key support-private.pem [файл|stdin]` — находит `MKS1…` в любом тексте (можно скормить письмо целиком), печатает JSON и таблицу по месяцам (с кодами на короб); `--public-jwk --key …` печатает запись `{kid, jwk}` для `support-keys.json` (только публичная половина). Скрипт `pnpm test:standalone-support:contract`, шаг в CI (verify_static), правило в `tools/ci/affected.mjs`.
- Документация: раздел в `apps/standalone/AGENTS.md` (формат, запросы, ключи, шаги владельца).

### Шаг владельца (обязателен для включения статистики)

```bash
openssl ecparam -name prime256v1 -genkey -noout -out support-private.pem
node tools/standalone-support/decrypt.mjs --public-jwk --key support-private.pem
```

Приватный ключ хранить у себя и не коммитить. Выданный `{ kid, jwk }` положить в `keys` файла `apps/standalone/proto/fixtures/support-keys.json` (передать мне публичный JWK — вставлю и соберу). Пока ключа нет, сборка честно пишет «недоступна в этой сборке».

### Тесты

- Хост (`host/tests/usage_stats.rs`, 5 тестов): точные числа на посеянной БД (смены в окне, вне окна, месяц по дате смены, станция/офис, все виды сканов/исключений/конфликтов/документов/репринтов, устройства с отозванным), отказ техологу (403), ключу устройства (401), без учётки; ни записи аудита, ни ревизии; белый список ключей и отсутствие строк с кодами/именами/SSCC/ПИН; окно в 12 месяцев; планы запросов (без SCAN таблиц фактов, нужные индексы использованы).
- proto (`proto/tests/fixtures.rs`): фикстура `usage-stats.json` round-trip, единственный текст — ключ месяца, лишнее поле отвергается; Zod-паритет в `test/protocol.test.ts`.
- Вебвью: `test/support-crypto.test.ts` (круг: шифрует код вебвью, открывает инструмент; сжатый/несжатый; нет открытых слов в токене; чужой ключ; подмена kid/флага/epk/nonce/шифртекста/тега/версии — всё падает), `test/support-report.test.ts` (токен только нужной формы, белый список полезной нагрузки против «загрязнённого» ответа, причины отказов), `test/about-page.test.tsx` (в сборке без ключа — «недоступна в этой сборке», без токена).
- Node: `tools/standalone-support/test/decrypt.test.mjs` — независимый писатель токена на node:crypto, CLI (файл/stdin/ошибки), `--public-jwk`.

## Пункт 2. Дата смены

### Что было не так

У смены была только дата производства (она же «дата смены» в бланке). Облако называет второе поле `plannedDate` (UI «Дата смены»), оно отдельно от `productionDate`.

### Что сделано

- Имя и семантика как в облаке: `plannedDate` / `planned_date`, подпись «Дата смены», гражданская дата YYYY-MM-DD. **Номер смены по-прежнему считается по дате производства** (ничего в нумерации не менялось, есть тест).
- **Миграция хоста `0028_shift_planned_date.sql`** (0027 занят b3-shifts; перенумерована после сообщения контроллера): колонка `shifts.planned_date` (nullable + CHECK формата), существующие строки получают дату производства, триггер `shifts_planned_date_default` даёт то же вставке без даты (старые сборки, сырые INSERT), индекс `shifts_planned_date`. Ответы читают `COALESCE(planned_date, production_date)`.
- **Протокол**: `OfficeShift.plannedDate` обязательное; `DeviceShift.plannedDate` необязательное (хост до беты 3 его не шлёт); `ShiftCreate`, `ShiftUpdate`, `DeviceShiftCreate` — необязательное поле, старые тела читаются как раньше (старые фикстуры не менялись, добавлены `*-planned-date.json`). `PROTOCOL_VERSION` не повышался (станция шлёт поле только на хост, обновлённый раньше, как и требует установка). Аудит: `shift.create` называет `plannedDate`, только если оно отличается от даты производства (старые строки аудита не меняют форму), `shift.update` — как любое изменённое поле. Дата — «фиксированное» поле: у открытой/закрытой смены не меняется (как дата производства).
- **Офис**: поле «Дата смены» в `ShiftDialog` (по умолчанию сегодня в часовом поясе организации, редактируется у запланированной), столбец и сортировка в списке (сразу после даты производства), фильтр периода «Дата смены с/по» (параметры `plannedFrom/plannedTo` хоста, сужает период по дате производства), строка-пояснение под фильтрами, строка в сводке и в шапке drawer-а смены (после слияния b3-shifts: правки перенесены в `ShiftDrawer.tsx`, не вручную в старый путь), бланк смены печатает её (`taskFormData`).
- **Станция**: `NewShift` шлёт `plannedDate` = сегодня в часовом поясе организации (`civilToday`, как и дату производства по умолчанию). Хост без этого поля берёт дату производства.
- Тесты: `host/tests/shift_planned_date.rs` (6: создание/правка/аудит/номер не меняется, валидация, фильтры, станция с датой и без, фоллбэк), `migration_planned_date.rs` (бэкфилл на БД до миграции), proto/Zod-паритет, `shift-form`, `shift-dialog`, `shift-edit`, `shifts-page`, `shift-card`, `shift-list`, `floor-new-shift`.

### Изменённые существующие тесты (решение продукта изменилось)

Точные тела/ожидания обновлены под новое поле: `host/tests/office_shifts.rs`, `device_shifts.rs` (ответы со `plannedDate`), `test/floor-new-shift`, `shift-dialog`, `shift-form` (порядок полей), `shift-mode-select`, `shift-card`, `form-data`, `form-data-rules`, `forms-parity` (пред-обработка кейсов облака), `shifts-page` (помощник `cells()` пропускает ячейку даты смены, чтобы остальные индексы остались; у даты смены свой тест `allCells`), `support-report` (контрибьютор в `SUPPORT_CONTRIBUTORS` теперь один). Ключ `officeKeys.shiftList` не меняет форму без периода по дате смены.

## Что НЕ проверено / не сделано

- Дата смены **не сохраняется в копии смены на станции** (`floor_shifts` не менялась, миграции оболочки нет): карточка смены на станции и список по-прежнему показывают дату производства. Причины: правки пола пересекаются с другими потоками, плюс Rust-тесты `local_db.rs` сравнивают `sqlite_master` до/после миграций. Хост уже отдаёт `plannedDate` в `GET /v1/device/shifts` и при входе; для станции остаётся `ALTER TABLE floor_shifts ADD COLUMN planned_date` (оболочка 0017+), поле в `HOST_FIELDS` и строка на `ShiftCard`.
- Импорт из облака: смены облака импорт не переносит (в host `cloud_import` смен нет), поэтому маппить `plannedDate` нечего.
- Не проверено: WebView2/Windows (WebCrypto и `CompressionStream` проверены в Chromium-браузере и в Node/jsdom; в WebView2 ожидается то же), реальный Tauri-хост, скорость 12-месячной агрегации на миллионе сканов (планы корректны, замеров на боевом объёме нет), установка/обновление Windows.
- Визуально проверены (браузерный harness на фикстурах, не закоммичен; скриншоты в `/tmp/claude/fb/b3-stats/`): список (колонка и фильтры), диалог смены, карточка, текст «Сведения для поддержки» с зашифрованным токеном. Шапка drawer-а (новая строка «Дата смены: …» после слияния b3-shifts) проверена только тестами, не глазами; фильтры периода на втором ряду панели фильтров.
- Среднее кодов на короб считается из `item_count_reported` закрытых коробов (отчёт станции), а не из живых позиций.
- «Ошибки outbox/синхронизации» со стороны станции хост не видит; взяты отклонённые хостом записи смен месяца (`syncRejected`). Отклонённые записи без смены (нечитаемые) не попадают.
- Для техолога блок статистики говорит «доступна администратору» (маршрут только для администратора, как просили).
