## What was done

- Proto: `pallet_sheet_template_id` in `OfficeShift` (always present, `null` for none), `ShiftCreate`, `ShiftUpdate`, `DeviceShiftCreate` (optional, sent only when set); `ShiftSnapshot.pallet_sheet` and `.organization` (optional, skipped when absent, so snapshots frozen by an older host still parse); new `ShiftSnapshotSheet`, `ShiftSnapshotOrganization`, `ShiftSnapshotLogo`. Fixtures `shift-create-pallet-sheet.json`, `device-shift-entered-sheet.json`, `office-shift.json` gets `palletSheetTemplateId: null`. Two proto tests (the brief's parity test and a request/answer-shape test).
- Host (`shifts.rs`, `office_shifts.rs`, `device_shifts.rs`): `shifts::pallets(.., sheet_id)` (request's sheet checked enabled, else `default_sheet`, else none; a sheet without pallets is `validation_failed` on `palletSheetTemplateId`); `insert` binds it; office update keeps / changes / defaults-on-turn-on / clears-on-pallets-off, `fixed_changed` includes it (an open shift takes the same sheet but not another: `shift_status`), a changed sheet is checked, an unchanged one is not (kept even if disabled since); update audit carries `palletSheetTemplateId {from,to}`; `shifts::snapshot(.., pallet_sheet_id)` freezes name, revision and the whole spec of the sheet and the organization name, INN and logo; `enter_shift` passes the shift's sheet and audits `palletSheetTemplateId` + `palletSheetRevision` in `shift.open`.
- Webview: Zod (`officeShiftSchema`, the three request schemas, `shiftSnapshotSheetSchema`, `shiftSnapshotOrganizationSchema`, snapshot), `ShiftPallets.sheetId` and the `shiftCreate`/`shiftUpdate` builders, `checkShiftSnapshot` returns `palletSheet: SnapshotSheet | null` and `organization: SnapshotOrganization | null`.
- No station table or shell migration was needed: the snapshot is stored as text in `floor_shifts.snapshot` (already round-trips the new keys because `keepEnteredShift` stores the Zod-parsed answer, and the schema now carries them). Retention: the sheet and logo are part of that one text, so they follow the shift's rows; the host stores them in `shifts.snapshot`, no separate rows.

## Fallback decisions (addenda: disabled or missing sheet at open) — as the brief says

- Sheet DISABLED after planning: frozen as it is (its revision and layout), the shift opens. Turning off only stops new shifts from choosing it. Test `a_disabled_sheet_is_frozen_as_it_is_and_a_missing_one_as_none`.
- Sheet MISSING from the table (the API never deletes one a planned shift names — `template_in_use`; only raw SQL/restore can): frozen as NONE (no `palletSheet`, no main-sheet substitution), the entry still opens, the open is audited without sheet keys. (T3's report suggested "main sheet"; the brief says none and I followed the brief: a silent swap of a sheet the office never chose seemed worse than the thermal fallback.)
- Delete of a sheet an ACTIVE or CLOSED shift names stays allowed; the snapshot owns the sheet and is never re-read after the open (re-entry parses the stored text). Tests: rename, switch off, spec changed under it in the table, organization renamed (name and INN), logo replaced and cleared, sheet deleted — the snapshot is byte-equal after each; a later new shift freezes the new state.

## Differences from the dispatch/brief (please check)

1. DISPATCH vs BRIEF on the station: the dispatch says "a sheet part that fails validation is refused with a precise error"; the brief (Interfaces + А4-7) says a sheet the domain does not read and a logo that does not read give `null` and do NOT close the shift (thermal labels print; an A4 print later fails `render_failed`). I implemented the brief. A MALFORMED SHAPE of the sheet or organization (id not a UUID, revision < 1, name not a string, organization without `logo`/`inn`, logo with a fractional size) is refused as `shape` by the Zod schema and is never stored; an unreadable LAYOUT / logo bits are `null`.
