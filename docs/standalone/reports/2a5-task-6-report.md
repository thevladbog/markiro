## Design check of the `requestId` (controller note c)

The brief draws the id in `choose` (once per product chosen = once per form), keeps it across retries, never redraws it after an edit or a success. This is the plan's decision (constraints line 78) and matches the host (`host/src/routes/device_shifts.rs:158`: "the same `requestId` again answers the shift it created, whatever the body says now"). Verified and pinned with tests:

- after a lost answer the same id is resent (brief test); the edited fields (plan 500, date +1) go with the same id (the host decides; test "makes no second shift when the answer was lost and the form was changed meanwhile");
- after a created-but-not-entered refusal (`shift_busy`), pressing again resends the same id and re-enters the same shift (`create` x2 with one id, `enter` x2 with `PLANNED.id`; test "enters the shift it made when it could not open it, without making another");
- a new product chosen (also the same product again after "Другой товар") draws a new id (`NEXT_REQUEST_ID`; test "starts a form of its own, with a request of its own, for every product chosen").
  This differs from the controller's wording «new after the form changes or a successful create» on two points, deliberately: a new id after a successful create would make a SECOND shift when the entry was refused and the operator retries, and a new id after editing a form whose first answer was lost would also make a second shift. The cost of the brief's design (retry after a lost answer whose host create succeeded returns the first shift's fields, not the edited ones) is the one constraints line 78 accepts; the number and plan are visible on the work screen. If the controller wants the other trade-off it is a decision, not a bug fix; I did not change it.
