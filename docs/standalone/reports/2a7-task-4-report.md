## Print integrity rules - how each is held

- **A label never printed twice by the program.** `sendLabelJob` is the only thing that sends; nothing in `print-jobs.ts`/`print-runtime.ts` retries. `unknown` (shell's `outcome_unknown`, the 20 s `timeout`, a restart's `interrupted`) is left for the operator. A send starts only from `prepared`, `failed`, `unknown`, `sent`; `sending`, `verified`, `skipped` are refused (`UnsendableJobError`) - a `sending` job would otherwise pass the stale check (state and attempts equal) and go out a second time; tests per state + mutants J1/J2/J2b.
- **Crash between "job decided" and "job written".** There is no such gap: the job row is a statement of the box's own close transaction (`boxLabelStep` returns it as a `CloseStep` addition). Either both box and job exist or neither (tests: failed write leaves neither; stale close writes no job; mutant M3 = job in its own transaction is killed).
- **Crash between "job written" and "bytes sent".** The job is `prepared`; the first send (Task 6, once, on entering the work screen) writes `sending` BEFORE the bytes go. A crash after `sending` leaves `sending`; `recoverInterruptedJobs` reads it as `unknown` `interrupted`, never as `prepared` (mutant M1 sends first and is killed by 10 tests).
- **Exact bytes vs regeneration.** The row carries BOTH: the exact bytes (`bytes_base64`, base64 because `local_query` reads no BLOB) and everything to regenerate them identically: `fields` (the label's fields, including the closing operator's name and the closing time), `template_id` + `template_rev` (the layout comes from the shift snapshot, never from the station's newer copy - test and mutant M8), the printer profile (`printer`, language and dpi). Why both: a retry on the SAME printer must send the very same bytes (rendering again could differ, e.g. if the rasterizer changed); a different printer (other language/dpi) needs a re-render from the same fields and the snapshot's template revision (Task 5, via `SendOptions.rebind`, which writes the new printer and bytes in the same transaction as `sending`). Tested: all 256 byte values survive base64 and reach the shell exactly (J34).
- **Survives restart.** The rows are in SQLite; `readOpenJob`/`shiftLabelsSettled` read them; a job this build cannot read (damaged printer/fields) is `UnreadableJobError` for `readPrintJob`/`readOpenJob` but still counted as waiting by `shiftLabelsSettled` (a count query, not a row read).
- **One in-flight send per printer.** `createPrintRuntime` chains sends per `printerTargetKey` (normalised address: `192.168.1.50.` and `192.168.1.50` are one printer); a send starts only after the earlier send's shell call has really settled, not when it merely timed out (mutants M7, R3, R9, R16). Jobs-level test: two jobs on one printer, shell sees one send while the first is held.
- **Bounded time on the awaiting side.** `PRINT_SEND_LIMIT_MS = 20_000` (20 s) from the moment of asking, queue wait included. Reason: the shell bounds connect+each write to 5 s, but a COM flush / spooler call can block past that and then never answer (2a4 task-7 concern 1). Outcomes: bytes already given to the shell and no answer -> `timeout` -> job `unknown` (a label may exist); bytes still waiting behind someone's stuck send -> `busy` -> job `failed` `printer_busy`, and those bytes are NEVER handed to the shell afterwards (`expired` flag; mutant M6/R15). A late answer after either changes nothing in the row (final write requires `state='sending'` and the same attempt; M4/J4/J13). The job stays "in flight" until the shell call really settles, so recovery does not touch it (M5, J39, J40).
- **Printing never blocks scanning of the next box beyond the documented rule.** Nothing here blocks anything: `sendLabelJob` is an async function the screen runs as tracked work; the documented rule (a waiting label stops the NEXT box close) is `readOpenJob` + the unique index `floor_print_jobs_open` (Task 6 uses `readOpenJob`).
- **A printer that is down leaves a visible, recoverable state.** The box is closed in any case. No printer assigned -> job `failed` `printer_unconfigured` (bytes and printer null); a label that will not render -> `failed` `render_failed` (printer kept, bytes null; `sendLabelJob` refuses it, tested); shell `not_sent`/`invalid_*`/`unsupported` -> `failed`; unknown outcomes -> `unknown`. All are "open" jobs the work screen shows (Task 6) and Task 5 resolves.

## Concerns

1. **Gap before the runtime holds the job.** `sendLabelJob` writes `sending`, awaits the transaction, and only then calls `runtime.send`, which registers the job as in flight synchronously. In that window (a local DB round trip, no network) `recoverInterruptedJobs` would not spare it and would turn it `unknown`; the send's final write would then be refused (`StaleJobError`) although the bytes went. The outcome is safe (unknown means "operator decides"), but it is a spurious `unknown`. It cannot happen when recovery runs only on entering the work screen, before any send is started, which is how the brief and Task 6 use it. Do not call `recoverInterruptedJobs` concurrently with a running send (N13: keep it in the work queue).
2. **`sent` job without a check can be re-sent** by `sendLabelJob` (SEND_FROM includes `sent` for the reprint-with-reason of a label whose check is pending). The reason/exception is the caller's `extra`; nothing here forces it. Task 5 (`printAgain`) must demand the reason when `unknown`/`sent`, as its contract says.
3. **Late write failure after the shell took the bytes.** If the final write throws a non-stale DB error, the job stays `sending` and the error propagates; the runtime releases it when the shell call settles, and the next recovery makes it `unknown`. Safe, but the screen must treat a rejection from `sendLabelJob` as "state unknown, re-read".
4. **`fakeHardware().releaseSend`** turns holding off after the last waiting send is released, so a queued second send is answered at once by `answer()`; my two-jobs test accounts for it (it asserts the shell saw one send while the first was held, and two after release).
5. `productionDate`/shift number of the label come from the shift copy (Task 3 concern, FOR THE 2a7 FINAL REVIEW, unchanged here); the job stores the fields it was made with, so a reprint of the same job never recalculates them.
6. Used `cd` once at the start of exploratory Bash calls (no `.cc-writes` left; tree clean).
