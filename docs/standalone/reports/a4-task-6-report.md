## Label correctness evidence

- Vectors pinned, hand-verified (test/floor-label-render.test.ts): 4x2 mm box at (2,2) on 58x40, logo 8x2 [F0,0F]. 203 dpi ZPL `^FO16,20^GFA,32,32,4,`+`FFFF0000`x4+`0000FFFF`x4; TSPL `BITMAP 16,20,4,8,0,` inverted bytes; 300 dpi (layout stays 203, printer 300) ZPL `^FO24,30^GFA,72,72,6,` 47x12 (`FFFFFF000000`x6, `000000FFFFFE`x6) and TSPL `BITMAP 24,30,6,12,0,` inverted (last pad bit 1).
- Absent logo: ZPL bytes with `logo` null/omitted === bytes of the same layout without the element; with the logo the ONLY difference is the one `^FO..^GFA..^FS` line (regex-removed equals); TSPL has exactly one BITMAP more. 203 and 300.
- No overflow: every stock default and pallet layout with a logo box, at 203 and 300, with wide/tall/square logos: graphic x === box x, y >= box y, bytes/row <= ceil(boxW/8), y+rows <= box bottom, box inside the label (RAW); same in the preview (drawLabel ink inside the box in px, 203/300, wide/tall).
- Preview == print: drawLabel uses the same `renderLabelLogo` as the generators; test compares its dots with the hand-computed print geometry (x 16, rows from 46 / 30 dots at 203, 236-dot width at 300).
- Driver page: logo bounds {16,20,48,28}; null logo === blank page bytes.
- End to end WorkScreen (floor-work-print): a box closed with the shift's frozen logo sends the exact `^FO16,20^GFA,32,32,4,...` graphic; "Другой принтер" (TSC 300) sends `BITMAP 24,30,6,12,0,`; a shift with no frozen logo in jsdom (no canvas for Markiro) still prints (job `sent`, `^XA`, no `^GFA`, next scan accepted) and `console.error` got the fixed line exactly once.
- Cloud parity: compared with bbcfc9c05 (`box-printing.ts`: logo only when the layout has the box, passed to RAW render and to `renderMonoLabel(..., {logo})`; a logo failure does not stop printing). Not ported (not in standalone): the cloud's "never replace a configured logo by Markiro on download failure" (the logo here is frozen in the snapshot; a frozen logo the build cannot read reads as null -> Markiro, task 4's rule).

## Concerns

1. Real-webview behaviour is not exercised: decoding the bundled SVG logo with `Image.decode`/canvas (jsdom has neither; tests use fakes/rejection), the logo on a real Zebra/TSC, a real Windows driver page. Needs the manual pass on a station.
2. Diagnostic goes to the webview console (`console.error`), like the cloud station; it is not in the host process log. If the owner wants it in the Rust stderr log (as ДРВ's "one stderr line per failed driver call"), a shell IPC is needed.
3. The ZPL/TSPL downloads of the editor are made with whatever `useLabelLogo()` holds at the click: while the logo query is still loading (or Markiro cannot be decoded) the file has an empty box silently (the hook returns null for both).
4. Markiro is decoded per label when no logo was frozen (`loadBundledMarkiroLogo` caches one success; a failure is retried per label and writes the line each time).
5. The office preview of a stored logo this build cannot read shows Markiro, as the print would (consistent with task 4's snapshot rule), but nothing says so on the template screen (the logo card does).
