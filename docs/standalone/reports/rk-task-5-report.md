### Deviations from the brief (all deliberate; the dispatch's DR attention list required them)

1. **The new database is built BESIDE the current one, then swapped in** (brief: move current aside first, then place + migrate + raise, and `put_back` on failure). Now: `verify_copy` (nothing touched) -> lock -> read the current database read-only -> `place` the copy to `host.db.partial` (streamed, synced, read back, SHA-256 compared) -> migrate -> one transaction -> single connection closed -> `settle` (no `-wal`/`-shm` may stay) -> `check_staged` (integrity_check, epoch, revision) -> **swap**: WAL and shm, then `host.db`, move into `restore-<time>/` (never deleted), then `host.db.partial` is renamed to `host.db`; each rename is retried up to 5x/300 ms (Windows virus scanners); a failing rename puts every moved file back. Consequences: any failure before the swap leaves the data folder exactly as it was (no rollback needed; the staging files are removed); the folder lacks a database only for the time of the renames; a crash in that window leaves either the old database without its WAL (usable, older) or no database with everything in the aside folder; the old WAL never lies beside a different database. The brief's test `a_failure_after_the_move_puts_the_current_database_back` still holds (name kept) and compares bytes of `host.db`/WAL and the folder's file names before/after.
2. **Revisions and audit ids are raised above both databases** (dispatch: "revisions / audit sequence set strictly above max(copy, live, issued-and-seen)"). The brief used `next_revision` (copy rev + 1), which would put the restored host BELOW every revision a station already holds; the station's upserts (`WHERE excluded.rev > ref_*.rev`, `src/local/reference-sync.ts`) and its `last_rev` cursor would then silently ignore new host data. Now `host_revision.rev = max(copy, live) + 1` (counters get that `rev`), `sqlite_sequence('audit_log') = max(copy, live)` (the `host.restore` row is the next id). When the current database is unreadable or absent the unknown is covered by `UNREADABLE_CURRENT_MARGIN = 1_000_000` above the copy. The brief's assertion `(rev, counter_revs) == (copy_rev + 1, ...)` was changed to `live_rev + 1`.
3. **Floors read more than the brief's counters+blocks** ("issued-and-seen"): per prefix/extension the max of counter, block end + 1, and the serial of every box and pallet; per month the max of the counter and the highest number a shift holds; tables an older schema lacks are skipped (a database older than this build is still read).
4. Smaller hardening: the copy being the host's own database is refused; a stray `-wal`/`-shm` with no `host.db` is moved aside too (a WAL beside a new database would be replayed); the aside name gets `-2`, `-3` if taken; stale `host.db.partial*` of an interrupted restore are removed first (a valid stale WAL would otherwise be replayed into the new file: tested with a real WAL); the staging file is written with `create_private` (not `fs::copy`, which carries a read-only flag from a flash drive onto a file SQLite must write; owner-only on Unix, folder ACL on Windows) and flushed through a write handle (a read-only handle cannot `sync_all` on Windows); months for shift-number counters run from the copy's day-before to `max(copy time, now)` + 1 day (clock set back cannot leave months out); `schema_version` is the max applied version (0011 may be applied after 0012); every failure after verification carries "Nothing was changed: the data folder is as it was."; the lock refusal says `sc stop MarkiroHost`; a failure to put the old files back names the aside folder and the manual steps.
5. `RestoreReport` gained `other_host` (copy made by another host -> summary line "the copy was made by another host: the stations pair with this one again", only then) and `revision`. The brief's summary lines are otherwise byte-identical.
6. Item 5 of rk-minors: `markiro_host::{RUNTIME_SHUTDOWN_TIMEOUT = 5 s, shutdown_runtime, shutdown_runtime_within}` (documented in lib.rs: after `RunningHost::stop`'s own 10 s, inside Windows' 30 s stop hint); used in `main.rs` (`run_foreground`, `restore`, `verify_copy`) and `service.rs` after `block_on`. No timeout around the write itself.

## Concerns / for the controller

1. **Revocations made after the copy come back.** The restored `devices`/`operators`/`operator_badges` are the copy's: a station revoked, an operator deactivated or a badge revoked after the copy is active again until someone repeats it. The brief is silent; I did not invent semantics (carrying `revoked_at` from the live database is possible when it is readable, not when it is not). The runbook (Task 8) should tell the administrator to re-check devices, operators and badges after a restore, or the controller may want a follow-up task.
2. **Station side of the new epoch (РК-С).** The host is now above every revision a station can hold, but the rows the copy carries keep their old `rev`; a station that holds a NEWER version of a row (changed after the copy) keeps it under `excluded.rev > existing.rev`. Convergence needs the station to wipe/re-sync on a changed `restoreEpoch`; nothing in this task re-stamps feed rows.
3. `HostConfig::load_or_create` refuses a data folder with `host.db` but no `host.json` with a message written for `start` ("restore it from a backup instead of starting a new host identity"); `restore` inherits it (nothing changed). A mistyped `--data-dir` creates a fresh data folder and restores into it (the summary says "there was no previous database").
4. Unreadable current database: SSCC counters rise by the margin (2 blocks) only; blocks printed after the copy and beyond that margin are closed only by the stations re-registering their blocks (Task 6). With `--without-manifest` and no readable current database, the months for shift numbers are bounded by the restore date, not by an unknown copy date.
5. Windows unverified: rename retry against a virus scanner, ACL inheritance of the staged/aside files, `FlushFileBuffers`, UNC/flash paths, `sc stop`, the service exit path with `shutdown_timeout`; `sync_dir` is a no-op there. A copy read from an unreachable share still blocks until the OS gives up (`verify_copy` hashes in `spawn_blocking`); only process exit is bounded.
6. `rk-implementer-rules.md` opens with another plan's scoping text; ignored as instructed. The cargo target used was the worktree's own warm `apps/standalone/target`.

### Self-review

- `restore_crashing`/`CrashPoint` are `#[doc(hidden)]` public test hooks in the library (integration tests need them). In production the parameter is `None`.
- A restore whose marker cannot be removed after a successful swap exits 1 without printing the summary, asking for a re-run or deletion (rare).
- The undo restore (`restore restore-<time>/host.db`) also goes back to that database's revision + 1. That is usually above the cursor of a station that resynced after the first restore, so such a station continues incrementally: same best-effort gap as C1, to be closed by РК-С.

### Concerns

1. `backup_start::the_office_of_a_started_host_reads_its_copies` is flaky under load (1 failure in 6 runs here). The worker renames the copy into the folder before `record` and `finish` set `lastAttempt`, and the test polls the listing, then asserts `lastAttempt.ok`. This is a test race in Task 3/4 code, not touched here. Suggested fix: poll until `lastAttempt` is set.
2. Windows still unverified: `FlushFileBuffers` on a folder handle (may be refused for the service account; then it is a no-op), the rename retry against a virus scanner, ACLs of the staged and aside files, the temp folder of the fold under the administrator, and `sc start` refusing with the marker.
3. C1 is best effort until РК-С (see Task 8 item 6). I1 does not carry password changes, and does not revoke the copy's devices on `other_host`: owner decisions.
4. I2 costs about 1 % of a prefix's serial range per restore without a readable current database. A site that restores often from dead disks should know this.
