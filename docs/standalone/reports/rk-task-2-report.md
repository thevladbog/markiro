Beyond the brief (data-integrity hardening, each with a test that kills its one-line mutant):

1. **Owner-only files on Unix.** A copy contains everything `host.db` contains (operator PIN/badge hashes, pairing keys), so it is as sensitive. `copy::create_private` (0600, `create_new` or truncating) is used for: the VACUUM target (an empty 0600 file is created first and SQLite fills it — no world-readable window, no later chmod), the manifest (`write_synced`), and the second-folder replica (replaces `fs::copy`). On Windows files inherit the folder ACL (same convention as `tls.rs::write_private`); stated in the module doc.
2. **A copy never replaces or removes a verified copy.** `make_copy_tagged(.., tag)` (new; `make_copy` calls it) refuses a name already present (`write_failed`) before any cleanup scope, so the cleanup of a failed attempt cannot delete the earlier copy. `replicate` removes only what it wrote: the partials always, the renamed target only when it did not exist before (`was_there`), so a failed re-replication (network down, source changed) keeps the good replica already in the second folder. (The brief's `replicate` removed `target` unconditionally.)
3. **No path traversal.** `copy::is_copy_file_name` (prefix `markiro-host-`, suffix `.db`, `[A-Za-z0-9.-]`, ≤128) guards `replicate`, which joins a manifest-supplied name to two paths (`internal` on a hostile name, nothing written anywhere). `list`/`rotate` already work only from names of real directory entries.
4. **Source vs destination errors.** An unreadable source copy in `replicate` is `local_copy_failed`, not `destination_unavailable` (the brief's `fs::copy` could not tell them apart and would blame the share).
5. `clean` doc: only valid while no copy is written into the folder (a copy in flight looks like a leftover) — the task-3 worker must run it at start-up / between copies.

Consistency/atomicity as built: `VACUUM INTO` on the worker's own connection (a reader; WAL content is read through SQLite, never a file-level copy of `host.db`/`-wal`); `.partial` → `integrity_check` on the partial (read-only, immutable) + `max(version)` of `_sqlx_migrations` → SHA-256 → fsync → rename to the final name → manifest through `.partial` + fsync + rename. A copy exists for `list`/`replicate`/restore only with a matching manifest and size. New file name per copy (UTC stamp + 8 random hex) so the last good copy is never overwritten; rotation runs on verified copies only and always keeps the newest 24. Names carry no user input.

## Where copies land and who can read them (for the runbook, task 8)

`<data dir>/backups/` (created by `HostPaths::ensure`) and the second folder the administrator names. Both hold full database copies including PIN/badge hashes and pairing keys. Unix: files 0600; the folders themselves keep the default mode, and `host.db` itself is created by SQLite with the default umask (0644) — pre-existing, not part of this task. Windows: inherit the folder ACL; the data folder is hardened by the installer; the second folder (share/USB) must be restricted by the administrator — the runbook must say so. Nothing here logs hashes, keys or database content: `Failure.detail` carries OS/SQLite error text and paths only (for the process log); the manifest holds `sha256` of the file, which is not a secret.

## Not verified / concerns

- **Free-space pre-check: not implemented.** Host has no `libc`/`fs2`/`sysinfo`/`windows-sys` dependency and manifests are not mine, so no portable free-space query was available. Disk full is handled reactively: `SQLITE_FULL` → `disk_full` (classification tested with a `max_page_count` limit), the partial is removed (cleanup tested by a VACUUM failure after the file exists), the last good copy is untouched (new name per copy, rotation only after a verified copy — task 3 must rotate only after `make_copy` succeeded). End-to-end `VACUUM INTO` onto a really full disk could not be reproduced on macOS (`max_page_count` does not limit VACUUM INTO's target — tried). If a pre-check is wanted, it needs a dependency (owner step).
- **Row counts** are not cross-checked against the live database: the source keeps moving between the snapshot and any later count, so a comparison would be false. Checks are `integrity_check`, newest applied migration (recorded in the manifest) and SHA-256 + size.
- **Windows not exercised**: no Windows run. The only `cfg(windows)` code is the brief's `classify_io` block (raw OS errors 53/64/67/21/55); a probe crate containing `create_private`, `is_copy_file_name`, `write_synced` and `classify_io` type-checks for `x86_64-pc-windows-msvc` (std only); the full crate cannot be cross-checked on this machine (aws-lc / libsqlite3 C build needs the MSVC headers). Unverified on Windows: rename of a freshly written file while an antivirus scanner holds it (a transient `PermissionDenied` would fail that copy as `access_denied` until the next cycle; a short retry on rename would be a cheap hardening — not added because it cannot be tested here), UNC/USB semantics, ACLs, behaviour of `VACUUM INTO` while the service holds `host.db` (the VACUUM path uses SQLite's own locking and is exercised here with a held write lock).
- `clean` must not run while a copy is in flight (doc says so); the task-3 worker is the only caller and runs copies sequentially.
- Orphan `.json` manifests (db removed by hand) are not cleaned (the brief's `clean` rule is partials and `.db` without manifest); a few hundred bytes, harmless.
