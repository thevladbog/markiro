## What the port does (and where it is not the plan's literal text)

The plan's code was applied verbatim; one reading of it needs saying: the plan's text says the port and the cloud differ in two places only (operation instant, Ч2; disassembled-pallet count, Ч1) and that these do not change the bytes. Checked against the cloud source and runner as they are in this tree: `loadFromTransaction`, `loadEligibleBoxes`, `toBoxesSource`, `toPalletsSource`, `loadPallet`, `loadOrganization` and the runner's `renderForShift` / `renderForPallet` / `safeDomainErrorCode` — the port is line-for-line equivalent, with these deliberate differences:

- `SHIFT_DATE_MISSING` is not reachable (host shift always has a production date); the validation reprocessings of the flat formats are not ported (stage 3). The cloud's `?? "Продукция"` fallback for a missing product name is not ported (the host's product name is a required string).
- `operation_date_time` of a shift: `stationClosedAt ?? closedAt ?? formedAt` (Ч2); the cloud's fallback `shift.closedAt ?? snapshotInstant` is the third term.
- `loadPallet`'s boxes are read from the shift's own rows (the cloud reads `boxes.pallet_id` for the tenant); the host's rows hold every box of the shift, and a pallet belongs to one shift.
- `EMPTY_SOURCE` and other domain codes not in the cloud's safe list map to `GENERATION_FAILED` at once (the cloud retries and then fails the same way).

## The new case `open-box-on-pallet`: can the host represent it?

No. The case has an UNCLOSED box that carries both an SSCC and a palletId. The host's `boxes` table forbids both halves: `CHECK ((closed_at IS NULL) = (sscc IS NULL))` (0010_facts.sql:82) and `CHECK (pallet_id IS NULL OR closed_at IS NOT NULL)` (0012_pallets.sql:45). So the host's `export-source` can never send such rows. The port still handles the case exactly as the cloud does, because it filters on `closedAt !== null` itself and never infers openness from the SSCC: the box is not eligible, its code is uncovered, so box formats give `BOX_COVERAGE_INCOMPLETE`, and the pallet document of its pallet lists only the closed box (`closedAt !== null` in `palletExportSnapshot`). The case also makes mutant P7d of the brief (open box eligible) NON-equivalent: the brief names it equivalent ("an open box has no SSCC"); with Task 4's case it fails 8 parity runs (`open-box-on-pallet/shift_txt_boxes@2/-` ...). Same pallet-document runs kill R1 (open boxes of the pallet listed).
Likewise the host's CHECKs make unreachable: a pallet with an SSCC and no close (or the reverse; `0012_pallets.sql:28`), a closed box with no SSCC, a group whose pallet has no close, and a box whose `palletId` is not among the pallets (FK). The cloud's schema allows all of them and the port answers them as the cloud does; my extra tests pin those answers with synthetic rows through the same Zod schema.
