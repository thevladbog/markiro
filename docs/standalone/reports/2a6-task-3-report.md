## Self-review / concerns

1. Overfilling is not the pipeline's: `processScan` does not know the box capacity (the brief's design); a box holds as many codes as the screen lets in. The guard is the plan's: the screen closes a full box after the scan that filled it, takes no ordinary scan while a stop is active (`no_serials`, `close_failed`) and closes a full box on entry (`closeIfFull`, Task 4). If the owner wants a database-level backstop, the counter UPDATE could carry `AND item_count < ?` (capacity) with `expectedChanges: 1`; I did not add it (it changes what Task 4/8 tests may do with more codes than a box holds).
2. The 300 ms bound of the host check is `HostApi.checkCode`'s (`timeoutMs`, pinned by Task 1's A8 mutant); the pipeline awaits the call and trusts it. A `checkCode` that never settles would hold the work queue; the shell's `timeoutMs` ends such a call with the `timeout` transport code, and the pipeline's tests cover that code (accepted locally). No second timer was added.
3. `onHostError` that throws would reject the scan (the callback runs in the `catch`). The screen's callback is a state dispatch; not hardened.
4. A scan whose reading says `km` but whose host registry owner is another device of the same pairing cannot occur (`sameDevice`), covered by the brief's own-scan test and the three-way test of mine.
5. Offline-first reconciliation: a scan accepted while the host is unreachable is `ok` locally, queued with `acked_at IS NULL`, `outcome IS NULL`, in `seq` order; the host's later `conflict`/`rejected` receipts (Task 6) must set `floor_scans.conflict` and `floor_boxes.needs_fix` without deleting the local rows.
