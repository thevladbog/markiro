# P1B.3 online entitlement owner inventory

This inventory records the existing server owner for each P1B.3 online operation. Shadow
observation does not replace security, subscription, quota, release, configuration, tenant, or
credential checks. `p1b_adapter` means that the listed owner now records a verified P1 shadow
observation for a new effect. `classified` and `pending` entries are not claimed as observed.

## Registry and compatibility boundary

The additive registry epoch is `p1b.v1`. Every prior operation definition and version remains
unchanged; the inventory, CommerceML, label-template and pallet owners are added or advanced to `p1b_adapter`. Existing cabinet pallet configuration authorization remains unchanged; station configuration and planned start have additive IDs. Observation
rows already stored with `p1a.v1`, confirmed source receipts, historical sources, snapshots and
manifests remain valid bytes and are never rewritten.

Prepared source previews bind a fingerprint of the whole operation registry. Therefore a preview
made against the earlier registry must be rejected as stale and regenerated with a new request ID
before confirmation. A confirmation that was completed before the registry change continues to
replay its stored result. Operation-scoped compatibility sources do not gain new inventory, station pallet configuration or pallet start
operation IDs automatically; the new IDs must be selected explicitly.

Device replacement preparations and device-retention selection intents also include the entitlement
registry fingerprint in their server-owned facts. Adding this registry epoch therefore moves a prior
preparation or intent to its existing `needsReview` / stale-preview path; the user must prepare the
decision again. Completed replacement and retention receipts continue to replay their original
stored result and are not regenerated.

## Validation boundary

The inventory adapter suite uses a migrated temporary localhost PostgreSQL database and actual Nest
dependency injection. It checks exact cabinet identity, operation IDs, registry epoch, canonical
scope digests, and one-observation behavior for idempotent import and start replays. Host tests do not
exercise live Chestny ZNAK, object storage, 1C, Android hardware, Station hardware, or customer
rollout.

## CommerceML observation ownership

Nest resolves the existing global `SubscriptionsModule` facade into `ExchangeSessionService`;
there is no duplicate provider or resolver in `ExchangeModule`. `runtime.enabled=true` records the
current deployed exchange protocol path after session verification: this transport has no separate
release/config toggle. It does not claim a live 1C server was contacted, and the actor never composes
`publicApi.request.v1` even if the tenant plan has public API disabled.

The query row already serialized concurrent writes through `UPDATE CASE`. A short `FOR UPDATE`
transaction moves that same serialization boundary before observation, so only the first proposed
batch is observed. Facts are captured immediately before the transaction; shadow proof and writes
use its connection and nested savepoint. Building XML, finding candidates and journal writes remain
outside the transaction. This adds bounded lock duration for observation; no new global lock exists.

Catalog completion deliberately does not add a cursor write: its existing redundant final reapply
semantics remain intact. `summary.entitlementImports` is observation bookkeeping, not application
authority. It stores the latest canonical digest per hashed `(action, filename)` key; there is no
arbitrary cap or eviction. Size is proportional to distinct uploaded filenames in that session, and
markers follow the existing session retention/pruning lifecycle. Atomic JSONB updates preserve
outstanding batches, import cursors and unrelated summary keys. A changed source file with the same
worklist keys is a different admission; progress on the retained cursor is continuation. Markers do
not promise a business commit: a failed apply can retry under the same admitted file identity.

Failed observation INSERTs roll back to a savepoint and produce unknown. Failed marker storage
rolls back its short bookkeeping transaction and also returns unknown; import still executes through
its original owner. If marker storage is unavailable, exact once observation cannot be established
for a later small-file retry; a later attempt may be observed again, but business cursor/history is
never advanced or rewritten for that purpose. Existing application/cursor failures still propagate.

CommerceML tests use real PostgreSQL, session resolution, Nest DI, HTTP protocol owners and real
catalog/order writes, with tenant-local failure triggers for observation/marker persistence. They
also cover concurrent batch winners, exact actor/reasons/digests, completed-file replay, retained
cursor/mapping, and subscription denial. Live 1C, physical factory workflows and production rollout
were not performed.

A sale file admission is not a successful per-order mutation receipt. A valid-shaped mapped document
may resolve to a missing order, a conflicting terminal state, or an already reconciled terminal
prefix. Those existing lookup/state outcomes still determine discrepancies and cursor counters;
commercial observation only describes admitting that fresh file for processing. Replaying its
completed source never creates another file observation or changes those saved business facts.

Catalog observation identity also includes the effective `priceType` configuration (unset is
canonical null). A fresh offset-zero import of identical offers with a different selected price
type therefore produces a new observation; unchanged retries do not. This field is exclusively
observation bookkeeping: the key-only business cursor fingerprint, source bytes and the existing
price application behavior remain unchanged. Sale's effective field/mapping are already included
in its fingerprint; export's document settings are represented by the final winning XML digest.

Catalog identity also binds the planner's effective `(externalRef, productId)` targets, sorted by
source reference. It includes both known and newly resolved links, so persisting a link does not
change an unchanged retry's identity. Resolving the same file to a different product creates a new
observation. This internal metadata does not alter the business worklist, cursor or protocol output.

## Template and pallet transaction/identity boundary

Template create and delete now have minimal owner transactions so the observation commits with the
actual write. Update retains its existing FOR UPDATE interlock with default-pointer selection.
No isolation level, default-selection authorization, template eligibility or FK conflict mapping is
changed. Facts are captured immediately before the transaction; shadow proof/insert use nested
savepoints on the same connection. Shifts retain their existing transaction and lock order,
including device-before-shift entry locks. Existing feature assertions remain in their original
positions. Shadow deny/unknown never changes the existing owner result.

The controllers pass verified cabinet or station identities internally. A station device is recorded
as `station_device`, including the existing handheld-authenticated online entry boundary; this does
not grant `handheld.work.start.v1`, change wire DTOs or create offline grants. The start metadata
`cabinet_or_station_device` documents two already-authorized routes; `operations.write` belongs to
the cabinet branch and is not imposed on device identity. The existing cabinet configuration ID
keeps its meaning; station creation uses a separate additive ID. No public-key identity is composed.

Template owners have no existing operational audit writer; this delivery does not invent one.
Shift production-date changes retain the existing exact tenant/user/target/before/after audit.
The actual HTTP owner suite checks these fields alongside shadow identities, canonical digests,
foreign-tenant/capability denial, default conflicts, no-op/replay exclusions and injected shadow
persistence failures. Existing template, pallet/default, handheld read and bundle regression suites
provide server evidence only. Native printing, scanners, Windows/Android execution, browser layout,
live external systems and customer rollout remain unverified by these server tests.

Delete also locks the tenant template row FOR UPDATE to serialize competing deletes. This makes
one concurrent request succeed and the loser return the existing 404 missing-template response;
previously both racing deletes could report success. The bounded compatibility cost is this race
response and the same-row lock duration, not a new feature requirement. The race test barriers both
captures, and the successful delete commits exactly one delete observation.
