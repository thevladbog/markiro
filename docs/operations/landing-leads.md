# Заявки с лендинга: лиды, оповещения, сводка

Спека: `docs/superpowers/specs/2026-10-20-standalone-download-trial-pricing-design.md`, раздел 15.

## Что происходит при отправке формы

`POST /api/landing-leads` (формы `/skachat/` и «Получить счёт» на `/stoimost/`) и старая
`POST /api/demo-requests` пишут в одной транзакции:

- лид в `landing_leads` — один на нормализованную почту. Повторная форма с той же почтой
  дополняет пустые поля и не трогает заполненные, статус и первую атрибуцию;
- событие в `landing_lead_events` (`download`, `invoice_request`, `demo_request`) с
  `public_request_id` — повтор с тем же `requestId` ничего не добавляет;
- письма: посетителю (`landing-download-link` или `landing-invoice-request-confirmation`) и
  владельцу (`landing-lead-notification`; у демо-формы — прежние два письма);
- строку очереди оповещений `lead_notifications`.

Приём заявок управляется переменными: `LANDING_DEMO_SUBMISSION_ENABLED`,
`LANDING_ORIGIN`, `LANDING_DEMO_RECIPIENT`, `LANDING_DEMO_REPLY_TO`,
`LANDING_DEMO_*_LIMIT`. Ссылки на карточку лида строятся от `SAAS_ADMIN_ORIGIN`.

## Telegram

Бот создаёт владелец (@BotFather). Для личных уведомлений владелец открывает диалог с ботом
и нажимает Start; для групповых — добавляет бота в рабочую группу с правом отправки сообщений.
Нужны токен одного бота и chat id каждого получателя. Токен хранится только в защищённом
файле окружения; его нельзя отправлять в чат, коммитить или печатать в логах.

| Переменная                    | Значение                                                           |
| ----------------------------- | ------------------------------------------------------------------ |
| `LEAD_TELEGRAM_ENABLED`       | `true`, чтобы включить; по умолчанию выключено                     |
| `LEAD_TELEGRAM_BOT_TOKEN`     | токен бота, секрет; обязателен при включении                       |
| `LEAD_TELEGRAM_CHAT_ID`       | основной получатель: числовой id личного чата, группы или `@канал` |
| `LEAD_TELEGRAM_GROUP_CHAT_ID` | второй получатель: числовой id группы или `@канал`                 |
| `LEAD_RETENTION_MONTHS`       | срок до обезличивания лида без движения, 1–60, по умолч. 12        |

При включённом флаге нужны токен и хотя бы один из двух chat id. Можно указать оба:
каждая заявка и ежедневная сводка отправляются обоим получателям. Старый `LEAD_TELEGRAM_CHAT_ID`
работает без изменений; одинаковые id объединяются (числовые id нормализуются, регистр
`@канала` не учитывается). Для надёжного определения получателя предпочтительны числовые id.
Готовность сервиса от Telegram не зависит. В сообщениях нет почты, имени и телефона: только
вид, компания, товарная группа, линии, тариф, источник, UTM и ссылка на карточку. Похожее на
почту или телефон вырезается и из этих полей.

Пока Telegram выключен, строки очереди помечаются `skipped`: после включения старые лиды не
приходят пачкой.

Результат доставки хранится отдельно для каждого получателя в `lead_notifications.payload`:
только SHA-256 идентификатора, состояние, число попыток и безопасный код ошибки. При обычном
повторе и перезапуске worker уже доставленное сообщение не отправляется снова; постоянная
ошибка одного получателя не мешает попыткам для другого. На каждого — до восьми попыток.
Получатели фиксируются при первой попытке: удалённый получатель пропускается, добавленный
получает только новые уведомления. Завершённые строки очереди не переигрываются.

Доставка остаётся at-least-once: авария после ответа Telegram, но до коммита БД может привести
к повтору. Перед откатом на worker без поддержки двух получателей нужно дождаться завершения
таких строк очереди либо принять ограничения старой доставки.

Для заявок с сайта отдельно требуется `LANDING_DEMO_SUBMISSION_ENABLED=true` и настроенная
почта. Включение Telegram само по себе не включает формы. Конфигурация и новый образ API
вводятся через штатный защищённый процесс релиза и развёртывания. После настройки проверяют
настроенных получателей согласованным тестовым сообщением; автоматические тесты используют заглушки
Bot API и не доказывают реальную доставку.

Для включения вместе с релизом V4 настроен один канал: его id задаётся через
`LEAD_TELEGRAM_CHAT_ID`. Личный чат пока не подключается, `LEAD_TELEGRAM_GROUP_CHAT_ID`
не задаётся. Токен и конкретный id получателя хранятся только в защищённой конфигурации.
Изменения кода сами по себе не включают уведомления в production; параметры применяются штатной операцией
развёртывания V4. Проверка прав бота не заменяет проверку фактической доставки.

## Задачи pg-boss

Задачи работают в обоих профилях API (`platform-only` и `legacy`): демо-форма пишет лиды в
обоих.

| Очередь                       | Расписание (UTC) | Что делает                                                   |
| ----------------------------- | ---------------- | ------------------------------------------------------------ |
| `dispatch-lead-notifications` | каждую минуту    | отправка в Telegram; до 8 попыток, задержка 30 с × 2ⁿ до 1 ч |
| `send-lead-digest`            | `0 6 * * *`      | сводка «кому пора написать» в 09:00 МСК; пустая не уходит    |
| `anonymize-landing-leads`     | `40 2 * * *`     | обезличивание лидов                                          |

Ни одна из трёх задач не запускается при старте API: сводка не должна приходить при каждом
перезапуске, а внешние вызовы Telegram не должны задерживать готовность.

Сводка — одна на календарный день Москвы (`lead_notifications.digest_date`), письмо идёт на
`LANDING_DEMO_RECIPIENT`. Разделы и правила — спека 15.5; лид с датой следующего контакта
позже сегодняшней в сводку не попадает.

## Обезличивание

Ежедневно: лиды в статусе «Потерян» дольше 30 дней (месяц, чтобы исправить ошибочный клик)
и лиды без движения `LEAD_RETENTION_MONTHS` месяцев. Очищаются почта, имя, телефон, заметка и
ИНН из 12 цифр (ИНН физлица или ИП) — и в карточке, и в событиях запроса счёта. Строка лида остаётся для статистики. Каждое обезличивание —
событие `anonymized` и строка платформенного аудита `landing_lead.anonymized` (что было
заполнено, без значений). В карточке есть ручное обезличивание по запросу субъекта.

Срок и правило сверить с политикой обработки ПД и текстом согласия до запуска.

## SaaS-админка

Раздел «Заявки» (`/leads`): `leads.read` у администратора и поддержки, `leads.write` — только у
администратора. Смена статуса, связь с клиентом и обезличивание пишутся в платформенный аудит
(`landing_lead.status_changed`, `landing_lead.tenant_linked`, `landing_lead.anonymized`).
«Создать клиента без кабинета» использует обычное создание клиента (`cabinetAccess: none`) и
дополнительно требует `tenants.write`.

Заявки скачивания и счёта не используют Yandex SmartCaptcha. Перед сохранением API
проверяет переключатель приёма, лимиты запросов по источнику и общему числу, пустую
ловушку для ботов (`website`) и актуальную версию согласия. Поле `captchaToken`
остаётся необязательным для совместимости с закешированными страницами и не сохраняется.

Лимиты форм скачивания и счёта общие для всех экземпляров API и сохраняются при
перезапуске: `landing_lead_rate_windows` в PostgreSQL. Источник представлен HMAC
от адреса с ключом `PLATFORM_AUTH_SECRET`, исходный IP не сохраняется. Серверное
время БД определяет истечение окна; устаревшие ключи удаляются при следующем
допущенном запросе. После исчерпания общего бюджета новые ключи источников не
создаются. При недоступности хранилища заявка отклоняется с 503 до записи и почты.
Смена platform auth secret сбрасывает только распознавание источников, общий
счётчик остаётся. Старая `/api/demo-requests` выключена без ключа SmartCaptcha.

Перед запуском новой версии API штатный migrator должен применить `0202`.
Откат API не требует удаления новой таблицы: прежняя версия её не использует.
