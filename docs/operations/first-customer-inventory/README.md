# Пакет доказательств первой инвентаризации

Используйте этот комплект только для первой, проводимой основателем операции
восстановления склада на одном устройстве. Версия протокола всегда
`inventory-recovery-v1`. Эта операция не участвует в оценке сотрудников.

Основной полевой документ — [protocol-v1.md](protocol-v1.md). Откройте его на
рабочем устройстве и проходите ворота строго сверху вниз.

## Используйте однозначные термины и форматы

- **Payload сканера** — строка символов перед терминатором `CR`, `LF` или
  `CRLF`, которую настроенная HID- или serial-интеграция передала потребителю.
  HID-путь собирает `KeyboardEvent.key`. Текущий serial-путь применяет
  `String::from_utf8_lossy`, находит терминатор и вызывает `trim()` до отправки
  события. Поэтому payload уже может отличаться от транспортных байтов.
- **Исходный файл** — текст UTF-8 с одной захваченной строкой на запись.
  Выбранный путь захвата записывает полученный payload без дополнительного
  изменения и добавляет один разделитель `LF`. Сохраните GS1-символ `U+001D`,
  если он присутствует в полученной строке. При первом контрольном хеше байты
  файла становятся неизменяемыми; последующие хеши подтверждают эти сохранённые
  байты, а не байты сканера или serial-линии.
- **Сопроводительная таблица (sidecar)** — CSV-файл, который ссылается на номер
  строки исходного файла и добавляет номер коробки, товар, дату и ссылки на
  доказательства. Он не копирует и не заменяет авторитетный старый SSCC.
- Используйте время строго как `YYYY-MM-DDTHH:mm:ss±HH:mm`, например
  `2026-08-24T09:00:00+03:00`. Всегда указывайте числовое смещение; не пишите
  локальное время без смещения и не заменяйте его `Z`.
- Для проверок используйте только `PASS`, `FAIL` или `NOT_RUN`. `PASS` означает,
  что проверка выполнена и результат совпал; `FAIL` — проверка выполнена с
  ошибкой или расхождением; `NOT_RUN` — проверка не выполнялась. Ворота проходят
  только при `PASS` всех обязательных проверок.

## Подготовьте каталог операции

Выберите один идентификатор вида `INV-YYYYMMDD-name-NN`. Не меняйте его после
начала работы. Создайте каталог до первого рабочего сканирования. Команда ниже
создаёт только отсутствующие каталоги, пустой
`baseline/old-sscc.raw.txt` и `manifest.json`:

```bash
corepack pnpm evidence:init -- evidence/INV-20260824-pilot-01 INV-20260824-pilot-01
```

Замените примерный идентификатор на выбранный. Инициализатор принимает путь
внутри репозитория или вне него. Каталог `evidence/` в корне репозитория
игнорируется Git, но держите реальные материалы клиента вне рабочего
репозитория.

Инициализатор откажется работать, если исходный файл уже содержит данные. Он не
перезаписывает существующий манифест другой операции и требует файловую систему
с поддерживаемой атомарной установкой файлов. Сначала выполните отдельную
одноразовую репетицию на том же Windows-устройстве и носителе по воротам 5.

Создайте каталог `exports/system/rehearsal-date/`. Скопируйте рабочие шаблоны в
созданный каталог операции, сохранив эти имена:

- `templates/old-box-index.csv` → `baseline/old-box-index.csv`;
- `templates/reconciliation.csv` → `metrics/reconciliation.csv`;
- `templates/production-date-proof.csv` →
  `exports/system/rehearsal-date/production-date-proof.csv`;
- `templates/customer-act.md` → `attestation/customer-act.md`;
- `templates/consent.json` → `attestation/consent.json`;
- `templates/backup-locations.txt` → `backup-locations.txt`.

Не копируйте `templates/final-custody-record.txt` в корень операции или в любую
из двух копий. После окончательного запечатывания скопируйте этот шаблон в
отдельное частное место вне `<operation-root>` и заполните его там. Он завершает
проверку копий, не изменяя запечатанные байты.

Заполните Markdown-источник акта, получите подписи согласованным с клиентом
способом и сохраните итог как `attestation/customer-act.pdf`. Если подписывают
бумагу, сканируйте подписанный экземпляр в этот PDF. Оставьте исходный Markdown
рядом: инструмент запишет хеш каждого файла отдельно, но не проверит подпись.

`templates/manifest.draft.json` — справочный минимальный черновик. Не копируйте
его поверх созданного `manifest.json`: инициализатор уже записал тот же основной
контракт и дополнительное поле `updatedAt: null`. Заполните созданный манифест.
Оставьте `artifacts` пустым до начального запечатывания. Если `updatedAt`
заполнено, инструмент использует его как время захвата нового артефакта; иначе
запишет `capturedAt: null`.

## Получите дату из зеркала Station без записи в базу

Текущая Station загружает `sqlite:station-mirror.db`. Закреплённый в Cargo.lock
`tauri-plugin-sql` 2.4.0 разрешает этот относительный URL от app-scoped каталога
конфигурации Tauri `BaseDirectory::AppConfig`. Идентификатор приложения равен
`app.markiro.station`, поэтому ожидаемый путь в Windows:

```text
%APPDATA%\app.markiro.station\station-mirror.db
```

Этот путь выведен из текущего кода и зависимости. Он не проверен на рабочем
Windows-устройстве. Перед чтением закройте Station, чтобы зафиксировать снимок.
В PowerShell задайте выбранные значения, проверьте файл и запустите диагностику:

```powershell
$operationRoot = 'D:\private-evidence\INV-20260824-pilot-01'
$shiftId = '00000000-0000-0000-0000-000000000001'
$stationDb = Join-Path $env:APPDATA 'app.markiro.station\station-mirror.db'
$output = Join-Path $operationRoot 'exports\system\rehearsal-date\station-production-date.json'
if (-not (Test-Path -LiteralPath $stationDb -PathType Leaf)) { throw 'Station DB not found' }
corepack pnpm evidence:station-date -- $stationDb $shiftId $output
```

Замените только примерные корень операции и ID смены. Команда открывает SQLite
в режиме `readOnly`, выполняет параметризованный запрос
`SELECT id, production_date FROM shift_mirror WHERE id = ?`, требует ровно одну
строку и отказывается перезаписывать существующий результат. Она записывает
новый JSON через соседний временный файл с режимом `0600` и атомарную установку
жёсткой ссылкой без перезаписи. Если файловая система не поддерживает такую
установку, команда останавливается и сохраняет существующий результат без
изменений. Вывод содержит только версию, источник, ID смены, дату или `null` и
время захвата. Команда не печатает путь к базе и не извлекает другие таблицы или
поля. После `PASS` запустите Station снова.

## Свяжите фото с манифестом

Сохраняйте оригинал камеры без пересохранения и переименования:

```text
photos/duplicates/<duplicate-group-id>/<original-camera-filename.ext>
```

Например:
`photos/duplicates/DUP-0001/IMG_1234.JPG`. Путь должен быть относительным корню
пакета, использовать `/` и включать расширение. Task 9 запрещает `\`, пустые
сегменты, `.`/`..`, NUL, CR и LF. Если два оригинала одной группы имеют
одинаковое имя, не перезаписывайте и не переименовывайте их: поместите второй в
`photos/duplicates/DUP-0001/capture-02/IMG_1234.JPG`. Исходное имя и расширение
останутся последним сегментом пути.

В `duplicatePhotoRefs` записывайте эти полные пути через `;`, а не псевдонимы.
Если имя содержит `;`, представьте этот символ как `\;`; при сверке снимите
экранирование и получите точный путь манифеста. Если CSV-поле содержит запятую
или кавычку, заключите всё поле в двойные кавычки по RFC 4180 и удвойте каждую
внутреннюю кавычку. CR/LF в пути запрещены.

До следующего запечатывания добавьте или обновите в `manifest.json` одну
предыдущую запись артефакта для каждого точного пути фото. Не добавляйте
неподдерживаемое поле `originalName`: исходное имя уже сохранено в последнем
сегменте пути. Минимальная запись:

```json
{
  "path": "photos/duplicates/DUP-0001/IMG_1234.JPG",
  "capturedAt": "2026-08-24T10:15:00+03:00",
  "actor": { "nameOrId": "", "role": "founder" },
  "physicalBoxRefs": ["BOX-0001", "BOX-0007"],
  "evidenceRefs": ["DUP-0001"]
}
```

Редактируйте только массив `artifacts` в закрытом для записи каталоге. Не
удаляйте другие записи и не создавайте два объекта с одинаковым `path`.
Проверьте JSON до запечатывания; команда ниже ничего не печатает из манифеста:

```bash
node --input-type=module -e 'const {readFile}=await import("node:fs/promises"); JSON.parse(await readFile(process.argv[1],"utf8")); console.log("manifest.json: valid JSON")' "<operation-root>/manifest.json"
```

При повторном `evidence:seal` Task 9 пересчитает `category`, `byteSize` и
`sha256`, но сохранит предыдущие `capturedAt`, `actor`, `physicalBoxRefs` и
`evidenceRefs` для совпавшего пути. После запечатывания вручную сравните путь и
все четыре поля с `old-box-index.csv`; затем выполните `evidence:verify`.

## Запечатайте и проверьте пакет

Остановите все программы и ручные операции, которые пишут в каталог. Затем
выполните:

```bash
corepack pnpm evidence:seal -- "<operation-root>"
corepack pnpm evidence:verify -- "<operation-root>"
```

Первая команда пересобирает список артефактов в `manifest.json` и создаёт
`SHA256SUMS`. Вторая проверяет все перечисленные файлы, манифест, отсутствие
пропущенных обычных файлов и контрольные суммы. Контрольные суммы описывают
только последнюю завершённую контрольную точку. После любой контролируемой правки
остановите запись, снова запечатайте и проверьте пакет.

Инструмент отклоняет символические ссылки, нестандартные файлы, небезопасные
пути, временные `*.tmp`, более 10 000 артефактов и изменившиеся байты. Он не
подписывает пакет и не удостоверяет личность автора. Пользователь с полным
доступом к каталогу может заменить все файлы и создать новый согласованный
набор хешей. Храните итоговый внешний хеш (detached digest) или подпись отдельно,
если нужна проверка подлинности.

Запечатывание рассчитано на неподвижный каталог. Внезапное выключение между
двумя заменами служебных файлов обнаружится при проверке и может оставить рядом
файлы восстановления `*.backup.tmp`. Не удаляйте их вслепую; сохраните каталог
и разберите сбой отдельно.

## Завершите хранение без циклического запечатывания

До финального `evidence:seal` заполните `backup-locations.txt` только заранее выбранными
`copyId`, метками контролируемых мест, хранителями и идентификатором будущего
внешнего журнала. Не записывайте туда итоговые хеши, результаты или времена
проверки.

После финального `evidence:seal` больше не меняйте корень или копии. Вычислите SHA-256
самого файла `SHA256SUMS` и запишите его во внешний журнал:

```bash
node --input-type=module -e 'const {createHash}=await import("node:crypto"); const {readFile}=await import("node:fs/promises"); console.log(createHash("sha256").update(await readFile(process.argv[1])).digest("hex"))' "<operation-root>/SHA256SUMS"
```

Скопируйте пакет в два заранее записанных частных места. Откройте каждую копию,
запустите `evidence:verify` по её корню и отдельно вычислите SHA-256 её
`SHA256SUMS`. Для итоговой проверки допустимы только `PASS` или `FAIL`.
Скопируйте `templates/final-custody-record.txt` в отдельное частное место вне
всех трёх корней, заполните результаты, количество файлов, имя/ID и роль
проверяющего, время со смещением и подпись/ссылку. Совпадение внешнего хеша и обе
проверки должны иметь `PASS`. Не запечатывайте пакет снова после этого шага.

## Соблюдайте правила данных

- Не помещайте реальные фото, ФИО, сканы подписей или исходные коды в Git,
  публичные ссылки, демонстрационные каталоги или общие чаты.
- Не храните в `backup-locations.txt` или внешнем журнале пароли, ключи, токены,
  учётные записи или секретные пути. Указывайте только непрозрачные
  идентификаторы, контролируемые метки и факты проверки.
- `baseline/old-sscc.raw.txt` — только свидетельство старого учёта и основание
  для разукрупнения. Никогда не импортируйте его как новое владение SSCC в
  Markiro.
- В `consent.json` каждое поле `decision` независимо принимает `true`, `false`
  или `null`. Оставляйте `null`, пока подписант не принял решение. Для принятого
  решения заполните точный объём в `scope`, имя и роль подписанта и `decidedAt`
  в обязательном формате времени.

## Не меняйте стабильные заголовки CSV

`old-box-index.csv`:

```text
rawLineNumber,physicalBoxNumber,product,printedProductionDate,note,duplicateGroupId,duplicatePhotoRefs,amendmentRef
```

`rawLineNumber` — единственная авторитетная связь со старым SSCC. Сам SSCC в
сопроводительной таблице не повторяется.

`production-date-proof.csv`:

```text
surface,expectedProductionDate,observedProductionDate,actorNameOrId,actorRole,capturedAt,evidencePath,result,scopeBinding
```

Сохраните шесть строк шаблона в порядке DB, API, Admin, Station mirror, Label,
Export. Не меняйте пути доказательств или заголовок.

`reconciliation.csv`:

```text
recordType,counterId,value,unit,formula,evidenceSource,delta,explanation,acceptedByNameOrId,acceptedByRole,acceptedAt
```

`counter` содержит обязательный наблюдаемый итог, `helper` — вспомогательный
итог, `control` — одну сравнимую дельту, `summary` — число результатов контроля.
Для каждого ненулевого `control` заполните `explanation`,
`acceptedByNameOrId`, `acceptedByRole` и `acceptedAt`. Не исправляйте исходные
материалы, чтобы получить ноль.

Вспомогательные строки `physical_legacy_box_observations`,
`legacy_scan_line_observations`, `duplicate_group_physical_box_observations`,
`duplicate_group_first_occurrences`, `unique_legacy_first_occurrences` и
`new_sscc_box_assignments` переводят физические коробки, строки, группы или
уникальные идентификаторы в названные наблюдения либо назначения. Каждый
примитивный контроль использует только операнды с одной буквальной единицей из
столбца `unit`.

Примитивный контроль — одна размерно согласованная проверочная дельта.
`reconciliation_delta` считает только эти шесть примитивных контролей:

1. `legacy_box_line_delta`;
2. `duplicate_group_membership_delta`;
3. `duplicate_occurrence_delta`;
4. `unit_terminal_delta`;
5. `new_box_sscc_delta`;
6. `legacy_box_terminal_delta`.

Он не считает собственную строку и `unexplained_difference`.
`unexplained_difference` считает ненулевые строки из этого же списка, у которых
не заполнено объяснение или любое поле явного принятия клиентом. Разборка и
перепечать считаются отдельно как множества уникальных коробок; одна коробка
может входить в оба множества, поэтому их нельзя складывать.
